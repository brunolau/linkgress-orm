# linkgress 1.0.5 → 1.0.10 → 1.0.11 → 1.0.12: performance

This report compares four versions:

- **1.0.5:** `v1.0.5`, f9f7f87;
- **1.0.10:** f08c8df;
- **1.0.11:** fbd98d7;
- **1.0.12:** the performance series on top of 1.0.11, described in `changelog/v1.0.12.md`.

It uses the 41 scenarios of `harness.ts`: the 35 of the 1.0.8 report plus six for what 1.0.11 changed (`selectmany-count`, `batch-plain`, `batch-numeric`, `batch-expression`, `batch-collection-max`, `transaction-reads`).

Machine and method are the README's:

- Both versions run in one process, with their samples interleaved.
- Each comparison is 8 rounds on Node 26.8.1, using `pg` 8.16.3 against PostgreSQL 18.3 on localhost.
- Every change is the geometric mean of the per-round ratios, with its 95 % interval.

Each version was measured against 1.0.5 in its own run. The times shown are each run's medians, and the 1.0.5 column is taken from the first run. Absolute times move a few per cent between runs, so compare the percentages, not the times.

There are two modes:

- **`MockRowCache` off**, the library default;
- **`MockRowCache` on** (`VERBENCH_MOCK_ROW_CACHE=1`), the way applications that enable the cache run.

## Summary

### How much it regressed, 1.0.5 → 1.0.10 → 1.0.11 (Node, cache off)

| | 1.0.10 | 1.0.11 |
| --- | --- | --- |
| End to end | +2.2 % | +5.3 % |
| End to end, without the whole-row navigation | +0.6 % | +3.7 % |
| linkgress's own time per query | +25 % | +38 % |
| Building a query | +22 % | +30 % |
| Importing the package | +27 % | +32 % |

With the cache on, 1.0.11 is +5.8 % end to end, +48 % in linkgress and +66 % to build. The cache makes builds cheap: a primary-key lookup costs ~3.5 µs instead of ~15 µs. So the same added passes weigh more in relative terms, while adding only a few µs per query.

### Where it came from

- **1.0.7:** build +16 %, in linkgress +19 %. It has four sources:
  - a navigation row projected whole is now one column per value, read through its mappers (a correctness fix);
  - collection read setup runs once per parent row;
  - selectMany got slower;
  - a spread of small build passes was added.
- **1.0.9:** `count()` / `exists()` now evaluate the query's projection. count-where's build went from 6.9 to 16.7 µs, and every batch and transaction that counts carries that cost.
- **1.0.11:** the QueryBatch transport sends every runtime-typed value's text (a fidelity fix): batch-expression +116 % end to end. selectMany's build also grew.
- **Import time:** grew in 1.0.6 (+21 %) and in 1.0.9 (+11 %).
- **No measurable change:** 1.0.8. 1.0.10 builds and reads every query as 1.0.9 does.

### 1.0.12 against 1.0.5

| | cache off | cache on |
| --- | --- | --- |
| End to end | +2.7 % | +2.8 % |
| In linkgress | +16 % | +22 % |

About half of 1.0.11's end-to-end and in-linkgress regression is gone. In linkgress, 1.0.12 now beats 1.0.10 (+25 %).

### What remains

- **Whole-row navigation:** +28 % end to end. For 500 rows it spends 311 µs in linkgress, against 59 µs in 1.0.5. The cause is one column per value read through its mapper, the 1.0.7 fix.
- **batch-expression:** +89 % end to end. The cause is the batch's client-faithful transport, the 1.0.11 fix: the server statement takes 0.53 ms, against 0.40 ms in 1.0.10.
- **The build tier:** 1.0.7's spread of 0.2–1 µs passes.
- **selectMany `count()`:** +85 % in linkgress (1.0.11: +80 %). It grew in 1.0.7 and in 1.0.11.
- **Import:** +27 … +37 % across the runs, from the package's size.
- **Two new, small build costs:**
  - projection-20k +1.3 µs, repaid while reading its rows (−7 % in linkgress);
  - selectmany-count +10 %. That figure is noisy (interval +2 … +20 %), and the cache-on run does not show it.

### Cold start

Against 1.0.11, import is −7.9 % (not significant) and context creation is +12 %. `node:crypto` now loads the first time a model with views computes its marker, not at import. A process that builds such a context pays the same ~2.4 ms, just later.

## Results that differ between versions

The verify phase runs each scenario once per version and compares the SQL and the rows. Changed SQL with identical results is expected wherever a release changed the SQL it emits: `coll-aggregates-*` (1.0.7), `selectmany-count` (1.0.11's hop alias) and the batch envelopes (1.0.11, 1.0.12). Four scenarios return different results:

- **nav-whole-row** (since 1.0.7):
  - 1.0.5 returned the navigation row as JSON. `createdAt` came back as a string, and `lastActiveAt` never went through its mapper.
  - Every column is now read through its mapper.
- **batch-expression and batch-collection-max** (since 1.0.11):
  - A batched `dateTrunc()` or raw timestamp expression now reads as it does standalone on the same client: a `Date` under `pg`'s defaults.
  - 1.0.10 returned the JSON text.
  - 1.0.12 returns exactly what 1.0.11 returns.
- **coll-temptable** (since 1.0.7): the same rows in another order. The scenario has no `ORDER BY`.
