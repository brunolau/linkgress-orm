# v1.0.18

## Fix: a table the migrating role has no privilege on no longer looks missing

`analyze()` read the list of existing tables from `information_schema.tables`. That view lists only the tables
the current role owns or holds some privilege on. A table another role created, with no grant to the
migrating role, was therefore reported as missing. This is the usual situation for an `isExternallyManaged()`
table: the owner loads it and never grants the application role anything on it.

`migrate()` then planned the table as new: its `CREATE TABLE IF NOT EXISTS` was skipped because the table was
there, and the `CREATE INDEX` that followed failed with `must be owner of table skied_kilometers` (42501). The
whole migration stopped there. It surfaced on a gopass staging deploy, where `dwh.skied_kilometers` is owned
by the migrator role and the application role holds no grant on it.

The existing tables are now read from `pg_class` / `pg_namespace` (`relkind` `r` or `p`, which is what
`information_schema` calls a `BASE TABLE`). The catalog lists every table regardless of privileges, so an
existing external table is recognised as existing and nothing is planned for it.

Tests: `tests/schema/externally-managed.test.ts`, "an external table the role holds NO privilege on still
counts as existing". It runs `analyze()` as a role that holds only `USAGE` on the schema, checks that
`information_schema.tables` shows it nothing, and expects no operation for the external tables. It fails
without the fix. It is skipped in memory mode, because the in-memory engine models no privileges.

### Upgrade notes

- No change for tables the migrating role can see through `information_schema`; the same tables are found.
- A table the role could not see before is now found, so `migrate()` no longer plans to create it (or its
  indexes). For an ordinary (not externally managed) entity, `analyze()` now compares it with the model like
  any other existing table.

## `transaction = false`: file migrations that cannot run in a transaction

`MigrationRunner` runs every file migration's `up()` / `down()` in one transaction. PostgreSQL refuses some
statements inside a transaction block, so a file migration could not contain them: `CREATE INDEX CONCURRENTLY`,
`DROP INDEX CONCURRENTLY`, `REINDEX … CONCURRENTLY`, `VACUUM`. A long data backfill also had to hold every lock
until one final commit.

A migration can now opt out:

```typescript
export default class implements Migration {
  transaction = false;

  async up(db: AppDatabase): Promise<void> {
    await db.query(`CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_order_created ON "order" (created_at)`);
  }

  async down(db: AppDatabase): Promise<void> {
    await db.query(`DROP INDEX CONCURRENTLY IF EXISTS ix_order_created`);
  }
}
```

- `up()` / `down()` receive the runner's own context, and each statement commits on its own. The migration is
  not atomic: a failure part-way keeps the statements that already ran.
- It is recorded in the journal only after `up()` resolves (removed only after `down()` resolves), as before.
  A failed migration stays pending and the next `up()` retries it, so write it to be re-runnable
  (`IF NOT EXISTS`, `IF EXISTS`, and drop the INVALID index a failed concurrent build leaves behind).
- On a pooled client, statements may run on different connections, so session state (`SET`, temp tables,
  advisory locks) does not carry over. Open a `db.transaction()` inside the migration for the parts that need it.
- The flag applies on every path that executes a migration: pending `up()`, `runOnBaseline` on a fresh
  database, and `down()`.

Guide: [Migrations → Migrations that cannot run in a transaction](../docs/guides/migrations.md#migrations-that-cannot-run-in-a-transaction-transaction--false).
Tests: `tests/migration/manual-migration.test.ts`. A default migration with `CREATE INDEX CONCURRENTLY` still
fails and stays pending; with `transaction = false` it builds the index, and `down()` drops it; a
`transaction = false` migration that fails part-way keeps its first statement and stays pending. The two
opt-out cases fail without the runner change.

### Upgrade notes

- No change for migrations that do not set `transaction`; the default is `true`.
