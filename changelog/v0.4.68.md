# v0.4.68

## Performance: memoised navigation-path search + tunable slow-query stack capture

Two follow-ups to the v0.4.67 prototype mock rows, from a CPU profile of the same
gopass-eshop `order/create` burst after that change (9 ms of event-loop CPU per request, of
which the query builder still took ~41 %):

### `NavigationPathCache` — the transitive alias search is now memoised (cache ON)

`findNavigationPath` runs a BFS over the schema graph whenever a projected alias has no direct
relation from an already-joined schema (the phase-2 fallback of navigation-join resolution).
The result is a pure function of (schema registry, target alias, the ordered joined
alias→table pairs) and the same query shapes ask the same question on every build — it was the
largest remaining query-build item (~9 % of request CPU).

`NavigationPathCache` retains the computed path per registry (WeakMap) and signature, bounded
at 5 000 entries, and hands out a fresh array per call. It is gated by the SAME opt-in switch
as the mock-row cache (`MockRowCache.setEnabled`), so a host that enabled query-build caching
gets it without a second switch; with the switch off every call computes as before.
Exported for diagnostics/tests (`NavigationPathCache.diagnostics()` / `.reset()`).

### `slowQueryStackTraceLimit` — the per-query stack capture is now tunable

While slow-query detection is active (`onQueryTakingTooLong` + `longRunningQueryThreshold`),
every statement captured a 50-frame stack up front so a slow one can report its caller. On a
deep async call chain that costs ~1 ms per 50 statements (~5 % of the burst above). The new
option sets the captured depth; `0` skips the capture (the callback still fires with an empty
`stack`). Default stays 50 — behaviour unchanged unless configured.
