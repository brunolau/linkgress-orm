# Features: mutation-gated SELECT (`toStatement` + `withMutation`) + insertBulkWithChildren as a MutationBatch leg

Both features exist for one goal: a payment webhook whose SUCCESS path is TWO
statements — a compare-and-swap-gated row load, then one grand write batch.

## Mutation-gated SELECT — `update(...).toStatement()` + `DbCteBuilder.withMutation`

A compare-and-swap UPDATE and the full row load used to be two statements by
necessity (the CAS gates whether the flow proceeds). Now the CAS rides the load
as a data-modifying CTE:

```ts
const gate = cteBuilder.withMutation(
  'cas_gate',
  db.orders
    .where(o => and(eq(o.id, id), /* status guards, currency conjunct */))
    .update({ status: state, paidPrice: sql`COALESCE("paid_price",0) + ${amount}::int` })
    .toStatement(o => ({ id: o.id, paidPrice: o.paidPrice })),
  { id: 'id', paidPrice: 'paidPrice' },
);

const row = await db.orders
  .where(o => and(eq(o.id, id), sql`"order"."id" IN (SELECT "id" FROM "cas_gate")`))
  .with(gate.cte)
  .select(o => ({
    /* the FULL load projection — laterals, nested toLists, raw scalars */
    casPaidPrice: sql<number>`(SELECT "paidPrice" FROM "cas_gate")`.as('casPaidPrice'),
  }))
  .firstOrDefault();
```

Pinned semantics (PostgreSQL data-modifying-CTE rules):
- the outer SELECT reading the table sees the **pre-update snapshot** — the
  load half keeps load semantics;
- the gate's RETURNING exposes the **post-update** values (scalar subselects);
- the mutation executes **exactly once** whether or not the outer query reads
  it — and gating the outer WHERE on the CTE makes `0 rows` mean "the CAS
  lost, nothing was updated".

`toStatement(returningSelector?)` compiles the fluent UPDATE (arbitrary WHERE,
SqlFragment SET values, fragment-capable RETURNING — navigation RETURNING
unsupported) without executing. `withMutation(name, statement, columns)` wraps
any compiled DML as a named CTE with the builder's param-offset accounting.
DML CTEs are only legal on the top-level statement — attach to the query that
executes directly. Tests: `tests/queries/mutation-cte-gate.test.ts`.

## `MutationBatch.addInsertBulkWithChildren`

The parent+children persist (task rows + their logs) can now ride the SAME
statement as upsert/update/delete legs — the CTE triple (ordinal-ordered
parent INSERT → `row_number()`-over-pk ordinal recovery → child INSERT joining
the ordinal for the FK) flattens into sibling CTEs of the batch:

```ts
const tasks = batch.addInsertBulkWithChildren(db.orderTasks, {
  rows: taskRows,                       // e.g. email task born FINISHED_SUCCESS, accounting born IN_PROGRESS
  children: { table: db.orderTaskLogs, foreignKey: 'orderTaskId', rows: logRows },
}, 'tasks', { parentReturning: ['id', 'type'] });
await batch.executeBatch();             // ONE statement with every other leg
batch.getLegRows(tasks!);               // parent rows in INPUT order (read task ids to publish post-commit)
```

`getAffectedCount` reports PARENT rows. Unlike the standalone
`insertBulkWithChildren`, childless parents are allowed (parents are read from
the ordinal CTE, not through the child join). Same v1 rules otherwise:
single-column serial PKs, flat columns, serial-ascend input ordering.
Tests: `tests/queries/mutation-batch-ibwc-leg.test.ts`.
