# v0.4.62

## Feature: `CteRootQueryBuilder.asSubquery()`

A CTE-rooted select (`db.selectFromCte(cte).select(...)`) can now become a real
`Subquery`, so a CTE can be read through the fluent condition helpers —
`inSubquery` / `notInSubquery`, `exists` / `notExists`, `eqSubquery` and friends —
instead of a hand-written `sql` fragment:

```typescript
const scope = cteBuilder.with('discount_scope', visibleDiscounts, { materialized: true });
const scopeIds = db.selectFromCte(scope.cte).select(r => ({ id: r.id })).asSubquery('array');

await db.links.where(l => inSubquery(l.discountId, scopeIds)).count();
```

The signature matches the two existing `asSubquery` implementations
(`SelectQueryBuilder`, the grouped builders):
`asSubquery<TMode extends 'scalar' | 'array' | 'table' = 'table'>(mode?: TMode)`.

### Where the `WITH` lands

A `DbCte` is not a free-floating expression: its body is compiled once by
`DbCteBuilder` with placeholders numbered **from `$1`**, i.e. built to occupy the
opening slots of a statement. Nesting one inside a host statement that has
already bound parameters therefore has to relocate the whole block, and there are
two legitimate destinations for the declaration. `asSubquery()` picks between
them by reading `SqlBuildContext.hoistedCteNames`:

- **Nothing declared upstream** — the subquery is **self-contained**. It emits its
  own `WITH` inside its own parentheses and contributes its CTE bodies'
  parameters, renumbered by the host's offset. PostgreSQL scopes that `WITH` to
  the subquery, so nothing leaks out. The cost is real: a CTE read from N such
  subqueries is written — and executed — N times.

  ```sql
  SELECT "users"."id" FROM "users"
  WHERE "users"."id" IN (
    WITH "older_users" AS MATERIALIZED (SELECT "users"."id" FROM "users" WHERE "users"."age" > $2)
    SELECT "older_users"."id" FROM "older_users")
  ```

- **Already declared upstream** — when the enclosing builder hoisted the CTE to
  statement level (`.with(cte)` on a union leg, see v0.4.61), the subquery emits
  **neither** the `WITH` **nor** the parameters and simply reads the
  statement-level relation by name. This is the shape that lets several readers
  share ONE materialization of an expensive candidate set.

  ```sql
  WITH "older_users" AS MATERIALIZED (SELECT "users"."id" FROM "users" WHERE "users"."age" > $1)
  (SELECT "users"."id" FROM "users" WHERE "users"."id" IN (SELECT "older_users"."id" FROM "older_users"))
  UNION ALL
  (SELECT "posts"."id" FROM "posts" WHERE "posts"."user_id" IN (SELECT "older_users"."id" FROM "older_users"))
  ```

Both shapes return the same rows; only how many times the CTE is planned and
executed differs.

### Parameter ordering

The class contract is preserved verbatim in the nested case: every CTE body's
parameters are emitted first, in `WITH` declaration order (root CTE, then each
joined CTE), followed by any `ON`-predicate and projection parameters. Because
the bodies number their placeholders from `$1`, nesting shifts the entire block
by `outerContext.paramCounter - 1` via `renumberPlaceholders` — the same
quote-aware helper `withMutation` / `QueryBatch` / `MutationBatch` already use, so
dollar-digit sequences inside string literals are not corrupted.

A **partially** hoisted CTE list now throws. Each body's `$N` is relative to one
contiguous block starting at the first CTE, so relocating only some of them would
need a per-CTE offset the baked-in numbering no longer describes — the survivors
would silently bind to the wrong parameters. This mirrors the stance
`UnionQueryBuilder` already takes on a CTE name collision: refuse rather than emit
wrong SQL.

### Supporting changes

#### `ConditionBuilder.build()` now carries `hoistedCteNames`

`ConditionBuilder.build()` creates a **fresh** `SqlBuildContext` for the condition
it compiles. It copied `paramCounter` and `placeholders` across but not
`hoistedCteNames`, so the "already declared upstream" signal died at the WHERE
clause boundary — precisely where a subquery lives.

The effect was invisible and expensive. A union leg that had been handed a hoisted
CTE would re-declare it anyway, once per leg, shadowing the statement-level
declaration:

```sql
WITH "older_users" AS MATERIALIZED (... WHERE "age" > $1)      -- hoisted, now DEAD
(SELECT ... WHERE "id" IN (
   WITH "older_users" AS MATERIALIZED (... WHERE "age" > $2)   -- shadows it
   SELECT ... FROM "older_users"))
UNION ALL
(SELECT ... WHERE "user_id" IN (
   WITH "older_users" AS MATERIALIZED (... WHERE "age" > $3)   -- and again
   SELECT ... FROM "older_users"))
```

Three declarations where the caller asked for one; parameters `[30, 30, 30]`
instead of `[30]`.

**What a user would have observed: nothing.** The rows are correct — each inner
copy is the same body, each renumbers onto its own parameter slot, and the
now-unreferenced hoisted declaration is a read-only CTE that PostgreSQL simply does
not execute. No error, no wrong answer. What is lost is the entire point of
hoisting: the expensive candidate set is materialized once per reader instead of
once per statement, which is the exact duplication v0.4.61 existed to remove. The
only way to notice is to read the emitted SQL or watch the query get slower as legs
are added.

There is one shape where it is **not** merely wasteful. PostgreSQL executes a
data-modifying CTE unconditionally, so a hoisted `withMutation` CTE re-declared per
leg would run its DML once per leg. That is a correctness bug, not a perf note.

The six `whereCond` build sites in `SelectQueryBuilder` now pass the set through.

#### `CteRootQueryBuilder` now honours `materialized` on its own `WITH`

`buildQuery()` assembled its `WITH` entries as `"name" AS (body)`, unconditionally.
A CTE created with `DbCteBuilder.with(..., { materialized: true })` and then used as
a `selectFromCte()` FROM root or as a join target therefore lost its `AS
MATERIALIZED` — **the caller asked for an optimizer fence and silently did not get
one.** (The entity-rooted `.with(cte)` path and `UnionQueryBuilder`'s hoist both
emitted it correctly; only this builder dropped it.)

There is no signal for this. The query compiles, runs, and returns the right rows;
PostgreSQL just inlines the CTE it was told not to inline, and the plan quietly
reverts to the shape the fence was added to prevent — which for a single-reference
CTE is exactly the duplicated-predicate plan. A user would discover it only by
reading the emitted SQL or by an unexplained regression in a plan they thought they
had pinned. Both build paths now share one `declareCte()` helper, so they cannot
drift apart again.

#### `'scalar'` / `'array'` modes are typed as the single column's value type

`SingleColumnValue<TSelection>` (i.e. `TSelection[keyof TSelection]`), not the
projection object. `x IN (SELECT ...)` is not a row comparison, so an array-mode
subquery's element type IS its one column's type; typing it as `{ id: number }[]`
described a shape the SQL can never produce.

**Scope of that benefit — read this before relying on it.** `Subquery`'s type
parameters are carried only by optional *private* phantoms
(`private __resultType?: TResult; private __mode?: TMode;`). TypeScript's
declaration emit strips type annotations from private members, so the published
`dist/query/subquery.d.ts` reads:

```typescript
private __resultType?;
private __mode?;
```

With no structural use of either parameter left, TypeScript measures both as
unrelated and `Subquery<A, 'table'>` is assignable to `Subquery<B, 'array'>` for
any `A`, `B`. **Consumers of the published package therefore get no compile-time
checking of subquery mode or element type at all** — `inSubquery(field, x)` accepts
a `'table'`-mode subquery today and always has. The improved typing here is real
inside this repository (where the annotated source is what type-checks) and is
invisible downstream.

That phantom-erasure gap is deliberately **not** fixed in this release: making the
constraint bite would newly reject existing `inSubquery` / `notInSubquery` call
sites across every consumer, which needs its own change and its own migration note.

Covered by `tests/queries/cte-root-as-subquery.test.ts`: `inSubquery` and
`notInSubquery` against a CTE-rooted subquery, both legs of a `unionAll` sharing
one hoisted declaration, the un-hoisted two-copy shape returning the same answer
with correctly renumbered placeholders, the nested renumbering contract driven
through a synthetic build context, where the `WITH` lands, the partial-hoist
refusal, and a control asserting the standalone CTE-rooted query is unchanged.
