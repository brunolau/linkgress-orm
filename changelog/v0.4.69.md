# v0.4.69

## Performance: per-schema column metadata (kills the `colBuilder.build()` storm)

Every query build called `colBuilder.build()` for **every column** of every touched schema —
in the main-table mock row, the reference mock descriptors, the collection mock item, the
ORDER BY db→property map, the temp-table primary-key probe, and — worst — **`mapDeleteReturningResults`
ran it per column PER RESULT ROW** on `returning: true` shapes. On a wide schema under load
this was a measurable slice of request CPU (`_createMockRow` alone ~2.6 % of process CPU in a
gopass-eshop purchase-path profile, with the shared `get`/`build()` machinery several points more).

Schemas are immutable after registration, so all of it is now served from one
`getSchemaColumnMeta(schema)` — a `WeakMap` keyed by schema identity holding
`{ mapper, type, name, primaryKey }` per column, computed once per schema object. Behaviour
is identical (the metadata comes from the same `build()` call, just cached); no switches, no
opt-in — the values are pure functions of the schema.

Full suite: 1,524 tests pass unchanged.

## Logging: `logFailedQueries` — failed statements reported without the per-statement firehose

The only `[SQL Error]` line the executor emitted was gated on `logQueries`, so a production
context that turned per-statement logging off (to stop formatting `sql.trim()`, the
`JSON.stringify(params)` line and three logger calls for EVERY statement) also lost the record
of statements that failed. The two are now separate duties:

- `logFailedQueries?: boolean` — report a failed statement through the `'error'` section as
  `[SQL Error] <driver message>\n<statement text>`, plus `\n[Parameters] […]` only while
  `logParameters` is on (so a production context keeps parameter values out of its error log).
  Applies to `query`, `querySimple`, `querySimpleMulti`, statements inside `transaction()` and
  `withQueryOptions()` overrides. **Default: the value of `logQueries`** — existing
  configurations are unchanged.
- The failure line now always carries the statement text (previously only the driver message,
  because the statement had just been logged on the `'sql'` section). A context with
  `logQueries: true` therefore sees the SQL twice on a failure — once as debug output, once in
  the error line — which keeps the error line self-contained where the debug channel is dropped.
- `QueryExecutor.isNeeded(options)` is the single predicate deciding whether a logging/timing
  executor is built (context constructor, transactional context, `withQueryOptions` on tables
  and contexts); `logFailedQueries` alone is enough to get one.

Motivation: gopass-eshop staging/production, where `LOG_QUERIES=false` must mean "log failed and
long-running statements only" (`tests/database/failed-query-logging.test.ts`).
