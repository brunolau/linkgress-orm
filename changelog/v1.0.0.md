# v1.0.0

Linkgress reaches 1.0. The last blocker for a stable release was a way to test applications without a
PostgreSQL server that still behaves like one — an in-memory database whose results are PostgreSQL's,
so a suite can switch between the two and get the same outcomes. That database ships in this release,
together with the tests that hold it to PostgreSQL: the whole suite runs in both modes and compares
per-test outcomes, and a differential SQL test compares statement results directly. The test suite
itself moved from Jest to `bun:test`. There are no breaking API changes from 0.4.85: upgrading is a
version bump.

Alongside it, `PGliteClient` runs linkgress on PGlite — the PostgreSQL engine itself, compiled to
WebAssembly and running in process — and the whole suite runs on either one (see below).

## In-memory PostgreSQL-compatible database

Linkgress now ships an in-memory database for fast, isolated tests that return **the same results
PostgreSQL returns** — not a mock. It parses, analyzes and executes PostgreSQL 18 SQL: type resolution
and implicit coercion, NULL semantics, MVCC visibility and isolation levels, row locks (`FOR UPDATE`,
`SKIP LOCKED`, `NOWAIT`), constraints and foreign-key actions with PostgreSQL's error codes and
messages, sequences, triggers and PL/pgSQL, JSON/JSONB and SQL/JSON path, window functions, CTEs
(including recursive and data-modifying), `MERGE`, `RETURNING OLD/NEW`, partitioning, and the
`pg_catalog` / `information_schema` views the schema manager reads.

Connections go through the **real** `pg` and `postgres` drivers — and Bun's `SQL` client — over an
in-process socket speaking the PostgreSQL wire protocol, text and binary formats, so driver
configuration, custom type parsers, prepared statements and transactions behave exactly as against a
server.

```typescript
import { createInMemoryDatabase, PgClient, PostgresClient } from 'linkgress-orm';
import postgres from 'postgres';

const memory = createInMemoryDatabase();
const pgClient = new PgClient(memory.pgPoolConfig());
const postgresClient = new PostgresClient(postgres(memory.postgresOptions({ types: myTypes })));
```

Snapshots let a suite build and seed a database once and start every worker from it:
`memory.snapshot()` / `restoreInMemoryDatabase(bytes)` / `memory.fork()`.

Other processes reach the same database over TCP (`memory.listen()` — `psql`, a child server, Bun's
`SQL`), and `InMemoryDatabaseThread` hosts it in a worker thread (a Bun `Worker` under Bun) so it keeps
serving while the test thread is blocked (e.g. `spawnSync('psql', …)`).

See [docs/guides/in-memory-database.md](../docs/guides/in-memory-database.md).

### PostgreSQL behaviour covered

Besides the everyday SQL an ORM emits, the engine reproduces the parts of PostgreSQL that tests trip
over, found by comparing statement results with PostgreSQL 18 (see *SQL parity test* below):

- **Wire protocol** — binary result and parameter formats (`typsend` / `typrecv` for scalars, numeric,
  date/time, uuid, jsonb, arrays, records, ranges, enums and domains), result format codes in Bind,
  PostgreSQL's protocol errors for malformed binary input.
- **Constraints** — `DEFERRABLE` / `INITIALLY DEFERRED` foreign keys checked at `COMMIT`,
  `SET CONSTRAINTS … DEFERRED | IMMEDIATE` (savepoint-aware), `ON DELETE / UPDATE RESTRICT` vs `NO ACTION`,
  domain `CHECK` / `NOT NULL` constraints wherever a value becomes the domain type (casts, defaults,
  assignment, PL/pgSQL), domain defaults.
- **Types** — ranges and multiranges (operators, functions, `range_agg`, input/output, GiST-free
  indexes by scan), `enum_first` / `enum_last` / `enum_range`, system columns (`ctid`, `xmin`, `tableoid`, …),
  `UPDATE` and `INSERT` of array elements, slices and composite subfields (`SET arr[2] = …`,
  `INSERT INTO t (c.x, arr[1:2]) …`), hash partitioning with PostgreSQL's hash functions so rows land in
  the same partitions.
- **Functions** — `to_char` / `to_number` for numeric, integer and float values (PostgreSQL's formatting
  code, including float rounding), exact `stddev` / `variance` over numeric, `json(b)_to_record(set)`,
  `JSON_VALUE` / `JSON_QUERY` / `JSON_EXISTS` / `IS JSON`, `MERGE_ACTION()`, row comparisons with a
  subquery (`(a, b) = (SELECT …)`), recursive CTEs with `SEARCH DEPTH | BREADTH FIRST` and `CYCLE`.
- **Statements** — SQL-level `PREPARE` / `EXECUTE` / `EXPLAIN EXECUTE` / `CREATE TABLE AS EXECUTE`
  (parameter coercion, re-analysis after DDL, `pg_prepared_statements` parameter and result types),
  updatable views (auto-updatable rewrite, `WITH CHECK OPTION`) and `pg_get_viewdef` output, PL/pgSQL
  `OUT` / `INOUT` / `RETURNS TABLE` parameters.
- **Triggers** — `FOR EACH STATEMENT` triggers (including for `ON CONFLICT` and `MERGE`, in PostgreSQL's
  event order) and transition tables: `REFERENCING NEW TABLE AS … OLD TABLE AS …` on statement and
  row `AFTER` triggers, readable by the trigger function's queries (partition rows in the parent's
  layout), with PostgreSQL's `CREATE TRIGGER` validation and `pg_trigger.tgnewtable` / `tgoldtable`.
- **Errors** — `column "…" does not exist` with PostgreSQL's hints (`Perhaps you meant to reference the
  column "t.name".`), expression-context errors (`cannot use subquery in EXECUTE parameter`, aggregates
  / set-returning functions in DDL expressions), expressions validated when an index predicate,
  partition key or domain `CHECK` is created, and PostgreSQL 18's constant folding of generation
  expressions (`GENERATED ALWAYS AS (upper('x') || qty)` fails with *could not determine which collation
  to use for upper() function*, as on the server).

### Performance

The executor keeps PostgreSQL's row order while avoiding work a planner would avoid:

- Equality restrictions are answered from hash indexes over the heap, built lazily and maintained on
  insert and on statement undo: `col = value`, `col = ANY(array)` / `IN (…)`, and `<expr> = value` when
  the table has an index on exactly that expression (`search_normalize(internal_id) = …`). Several
  equalities probe the smallest bucket; values from STABLE / IMMUTABLE functions are computed once.
- `LEFT JOIN`s that a `WHERE` restriction makes inner run as inner joins; restrictions relating both
  sides of an inner join drive hashing or probe the left table's index instead of a cross product.
- A `LIMIT` that nothing sorts, groups or deduplicates stops the scan (and `EXISTS` subqueries stop at
  the first row); the target list is evaluated for the returned rows only, as in PostgreSQL.
- Correlated subqueries remember results per outer-column values within a statement, and stop doing
  so when the values do not repeat. Grouping uses per-column hash maps; aggregates without `ORDER BY`
  / `DISTINCT` stream. `pg_type` / `pg_namespace` rows are rebuilt only when the catalog changes.

On the downstream suite below the in-memory run takes about the same wall time as PostgreSQL (with 10
Jest workers: 251 s vs 229 s for the tests in the final run, now that its statement-level audit
triggers fire as they do on the server; 230 s before they did), while replacing about 3.5 minutes of
PostgreSQL template setup with an in-memory migrate + seed of about 3 minutes that is then snapshotted,
and running four suites PostgreSQL skips. The database thread of a worker holds about 420 MB on average
(peak 790 MB).

## Tests: PostgreSQL / in-memory parity

### `test:memory` and `test:parity`

```bash
bun run test            # the suite against PostgreSQL
bun run test:memory     # the same files against in-memory databases (no server needed)
bun run test:parity     # both, then per-test outcomes compared — exits non-zero on any difference
```

`test:memory` runs every file unchanged: the preload replaces the `pg` and `postgres` modules with
wrappers that connect to an in-memory database, built once from the test schema as a snapshot and
restored per file. `--thread` hosts the databases in worker threads. `test:parity` runs both at once,
then reports every file whose result or any test whose status differs; the SQL parity test may not skip
itself there. `npm publish` runs `test:parity` after the build (`prepublishOnly`), so a release cannot go
out unless the suite passes against PostgreSQL and in memory with the same outcomes.

### PostgreSQL runs in parallel

PostgreSQL runs no longer run the files one after another on `DB_NAME`: the runner builds a template
database (the extensions the suite uses and the test schema), clones it into 6 worker databases
(`<DB_NAME>_<host>_<pid>_w1..w6`, `CREATE DATABASE … TEMPLATE`, ~2 s including the schema) and runs 6
files at a time, each on its own database. Every database it created is dropped `WITH (FORCE)` when the run
ends — passed, failed, failed during setup, stopped with Ctrl+C / SIGTERM, or crashed — and databases left
by a runner that was killed outright are dropped by the next PostgreSQL run on the same machine (`<host>`
is a hash of the host name, so runs on other machines sharing the server are never touched). `--pg-jobs N`
sets the count; `--pg-jobs 1` keeps the serial run on `DB_NAME`. The suite against PostgreSQL takes ~53 s
with 6 workers instead of ~115 s serially (4 workers: ~58 s; 12 gave no further gain — the server's disk is
the limit), and `test:parity` ~62 s.

### SQL parity test

`tests/memory/sql-parity.test.ts` is a differential test over `tests/memory/sql-parity-corpus.ts`:
32 cases, 641 statements (literals and casts, numeric and date/time arithmetic, text and pattern
matching, arrays, JSON and SQL/JSON, aggregates, window functions, joins, subqueries, CTEs with
`SEARCH` / `CYCLE`, DML with `RETURNING`, `ON CONFLICT` / `MERGE`, constraints, sequences and identity,
DDL and views, PL/pgSQL, triggers and transition tables, enum / domain / composite types, generated columns and partitioning,
ranges, binary output, bind parameters, `PREPARE` / `EXECUTE`, locking and transactions, catalog
functions, syntax errors and ORM-style statements).
Each case runs on PostgreSQL and on a fresh in-memory database in a rolled-back transaction, and every
statement must give the same command tag, row count, column names and type OIDs, rows as the exact
text PostgreSQL sends, or the same error — SQLSTATE, message, detail, hint and position. Without a
reachable PostgreSQL the cases are skipped (`LINKGRESS_SQL_PARITY_REQUIRE_PG=1` fails instead).

## Tests: Jest → `bun:test`

The suite runs on Bun's test runner; Jest, `ts-jest`, `@jest/globals` and `@types/jest` are gone.

- **Runner** — `tests/run.ts` runs each test file in its own `bun test` process (module and database
  isolation, as Jest's per-file module registry gave), serially against PostgreSQL and in parallel in
  memory and on PGlite, collects per-test results from JUnit reports and prints one summary. Options: paths or path
  substrings, `--memory`, `--thread`, `--parity`, `--driver pg|postgres|bun|pglite`, `-t` (name pattern),
  `-j` (jobs), `--timeout`, `--json`, `--coverage` (lcov merged into `coverage/lcov.info`), `--verbose`.
- **Setup** — `bunfig.toml` preloads `tests/setup.ts` (dotenv, custom matchers, the in-memory driver
  modules via `mock.module`). PostgreSQL runs create the schema once (`tests/global-schema.ts`), replacing
  Jest's `globalSetup` / `globalTeardown`.
- **Test files** — imports from `bun:test`; `expect(promise).rejects` became `expectToReject(…)` where
  the value is a query builder (a thenable Bun does not await); the separate `tests-bun/` suite for Bun's
  `SQL` client is part of the main suite (`tests/database/bun-sql-contract.test.ts`, also run in memory
  over TCP).
- **In-process socket under Bun** — the in-memory database's socket delivers responses with
  `process.nextTick` under Bun (`setImmediate` stays on Node): `bun test` does not wake for immediates
  queued as a test settles, which stalled every test boundary; the in-memory suite went from 44.6 s to
  12.7 s on 12 files.
- **Scripts** — `test`, `test:memory`, `test:pglite`, `test:parity`, `test:driver:postgres`, `test:driver:bun`,
  `test:watch`, `test:coverage`, `test:verbose`, `test:single`, `type-check:tests` (`tests/tsconfig.json`
  with Bun types).

### Verification

- **Linkgress suite** (`bun run test:parity`) — 140 files, 1865 tests against PostgreSQL 18 (114 s,
  files serial) and in memory (13.4 s, 12 files in parallel): identical outcomes for every file and
  test, all passing. The in-memory run with databases in worker threads (`--memory --thread`) passes the
  same 1865. On PGlite (`bun run test:pglite`) 1858 pass and the 7 attributed failures below remain.
- **SQL parity test** — 32 / 32 cases, 641 statements identical to PostgreSQL 18, run with
  `LINKGRESS_SQL_PARITY_REQUIRE_PG=1` so a missing server cannot turn them into skips.
- `tests/memory/in-memory-database.test.ts` covers the API (snapshots, TCP endpoint, thread host,
  per-name databases, procedures, `EXPLAIN`) and checks the index lookups and `LIMIT` against scans.
- `tsc` over the sources and over the tests (`type-check:tests`) is clean.
- **Downstream application** — a large application suite (17 225 Jest tests: services, migrations,
  psql-driven backfill scripts, a child server over TCP) was run against PostgreSQL 18 and in memory,
  unchanged, with the final engine (migrated and seeded afresh in memory): 17 224 identical test
  outcomes. The one difference reads the first row of an unordered
  query whose order in PostgreSQL comes from heap page reuse after an autovacuum during seeding. Two
  suites can also fail their `afterAll` cleanup in memory: the application writes an order in a
  background transaction it does not await, and the in-memory database answers the cleanup statements
  before that transaction commits (with 1 ms of added latency per response they pass) — a race in those
  tests, not a difference in query results.
- The engine is only loaded when an in-memory database is created (`createInMemoryDatabase` requires it
  lazily), so there is no cost on the regular PostgreSQL path.

## PGlite support — `PGliteClient`

`PGliteClient` runs linkgress on [PGlite](https://pglite.dev): the PostgreSQL engine itself (18.3 in
PGlite 0.5.8) compiled to WebAssembly, running inside the process — Node, Bun, Deno or a browser — with
no server. Where the in-memory database is reached through the real drivers, PGlite is a driver of its
own: `PGliteClient` is a `DatabaseClient` next to `PgClient`, `PostgresClient` and `BunClient`.

```typescript
import { PGliteClient } from 'linkgress-orm';

const db = new AppDatabase(new PGliteClient());                       // in-memory
const db = new AppDatabase(new PGliteClient('./pgdata'));             // persisted to a directory
const db = new AppDatabase(new PGliteClient(await PGlite.create()));  // an instance you own
```

### What changed

- **`PGliteClient`** (`@electric-sql/pglite`, a new optional peer dependency, `^0.5.0`):
  - **One session.** PGlite has a single session, so a FIFO lock per PGlite instance serializes root
    calls and `connect()` leases the session until `release()` — a pool of one, shared by every client
    over the same instance, so no other caller's statement can land inside a leaseholder's open
    `BEGIN`. `transaction()` uses PGlite's own (BEGIN / COMMIT, ROLLBACK when the callback throws).
  - **No silent deadlock.** From inside a `transaction()` callback, a root-level call on the same
    instance — another query, a nested transaction — could only run after that transaction ends, so
    it throws at once instead of hanging (tracked with AsyncLocalStorage; skipped where unavailable).
  - **Multi-statement SQL** runs through `exec()`: `querySimple` returns the last row-bearing result,
    `querySimpleMulti` one result per statement (row-less ones included, as the fully-optimized path
    indexes them positionally). The temp-table strategy, `FutureQuery` batches and the fully-optimized
    path therefore take their single-call routes; native arrays decode, so `array_agg` is kept.
  - **pg-parity values** for an instance the client creates, wherever pg and postgres.js agree and
    PGlite does not: int8 arrives as a decimal string (PGlite: a number, a BigInt once unsafe), bytea
    as a `Buffer` (PGlite: a plain `Uint8Array`), and a `Date` bound to a date / timestamp /
    timestamptz parameter is sent in local time with its offset, as pg sends it. PGlite's own default
    sends UTC text: east of Greenwich a local-midnight `Date` lands on the previous day in a `date`
    column, and every `Date` round-tripped through `timestamp` comes back shifted by the host's
    offset. Caller `parsers` / `serializers` override any type; a passed-in instance is used exactly
    as configured and is never closed by `end()`.
  - `timeoutMs` (`.withTimeout()`) and `prepare` are ignored, as in PgClient and BunClient — PGlite
    cannot cancel a running statement.
- **The suite runs on PGlite**: `bun run test:pglite` (`bun tests/run.ts --driver pglite`) builds the
  AppDatabase schema on one PGlite and dumps it with `dumpDataDir()` (`tests/global-schema.ts
  pglite-snapshot`); every test file then boots its own instance from that snapshot in ~150 ms, so the
  files run in parallel — half the cores unless `-j` says otherwise. Bun loads PGlite's WASM natively
  (under Jest it needed node's `--experimental-vm-modules`). Files that construct `PgClient` /
  `PostgresClient` themselves still use the server, which is optional on this driver: without one the
  runner warns and those files fail.
- **Comparing two runs**: `LINKGRESS_TEST_RECORD_DIR=<dir>` records every statement the harness runs
  with a digest of its result (under Bun a statement's test is its position in the file);
  `bench/pglite/compare-runs.mjs` diffs two runs — the runner's `--json` output or jest reports — for
  per-test outcomes, per-file timings, and statement results paired by test and SQL text.

### Measured: the suite on PostgreSQL 18.3 and on PGlite 0.5.8

Full numbers, method and every attributed difference: `bench/pglite/README.md`. Measured on the Jest suite,
before it moved to `bun:test`; at least two runs per configuration on the same host, identical outcomes
across repetitions:

- **Time**: the suite takes 23.5 s on PGlite with 8 workers against 147.8 s serially on the real server
  (6.3×), with per-test outcomes identical to a serial PGlite run; the in-memory database takes 11.6 s
  with 12 workers. Serially PGlite is only 8–20% faster than the server: it is slower per statement
  (0.14 ms vs 0.09 ms for a trivial `SELECT` — a WASM engine and the wire protocol in JavaScript) but
  4–5× faster at what touches the server's disk (a truncate-and-reseed reset takes 17 ms instead of
  77 ms), and each test file boots its own instance (~0.25 s under jest). `bench/pglite/latency.ts`
  measures each part.
- **Outcomes**: pg 1,791 passed / 0 failed; PGlite 1,780 / 11. Of the 11, five are harness artifacts
  (specs that seed through the harness but query their own `PostgresClient`), four are the
  pre-existing `QueryBatch` date revival below, one needs two concurrent sessions (`for-update`, which
  fails at once on PGlite's single session) and one an ICU collation PGlite has no data for.
- **Results**: 24,167 of 24,344 paired statements (99.3%) return identical rows. The rest trace to the
  test environment (a shared long-lived server database vs a fresh one per file), to driver conventions
  (`pg` returns `name[]` as text and `date` as local midnight), to PGlite defaults (collation `C`, a
  fixed-offset session `TimeZone` that ignores daylight saving), or to `pg` storing a JS `[]` bound to
  `json` as `{}`.

On the Bun runner, same host (`bun tests/run.ts`, 140 files including the PGlite contract spec):

| run | wall time | passed / failed |
| --- | --- | --- |
| PGlite, 8 files in parallel | 21.0 s | 1,858 / 7 |
| in-memory database, 12 files in parallel | 12.7 s | 1,865 / 0 |

The 7 PGlite failures are the attributed ones above minus the four `query-batch-fidelity` date-revival
tests, which pass under Bun: five harness artifacts (`query-timeout` × 4, `query-batch` × 1),
`for-update` and `collation`. Moving the in-memory database's socket off `setImmediate` under Bun took
its run from 44.6 s to 12.7 s: `bun test` does not wake for immediates queued as a test settles, so
responses waited for the next timer tick between tests.

### Found along the way (pre-existing, not changed here)

- **The suite spends most of its pg time resetting.** `setupDatabase()` truncates 22 tables before
  1,087 tests; on the server used here that costs ~98 ms per reset with the seed, because `TRUNCATE`
  creates new relation files. A DELETE-based reset measured 31 ms (9.5 ms vs 17 ms on PGlite) — about
  73 s off a serial pg run.
- **`QueryBatch` revives `date` columns at local midnight** — pg's convention — while standalone reads
  through postgres.js (and PGlite) give UTC midnight, so batched and standalone results differ by the
  host's UTC offset on those drivers: the four `query-batch-fidelity` tests that compare them fail with
  `LINKGRESS_TEST_DRIVER=postgres` exactly as they do on PGlite.
- **On the `pg` driver a JS array bound to a `json` column is sent as a PostgreSQL array literal**:
  node-postgres serializes arrays that way whatever the parameter type, so `[]` is stored as `{}` and
  `[1, 2]` fails with "invalid input syntax for type json" (the type-matrix row of
  `query-batch-fidelity` stores `{}` on pg, `[]` on PGlite). `jsonb` is affected the same way.
- `all-strategies-comparison` › "identical results with multiple collections" has no `orderBy` on the
  outer query, so its row order — and the test — is nondeterministic on any driver.
- `recreate-changed-index` › the plain-btree → gin-trgm case assumes `pg_trgm` is already installed in
  the test database; on a fresh database (and in memory) it fails until another spec has created it.
  (Fixed with the move to `bun:test`: the spec now installs the search support it uses.)
- `bun-client.test.ts` does not compile against the jest 30.5 typings a fresh install resolves
  (`jest.fn<any>().mockResolvedValue(x as any)` → "not assignable to parameter of type 'never'").
  (Gone with Jest: the suite type-checks against `@types/bun`.)
- `query-timeout` (builder / context level) and `query-batch` (custom-mapper timestamps) seed through
  the harness but query through their own `PostgresClient`, so they only work when the harness driver
  talks to that same server.
