# v1.0.0

Linkgress reaches 1.0. The last blocker for a stable release was a way to test applications without a
PostgreSQL server that still behaves like one — an in-memory database whose results are PostgreSQL's,
so a suite can switch between the two and get the same outcomes. That database ships in this release.
There are no breaking API changes from 0.4.85: upgrading is a version bump.

Alongside it, `PGliteClient` runs linkgress on PGlite — the PostgreSQL engine itself, compiled to
WebAssembly and running in process — and the whole suite runs on either one (see below).

## In-memory PostgreSQL-compatible database

Linkgress now ships an in-memory database for fast, isolated tests that return **the same results
PostgreSQL returns** — not a mock. It parses, analyzes and executes PostgreSQL 18 SQL: type resolution
and implicit coercion, NULL semantics, MVCC visibility and isolation levels, row locks (`FOR UPDATE`,
`SKIP LOCKED`, `NOWAIT`), constraints and foreign-key actions with PostgreSQL's error codes and
messages, sequences, triggers and PL/pgSQL, JSON/JSONB and SQL/JSON path, window functions, CTEs
(including recursive and data-modifying), `MERGE`, `RETURNING OLD/NEW`, partitioning, and the
`pg_catalog` / `information_schema` views the schema manager reads.

Connections go through the **real** `pg` and `postgres` drivers over an in-process socket speaking the
PostgreSQL wire protocol, so driver configuration, custom type parsers, prepared statements and
transactions behave exactly as against a server.

```typescript
import { createInMemoryDatabase, PgClient, PostgresClient } from 'linkgress-orm';
import postgres from 'postgres';

const memory = createInMemoryDatabase();
const pgClient = new PgClient(memory.pgPoolConfig());
const postgresClient = new PostgresClient(postgres(memory.postgresOptions({ types: myTypes })));
```

Snapshots let a suite build and seed a database once and start every worker from it:
`memory.snapshot()` / `restoreInMemoryDatabase(bytes)` / `memory.fork()`.

Other processes reach the same database over TCP (`memory.listen()` — `psql`, a child server), and
`InMemoryDatabaseThread` hosts it in a worker thread so it keeps serving while the test thread is
blocked (e.g. `spawnSync('psql', …)`).

See [docs/guides/in-memory-database.md](../docs/guides/in-memory-database.md).

### Performance

The executor keeps PostgreSQL's row order while avoiding work a planner would avoid:

- Equality restrictions are answered from hash indexes over the heap, built lazily and maintained on
  insert and on statement undo: `col = value`, `col = ANY(array)` / `IN (…)`, and `<expr> = value` when
  the table has an index on exactly that expression (`search_normalize(internal_id) = …`). Several
  equalities probe the smallest bucket; values from STABLE / IMMUTABLE functions are computed once.
- `LEFT JOIN`s that a `WHERE` restriction makes inner run as inner joins; restrictions relating both
  sides of an inner join drive hashing or probe the left table's index instead of a cross product.
- A `LIMIT` that nothing sorts, groups or deduplicates stops the scan (and `EXISTS` subqueries stop at
  the first row); the target list is evaluated for the returned rows only, as in PostgreSQL.
- Correlated subqueries remember results per outer-column values within a statement, and stop doing
  so when the values do not repeat. Grouping uses per-column hash maps; aggregates without `ORDER BY`
  / `DISTINCT` stream. `pg_type` / `pg_namespace` rows are rebuilt only when the catalog changes.

On the downstream suite below the in-memory run takes the same wall time as PostgreSQL (with 10 Jest
workers: 230 s vs 229 s for the tests, plus about 3.5 minutes of PostgreSQL template setup the in-memory
run replaces with a snapshot), while also running four suites PostgreSQL skips; the remaining files take
8 % less time in total. The database thread of a worker holds about 420 MB on average (peak 790 MB).

### Verification

- The whole Linkgress suite runs in memory with `LINKGRESS_TEST_DB=memory` (Jest maps `pg` / `postgres`
  to wrappers adding the in-memory socket — no test changes). Per-test outcomes were compared with the
  same suite run file-by-file against freshly created PostgreSQL 18 databases: 1786 / 1786 identical,
  both in-process and with the database in a worker thread (`LINKGRESS_MEMORY_THREAD=true`).
  `tests/memory/in-memory-database.test.ts` covers the API (snapshots, TCP endpoint, thread host,
  per-name databases, procedures, `EXPLAIN`) and checks the index lookups and `LIMIT` against scans.
- A large downstream application suite (17 225 Jest tests: services, migrations, psql-driven backfill
  scripts, a child server over TCP) was run against PostgreSQL 18 and in memory, unchanged: 17 224
  identical test outcomes. The one difference reads the first row of an unordered query whose order in
  PostgreSQL comes from heap page reuse after an autovacuum during seeding. Two suites can also fail
  their `afterAll` cleanup in memory: the application writes an order in a background transaction it
  does not await, and the in-memory database answers the cleanup statements before that transaction
  commits (with 1 ms of added latency per response they pass) — a race in those tests, not a difference
  in query results.
- The real-database suite is unchanged and green; the engine is only loaded when an in-memory database
  is created (`createInMemoryDatabase` requires it lazily), so there is no cost on the regular path.

## PGlite support — `PGliteClient`

`PGliteClient` runs linkgress on [PGlite](https://pglite.dev): the PostgreSQL engine itself (18.3 in
PGlite 0.5.8) compiled to WebAssembly, running inside the process — Node, Bun, Deno or a browser — with
no server. Where the in-memory database is reached through the real drivers, PGlite is a driver of its
own: `PGliteClient` is a `DatabaseClient` next to `PgClient`, `PostgresClient` and `BunClient`.

```typescript
import { PGliteClient } from 'linkgress-orm';

const db = new AppDatabase(new PGliteClient());                       // in-memory
const db = new AppDatabase(new PGliteClient('./pgdata'));             // persisted to a directory
const db = new AppDatabase(new PGliteClient(await PGlite.create()));  // an instance you own
```

### What changed

- **`PGliteClient`** (`@electric-sql/pglite`, a new optional peer dependency, `^0.5.0`):
  - **One session.** PGlite has a single session, so a FIFO lock per PGlite instance serializes root
    calls and `connect()` leases the session until `release()` — a pool of one, shared by every client
    over the same instance, so no other caller's statement can land inside a leaseholder's open
    `BEGIN`. `transaction()` uses PGlite's own (BEGIN / COMMIT, ROLLBACK when the callback throws).
  - **No silent deadlock.** From inside a `transaction()` callback, a root-level call on the same
    instance — another query, a nested transaction — could only run after that transaction ends, so
    it throws at once instead of hanging (tracked with AsyncLocalStorage; skipped where unavailable).
  - **Multi-statement SQL** runs through `exec()`: `querySimple` returns the last row-bearing result,
    `querySimpleMulti` one result per statement (row-less ones included, as the fully-optimized path
    indexes them positionally). The temp-table strategy, `FutureQuery` batches and the fully-optimized
    path therefore take their single-call routes; native arrays decode, so `array_agg` is kept.
  - **pg-parity values** for an instance the client creates, wherever pg and postgres.js agree and
    PGlite does not: int8 arrives as a decimal string (PGlite: a number, a BigInt once unsafe), bytea
    as a `Buffer` (PGlite: a plain `Uint8Array`), and a `Date` bound to a date / timestamp /
    timestamptz parameter is sent in local time with its offset, as pg sends it. PGlite's own default
    sends UTC text: east of Greenwich a local-midnight `Date` lands on the previous day in a `date`
    column, and every `Date` round-tripped through `timestamp` comes back shifted by the host's
    offset. Caller `parsers` / `serializers` override any type; a passed-in instance is used exactly
    as configured and is never closed by `end()`.
  - `timeoutMs` (`.withTimeout()`) and `prepare` are ignored, as in PgClient and BunClient — PGlite
    cannot cancel a running statement.
- **The suite runs on PGlite**: `pnpm test:pglite` sets `LINKGRESS_TEST_DRIVER=pglite` and starts jest
  under `--experimental-vm-modules` (PGlite loads its WASM through dynamic `import()`, which jest's vm
  context only allows with that flag; `globalSetup` refuses to start without it). `globalSetup` builds
  the AppDatabase schema once and dumps it with `dumpDataDir()`; every test file then boots its own
  instance from that snapshot in ~150 ms, so the files run on parallel workers — half the cores unless
  a worker option is given. Files that construct `PgClient` / `PostgresClient` themselves still use the
  server, which is optional on this driver.
- **Comparing two runs**: `LINKGRESS_TEST_RECORD_DIR=<dir>` records every statement the harness runs
  with a digest of its result; `bench/pglite/compare-runs.mjs` diffs two jest runs — per-test outcomes,
  per-file timings, and statement results paired by test and SQL text.

### Measured: the suite on PostgreSQL 18.3 and on PGlite 0.5.8

Full numbers, method and every attributed difference: `bench/pglite/README.md`. At least two runs per
configuration on the same host, identical outcomes across repetitions:

- **Time**: the suite takes 23.5 s on PGlite with 8 workers against 147.8 s serially on the real server
  (6.3×), with per-test outcomes identical to a serial PGlite run; the in-memory database takes 11.6 s
  with 12 workers. Serially PGlite is only 8–20% faster than the server: it is slower per statement
  (0.14 ms vs 0.09 ms for a trivial `SELECT` — a WASM engine and the wire protocol in JavaScript) but
  4–5× faster at what touches the server's disk (a truncate-and-reseed reset takes 17 ms instead of
  77 ms), and each test file boots its own instance (~0.25 s under jest). `bench/pglite/latency.ts`
  measures each part.
- **Outcomes**: pg 1,791 passed / 0 failed; PGlite 1,780 / 11. Of the 11, five are harness artifacts
  (specs that seed through the harness but query their own `PostgresClient`), four are the
  pre-existing `QueryBatch` date revival below, one needs two concurrent sessions (`for-update`, which
  fails at once on PGlite's single session) and one an ICU collation PGlite has no data for.
- **Results**: 24,167 of 24,344 paired statements (99.3%) return identical rows. The rest trace to the
  test environment (a shared long-lived server database vs a fresh one per file), to driver conventions
  (`pg` returns `name[]` as text and `date` as local midnight), to PGlite defaults (collation `C`, a
  fixed-offset session `TimeZone` that ignores daylight saving), or to `pg` storing a JS `[]` bound to
  `json` as `{}`.

### Found along the way (pre-existing, not changed here)

- **The suite spends most of its pg time resetting.** `setupDatabase()` truncates 22 tables before
  1,087 tests; on the server used here that costs ~98 ms per reset with the seed, because `TRUNCATE`
  creates new relation files. A DELETE-based reset measured 31 ms (9.5 ms vs 17 ms on PGlite) — about
  73 s off a serial pg run.
- **`QueryBatch` revives `date` columns at local midnight** — pg's convention — while standalone reads
  through postgres.js (and PGlite) give UTC midnight, so batched and standalone results differ by the
  host's UTC offset on those drivers: the four `query-batch-fidelity` tests that compare them fail with
  `LINKGRESS_TEST_DRIVER=postgres` exactly as they do on PGlite.
- **On the `pg` driver a JS array bound to a `json` column is sent as a PostgreSQL array literal**:
  node-postgres serializes arrays that way whatever the parameter type, so `[]` is stored as `{}` and
  `[1, 2]` fails with "invalid input syntax for type json" (the type-matrix row of
  `query-batch-fidelity` stores `{}` on pg, `[]` on PGlite). `jsonb` is affected the same way.
- `all-strategies-comparison` › "identical results with multiple collections" has no `orderBy` on the
  outer query, so its row order — and the test — is nondeterministic on any driver.
- `recreate-changed-index` › the plain-btree → gin-trgm case assumes `pg_trgm` is already installed in
  the test database; on a fresh database (and in memory) it fails until another spec has created it.
- `bun-client.test.ts` does not compile against the jest 30.5 typings a fresh install resolves
  (`jest.fn<any>().mockResolvedValue(x as any)` → "not assignable to parameter of type 'never'").
- `query-timeout` (builder / context level) and `query-batch` (custom-mapper timestamps) seed through
  the harness but query through their own `PostgresClient`, so they only work when the harness driver
  talks to that same server.
