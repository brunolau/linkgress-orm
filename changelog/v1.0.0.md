# v1.0.0

Linkgress reaches 1.0. The last blocker for a stable release was a way to test applications without a
PostgreSQL server that still behaves like one — an in-memory database whose results are PostgreSQL's,
so a suite can switch between the two and get the same outcomes. That database ships in this release.
There are no breaking API changes from 0.4.85: upgrading is a version bump.

## In-memory PostgreSQL-compatible database

Linkgress now ships an in-memory database for fast, isolated tests that return **the same results
PostgreSQL returns** — not a mock. It parses, analyzes and executes PostgreSQL 18 SQL: type resolution
and implicit coercion, NULL semantics, MVCC visibility and isolation levels, row locks (`FOR UPDATE`,
`SKIP LOCKED`, `NOWAIT`), constraints and foreign-key actions with PostgreSQL's error codes and
messages, sequences, triggers and PL/pgSQL, JSON/JSONB and SQL/JSON path, window functions, CTEs
(including recursive and data-modifying), `MERGE`, `RETURNING OLD/NEW`, partitioning, and the
`pg_catalog` / `information_schema` views the schema manager reads.

Connections go through the **real** `pg` and `postgres` drivers over an in-process socket speaking the
PostgreSQL wire protocol, so driver configuration, custom type parsers, prepared statements and
transactions behave exactly as against a server.

```typescript
import { createInMemoryDatabase, PgClient, PostgresClient } from 'linkgress-orm';
import postgres from 'postgres';

const memory = createInMemoryDatabase();
const pgClient = new PgClient(memory.pgPoolConfig());
const postgresClient = new PostgresClient(postgres(memory.postgresOptions({ types: myTypes })));
```

Snapshots let a suite build and seed a database once and start every worker from it:
`memory.snapshot()` / `restoreInMemoryDatabase(bytes)` / `memory.fork()`.

Other processes reach the same database over TCP (`memory.listen()` — `psql`, a child server), and
`InMemoryDatabaseThread` hosts it in a worker thread so it keeps serving while the test thread is
blocked (e.g. `spawnSync('psql', …)`).

See [docs/guides/in-memory-database.md](../docs/guides/in-memory-database.md).

### Performance

The executor keeps PostgreSQL's row order while avoiding work a planner would avoid:

- Equality restrictions are answered from hash indexes over the heap, built lazily and maintained on
  insert and on statement undo: `col = value`, `col = ANY(array)` / `IN (…)`, and `<expr> = value` when
  the table has an index on exactly that expression (`search_normalize(internal_id) = …`). Several
  equalities probe the smallest bucket; values from STABLE / IMMUTABLE functions are computed once.
- `LEFT JOIN`s that a `WHERE` restriction makes inner run as inner joins; restrictions relating both
  sides of an inner join drive hashing or probe the left table's index instead of a cross product.
- A `LIMIT` that nothing sorts, groups or deduplicates stops the scan (and `EXISTS` subqueries stop at
  the first row); the target list is evaluated for the returned rows only, as in PostgreSQL.
- Correlated subqueries remember results per outer-column values within a statement, and stop doing
  so when the values do not repeat. Grouping uses per-column hash maps; aggregates without `ORDER BY`
  / `DISTINCT` stream. `pg_type` / `pg_namespace` rows are rebuilt only when the catalog changes.

On the downstream suite below the in-memory run takes the same wall time as PostgreSQL (with 10 Jest
workers: 230 s vs 229 s for the tests, plus about 3.5 minutes of PostgreSQL template setup the in-memory
run replaces with a snapshot), while also running four suites PostgreSQL skips; the remaining files take
8 % less time in total. The database thread of a worker holds about 420 MB on average (peak 790 MB).

### Verification

- The whole Linkgress suite runs in memory with `LINKGRESS_TEST_DB=memory` (Jest maps `pg` / `postgres`
  to wrappers adding the in-memory socket — no test changes). Per-test outcomes were compared with the
  same suite run file-by-file against freshly created PostgreSQL 18 databases: 1786 / 1786 identical,
  both in-process and with the database in a worker thread (`LINKGRESS_MEMORY_THREAD=true`).
  `tests/memory/in-memory-database.test.ts` covers the API (snapshots, TCP endpoint, thread host,
  per-name databases, procedures, `EXPLAIN`) and checks the index lookups and `LIMIT` against scans.
- A large downstream application suite (17 225 Jest tests: services, migrations, psql-driven backfill
  scripts, a child server over TCP) was run against PostgreSQL 18 and in memory, unchanged: 17 224
  identical test outcomes. The one difference reads the first row of an unordered query whose order in
  PostgreSQL comes from heap page reuse after an autovacuum during seeding. Two suites can also fail
  their `afterAll` cleanup in memory: the application writes an order in a background transaction it
  does not await, and the in-memory database answers the cleanup statements before that transaction
  commits (with 1 ms of added latency per response they pass) — a race in those tests, not a difference
  in query results.
- The real-database suite is unchanged and green; the engine is only loaded when an in-memory database
  is created (`createInMemoryDatabase` requires it lazily), so there is no cost on the regular path.
