# v1.0.17

A performance release with one new opt-in option:

- **Custom types can share mapped values.** A custom type can declare its mapped values immutable (`immutable: true`). Its `fromDriver` then runs once per distinct driver value of a column in a result set, not once per row. Reading 10,000 rows through a Temporal-parsing mapper, with 10 to 100 distinct values, is 9–35× faster in linkgress.
- **QueryBatch is cheaper.** Its statement is shorter, each value's type is tested once per row instead of up to seven times, and a text a column repeats is parsed once per result set.
- **One pre-existing bug is fixed:** a grouped select now applies a builder-form custom type's mapper.

Nothing else changes in the results. The upgrade notes list every observable difference.

Measured with `bench/versions` (8 interleaved rounds, Node 26.8.1, PostgreSQL 18.3). Against 1.0.16:

| scenario | end to end | in linkgress |
| --- | --- | --- |
| batch-expression | 1.51 → 1.15 ms (−22 %) | 520 → 225 µs (−56 %) |
| batch-numeric | 1.33 → 1.22 ms (−9.7 %) | |

- **Every other scenario** is unchanged within noise. The geometric means are −0.5 % end to end, −1.9 % in linkgress and −0.3 % for building.
- **Against 1.0.5:** end to end +1.4 % (1.0.11: +5.3 %, 1.0.12: +2.7 %), in linkgress +14 % (+38 %, +16 %), building +22 % (+30 %, +21 %). The full comparison is in `bench/versions/results/1.0.16-vs-1.0.17.md`.
- **The `immutable` option does not show in these scenarios**, because their model declares no immutable type. Its own measurements are below.

## Upgrade notes

No API is removed. `immutable` is off by default, and a type without it is built and read exactly as before.

### Results and semantics that change

- **A grouped select's expression read through a builder-form custom type (`customType()`) is now mapped.**
  - Before, it came back as the driver delivered it, e.g. `'45'` instead of the mapped value, and a `min()` / `max()` of such an expression read as a number. See *Fix* below.
  - Code that parsed the raw value itself now receives the mapped value.
- **A value named `__batch_q`** in a QueryBatch branch that sends texts now reads as it does standalone.
  - 1.0.16 raised `function row_to_json(integer) does not exist`.
  - A branch that sends no text keeps 1.0.10's envelope byte for byte, and fails on that name as before.
- **A client's type parser runs once per distinct text of a column per batched result set**, not once per row, when it returns a primitive or a plain `Date`.
  - A parser with side effects sees fewer calls.
  - A parser that returns any other value is called for every row, as before.
  - A plain `Date` is handed out as a fresh copy for every row, even when a caching parser returned one shared `Date`. Such rows no longer share it, as they don't when the query runs on its own. The values are equal.
- **The batch envelope's JSON text is not byte-identical** to 1.0.16's.
  - Types and texts travel as one array column each, texts are grouped per value, and rows are aggregated as whole records.
  - The values a client reads are the same, also for a client that parses `json` with a reviver of its own.
- **A branch may select up to 1,663 values beside an id** (1.0.16: 1,662). PostgreSQL's target list holds at most 1,664 entries.
- **Internal:** `FutureBatchMeta.reviveJsonRow`, a per-row closure, is replaced by `jsonRevivals` and `reviveJsonRows()`.

## New: a custom type can share its mapped values within a result set (`immutable: true`)

A custom type whose mapped values are never mutated — Temporal values, primitives, frozen objects — can now say so.
linkgress then calls its `fromDriver` **once per distinct driver value** of a column within one result set, and every
row with that driver value gets the **same** mapped value. Bulk reads repeat their dates and moments a lot, and a
`fromDriver` that parses them (a Temporal parse, a date library) is often the largest cost of reading a result set:
it now runs once per distinct value instead of once per row. Without the option nothing changes: `fromDriver` runs for
every value, and every row gets a value of its own.

### How to opt in

The key is the value the DRIVER hands the mapper, and only a string, a number, a bigint or a boolean is one. With
every driver's defaults, an integer column of days read into a `Temporal.PlainDate`:

```typescript
const EPOCH = Temporal.PlainDate.from('1970-01-01');

const epochDay = createCustomType<{ data: Temporal.PlainDate; driverData: number }>({
  dataType: () => 'integer',
  toDriver: value => (value == null ? null : EPOCH.until(value).days),
  fromDriver: value => (value == null ? null : EPOCH.add({ days: value })),
  immutable: true,
});
```

A `timestamp` column shares only on a client that hands its mappers the value's TEXT — a text pass-through parser
for `timestamp` (node-postgres `pg.types.setTypeParser(1114, v => v)` or a pool's `types`, postgres.js `types`,
PGlite `parsers`; see *Querying › What a batched query reads*). **Under a driver's default parsing a timestamp
arrives as a `Date`, which is never shared** (and a mapper written for the text, like this one, fails on it):

```typescript
// On a client with a text pass-through parser for timestamp (OID 1114): the text is the key
const plainDateTime = createCustomType<{ data: Temporal.PlainDateTime; driverData: string }>({
  dataType: () => 'timestamp',
  toDriver: value => (value == null ? null : value.toString().replace('T', ' ')),
  fromDriver: value => (value == null ? null : Temporal.PlainDateTime.from(value.replace(' ', 'T'))),
  immutable: true,
});
```

- `createCustomType({ …, immutable: true })` and `customType({ …, immutable: true })` (the builder form: its
  `getType()` carries it). The mapper object says so as `TypeMapper.immutable` / `CustomType.immutable`, so a
  hand-written mapper object can set it too.
- A column reads through it as before (`hasCustomMapper()`, `mapWith()` of a column); an expression through
  `.mapWith(type)`. An inline function mapper (`.mapWith(fn)`) never shares.
- The option is off by default; `immutable: false` is the same as leaving it out, and a type without it is built
  exactly as before (the same object shape).

### What is shared

- **One result set, one column.** One query execution, one `QueryBatch` branch, one collection's items across all of
  its parent rows. Each value a projection reads through the type — a column, a navigation's column, a nested
  object's value, an expression, each key of a `.returning()` (one collection returned under two keys: two memos) —
  keeps its own memo. Never across queries or statements, `QueryBatch` branches, or executions of one future or
  prepared query: a read plan that serves several result sets (a future's, a prepared query's, a grouped query's
  readers kept by its join, a mutation's RETURNING plan) makes a fresh memo for each one.
- **Every read path that applies `fromDriver`**: plain selects (the row loop), a selector returning one column,
  navigation columns and navigation rows projected whole, nested objects, collections (lists, `firstOrDefault()`,
  nested collections, nested objects in their items) under every strategy, `QueryBatch` branches (a declared
  timestamp column's text rebuilt from the batch's JSON form is the driver value), futures and `FutureQueryRunner`,
  prepared queries, grouped queries (grouping keys, `min()` / `max()`) and their joins, UNIONs, CTE columns (joined,
  as a query's root, `withAggregation()` items), `agg.arrayAgg()` elements, `JoinQueryBuilder`, a table's `toList()` /
  `first()` / `firstOrDefault()`, and every mutation's `.returning()` (a selector, whole entities, their collections).
- **Keys**: the driver value when it is a string, a number, a bigint or a boolean (`1`, `'1'`, `1n` and `true` are
  different values; `-0` is not `0` and maps on its own). NULL / undefined and a driver value of any other kind — a
  `Date`, a `Buffer`, an array, a parsed json document — go through `fromDriver` every time, as without the option. A
  driver value `fromDriver` maps to `undefined` is not kept.
- **Bounded**: at most 1,024 distinct values per column and result set. A column whose first distinct values bring no
  repeat stops sharing: after 128 of them — or, for a result set of N values (its rows; a collection's items across
  them), after N / 2, at most 1,024 — so a column whose values repeat only more than 128 rows apart (a calendar of a
  year read entity by entity) still shares once each value repeats, and an all-distinct column costs that many
  lookups, then nothing. Where the count is not known (a collection nested in another's items, an `agg.arrayAgg()`
  list) the window is 128. A column that fills the 1,024 with fewer repeats than distinct values stops too; one with
  at least as many keeps what it holds and maps the values it does not hold on their own. A result set of fewer than
  two values reads through the type itself, without a memo.
- **Errors**: a `fromDriver` that throws fails the read as it always did — the same error, from the same value — and
  nothing is kept for that value.

### What a caller sees

Rows with the same driver value now hold the **same object**. Declare the option only for values nothing mutates:
mutating a shared value changes every row that holds it, and code that tells values apart by identity (`===` between
two of them, a `Set` / `Map` keyed by them, a `WeakMap`) sees one value where it used to see several. Values that
compare by content (`Temporal.*.equals()` / `compare()`, `toString()`, JSON) are unaffected.

## Performance: QueryBatch — one type test per row, a repeated text parsed once

### What changed

#### A branch that sends texts: shorter statement, one type test per row

1.0.12's envelope for a branch with runtime-typed or int8 / numeric values tested each runtime-typed value's type up to seven times per row (`pg_typeof(v)`: three times in a CASE, three in the row's FILTER, once for the type header). It resolved each value's domain in a pg_type subquery of its own. batch-expression's statement was 2 529 characters.

The envelope now has one aggregate per text-sent value:
- **Texts:** `json_agg(concat(v)) FILTER (WHERE <its type needs its text>)`. The type test runs once per row, in its FILTER, and the value's texts come back as one array per value.
- **Types:** `min(pg_typeof(v))`, as before.
- **One column each:** the texts and the types travel as ONE array column each (`ARRAY[…] AS x`, `ARRAY[…] AS t`). A branch therefore sends as many values as the query selects on its own: 1 663 beside an id, where 1.0.16 took 1 662. A PostgreSQL target list holds at most 1 664 entries.
- **Domains:** one pg_type lookup per branch resolves the values that are domains whose text the server sends (`{ domain: base }`), by the same rule as before.
- **Rows:** aggregated as whole records (`json_agg(__batch_q.*)`): row_to_json's text, without a json datum per row.

batch-expression's statement is now 1 540 characters. The texts the server sends, the types and the rows the client reads are those of 1.0.16. A branch that sends no text keeps 1.0.10's envelope, byte for byte.

#### A text a column repeats is parsed once per result set

A batch parsed every text-sent value per row: the text the server sent, the text rebuilt from its JSON form, and a declared date / timestamp / timestamptz column revived from its JSON form. Each column of a result set now parses a distinct text once (`ParsedValueMemo`):
- a primitive (string, number, boolean, bigint, null, undefined) is reused as it is;
- a plain Date (a real Date, extensible, with the Date prototype and no property of its own), an invalid one included, is handed out as a fresh copy for every row, so no two rows share a Date. That holds even when the parser returned one Date it shares between texts (a parser that caches its results): such rows no longer share it, as they do when the query runs on its own, and the values are equal;
- any other value (a Buffer, an interval object, an array, a Date subclass, a frozen Date or one with a property of its own, a Proxy, a custom parser's object) is parsed for every row, as before;
- only a text is a memo key: a text a client's own json parser made into something else (a number, say) is parsed as it is, row by row.

The memo stops when repeats are rare (fewer than a quarter after 64 texts), holds at most 4 096 texts, and never outlives its result set. Custom fromDriver mappers are not memoized.

## Fix: a grouped select's expression read through a builder-form custom type (`customType()`) is mapped

A grouped select kept the mapper an expression reads through as `getMapper()` returned it. For the builder form of a
custom type (`customType()`, whose `getType()` holds `fromDriver`) that is the builder itself, which has no
`fromDriver`, so the field came back as the driver delivered it:

```typescript
const load = customType<Span, number>({ dataType: 'integer', toDriver: …, fromDriver: minutes => ({ … }) });

db.jobs.select(j => ({ machineId: j.machineId }))
  .groupBy(r => ({ machineId: r.machineId }))
  .select(g => ({ machineId: g.key.machineId, load: sql`count(*) * 15`.mapWith(load) }))
  .toList();   // load: '45' (the driver's text) — now { hours: 0, minutes: 45 }
```

A `min()` / `max()` of such an expression read as a number. A plain select, a CTE read and a grouped join always
unwrapped the builder; the grouped select now does too (`fromDriverMapper()` in its projection and extreme reads) —
standalone, in a `QueryBatch`, and in the metadata a CTE over the grouped query reads its columns by. A
`createCustomType()` mapper, a column's mapper and the helpers' result mappers read as before.

**Result change**: such a grouped field now comes back mapped; code that parsed the raw value itself gets the mapped
value instead.

## Not done

- **Deciding each value's type once per statement** (an InitPlan over `pg_typeof(CASE WHEN false THEN v END)`) runs once on PostgreSQL 18, but it cannot be exact:
  - CASE resolves a domain to its ultimate base type, which would change the texts sent for domains;
  - the one probe that keeps a domain exact, `ARRAY[v]`, fails to parse for a type without an array type (`void`).

  The type test therefore stays per row, once per row per value.
- **Aggregating records in a branch that sends no texts** would save about 33 µs of execution per 500 rows, but that envelope is kept exactly as in 1.0.10.

**Review.** Each part had an independent review: the batch changes, and the `immutable` option with the grouped fix. Neither found a blocking or major issue. The fixes for their minor findings are in this release:
- a branch's value limit is back to 1.0.16's;
- a `__batch_q` value reads as it does standalone;
- the memo copies only a real `Date` and keys only on texts;
- the probe window adapts to the result size;
- memos are allocated lazily, with none below two values;
- each RETURNING key gets its own memo;
- the factory registry can no longer be copied by an object spread;
- the grouped builder-form mapper is applied.

- PostgreSQL 18.3 and the in-memory engine as the server;
