# v1.0.32

Two things a `MutationBatch` caller had to work around, and the defect their matrices ran into. A leg registered
`ifFits` rides the batch's ONE statement only when that statement can carry it, and is declined — null, nothing
registered — when it cannot, so the caller writes the same input standalone; before, the caller had to copy a private
budget rule to know. `addUpdateWhereIn` takes a `where` guard, so a constant SET over a key list applies only to the
rows still in the state it was decided for; before, that took `addBulkUpdate` with a VALUES row per key repeating the
same values. And a standalone bulk mutation now keeps each chunk within its client's parameter limit — on PGlite
(32 767) `insertBulk`, `upsertBulk`, `bulkUpdate` and `mergeBulk` were refused for any chunk binding more, which is
what writing a declined leg standalone ran into. Each is tested by a generated matrix against an oracle on PostgreSQL,
PGlite and the in-memory database (995 new cases, RED on the 1.0.31 code). Statements that use neither option are
unchanged: every one of the 116 154 statements the 1.0.31 suite runs in memory (116 973 on PostgreSQL, 103 422 on
PGlite) is sent with the same SQL text by this release. Everything that behaves differently from 1.0.31 is listed
under [What a caller may notice](#what-a-caller-may-notice).

## Added: `ifFits` on every leg kind with a standalone form

```typescript
const batch = new MutationBatch();
batch.addBulkUpdate(db.routes, touchedRoutes, 'routes');
const parcels = batch.addInsertBulk(db.parcels, newParcels, 'parcels', { returning: ['id', 'label'], ifFits: true });
await batch.executeBatch();
const written = parcels != null
  ? batch.getLegRows(parcels)                                                    // in the statement
  : await db.parcels.insertBulk(newParcels).returning(p => ({ id: p.id, label: p.label })); // standalone, chunked
```

1.0.29 documented the fit check as `batch.parameterCount + rows × columns <= maxParameters()`. It was not enough: a
leg within the statement's limit could still be over its OWN budget — the rows a standalone mutation sends in one
chunk, `⌊⌊65 535 / columns⌋ · 0.6⌋` — which only a private method knew, and which threw as the leg registered.

- `addInsertBulk` (plain and row-guarded), `addUpsertBulk`, `addBulkUpdate` (in its config), `addDeleteWhereIn` (a new
  trailing `options`), `addUpdateWhereIn`, `addInsertBulkWithChildren`. The option type is exported as
  `LegFitOptions`; `InsertLegOptions`, `BulkUpdateLegConfig` and `UpdateWhereInLegOptions` extend it.
- The verdict is the rule a leg registered WITHOUT the option is held to, as a verdict instead of an error: its rows
  (a where-in leg's values; an insert-with-children leg's parents and children) within its own budget — over it, the
  leg throws as it registers — and the parameters it binds, together with every leg registered before it, within the
  most one statement binds through its client (`DatabaseClient.maxParameters()`: PostgreSQL's 65 535, PGlite's
  32 767) — over it, `executeBatch()` refuses the statement.
- It counts the leg as compiled: an SQL fragment cell binds nothing; a typed row guard and an update leg's `where`
  bind their own parameters.
- A leg that fits compiles to the statement it compiles to without the option. Empty input returns null either way;
  a duplicate identifier and an executed batch still throw. A declined leg leaves its identifier free; one declined
  for its row count is not compiled, so the standalone mutation validates that input.
- What a caller writes instead of a declined leg:

  | Leg | Standalone |
  |---|---|
  | `addInsertBulk` | `insertBulk(rows)`, `.returning(…)` for the readback — chunked |
  | `addUpsertBulk` | `upsertBulk(rows, config)` — chunked |
  | `addBulkUpdate` | `bulkUpdate(rows, config)` — chunked |
  | `addDeleteWhereIn` | `where(r => eqAny(r.col, values)).delete()` — one array parameter |
  | `addUpdateWhereIn` | `where(r => and(eqAny(r.col, values), guard(r))).update(set)` |
  | `addInsertBulkWithChildren` | `insertBulkWithChildren(…)` — ONE statement under a budget of its own, every parent with a child; split a larger input |
  | `addInsertBulk` with `rowGuard` | no standalone form: register it `ifFits` in a batch of its own, its rows split in parts until each registers |

  (A row-guarded leg's own budget is no recipe for its parts: on PGlite such a part binds more than 32 767 parameters.)
- `addDependentInsert` takes no `ifFits`: it reads its parent leg's CTE and has no standalone form. Its parameters
  count against the statement like any leg registered later, which `executeBatch()` holds to the limit.
- The leg's own budget is read from `calculateOptimalChunkSize` — the function the standalone mutations chunk by —
  instead of a copy of its formula; `executeBatch()`, the verdict and the chunkers share one statement limit
  (`clientParameterLimit`).

## Added: `where` on `MutationBatch.addUpdateWhereIn`

```typescript
const batch = new MutationBatch();
const requeued = batch.addUpdateWhereIn(db.printJobs, 'id', stalledIds, { state: 'queued', printerId: null }, 'requeue', {
  where: j => eq(j.state, 'printing'),   // not the jobs a printer finished or failed meanwhile
});
batch.addInsertBulk(db.printLog, entries, 'log');
await batch.executeBatch();
batch.getAffectedCount(requeued!);      // the jobs the guard let through
// WITH "__mb_0" AS (UPDATE "print_jobs" AS t SET "state" = $1, "printer_id" = $2 WHERE "id" IN ($3, …) AND ("t"."state" = $n) RETURNING 1), …
```

- `where(target)` is applied exactly as `addBulkUpdate`'s / `bulkUpdate`'s `where` is — one code path
  (`updateWhereCondition`, `andUpdateWhere`): a typed condition over the column row `t` (its columns render
  `"t"."<column>"` and bind through their mappers; navigations are not in scope and are refused, naming the call),
  ANDed into the leg's WHERE after its key list, its parameters numbered after the list's — and renumbered with the
  rest of the leg when other legs precede it. It takes the target row only: the leg has no VALUES row.
- A subquery correlated to `t` works — also one over the SAME table (`notExists(db.printJobs.where(x => and(eq(x.queue,
  j.queue), …)))`), which the standalone `where()` refuses: its inner and outer rows would share the table's name.
- Only the rows it lets through are updated: `getAffectedCount` counts them, and `exposeColumns` / `exposeOldColumns`
  publish only them to dependent legs. Its parameters are the leg's (`parameterCount`, `ifFits`).
- `addUpdateWhereIn` is generic over the table's entity, as `addInsertBulk` is: the guard is typed by it (an untyped
  table: any column). Its options are exported as `UpdateWhereInLegOptions<TEntity>`.
- Without `where`, the leg compiles to the 1.0.31 statement byte for byte. With it the target is aliased `t`: a raw
  `sql` SET value that names the table names it `t` (the SET's column refs render unqualified, as before).

## Fix: a standalone bulk mutation's chunks stay within the client's parameter limit

`insertBulk`, `upsertBulk`, `bulkUpdate`, `mergeBulk` — and the untyped table's (`getTable()`) `insertBulk` /
`upsertBulk` — split a large input into chunks of `⌊⌊65 535 / columns⌋ · 0.6⌋` rows: up to ~39 321 parameters, which
PGlite refuses (it takes 32 767: `PGliteClient: the statement binds 39320 parameters — PGlite takes at most 32 767`).
Writing 7 864 rows of 5 columns failed there — and so did writing standalone the input of a leg `ifFits` declined,
whenever it bound more than 32 767 (a 7 000-row insert of 5 columns; an upsert or a bulk update of 16 384 rows of 2
columns or more).

A chunk is now also no larger than the most rows of that many columns the client binds (`DatabaseClient.maxParameters()`):
on PGlite `⌊32 767 / columns⌋` rows. On PostgreSQL and in memory (65 535) nothing changes. An explicit `chunkSize`
is used as given. `insertBulk(…).toStatement()`, which compiles at most what execution sends as ONE statement, follows
the same chunk.

## What a caller may notice

1. Nothing, without the new options, on PostgreSQL and in memory: the same statements, the same errors with the same
   text.
2. `addDeleteWhereIn` takes a fifth, optional parameter (`LegFitOptions`). `addUpdateWhereIn` is generic over the
   table's entity — `addUpdateWhereIn<TEntity>(table: DbEntityTable<TEntity> | …, …, options?:
   UpdateWhereInLegOptions<TEntity>)`; existing calls compile unchanged. New exported types: `LegFitOptions`,
   `UpdateWhereInLegOptions`.
3. On a client that binds fewer parameters than a chunk would (PGlite): `insertBulk`, `upsertBulk`, `bulkUpdate`,
   `mergeBulk` and `getTable()`'s `insertBulk` / `upsertBulk` send an input of more than `⌊32 767 / columns⌋` rows
   in more statements — inputs it refused now run — and `insertBulk(…).toStatement()` refuses those rows
   (`toStatement(): 8192 rows exceed the 8191-row chunk …` for 4 columns), where it compiled a statement PGlite
   would refuse.
