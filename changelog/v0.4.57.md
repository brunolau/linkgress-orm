# Features: value-side flag operators (`flagSet` / `flagUnset`) + `insertBulkWithChildren` + SqlFragment in UPDATE/DELETE RETURNING + MutationBatch delete leg

## `insertBulkWithChildren` — N parents + their children in ONE statement

The bulk sibling of `insertWithChildren` (v0.4.56): task-DAG-style persists —
N parent rows each carrying dependent child rows (audit logs, detail rows) —
used to cost two statements. Parent identity mapping rides the SAME
serial-ascend guarantee the single-parent variant documents: the parent leg
inserts `ORDER BY` an input ordinal (serial ids ascend in input order) and a
`row_number() OVER (ORDER BY pk)` CTE recovers each parent's input index for
the child join.

```ts
const { parents, children } = await db.orderTasks.insertBulkWithChildren({
  rows: tasks,
  children: {
    table: db.orderTaskLogs,
    foreignKey: 'orderTaskId',
    rows: tasks.map((t, ix) => ({ parentIndex: ix, row: buildCreatedLog(t) })),
  },
  returning: {
    parents: t => ({ id: t.id, type: t.type, payload: t.payload /* … */ }),
    children: l => ({ id: l.id }),
  },
});
```

Single-statement atomicity (a failing leg rolls back both inserts); parents
return in input order, children in child-input order. v1 restrictions
(validated up front): flat returning selectors on both sides, single-column
serial primary keys, no `unlessExists`, child rows must not carry the
foreign-key property, and every parent must be referenced by at least one
child (parents return through the child join — use `insertBulk` for childless
rows). Tests: `tests/queries/insert-bulk-with-children.test.ts`.

# Feature: value-side flag operators — `flagSet` / `flagUnset` for UPDATE assignments

Flag columns could be *tested* first-class (`flagHas` family) but not *flipped*:
setting a bit meant either a read-modify-write (SELECT flags → OR in JS →
UPDATE — two roundtrips and a lost-update window) or a freehand `sql` fragment.
Both showed up on hot paths (a payment-webhook completion marker cost 2
statements where 1 suffices).

```ts
db.orders.where(o => eq(o.id, id)).update(o => ({
  workflowFlags: flagSet(o.workflowFlags, OrderWorkflowFlag.COMPLETED),
}));
db.users.where(u => eq(u.id, id)).update(u => ({
  state: flagUnset(u.state, UserStateFlags.Banned),
}));
```

emits

```sql
UPDATE "order" SET "workflow_flags" = ("workflow_flags" | $1::smallint) WHERE ...
UPDATE "user"  SET "state"          = ("state" & ~($1::integer))        WHERE ...
```

One atomic statement, no read, no lost-update window; idempotency is bit
algebra (`x | m | m = x | m`, `x & ~m & ~m = x & ~m`).

## Mask casts

`flagSet` follows the v0.4.54 width rules exactly (`flagMaskCast`): smallint /
bigint columns get an explicit `::smallint` / `::bigint` mask cast, int4 and
width-less refs stay bare — the deterministic-expression-tree guarantee carries
over to the value side.

`flagUnset` differs in ONE way: its mask is **always** cast, falling back to
`::integer` when the ref carries no width type. Unlike `col & $1` (where the
column operand fixes the parameter's type), `~($1)` presents the bare parameter
to the operator alone and Postgres rejects it as ambiguous
(`operator is not unique: ~ unknown`). The int4 fallback promotes cleanly
against any integer column.

## Tests

`tests/queries/flag-operators.test.ts` gains a value-side block: set/clear
preserve sibling bits, idempotency, absent-bit clear is a no-op, smallint
round-trips through both operators, and fragment-level pins for the
`::smallint` / `::bigint` / `::integer`-fallback cast emission.

# Feature: SqlFragment fields in UPDATE/DELETE `.returning(selector)`

The plain returning-clause builder recognised only entity field refs and
**silently dropped** any `sql\`…\`` fragment from the selector (a
fragment-only selector even emitted an empty `RETURNING` list — a syntax
error). Fragments now render under their selector key, with parameters
appended after the SET and WHERE parameters (RETURNING is last in statement
text, so positional order stays correct) and `mapWith` mappers applied to the
returned value.

Headline use case — PostgreSQL 18's `old.` / `new.` RETURNING qualifiers: a
status-transition UPDATE can report the pre-update value without a separate
pre-read, collapsing read-then-write idioms into one atomic statement:

```ts
const [row] = await db.orderTasks
  .where(t => eq(t.id, taskId))
  .update({ status: FINISHED_SUCCESS })
  .returning(t => ({ id: t.id, orderId: t.orderId, oldStatus: sql<number>`old."status"` }));
// row.oldStatus === the status BEFORE this update
```

v1 restriction: fragments in returning selectors must not embed entity
FieldRefs (`${p.col}`) — navigation detection skips fragments wholesale, so
reference columns as raw quoted SQL (`old."age"`); parameters via `${}` work
normally. Tests: `tests/queries/update-delete-returning-sqlfragment.test.ts`.

# Feature: MutationBatch DELETE leg — `addDeleteWhereIn`

`MutationBatch` legs were insert/update-only; post-mutation cleanup DELETEs
(child rows by FK + parent rows by PK) still cost one statement each.
`addDeleteWhereIn(table, field, values, id)` registers
`DELETE FROM t WHERE "col" IN ($1, …)` as a CTE leg — values run through the
column's toDriver mapper, empty arrays register nothing and return null, and
`getAffectedCount` reports rows deleted.

```ts
const batch = new MutationBatch();
const attrs = batch.addDeleteWhereIn(db.cartItemAttributes, 'cartItemId', itemIds, 'attrs');
const items = batch.addDeleteWhereIn(db.cartItems, 'id', itemIds, 'items');
await batch.executeBatch();               // ONE statement
batch.getAffectedCount(items!);           // rows the parent leg deleted
```

Parent + child rows CAN be deleted by two legs of one batch when the child's
foreign key is **NO ACTION** (PostgreSQL's default): NO ACTION is checked at
END of statement, when both legs' deletes are already visible to the
constraint. A **RESTRICT** foreign key (checked per-row) would still reject
the parent leg — keep such pairs in separate statements. Pinned (both
directions) in `tests/queries/mutation-batch-delete-leg.test.ts`.

# Feature: MutationBatch fused legs — `addUpdateWhereIn`, `addUpsertBulk`, `addDependentInsert`

Three leg types that let an entire mutation tail (status flip + conditional
audit log + accumulator upsert + cleanup deletes) ride ONE statement:

- **`addUpdateWhereIn(table, field, values, set, id, opts)`** —
  `UPDATE .. WHERE "col" IN (…)` with the fluent `update()` SET semantics
  (mappers, SqlFragment values, lambda form). `opts.exposeColumns` /
  `opts.exposeOldColumns` publish columns on the leg's CTE for dependent
  legs — old-columns via PostgreSQL 18's `old.` RETURNING qualifier, aliased
  `old__<prop>`.
- **`addUpsertBulk(table, rows, {primaryKey, updateColumns}, id, {returning})`** —
  `INSERT .. ON CONFLICT DO UPDATE` (EXCLUDED semantics), SqlFragment cells
  supported (statement-computed accumulator folds). `returning` (prop names)
  exposes the upserted rows to the new **`getLegRows(id)`** readback —
  raw JSON values via `json_agg`, suited to scalar accumulator reads.
- **`addDependentInsert(table, row, {onLeg, whereColumn, whereNotEquals}, id)`** —
  a single row inserted iff the PARENT leg's exposed column differs from the
  sentinel: `INSERT .. SELECT $cells FROM "__mb_parent" WHERE "old__status" <> $x`.
  The conditional-audit-log shape — an idempotent replay (old value already
  final) writes no log. Cells use the insertWithChildren `$n::type` cast
  technique and column mappers.

```ts
const batch = new MutationBatch();
const compl = batch.addUpdateWhereIn(db.orderTasks, 'id', [taskId],
  { status: FINISHED_SUCCESS, finishedAt: sql`CASE WHEN "status" = ${4} THEN "finished_at" ELSE ${now}::timestamp END` },
  'compl', { exposeOldColumns: ['status'] });
batch.addDependentInsert(db.orderTaskLogs, logRow,
  { onLeg: compl!, whereColumn: 'old__status', whereNotEquals: FINISHED_SUCCESS }, 'log');
const spend = batch.addUpsertBulk(db.userEshopSpends, [foldRow],
  { primaryKey: 'userEshopId', updateColumns: ['cashbackSpend'] }, 'spend', { returning: ['cashbackSpend'] });
await batch.executeBatch();          // ONE statement
batch.getLegRows(spend!);            // [{ cashbackSpend: … }]
```

The shared `INSERT .. ON CONFLICT` assembly was extracted into
`buildUpsertStatementCore` (used by both `upsertBulk` execution and the leg
compile — no drift). Tests: `tests/queries/mutation-batch-fused-legs.test.ts`.
