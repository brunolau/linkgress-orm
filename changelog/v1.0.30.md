# v1.0.30

The query roots of a context on its TABLES — `<table>.selectFromCte(cte)`, `<table>.selectFromSet(set)` — with
`<table>.isInTransaction()` and `<table>.getClient()`: code that is handed a table, the root's or a transaction's,
builds data-modifying CTEs on it AND executes and reads them back in ONE statement on that table's own connection —
inside the caller's transaction. Every public entry point of a context was audited for what a table-holder could not
reach (below). The defects the matrices ran into are fixed in the same release: `count()` of a union whose legs
declare data-modifying CTEs (0A000), and the in-memory engine's foreign keys, which did not follow PostgreSQL's
locking rules — a check waited for a parent another transaction had not committed, wrote over one another
transaction was deleting, and a deferred one failed its COMMIT with XX000 when it had to wait. Tested by generated
matrices (2 new files and an extended one, 1 514 cases) on PostgreSQL, PGlite and in memory against an oracle: the
same query rooted on the context, PostgreSQL's own outcome. Queries that do not use the new methods emit the SQL they emitted before: of the 95 880
statements the 1.0.29 suite runs in memory (96 699 on PostgreSQL), none changed.

## Added: `<table>.selectFromCte()`, `<table>.selectFromSet()`, `<table>.isInTransaction()`, `<table>.getClient()`

`db.selectFromCte(cte)` / `db.selectFromSet(set)` run on the context they are called on. A helper that writes
versioned rows is handed a TABLE — `db.leases` as often as a caller's `trx.leases` — and builds the close leg and the
open leg on it (`table.where(…).update(…).toStatement(…)`, `table.insertFrom(…, { where: () => afterMutation(closed.cte) })`),
but the typed readback of the legs needed the context. Rooted on the root context, the WHOLE statement ran on another
connection, outside the caller's transaction: on PostgreSQL its foreign-key check could not see the parent row the
transaction had just inserted (23503); on a pool of one connection it waited for a second one forever; on PGlite (one
session) it was refused. The only routes were internals (`new CteRootQueryBuilder(cte, table._getClient(), …)`).

A table now offers the same roots on its own context — the same client, the same executor (a table derived with
`.withTimeout()`, `.withQueryOptions()`, `.withPreparedStatements()` or `.expectedExecutionTime()` runs them through
its derived executor), the same transaction — with the context's signatures, typings and SQL:

```typescript
const foldLeases = async (leases: DbEntityTable<Lease>, units: number[], desired: DesiredLease[], now: Date) => {
  const builder = new DbCteBuilder(leases.getClient());
  const closed = builder.withMutation('closed', leases
    .where(l => and(eqAny(l.unitId, units), eq(l.isCurrent, true), notExists(/* desired (unit, tenant) */)))
    .update({ validTo: now, isCurrent: false })
    .toStatement(l => ({ id: l.id, unitId: l.unitId })));
  const opened = builder.withMutation('opened', leases.insertFrom(
    fromRows(leases, desired, { columns: ['unitId', 'tenantId'], alias: 'd' }).where(/* not current */).asSubquery('table'),
    src => ({ unitId: src.unitId, tenantId: src.tenantId, validFrom: now, isCurrent: true }),
    { where: () => afterMutation(closed.cte) },
  ).toStatement(l => ({ id: l.id, unitId: l.unitId })));

  const rows = await leases.selectFromCte(opened.cte).select(r => ({ leg: 'opened', id: r.id, unitId: r.unitId }))
    .unionAll(leases.selectFromCte(closed.cte).select(r => ({ leg: 'closed', id: r.id, unitId: r.unitId })))
    .toList();

  // outside a caller's transaction the statement commits on its own: running it again after 40P01 / 40001 is the
  // helper's call; inside one, the failure aborted the CALLER's transaction
  return { rows, ownsUnitOfWork: !leases.isInTransaction() };
};
```

- `isInTransaction()` — `true` on the tables of the context `db.transaction()` hands its callback (also once that
  transaction has ended: their statements are refused with `TransactionEndedError`), `false` on the root's. The
  library has no nested transactions (`transaction()` on a transaction's context throws); a SAVEPOINT stays inside
  the transaction.
- `getClient()` — the client of the table's context (the transaction's on `trx.<table>`), for what takes a client:
  `new DbCteBuilder(client)` renders the driver's array capability into the CTE bodies it builds.
- A view (`DbViewTable`) has the four methods too.

## The audit: what a context offers, and whether a table does

| The context's entry point | On a table | Why |
|---|---|---|
| `selectFromCte(cte, alias?)` | added | the root that executes and reads back CTEs built on the table — it must run where the table runs |
| `selectFromSet(set, alias?)` | added | a set query (`unnest`, `unnestZip`, `unnestRows`, `jsonbArrayElements`, `jsonbEachText`), a union's first leg, a set correlated to the table: it reads the transaction's rows only on its connection |
| `getClient()` | added | `new DbCteBuilder(client)` and everything else that takes a client; the transaction's on a transaction's table |
| — | added: `isInTransaction()` | whether the table's context is a transaction's — the question a helper decides its retry policy by |
| `query(sql \| fragment)` | not added | raw SQL is not a query over the table, and `table.query()` would read as one; on the table's connection it is `getClient().query(text, params)` |
| `advisoryXactLock()`, `tryAdvisoryXactLock()`, `advisoryXactLockAll()` | not added | a lock on a key that is not a row belongs to the unit of work — taken where the transaction is opened; not a query root |
| `transaction(fn)` | not added | a table runs in the transaction its context is in; opening one is the context's (nested transactions do not exist) |
| `getTable(name)` | not added | a table is one table; the context's other tables are the context's |
| `getSchemaManager()`, `dispose()` | not added | DDL and the context's lifecycle, not queries |
| `runtimeSequence(config)` | not added | bound to the ROOT client on purpose, outside any transaction |
| `new DbCteBuilder(client?)`, `fromSet()`, `fromRows()`, `unnest*()`, `jsonb*()`, `QueryBatch`, `MutationBatch`, `FutureQueryRunner` | reachable before | context-free, or they run on the client of their legs; the CTE builder's client through `getClient()` |
| the schema-first `DataContext`'s `TableAccessor` | unchanged | internal (not exported); `DbEntityTable` is the public table |

## Fix: `count()` of a union whose legs declare data-modifying CTEs

`db.selectFromCte(opened.cte).select(…).unionAll(db.selectFromCte(closed.cte).select(…)).count()` wrapped the whole
union — its `WITH` included — in its subquery: `SELECT COUNT(*) … FROM (WITH "closed" AS (UPDATE …) …) AS union_count`,
which PostgreSQL refuses (0A000 "WITH clause containing a data-modifying statement must be at the top level"), on every
engine. Such a `WITH` now leads the statement and the count reads the union below it:
`WITH "closed" AS (…), "opened" AS (…) SELECT COUNT(*) as count FROM ((…) UNION ALL (…)) as union_count`. A union of
plain CTEs counts as before, byte for byte.

## Fix (in-memory database): foreign keys follow PostgreSQL's locking rules

PostgreSQL checks a reference with `SELECT 1 FROM ONLY <referenced> WHERE <key> FOR KEY SHARE` on a snapshot of its
own, and the lock it takes protects the reference until the transaction ends. The in-memory engine read the
referenced versions "dirty" and took no lock:

- a parent another transaction had inserted and not committed made the statement WAIT for that transaction, where
  PostgreSQL does not see it and raises 23503 at once — the consumer's statement above, rooted on the root context
  inside a transaction that had just inserted the parent, hung until it was cancelled;
- a parent another transaction was deleting, re-keying or holding `FOR UPDATE` did not make it wait: the child was
  written at once, and stayed an orphan once the delete committed;
- `FOR UPDATE` of a parent whose child another transaction had just written did not wait for that transaction;
- a `DEFERRABLE` check that had to wait at COMMIT failed the COMMIT with XX000 (an engine signal escaping), and one
  that met a pending delete passed.

Now a version another transaction has not committed is not there (23503, no wait). A visible one is held FOR KEY
SHARE until the transaction ends — its version and every newer one; a running delete, key change or `FOR UPDATE` of
another transaction makes the check wait, then run again on a new snapshot: the parent gone (a committed delete or
key change: 23503) or there (a rollback, a released lock). A non-key update and the weaker row locks do not
conflict, and a non-key update carries the locks on to the row's new version (a delete that follows it waits). An
UPDATE that changes a key column — of a unique index without predicate or expression — locks the row FOR UPDATE
(any other FOR NO KEY UPDATE), so it waits for the checks that hold the row. The referenced side's check (a delete or
key change looking for children) no longer waits for a child another transaction has not committed: that
transaction's check holds the parent, so the delete already waited for it — or, deferred, it finds the parent gone at
its COMMIT. An explicit COMMIT runs its deferred checks first and waits as a statement does (a deadlock or a timeout
aborts the transaction, as a violation does). Under REPEATABLE READ a parent deleted or re-keyed by a transaction
that committed after the writer's snapshot is refused as 23503 — PostgreSQL raises 40001 there; the engine models no
serialization failure.

## What a caller may notice

- `DbEntityTable` and `DbViewTable` carry four new members; code that types an object of its own as either (rather
  than receiving one from a context) must add them.
- A context-free set query run on its own points to `<table>.selectFromSet(...)` beside `db.selectFromSet(...)`.
- In memory: a write referencing a parent another transaction has not committed fails with 23503 at once instead of
  waiting; one referencing a parent another transaction deletes or re-keys waits for it; a delete, key change or
  `FOR UPDATE` of a parent whose child another open transaction wrote waits for that transaction.
