# v1.0.11

This release closes four gaps. The schema manager repairs an INVALID index — what a failed `CREATE INDEX
CONCURRENTLY` leaves behind — instead of counting it as present (`repair_index`, `IndexRepairError`). A model
sequence reached through a transaction (`tx.<sequence>`) draws inside that transaction. A `where()` / `orderBy()` /
`limit()` / `offset()` written before `selectMany()`, or on the collection its selector returns, applies with LINQ's
meaning under every collection strategy, and a correlated `count()` / `exists()` applies its own `limit()` /
`offset()`. And a grouped query joins a `QueryBatch` (`future()`, `futureFirstOrDefault()`, `futureCount()`), while a
batched value now reads as the same query reads on its own through the same client — under its driver's
configuration, parsers of the application's own included (`DatabaseClient.parseTypedText()`) — apart from the
documented limits of the batch's JSON transport.

It also fixes the defects found on the way — among them a transaction's objects and a released pooled connection that
kept running statements on a connection another caller may hold by then (now refused with `TransactionEndedError` /
`ConnectionReleasedError`), a `FutureQueryRunner` batch that ran a transaction's future outside its transaction,
sequence reads and `resync()` that produced a different number beyond 2^53 (exact bigint variants are new), columns of
a manually joined table read through another table's column config — in standalone queries too —, `selectMany()`
shapes and nested correlated `count()` / `exists()` subqueries that returned wrong rows without an error, and
in-memory engine gaps around INVALID indexes, `pg_index` and `lastval()`.

## Upgrade notes

**Upgrading from 1.0.10: read this list before anything else.** The LOUD items make code that used to run on the wrong
connection fail at the statement; the others change values, SQL text or deploy behaviour, most of them without an
error. Each item names the section with the details; every section ends with its **Behaviour changes**, followed by
its **Known limitations** where it has any.

### Refused now

- **LOUD — `TransactionEndedError`: a transaction's objects refuse every statement once the `transaction()` callback
  has settled** (committed, rolled back or failed). Tables, model sequences, query builders, futures, `QueryBatch` /
  `MutationBatch` legs, prepared queries, `tx.getSchemaManager()`, `tx.getClient()` and the query function of a
  client's own `transaction(query => …)` used to run such a statement on the pooled connection the transaction had
  released — outside any transaction, or INSIDE ANOTHER TRANSACTION that held it by then — so code that kept a `tx`
  past its callback now fails there: keep results, not transaction-scoped objects (the deprecated
  `PostgresClient.begin()` is not guarded). → *Transactions & connections*
- **LOUD — `ConnectionReleasedError`: a `connect()` connection refuses every statement after its `release()`, and a
  second `release()` never reaches the driver.** Such a statement used to run on a session the pool may already have
  handed to another caller (with a pool of one, inside that caller's open transaction), and a stale second `release()`
  freed another caller's lease; now `PgClient`'s second `release()` throws node-postgres's own error and the other
  drivers' do nothing. → *Transactions & connections*
- **LOUD — `FutureQueryRunner.runAsync()` refuses futures of different connection contexts**, as `QueryBatch` does,
  before any statement runs; a future built with its own per-query options (`.withTimeout()`,
  `.expectedExecutionTime()`, `.withPreparedStatements()`, `withQueryOptions(…)`) counts as another context. On
  postgres.js, Bun and PGlite a batch without parameters used to run every future on the FIRST future's client — a
  transaction's future outside its transaction. → *Transactions & connections*
- **`DbSequence` number reads throw a `RangeError` outside ±(2^53 − 1).** `nextValue()`, `currentValue()` and
  `nextValueCreatingIfMissing()` returned a rounded number, and now throw even for a value above 2^53 a double holds
  exactly (1e16) — use `nextValueBigInt()` / `currentValueBigInt()` / `nextValueCreatingIfMissingBigInt()`;
  `resync(number)` refuses a number that is no safe integer — 2^53 itself included — with a `RangeError` before any
  SQL: pass a bigint. → *Sequences*
- **`selectMany()` shapes whose meaning is ambiguous throw when the query is built**, where they returned wrong rows or
  failed: `selectDistinct()` or a terminal before `selectMany()`; a selector returning anything but a collection of the
  item it is handed; a limit over a table without a primary key or through a navigation of a hop; a ranking limit /
  offset that is negative or no integer; a collection of a hop's row aggregated in the projection of the collection a
  selector returns; in that projection, a collection of any row but the flattened items (the OUTER row's), and, in the
  projection or the filter of a collection nested there, one of any row but that collection's own items.
  → *Collections / selectMany*

### Results and semantics that change

- **STANDALONE reads: a manually joined table's columns read through their OWN column config** (`leftJoin` /
  `innerJoin` of a table) — their mapper and SQL type, as the navigation form reads them — not through the queried
  table's column of the same name. A custom-mapped joined column now maps (`{ hours: 1, minutes: 30 }` where it read
  `90`), one named like a mapped column of the queried table no longer does (`600` where it read `{ hours: 10,
  minutes: 0 }`), a text of digits stays text, and a condition on a mapped joined column binds through its mapper —
  code that compensated now converts twice. → *QueryBatch / grouped queries / joined reads*
- **`QueryBatch` values read as the same query reads on its own through the same client**, under its driver's
  configuration — the driver's defaults or the application's own parsers. A value JSON cannot carry as the driver
  delivers it (a date / time / timestamp, an interval, an int8 / numeric / money, a bytea, a point / circle, their
  arrays, a value of a user-defined type or of a type the client parses itself) travels as its text and is parsed by
  the client: a `dateTrunc()` arrives as a `Date`, a `castAsBigInt()` or a `bigserial` / `numeric(p, s)` value as the
  driver's exact text, a composite value as its text; a `mapWith()` mapper, and that of a custom type of
  `timestamp(3)` / `timestamp with time zone` / `numeric(12,2)`, gets the client's value; a UNION column whose legs
  declare different types is typed as PostgreSQL resolves it; a client with parsers of its own gets their value, for a
  declared `bigint` / `numeric` column too (1.0.10: the text). A `json` value or a collection in a query with a declared
  int8 / numeric column keeps its keys in their order, and a `\u0000` or a lone surrogate no longer fails the batch. A
  plain select's declared `timestamp` / `timestamptz` / `date` / `bytea` column still reads as in 1.0.10 (a known
  limitation). A custom `DatabaseClient` parses by node-postgres's default rules unless it overrides the new
  `parseTypedText()` / `customParsedTypeOids()`. → *QueryBatch / grouped queries / joined reads*
- **`selectMany()` results**: shapes that returned wrong rows without an error now return the rows they describe —
  limits and orders before `selectMany()`; filters, orders, limits and projections on the collection a selector
  returns; `select()` before `selectMany()`; a selector through a navigation; grandchildren of a self-referencing table
  under LATERAL; constant key parts; a correlated `count()` / `exists()`'s own `limit()` / `offset()`; nested
  correlated subqueries through navigations named like the table they point at (such a join took the name the OUTER
  row of that table is read by). Under the temp-table strategy a `min()` / `max()` of 0 reads 0 (it read `null`).
  `selectDistinct()` after flattening an ordered collection lists each value once, in no particular order.
  → *Collections / selectMany*
- **A model sequence reached through a transaction (`tx.<sequence>`) draws inside it**: a READ ONLY transaction refuses
  the draw (25006) and a failed draw aborts the transaction; `nextValueCreatingIfMissing()` still creates a missing
  sequence, on the root client (PGlite refuses that CREATE, as it refused every such draw before). `tx.<sequence>` is
  no longer the same object as `db.<sequence>`. → *Sequences*
- `tx.getSchemaManager()` of a model with `model.useSearchNormalize()` now creates the `search_normalize` support like
  the root's. → *Transactions & connections*

### Schema manager and migrations

- **`MigrationOperation` gains the `repair_index` variant; `IndexRepairError` and `IndexRepairFailure` are new
  exports.** A `switch` over `MigrationOperation['type']` with a `never` exhaustiveness check stops compiling until it
  handles `'repair_index'`; one without such a check silently skips it. → *Schema manager: INVALID indexes*
- **`migrate()` now repairs every INVALID model index it used to ignore.** On the blocking path (no `.concurrent()`, no
  `concurrentIndexes`) that is a `CREATE INDEX` that blocks writes for the build plus a brief ACCESS EXCLUSIVE swap, for
  every leftover INVALID model index, on the first deploy after upgrading; a repair that fails ends `migrate()` — and
  every later one, until the cause is fixed — with an `IndexRepairError` after everything else has run. It leaves
  alone, with a warning at every `analyze()` / `migrate()`, an INVALID index with an index build running on its table,
  a partitioned index, one a constraint requires, and a unique one still ready (`indisready`); `ensureCreated()` is
  unchanged. Before deploying, list the candidates:
  `SELECT indexrelid::regclass, indisready FROM pg_index WHERE NOT indisvalid`. → *Schema manager: INVALID indexes*
- A scaffolded repair (`MigrationScaffold`) drops and rebuilds inside the migration file's transaction: its ACCESS
  EXCLUSIVE lock — reads and writes wait — is held through the whole build, until the file commits. A model index
  PostgreSQL cannot build now fails before anything is dropped, for `recreate_index` too. → *Schema manager: INVALID
  indexes*
- The schema manager's catalog reads return real `string[]` for index `column_names` and foreign-key `column_names` /
  `referenced_column_names` (they were the array literal text on pg); internal reads only. → *Schema manager: INVALID
  indexes*

### SQL text

- **Every `selectMany()` renders new SQL** — the same results, where the old SQL ran: a hop renders under
  `<relation>__bridge<n>` instead of its table's name, and a navigation of its item under
  `<hop alias>__<relation path>`; a limit on a hop or on the collection a selector returns renders as a ranking
  (`"<alias>"."id" IN (SELECT … LIMIT n OFFSET m)` where the query is correlated, `ROW_NUMBER() OVER (PARTITION BY …)`
  in the CTE / temp-table aggregations); an `orderBy()` before `selectMany()` appends ORDER BY keys; an alias an
  enclosing scope already uses takes a suffix (`shelves__bridge1_2`, `children__count_2`). A limited or nested
  correlated `count()` / `exists()` renders differently too: one nested in another over the OUTER row's table renders
  under an alias of its own (`"shelves__exists"`), and, deeper than one level, a join whose plain name the subqueries
  around it read a row by takes a suffix or its path alias (`"nt_shelf_2"`, `"nt_book__nt_shelf"`) — also where 1.0.10
  answered right, with the same rows. Tests that pin that SQL need updating. → *Collections / selectMany*
- **`QueryBatch`**: a query with no value to send as its text sends 1.0.10's text, byte for byte. Every other query
  takes ONE envelope — `json_build_object('t', …, 'r', …, 'x', …)` over its query fenced by `OFFSET 0` — also one with
  a declared int8 / numeric column, which 1.0.10 sent as `to_jsonb(__batch_q) || jsonb_build_object(…)` (its int8 /
  numeric values unchanged); a selector returning one text-sent expression names its column
  (`__batch_q0("__batch_value")`). → *QueryBatch / grouped queries / joined reads*
- **A manually joined column** renders the helpers that type their SQL by a column's declared type as a column of the
  queried table does — the `eqAny()` / `neAll()` array cast, the `flag*` mask casts, `agg.arrayAgg()` of an int8 /
  numeric column in a JSON projection, `arrayContains()` and `unnest()` of a joined array column; a plain comparison,
  an ORDER BY and its projection render byte for byte as before. → *QueryBatch / grouped queries / joined reads*

### In-memory engine

- **Stricter** — statements that used to succeed now fail with PostgreSQL's error: an index build whose expression or
  predicate raises for an existing row (`22012` and the like); `CREATE` / `DROP INDEX CONCURRENTLY` in a
  multi-statement query string or from a function / `DO` block (`25001`); `CREATE INDEX CONCURRENTLY` on a partitioned
  table, and `DROP INDEX CONCURRENTLY` with several names, `CASCADE` or on a partitioned index (`0A000`); a later
  `CREATE INDEX` without `IF NOT EXISTS` over the INVALID index a failed `CREATE INDEX CONCURRENTLY` now leaves
  (`42P07`); dropping an index attached to a partitioned index on its own (`2BP01`). `CREATE INDEX … ON ONLY` a
  partitioned table with partitions creates an INVALID index. → *In-memory engine*
- **More permissive** — `UPDATE pg_index` of `indisvalid` / `indisready` is executed (it was `42501`), `ALTER INDEX …
  ATTACH PARTITION` is accepted, and a unique index built on an INHERITS parent no longer checks its child's rows.
  → *In-memory engine*
- `lastval()` / `currval()` follow PostgreSQL — `lastval()` fails with 55000 once its sequence is gone and is never set
  by `setval()`; `DISCARD SEQUENCES` / `DISCARD ALL` reset both. → *In-memory engine*

### Test runner

- A PostgreSQL run's files run on private worker databases — a one-file run too; only an explicit `--pg-jobs 1` runs
  them on `DB_NAME`. A PGlite run's server-bound files get private worker databases too, and fall back to `DB_NAME`
  (the test schema created there and dropped at the end, as before) when they cannot be created. → *Test runner*

## Transactions & connections

### Fixed

#### A transaction's objects kept running statements after the transaction had ended

`db.transaction(fn)` builds the transaction's context on a `TransactionalClient` that routes every statement through
the query function of the driver's `transaction()` — a closure over the connection the driver checked out for the
transaction. Nothing stopped that closure after the transaction: an object of the context kept past `fn` (the context
itself returned from `fn`, a query builder or prepared query built inside and awaited later, a model sequence, a batch
leg, the schema manager) sent its statement through it anyway. On `pg`, the closure calls the checked-out `PoolClient`
directly, which by then is back in the pool: with a pool of one, a kept `tx.<table>.insert(…)` issued while a second
transaction held the connection ran INSIDE that second transaction (its `count()` saw the stray row; the second
transaction then committed it or rolled it back as its own). postgres.js and Bun ran it on their reserved connection
the same way; PGlite threw its own generic "Transaction is closed".

A transaction's objects are now refused once it has ended:

- `TransactionalClient.query()` refuses once `DataContext.transaction()` has marked it ended — in a `finally` around
  `fn`, before COMMIT / ROLLBACK. Every path of the context funnels through it (table reads and writes, sequences, raw
  `query()`, `getClient().query()`, advisory locks, `selectFromSet` / CTE roots, futures, `QueryBatch`,
  `MutationBatch`, prepared queries, `getSchemaManager()`), so none reaches the database: the refused statement is
  never sent. A `FutureQueryRunner` batch now keeps to one context (below), so its futures funnel through their own
  context's client too.
- The query function of every client's own `transaction()` — `PgClient`, `PostgresClient`, `BunClient`,
  `PGliteClient` — refuses the same way once the callback has settled, for code that uses the drivers directly.
- `TransactionEndedError` (exported beside `QueryTimeoutError`): `name` `'TransactionEndedError'`, message `this
  transaction has already ended — objects obtained from its context (tables, sequences, queries, batches, its schema
  manager, its client) are only valid inside transaction(); use the root context or a new transaction instead. The
  statement was not run.`, `sql` = the refused SQL text (parameters are not included).
- `transaction()` on an ENDED transaction's context throws that `TransactionEndedError` (`sql` `'BEGIN'`, nothing
  sent) — it used to say "Nested transactions are not supported", which hid the real cause. On a LIVE transaction's
  context it still throws "Nested transactions are not supported".
- Nothing changes inside the transaction — statements issued in parallel included — nor on the root context, nor for
  a statement that was already sent when the callback settled. `isInTransaction()` of the kept client stays `true`.
- NOT guarded: the deprecated `PostgresClient.begin(callback)`. It hands the callback postgres.js's own transaction
  handle (a callable tagged template with its own helpers), and a statement sent through that handle after the
  callback has settled still runs on the connection the transaction handed back — inside another caller's
  transaction if one holds that connection by then (probed on a pool of one). Wrapping that handle is not a small
  change; its JSDoc now says so. Use `transaction()`.

A statement sent through a transaction-scoped object after its transaction throws `TransactionEndedError`
immediately, instead of succeeding on a connection it does not own. The library's own suite had no such use: it
passes unchanged on PostgreSQL and in memory.

#### A released pooled connection kept running statements on the session it had handed back

A `PooledConnection` — the lease `client.connect()` returns — kept running statements after its `release()`, on the
session it had handed back: `PgClient`'s wrapper called the pg `PoolClient` that was back in the pool,
`PostgresClient`'s and `BunClient`'s the reserved connection that was, and `PGliteClient`'s lease ran on the one
session outside the session lock. With a pool of one, a released connection's INSERT issued while another caller held
the connection in a transaction landed INSIDE that transaction (pg, postgres.js, Bun in both modes, and the in-memory
engine through pg; PGlite ran it once the transaction had ended — outside any lease), and a released connection's
`SET` changed the session of the next lease.

Every `PooledConnection` now refuses a statement issued after `release()` with a `ConnectionReleasedError` — `name`
`'ConnectionReleasedError'`, message `this connection has already been released — a statement on it would run on a
pooled connection that may belong to another caller by now; acquire a new one with connect(). The statement was not
run.`, `sql` = the refused text (parameters are not included) — so it never reaches the database; a `BEGIN` on a
released connection (there is no transaction API on a `PooledConnection`) is refused like any statement. Unchanged: a
statement issued before `release()` completes (also when still running at `release()`), a lease in use, a fresh
`connect()`, and the client's own `query()` / `transaction()`.

#### A stale second `release()` freed another caller's lease

A second `release()` used to be passed to the driver: pg-pool gives every checkout its own `client.release`, so on a
client the pool had handed to another caller a stale second `release()` released THAT caller's checkout, without an
error; postgres.js's stale reserved `release()` returned the connection to the pool under its new holder. With a pool
of one — A connects and releases, B connects and opens a transaction, A releases again — the next `connect()` got the
session at once and saw B's uncommitted rows, its own writes were rolled back with B's transaction, and on pg B's
later `release()` freed that caller's lease in turn. Bun.SQL and PGlite were not affected.

A second `release()` now never reaches the driver's pool: `PgClient`'s throws node-postgres's own error (`Release
called on client which has already been released to the pool.`) before pg-pool sees it; `PostgresClient`'s and
`BunClient`'s do nothing (`PGliteClient`'s already did nothing). The next `connect()` now waits for B.

#### `FutureQueryRunner.runAsync()` ran futures of different connection contexts on the first future's client

`runAsync(futures)` took the client of `futures[0]` and, where the driver runs a batch as one multi-statement round
trip (postgres.js, Bun, PGlite — a batch without parameters), sent every future's SQL through it: inside an open
transaction, `runAsync([db.x.future(), tx.x.future()])` ran the transaction's future OUTSIDE the transaction (it did
not see the transaction's uncommitted rows), and `runAsync([db.x.future(), kept.x.future()])` ran an ENDED
transaction's future on the root instead of refusing it. (node-postgres, and every batch with parameters, ran each
future on its own client.) `runAsync()` now applies `QueryBatch`'s rule before any statement runs — every future must
have the first one's client AND executor — and throws otherwise, whatever the driver:

```
FutureQueryRunner: future #<i> uses a different database client or transaction than the rest of the batch — all futures must share one connection context
```

Futures of one context run as before; futures of one ENDED transaction are refused with its `TransactionEndedError`.

A future built with per-query options (`.withTimeout()`, `.expectedExecutionTime()`, `.withPreparedStatements()`,
`withQueryOptions(…)`) carries an executor of its own — each such call derives a new one — and is refused next to
plain futures or those of another such call, exactly as a `QueryBatch` leg is. Futures built from ONE such builder or
accessor (`const timed = db.x.withTimeout(5000)`) share its executor and run together.

#### `trx.getSchemaManager()` skipped the `search_normalize` support

`createTransactionalContext()` did not copy `searchNormalizeRequired`, so on a transaction's context it read
`undefined`: for a model that calls `model.useSearchNormalize()` without an `ixNormalized` index,
`trx.getSchemaManager().ensureSearchNormalizeSupport()` / `ensureCreated()` / `migrate()` skipped the `unaccent`
extension and the `public.search_normalize(text)` function the root's schema manager creates. It is copied now. A
model with an `ixNormalized` index was unaffected (that path reads the shared schema registry).

### Behaviour changes

- **LOUD:** everything obtained from the context `db.transaction()` hands its callback — table accessors, model
  sequences, query builders, futures, `QueryBatch` / `MutationBatch` legs, prepared queries, `tx.getSchemaManager()`,
  `tx.getClient()` — and the query function a client's own `transaction(query => …)` hands its callback, now REFUSE
  every statement once the callback has settled (committed, rolled back or failed), with a `TransactionEndedError`
  (exported; `.sql` = the refused text). Such a statement used to run silently on the pooled connection the
  transaction had released: outside any transaction — or INSIDE ANOTHER TRANSACTION that held that connection by then,
  mixing one request's writes into another's. Code that kept a `tx` object past its callback (returned it, cached it,
  used it from a timer or an un-awaited promise) now fails at that statement: keep results, not transaction-scoped
  objects, and use the root context or a new transaction outside the callback.
- `transaction()` on an ended context throws the same error (`.sql` `'BEGIN'`) instead of "Nested transactions are not
  supported".
- **LOUD:** a `PooledConnection` used after its `release()` refuses every statement with a `ConnectionReleasedError`
  (exported; `.sql` = the refused text) — on every driver: `PgClient`, `PostgresClient`, `BunClient`, `PGliteClient`,
  and the in-memory database through the pg / postgres.js wrappers. A statement issued before `release()` completes.
- A second `release()` never reaches the driver's pool any more: `PgClient`'s throws node-postgres's own `Release
  called on client which has already been released to the pool.`, the other drivers' do nothing.
- **LOUD:** `FutureQueryRunner.runAsync()` throws for futures of different connection contexts before any statement
  runs (see Fixed); a future built with its own per-query options counts as another context, while futures built from
  ONE such builder or accessor share it.
- `tx.getSchemaManager()` of a model with `model.useSearchNormalize()` creates the `search_normalize` support like the
  root's.
- Not guarded: the deprecated `PostgresClient.begin()`, whose callback gets postgres.js's own handle — use
  `transaction()`.

## Sequences

### Added

#### Exact int8 reads — `nextValueBigInt()`, `currentValueBigInt()`, `nextValueCreatingIfMissingBigInt()`

The bigint variants run the same statements as the number reads, and every int8 value comes back exact (all five
drivers deliver int8 as its exact decimal text). A value the driver itself delivered as an inexact double (a driver
configured to parse int8 as a number) is refused by both variants with a `RangeError`, and anything that is no integer
(null, a fraction) with a `TypeError` — never a wrong number, 0 or NaN. `resync(value: number | bigint)` takes a
bigint too, and sets any int8 value exactly.

### Fixed

#### A model sequence reached through a transaction ran outside it

`db.transaction()` built the transaction's context with `createTransactionalContext()`, which handed it the ROOT
context's map of model-sequence instances by reference. `trx.<sequence>` — a getter over the protected
`sequence(config)` — therefore returned the root's `DbSequence`, bound to the root client, and its `nextValue()` /
`currentValue()` / `resync()` ran on a SECOND pool connection, outside the caller's transaction:

- `currval()` / `lastval()` in the transaction were not set by the draw — 55000 `currval of sequence "…" is not yet
  defined in this session`, or a stale value from an earlier use of the pooled connection;
- the transaction's own state did not apply: a `SET LOCAL search_path` did not resolve an unqualified name, a
  `READ ONLY` transaction did not refuse the draw, a sequence created in the still-uncommitted transaction was
  invisible (42P01), and a failed draw did not abort the transaction;
- every draw needed a second connection: on a pool of N, N concurrent transactions that each drew deadlocked (a
  `pg.Pool` waits forever by default) — on a pool of one, a single transaction that drew did;
- PGlite, which has one session, refused every such draw (`PGliteClient: PGlite has a single session, and the
  transaction running this callback holds it — …`);
- a migration (`MigrationRunner` runs `up(db)` on a transaction's context) that created a sequence and numbered its
  seed rows from it failed with 42P01.

It leaked the other way too: a sequence FIRST reached inside a transaction (a getter `setupSequences()` does not touch)
was created bound to the TRANSACTION's client and cached in the shared map, so the root context used that instance for
the rest of its life — on `pg` a later root draw ran on the released pooled connection, inside whatever transaction
held it at that moment, and one made while the transaction was still open ran inside it.

A transaction's context now gets a map of its own: `sequence(config)` on it creates instances bound to the
transaction's client, cached for that transaction. The root keeps its own instances; the sequence registry — the
configuration the schema manager reads — stays shared, so a sequence first reached inside a transaction is still
registered. The statements are unchanged (`SELECT nextval($1::regclass) as value`, still unlogged); only the
connection they run on differs. A drawn value stays consumed when the transaction rolls back (sequences are not
transactional), and `resync()` is still not undone by a rollback. `trx.<sequence>` is no longer the same object as
`db.<sequence>`, and each transaction gets its own instance (refused after the transaction — see Transactions &
connections).

`nextValueCreatingIfMissing()` / `nextValueCreatingIfMissingBigInt()` of a transaction's instance keep 1.0.10's outcome
— the first value, and a sequence that exists afterwards whatever the transaction does — without letting a failed
`nextval` abort the caller's transaction (a plain `nextval` of a missing sequence would: 42P01, then 25P02 for every
later statement). The transaction's instance knows the context's root client, and its ladder is:

1. `SELECT to_regclass($1)::oid::text AS oid` in the transaction — never an error, so never an abort; it sees the
   transaction's own uncommitted CREATE and its `search_path`;
2. found: `SELECT nextval($1::regclass) as value` in the transaction;
3. missing: `CREATE SEQUENCE IF NOT EXISTS <name> <options>` on the ROOT client (committed at once, so a rollback of
   the caller never restarts the numbering; a lost race is swallowed as before), the new sequence's OID read there
   with the query of step 1, then `SELECT nextval($1::regclass) as value` in the transaction with that OID — by OID,
   so the draw never meets a name lookup the transaction's session cached before the CREATE.

The draw sets the transaction's `currval()` / `lastval()`, and a READ ONLY transaction refuses it. The CREATE needs a
second pooled connection, as every draw of a transaction's sequence did in 1.0.10: on a pool of one it waits for the
transaction's connection (node-postgres, by default, forever). PGlite, which has one session, refuses the CREATE with
its single-session error — as it refused every such draw in 1.0.10 — and the transaction stays usable; an existing
sequence is drawn in the transaction there too. The root context's ladder is unchanged.

`runtimeSequence()` keeps its deliberate ROOT binding (a CREATE must survive the caller's rollback, and a failed first
`nextval` must not abort the caller's transaction); its JSDoc and the schema-configuration guide now state the two
behaviours side by side ("Sequences inside `transaction()`").

#### The number reads and `resync()` produced a different number beyond 2^53

`nextValue()` / `currentValue()` / `nextValueCreatingIfMissing()` returned `Number(value)`: beyond 2^53 a different
number than the database drew (2^53 + 1 came back as 2^53). They now throw a `RangeError` outside ±(2^53 − 1):

```
sequence "<name>": nextValue() drew 9007199254740992, beyond the safe integer range of a JS number
(±9007199254740991) — the value is consumed; draw it with nextValueBigInt()
```

(`currentValue() is …` — read it with `currentValueBigInt()`.)

`resync(value: number | bigint)`: a number must be a safe integer. Anything else — 2^53 and beyond (2^53 itself
included, the reads' boundary), below −(2^53 − 1), a fraction, NaN, ±Infinity — throws before any SQL:

```
sequence "<name>": resync() takes a number only within the safe integer range (±9007199254740991), got
1152921504606846976 — pass the exact value as a bigint
```

1.0.10 bound such a number as its shortest round-trip decimal, which beyond 2^53 is often another value
(`resync(2 ** 60)` set 1152921504606847000, not 1152921504606846976); a fraction or NaN failed in the database.
Numbers and bigints are now bound as their exact decimal text, which also fixes `resync()` on `BunClient` for a number
of 2^51 or more: Bun 1.4 declares such a parameter `double precision`, and `setval(regclass, double precision,
boolean)` does not exist (42883).

### Behaviour changes

- A model sequence reached through a transaction's context (`tx.<sequence>`) now draws INSIDE the transaction: a READ
  ONLY transaction refuses the draw (25006), and a failed draw aborts the transaction like any failed statement. Its
  `nextValueCreatingIfMissing()` keeps 1.0.10's outcome for a sequence that does not exist yet (the first value, and the
  sequence exists afterwards, whatever the transaction does) without aborting the transaction: the CREATE runs on the
  root client, the draw in the transaction. PGlite refuses that CREATE (one session), as it refused every such draw
  before.
- `trx.<sequence>` is no longer the same object as `db.<sequence>`; each transaction gets its own instance.
- `DbSequence.nextValue()` / `currentValue()` / `nextValueCreatingIfMissing()` throw a `RangeError` for a value outside
  ±(2^53 − 1) instead of returning a rounded number — also for values above 2^53 that a double happens to hold exactly
  (1e16 came back right before; it now throws). The new `nextValueBigInt()`, `currentValueBigInt()` and
  `nextValueCreatingIfMissingBigInt()` return every int8 exactly. Every value within ±(2^53 − 1) reads exactly as
  before.
- `resync()` also takes a bigint. It refuses a number that is no safe integer — 2^53 itself included — with a
  `RangeError` before any SQL (pass a bigint); 1.0.10 set another value for many numbers beyond 2^53.

## Collections / selectMany

A collection flattened with `selectMany()` reads its items through the collections it was flattened through — its
HOPS: `l.shelves.where(s => …).selectMany(s => s.books)` has one hop, the shelves;
`….selectMany(s => s.books).selectMany(b => b.reviews)` has two. Everything written on a hop or on the collection a
selector returns now applies, with LINQ's meaning, under every collection strategy (LATERAL, CTE, temp table —
including its single round-trip form on postgres.js / Bun) and in the correlated subquery of a flattened collection in
a WHERE or a `sql` fragment, for every terminal (`count`, `exists` / `notExists`, `sum` / `min` / `max`,
`select().toList()`, `toNumberList` / `toStringList`, `firstOrDefault`, `orderBy` + `limit` / `offset`,
`selectDistinct`). Shapes whose meaning is ambiguous are refused with an error instead of returning rows. Several of
the shapes below used to return WRONG ROWS without an error.

### Fixed

#### A `where()` before `selectMany()` referenced a table no FROM clause defined

The filter's columns carry the filtered collection's marker; `selectMany()` handed the filter to the flattened
collection, which resolves only its own table's marker, so the marker reached the database — for every terminal and
every strategy:

```sql
-- libraries.select(l => ({ n: l.shelves.where(s => eq(s.archived, false)).selectMany(s => s.books).count() }))
-- before
SELECT (SELECT COALESCE(COUNT(*), 0)
FROM "books" "lateral_0_shelves"
INNER JOIN "shelves" "shelves" ON "lateral_0_shelves"."shelf_id" = "shelves"."id"
WHERE "shelves"."library_id" = "libraries"."id" AND "__collection_shelves__"."archived" = $1) as "n"
FROM "libraries"
-- ERROR: missing FROM-clause entry for table "__collection_shelves__"
-- after
SELECT (SELECT COALESCE(COUNT(*), 0)
FROM "books" "lateral_0_shelves"
INNER JOIN "shelves" "shelves__bridge1" ON "lateral_0_shelves"."shelf_id" = "shelves__bridge1"."id"
WHERE "shelves__bridge1"."library_id" = "libraries"."id" AND "shelves__bridge1"."archived" = $1) as "n"
FROM "libraries"
```

Several `where()` calls on either side of `selectMany()` are ANDed, each on its own rows. A filter may read the OUTER
row (`s => eq(s.floor, l.mainFloor)`), use `and()` / `or()` / `not()`, a raw `sql` fragment, a placeholder of a
prepared query, a subquery, or an `exists()` / `count()` over the hop item's own collections. Two differently filtered
flattenings of one navigation in one select stay apart, and the filtered collection stays usable on its own after it
has been flattened.

#### `orderBy()` / `limit()` / `offset()` before `selectMany()` were ignored

`l.shelves.orderBy(s => s.code).limit(1).selectMany(s => s.books)` flattened EVERY shelf, and an `orderBy()` before
`selectMany()` did not order anything — no error. The first rows of each parent are flattened now, the rows a
hand-written `… ORDER BY … LIMIT n` per parent keeps: the filter applies first (wherever it is written), ties are
broken by the primary key, `offset()` without `orderBy()` skips in primary-key order, `limit(0)` keeps none. The
flattened items come in the order of the rows they come from — an `orderBy()` after `selectMany()` sorts first and the
earlier orders break its ties — so a `limit()` after `selectMany()` takes the first items in that order. A limit on a
flattened collection before a further `selectMany()`, and limits at several levels, apply level by level; a constant
key part of the relation, a table of another schema and a composite primary key of mixed-case columns hold inside the
ranking.

#### A `where()` / `orderBy()` / `limit()` / `select()` on the collection the selector returns were ignored

`l.shelves.selectMany(s => s.books.where(b => gt(b.pages, 200)))` flattened every book — no error. The filter applies
now, and it may read the item it was returned for (`s => s.books.where(b => eq(b.curatorId, s.curatorId))` — over one
self-referencing table too), a collection of that item (`exists(s.visibleBooks…)`, correlated to the hop), or the
outer row; a flattening nested in it through the same relations takes hop aliases of its own. Its `orderBy()` orders
each row's items; its `limit()` / `offset()` keep the first items OF EACH ROW
(`s => s.books.orderBy(b => b.pages).limit(1)`: each shelf's shortest book), after its own filter and before the
filters written after `selectMany()`. Its `select()` projects the flattened items (`s => s.books.select(b => b.title)`
flattens titles, and may read the shelf, `s.code`) — 1.0.10 dropped the projection: a `count()` was right, a list
returned whole book rows. `min()` / `max()` / `sum()` with a selector aggregate the field it selects of that
projection (`selectMany(s => s.books.select(b => ({ p: b.pages }))).max(x => x.p)`); `count()` / `exists()` do not
read the projection at all.

#### A selector returning a flattened collection failed

`l.shelves.selectMany(s => s.books.selectMany(b => b.reviews))` joined the reviews to the shelves on the books' key:
`column "reviews"."shelf_id" does not exist`. The inner collection's hops become hops of the flattening, with their
filters, orders and limits — a limit of the inner collection now keeps the first items of each shelf.

#### A second `selectMany()` replaced the first hop

`l.shelves.selectMany(s => s.books).selectMany(b => b.reviews)` kept only the books hop and correlated the shelves'
foreign key through it: `column "books"."library_id" does not exist`, under every strategy. Hops now accumulate; the
joins run from the flattened table outwards and the correlation reads the first hop — also when the second selector
reads a navigation's collection an earlier filter read too
(`….selectMany(s => s.books.where(b => exists(b.curator.shelves))).selectMany(b => b.curator.shelves)`).

#### A selector reaching its collection through a navigation of its item joined the wrong keys

`l.shelves.selectMany(s => s.curator.shelves)` joined the curator's shelves ON `shelf.curator_id = <hop>.id` — the
curator key against the shelf key, wrong rows without an error. The navigation is joined now (in reverse, from the
flattened items back to the hop), with filters, orders and per-row limits on either side. A limit on the hop ordered
or filtered through that same navigation
(`l.shelves.orderBy(s => s.curator.name).limit(1).selectMany(s => s.curator.shelves)`) ranks each shelf by its own
curator: the ranking joins the steps of the navigation its keys and filters read
(`LEFT JOIN "curators" "shelves__bridge1__curator"` inside it). 1.0.10 ignored the limit.

#### `select()` before `selectMany()`

`l.shelves.select(s => ({ books: s.books })).selectMany(x => x.books)` handed the selector the SHELF, not the
projection, and flattened the shelf's navigation named like the field it read — right for `books`, wrong for a field of
another name or a filtered collection (`select(s => ({ long: s.books.where(…) }))` flattened every book). The selector
is handed the projection now and flattens the collection it holds.

#### `selectMany()` over a self-referencing table

`t.children.selectMany(c => c.children)` rendered the hop under the table's own name: `table name "topics" specified
more than once` under the CTE / temp-table strategies, and under LATERAL the hop shadowed the outer node the
correlation reads — every node came back without grandchildren, no error. A filter comparing the child with the outer
node of the same table (`c => gt(c.name, t.name)`) compared the child with itself.

#### A navigation in the filter of a flattened collection was resolved from the flattened table

`l.shelves.where(s => eq(s.curator.name, 'Max')).selectMany(s => s.books)` joined `curator` by relation NAME from the
BOOK — the book's own `curator` when it had one (the filter then read another row, silently), else whatever path the
schema offered. A navigation of a hop's item is joined from the hop now, at every depth, and apart from a navigation of
the same name on the flattened items.

#### A flattening nested in another collection, filtered by the enclosing item of the same table

`l.shelves.select(s => ({ peers: s.library.shelves.where(x => ne(x.id, s.id)).selectMany(x => x.books).count() }))`
rendered both `s.id` and `x.id` under one alias — `x.id <> x.id`, a count of 0 for every shelf.

#### The constant key part of a flattened relation, and of a hop's relation

A relation keyed with a constant part
(`withForeignKey(s => [s.libraryId, s.archived]).withPrincipalKey(l => [l.id, false])`), flattened, read its constant
column from the FLATTENED table under the CTE / temp-table strategies: `column "books"."archived" does not exist` (or,
silently, another column of that name). It is read from the first hop, which holds the foreign key. The correlated
subquery of a flattened collection joined a hop on its relation's first key pair only — through
`[shelfId, visible] = [id, true]`, a `count()` in a `sql` fragment counted the hidden rows too.

#### The correlated subquery ignored the collection's own `limit()` / `offset()`

`sql\`${l.shelves.orderBy(s => s.code).limit(1).count()}\`` counted every shelf, and `exists(l.shelves.offset(1))` in a
WHERE matched libraries with a single shelf — no error, for plain and flattened collections alike. The correlated
`count()` / `exists()` applies its limit / offset now (LIMIT / OFFSET, no ORDER BY — see SQL text changes).

#### A `count()` / `exists()` whose filter holds a collection of its own items

`sql\`${l.shelves.where(s => exists(s.books)).count()}\`` failed with `invalid reference to FROM-clause entry for table
"shelves"` (the count renders its table as `shelves__count`, the nested `exists()` correlated to the table's name).
Over a self-referencing table the nested collection correlated to the OUTER node the enclosing collection hangs off,
not to the child it was written on: `sql\`${t.children.where(c => exists(c.children)).count()}\`` counted every child
of a node with children — `exists()` true and `count()` too high, no error. The nested collection correlates to the
enclosing collection's item now (by the row that minted it — see SQL text changes), and takes a suffixed alias of its
own. A collection of the OUTER row in the same filter (`t.children.where(c => sql\`${t.children.count()} > 1\`)`)
keeps correlating to the outer row, as in 1.0.10 — also a level deeper, under a subquery over the OUTER row's table
(`x.library.shelves.where(y => exists(y.library.shelves.where(z => exists(x.books))))`), where the subquery between
them now takes an alias of its own (see SQL text changes). Tests pin the 1.0.10 answers. Where 1.0.10 failed on such a
shape (`invalid reference to FROM-clause entry`), it now returns the rows it describes.

The PROJECTED form of such a shape — a collection of the OUTER row nested two subqueries deep in a collection
projected by a strategy (`x.books.where(b => exists(b.shelf.library.shelves.where(y => exists(x.slots)))).count()` in
a `select()`) — still binds that collection to the nearest row of the outer row's table, as 1.0.10 does, under every
strategy; the `sql` fragment form of it is right. A test pins the 1.0.10 answer (see Known limitations).

#### Navigations named like the table they point at, in nested correlated subqueries

With reference navigations named like their tables (`nt_book.nt_shelf`, `nt_shelf.nt_library`), a nested `exists()` /
`count()` joined such a navigation under that very name — the name the OUTER row of that table is read by:

- `x.nt_library.shelves.where(y => exists(y.books.where(bk => exists(bk.nt_shelf.nt_library.shelves.where(z =>
  exists(x.slots))))))`: `x.slots` read the joined `nt_shelf` (1.0.10 failed: `table reference "nt_shelf" is
  ambiguous`);
- a book's navigation named like the OUTER library table, the inverse of no collection (`k.nt_library`), next to a
  collection of the OUTER library in the same filter: the collection read the book's library (1.0.10: no row);
- the inverse of a collection's key (`y.books.where(k => eq(k.nt_shelf.code, 'B'))`), which is read as the parent row
  itself: it read the OUTER shelf by that name, not the enclosing item `y` (1.0.10: `[B]` for `[A, B]`, in a WHERE and
  in a projected LATERAL count; one level deeper 1.0.10 failed).

Each now reads the row it names (see "SQL text changes"). Two forms built by a collection strategy answer as 1.0.10
does — a separate defect of the projection path (see Known limitations): the inverse navigation in a collection
nested in a projected list
(`x.nt_library.shelves.select(y => ({ n: y.books.where(k => eq(k.nt_shelf.code, 'B')).count() }))`: wrong under
LATERAL, `missing FROM-clause entry` under CTE — and `x.books.where(k => eq(k.nt_shelf.code, 'A')).count()` under
CTE / temp table), and the second shape in the filter of a projected `count()` (no row under every strategy).

#### A ranking ordered through a navigation of the OUTER row, in a WHERE

`where(b => exists(b.shelf.library.shelves.orderBy(x => sql\`${x.code} = ${b.curator.name}\`).limit(1).selectMany(…)))`
left `curator` unjoined in the outer query: `missing FROM-clause entry for table "curator"`. The order keys of a
flattening's rankings are reported to the enclosing query with its filters now, so it joins the navigations they read;
a value aggregate (`sum` / `min` / `max`) over `orderBy(<navigation>).limit()` keeps its ORDER BY.

#### A `min()` / `max()` of 0 came back as null under the temp-table strategy

The temp-table strategy merged each parent's aggregate into its row with `||`: an aggregate the driver hands back as
the number 0 — a `min()` / `max()` of 0, of a collection or of a selector's projection — read as missing and came back
as `null`, as in 1.0.10. It merges with `??` now: only a parent without rows gets the default (`null`; 0 for
`count()`, false for `exists()`). The LATERAL and CTE strategies were right.

### Refused with an error

Each of these returned wrong rows or failed in 1.0.10 (the limits below were ignored there outright); each throws a
message naming the collection and the way out when the query is built:

- `selectDistinct()` before `selectMany()`, or a terminal (`count()`, `toList()`, …) before it; a `select()` whose
  projection holds no collection for the selector to return;
- a selector returning anything but a collection of the item it is handed — a reference navigation, a value, a
  collection of the OUTER row or of an enclosing row of the same table (`c => t.children`) — or a collection with
  `selectDistinct()` (distinct per flattened row) or a terminal on it;
- a limit that keeps rows of a table without a primary key (`has no primary key`);
- a limit ranking rows reached through a navigation of a hop (one row can be reached from several);
- a limit / offset that ranks (before `selectMany()`, or on the collection a selector returns) and is not a
  non-negative integer: `LIMIT must not be negative` / `OFFSET must not be negative` — the text PostgreSQL gives a
  negative LIMIT — and `LIMIT must be an integer`;
- a collection of a row the items were flattened through, aggregated in the projection of the collection a selector
  returns (`s => s.books.select(b => ({ n: s.visibleBooks.count() }))`): a nested aggregation correlates to the item's
  own row. Count it in a `sql` fragment of that projection itself (`` sql`${s.visibleBooks.count()}` ``), which reads
  the hop's row. A `count()` / `exists()` of the flattened items drops their projection and is not refused;
- in that projection (new in this release), a collection of any row but the flattened items — the OUTER row's
  (`s => s.books.select(b => ({ n: l.crates.count() }))`), directly, in a `sql` fragment, or in the projection of a
  collection it holds: the aggregations that project the flattened items are not correlated to that row (the CTE
  strategy read it as another row, the temp-table strategy as none). Read it outside `selectMany()`, next to the
  flattened list;
- in the projection or the filter of a collection nested in that projection, a collection of any row but that
  collection's own items — the flattened item's (`b.reviews.select(r => ({ n: b.reviews.count() }))`: under the CTE
  strategy, 1 for a book with 2 reviews), a hop's row, directly or in a `sql` fragment. Read a collection of the
  flattened item in the projection of the flattened items itself; a hop's row's outside `selectMany()`.

### SQL text changes

The SQL of every `selectMany()` changes — the results do not, where the old SQL ran and returned the right rows:

- **A hop renders under an alias of its own, `<relation>__bridge<n>`**, `n` counted from the parent — no longer under
  its table's name. `l.shelves.selectMany(s => s.books)` joins
  `INNER JOIN "shelves" "shelves__bridge1" ON … = "shelves__bridge1"."id"` and correlates
  `"shelves__bridge1"."library_id" = …`; a second flattening adds `"books__bridge2"`. `foreignKeyTableAlias` in the
  collection strategies' config is the first hop's alias. An alias an enclosing scope already uses — an enclosing
  LATERAL's, or any alias an enclosing collection subquery renders (its own, its hops', its hops' navigations') —
  takes a suffix (`shelves__bridge1_2`).
- **A navigation of a hop's item renders under `<hop alias>__<relation path>`** (`"shelves__bridge1__curator"`),
  joined from the hop — always, not only when its name collides with a navigation of the flattened items.
- **A limit on a hop or on the collection a selector returns renders as a ranking of the rows it keeps.** Where the
  query is correlated to the collection's parent row — the LATERAL strategy, and the correlated subquery of a WHERE /
  `sql` fragment — it reads the rows of the ONE row it ranks within, through that row's key:
  `"<alias>"."id" IN (SELECT "<alias>"."id" FROM … WHERE "<alias>"."<fk>" = "<that row>"."<key>" AND …
  ORDER BY <keys>, "<alias>"."id" ASC LIMIT n OFFSET m)` (row-valued for a composite primary key:
  `("<alias>"."a", "<alias>"."b") IN (SELECT …)`). The set-based CTE / temp-table aggregations rank every parent's
  rows at once: `EXISTS (SELECT 1 FROM (SELECT "<alias>"."id" AS "__pk0", ROW_NUMBER() OVER (PARTITION BY <key>
  ORDER BY <keys>, "<alias>"."id" ASC) AS "__rn" FROM … WHERE …) "__ranked" WHERE "__ranked"."__rn" > <offset>
  AND "__ranked"."__rn" <= <offset + limit> AND "__ranked"."__pk0" = "<alias>"."id")`.
- **An `orderBy()` before `selectMany()` or on the collection a selector returns** appends its keys to the flattened
  list's ORDER BY (after the flattened collection's own keys).
- **The correlated subquery** of a flattened `count()` / `exists()` in a WHERE or a `sql` fragment joins each hop with
  `INNER JOIN` on every key pair of its relation (it wrote `JOIN` on the first pair only), and names its own table
  (`<relation>__count` / `__exists`) only when the enclosing scope reads a row under that name — for a flattened
  `count()` too, which kept its table unaliased before. A correlated `count()` / `exists()` with its own `limit()` /
  `offset()` renders `SELECT COUNT(*) FROM (SELECT 1 FROM … LIMIT n OFFSET m) "<alias>__rows"` /
  `EXISTS (SELECT 1 FROM … LIMIT n OFFSET m)` — without ORDER BY: which rows those are cannot change how many there
  are, nor whether one is past the offset. A `<relation>__count` / `__exists` alias an enclosing collection subquery
  already uses takes a suffix (`children__count_2`).
- **A collection nested in the filter of a correlated `count()` / `exists()`** correlates to the row that MINTED it,
  under the alias the enclosing subquery renders that row with: an item of the enclosing collection
  (`"children__count"."id"`), a row of one of its hops (`"shelves__bridge1"."id"`). A collection of a row outside
  every such subquery — the OUTER row's own collection, say — reads that row by its bare name, as in 1.0.10; so a
  correlated `exists()` or flattened `count()` nested in another one over the OUTER row's TABLE now renders under an
  alias of its own (`"shelves__exists"`, `"children__exists_2"`) instead of that bare name, which shadowed the outer
  row for such a collection nested deeper still (see Fixed). Nested subqueries over other tables keep their 1.0.10 SQL.
- **The joins of a nested correlated subquery keep off the names the subqueries around it read rows by** — an alias
  an enclosing subquery renders, and the bare name of the row outside every enclosing collection subquery that a
  correlated `exists()` / `count()` around it hangs off (the outer query's row, in a WHERE or a `sql` fragment). A
  collection projected in `select()` by a collection strategy reserves no such name for the subqueries nested in its
  filter — see "Known limitations". Where a join's plain name is one of those, a join of the navigation path the
  subquery hangs off takes a suffix (`LEFT JOIN "nt_shelf" "nt_shelf_2"`), a navigation of its items its path alias
  (`LEFT JOIN "nt_shelf" "nt_book__nt_shelf"`): with navigations named like the table they point at
  (`nt_book.nt_shelf`), the plain name shadowed the outer row. And the inverse of a collection's own key is read as
  the parent under the alias the parent renders under: when that is an alias of its own (`"shelves__exists"`), the
  navigation is joined. One level deep nothing changes. Deeper, a join is renamed whenever its plain name is
  reserved — also in shapes 1.0.10 answered right, where nothing read the row the name shadowed
  (`libraries.where(lib => exists(lib.shelves.where(y => exists(y.books.where(bk => eq(bk.nt_library.name, 'B'))))))`
  joins the book's home library as `"nt_book__nt_library"`, 1.0.10 as `"nt_library"`): their SQL changes by the alias
  alone, their rows do not.

Tests that pin the SQL of a `selectMany()`, or of a limited or nested correlated `count()` / `exists()`, need
updating. Every other collection shape — aggregates, lists, nested collections, `exists()` / `count()` in a WHERE or a
`sql` fragment — renders byte for byte as in 1.0.10 (compared under all three strategies).

### Performance

A limit before `selectMany()`, or on the collection a selector returns, is tied to the row it ranks within under
LATERAL and in the correlated subquery: PostgreSQL reads it through the foreign-key index — once per parent when the
ranking hangs off the parent. PostgreSQL 18, 2 000 libraries / 40 000 shelves / 200 000 books, foreign keys indexed,
200 libraries per query (median of 3):

| shape | LATERAL, before → after | correlated `sql` count, before → after | hand-written |
|---|---|---|---|
| `l.shelves.orderBy(code).limit(1).selectMany(s => s.books).count()` | 4 048 → 3.1 ms | 3 932 → 2.7 ms | 1.9 ms |
| `l.shelves.selectMany(s => s.books.orderBy(pages).limit(1)).count()` | 7 617 → 13.8 ms | 7 466 → 12.3 ms | 12.0 ms |
| the first shape, one library | 21.3 → 0.6 ms | 21.1 → 0.5 ms | |
| a hop filter reading the outer row, then a limit | 1 331 → 2.4 ms | 1 364 → 2.2 ms | 1.5 ms |

("Before" is the earlier form of this change, which ranked every parent's rows with `ROW_NUMBER()` for each row it
asked about; 1.0.10 ignored these limits.) The CTE and temp-table strategies aggregate every parent at once and keep
one `ROW_NUMBER()` ranking (31 / 63 ms and 46 / 71 ms for the first two shapes) — a per-row `LIMIT` there measured
3.5-4.6x slower. A collection that reads its parent row (the last shape) renders as LATERAL under them, and gets the
per-row form: 1 311 → 2.7 ms (CTE), 1 294 → 2.6 ms (temp table).

### Behaviour changes

- RESULTS that change: every shape above that failed now evaluates; the silently wrong ones return the rows they
  describe — limits and orders before `selectMany()`, filters / orders / limits / projections on the collection a
  selector returns, `select()` before `selectMany()`, a selector through a navigation, grandchildren of a
  self-referencing table under LATERAL, a hop filter through a navigation the flattened item also has, a flattening
  filtered by an enclosing item of the same table, constant key parts, the correlated subquery's own limit / offset and
  its nested collections of the same table, nested correlated subqueries through navigations named like the table
  they point at. A `min()` / `max()` of 0 under the temp-table strategy reads 0, where it read `null`.
- `selectDistinct()` after a flattening of an ordered collection lists each value once, in no particular order: the
  order the items inherit from the rows they were flattened through is dropped (as LINQ providers drop an ordering
  under `Distinct()`); a limit ranked in that order still picks its rows.
- REFUSALS: the shapes listed under "Refused with an error" throw instead of returning rows.
- SQL TEXT: see "SQL text changes".

### Known limitations

Pre-existing — each answers as 1.0.10 does:

- **A field of the outer query's row, read in a subquery nested in the filter of a PROJECTED collection, where a join
  there is named like the outer row's table.** A field of the outer query's row renders as that row's bare table
  name — it does not record which row it belongs to — and the database reads the name from the nearest FROM entry that
  has it. A correlated `exists()` / `count()` of a WHERE or a `sql` fragment reserves the name for every subquery
  nested in it (see "SQL text changes"); a collection projected in `select()` by a collection strategy — a count, an
  `exists()`, a list — does not. So in
  `libraries.select(lib => ({ n: lib.shelves.selectMany(s => s.books).where(bk =>
  exists(bk.nt_library.shelves.where(z => ne(z.libraryId, lib.id)))).count() }))` the nested `exists()` joins the
  book's home library (`bk.nt_library`, named like the library table) as `"nt_library"`, and `lib.id` reads the HOME
  library's key: never true, a count of 0 for every library. The same filter in a WHERE, or the count in a `sql`
  fragment of the projection, reads the outer library. Name the navigation apart from the table, or count in a `sql`
  fragment.
- The projection-path forms noted above: the projected form under "A `count()` / `exists()` whose filter holds a
  collection of its own items", and the two forms under "Navigations named like the table they point at".

## QueryBatch / grouped queries / joined reads

Three things change here. A manually joined table's columns read through their own column config, **in standalone
queries too**. Grouped queries join a `QueryBatch`. And a value a `QueryBatch` delivers is the one THIS client
delivers for the same query standalone — under its driver's configuration, the driver's defaults or parsers of the
application's own — apart from the known limitations of the batch's JSON transport (below).

### Added

#### Grouped queries in a `QueryBatch` — `future()`, `futureFirstOrDefault()`, `futureCount()`

`GroupedSelectQueryBuilder` (`.groupBy(...).select(...)`) and `GroupedJoinedQueryBuilder` (a grouped query
`.leftJoin()` / `.innerJoin()`ed to a CTE or a table subquery) had no future API. `QueryBatch.addList()` /
`addFirstOrDefault()` / `addCount()` refused them at compile time and threw `query.future is not a function` at
runtime, and `FutureQueryRunner` could not run them either — every grouped read paid a round trip of its own, even when
the caller batched everything else.

Both grouped builders now have the future API of a plain select, the same three methods with the same meaning:

```ts
const perDay = db.tasks
  .select(t => ({ day: dateTrunc('day', t.openedAt), points: t.points }))
  .groupBy(r => ({ day: r.day }))
  .select(g => ({ day: g.key.day, tasks: g.count(), points: g.sum(r => r.points) }))
  .orderBy(r => r.day);

const batch = new QueryBatch();
const pageKey = batch.addList(perDay.limit(10), 'perDay');   // BatchListKey<{ day: Date; tasks: number; points: number }>
const daysKey = batch.addCount(perDay, 'days');              // the number of groups, past the LIMIT
const userKey = batch.addFirstOrDefault(db.members.where(m => eq(m.id, id)).select(m => m), 'member');
await batch.executeBatch();                                  // ONE round trip
batch.getList(pageKey);                                      // exactly what perDay.toList() reads
```

- `future()` — a `FutureQuery<T>`, `T` exactly the element type `toList()` reads (the grouped projection, resolved).
- `futureFirstOrDefault()` — a `FutureSingleQuery<T>`. LIMIT 1 applies to the future only; the builder keeps its own
  paging (as the plain select's `futureFirstOrDefault()` does).
- `futureCount()` — a `FutureCountQuery`: the number of groups the HAVING keeps (of a grouped join: its rows), the
  query's ORDER BY / LIMIT / OFFSET aside — as a plain select's `futureCount()` counts its rows past its paging. It
  renders `SELECT COUNT(*) as count FROM (<the grouped statement>) AS "grouped_count"`.

A future fixes its statement and its reads when it is created (changing the builder afterwards changes nothing),
carries the builder's executor (a transaction's; a `withTimeout()` one of its own, which the batch refuses to mix, as
for a plain select), and runs through `execute()` and `FutureQueryRunner.runAsync()` as well.

Through a batch, a grouped query reads exactly what its `toList()` / `firstOrDefault()` reads through the same
client — the same values, of the same JS types, in the same key order — whatever it projects: grouping keys (columns,
navigation columns, columns of a manual join or of a `crossJoinLateral` set, expression keys in the `"q1"` subquery
form), NULL groups, `g.count()` / `g.sum()` / `g.avg()` / `g.min()` / `g.max()` (a MIN / MAX of a date, a timestamp, a
mapped column), the `agg.*` fragments with `FILTER` / `DISTINCT` / `ORDER BY`, `sql` expressions over keys and
aggregates, `withReadType()` / `mapWith()` expressions, constants. A grouped join's fields read as the grouped query
reads them, its joined side's columns as they read standalone.

#### `DatabaseClient.parseTypedText()` / `customParsedTypeOids()` — a value's text, parsed as the client parses it

Two methods of `DatabaseClient`, through which a `QueryBatch` reads the values it sends as their text (see Fixed):
`parseTypedText(oid, text, read?)` parses a value's PostgreSQL text as the client's driver parses a column of the
type — `PgClient`, `PostgresClient`, `PGliteClient` and `BunClient` each through their driver's rules, any other
client by node-postgres's default rules unless it overrides the method — and `customParsedTypeOids()` names the types
the client parses with a parser of the application's own. The `TypedTextRead` type (`read`) is exported, and
`TransactionalClient` delegates both; `docs/database-clients.md` describes them as the two hooks a custom client may
override.

### Fixed

#### Columns of a manually joined table read as a column of ANOTHER table (silent wrong data)

**This changes what STANDALONE queries return**, not only batched ones. A column of a manually joined table
(`leftJoin` / `innerJoin` of a table — `db.jobs.leftJoin(db.machines, on, (j, m) => ({ … m.col … }))`) was looked up
by its property NAME on the queried (base) table, for every read and for every condition:

- a joined column named like a MAPPED column of the queried table read through THAT column's mapper — a machine's
  plain integer hour counter `600` came back `{ hours: 10, minutes: 0 }` through the job's `runtime` mapper;
- a MAPPED joined column the queried table has no column of read through NO mapper (`90` for an interval of
  1 h 30 min), and a condition on it bound the JS value unconverted — PostgreSQL refused the statement
  (`invalid input syntax for type integer: "{"hours":1,"minutes":0}"`);
- a joined text column of digits the queried table has no column of read like an expression: `'00042'` came back as
  the number `42`;
- through a QueryBatch, a joined date / timestamp / bytea column the queried table lacks came back as its JSON text,
  and a joined text column named like a TIMESTAMP column of the queried table as an Invalid Date.

The navigation form (`j.machine!.service`) always read these columns right. A joined table's columns now carry what a
navigation's do — their table, their mapper, their SQL type — so every read path (standalone, batched, a CTE or table
subquery of the join, a grouped query over it, `select()` over the joined projection, `firstOrDefault()`) and every
condition resolves a joined column by its OWN table: exactly as the navigation form reads and binds it. The same on
every driver (node-postgres, postgres.js, Bun in both modes, PGlite, the in-memory engine).

| A joined table's column (`leftJoin` / `innerJoin` of a table) | Before, standalone | Before, batched | After, both |
|---|---|---|---|
| named like a MAPPED column of the queried table (`m.runtime`, integer `600`; the job's `runtime` is mapped) | `{ hours: 10, minutes: 0 }` | the same | `600` |
| a MAPPED column the queried table has no column of (`m.service`, 90 minutes) | `90` | `90` | `{ hours: 1, minutes: 30 }` |
| the same, NULL (a `leftJoin` without a match) | `undefined` | `undefined` | `null` (the mapper's read of NULL — as the navigation form) |
| a text column of digits the queried table has no column of (`m.serial`, `'00042'`) | `42` | `42` | `'00042'` |
| a timestamp / date column the queried table has no column of (`m.installedAt`) | `Date` | `'2020-01-15T08:30:00'` (ISO text) | as the client's parser makes it (a `Date` by default) |
| a text column named like a TIMESTAMP column of the queried table (`m.due`, `'weekly'`) | `'weekly'` | `Invalid Date` | `'weekly'` |
| an int8 / numeric column named like an integer column of the queried table | the driver's text (`'12.50'`) | a JSON number (`12.5`) | the driver's text |
| `agg.min()` / `agg.max()` over a MAPPED joined column | `90` | `90` | `{ hours: 1, minutes: 30 }` |
| `agg.min()` / `agg.max()` over an int8 / numeric joined column | the driver's text | the same | a number (as over a column of the queried table) |
| `coalesce()` / `caseWhen()` / arithmetic whose first mapped operand is a joined column | unmapped (or the next operand's mapper) | the same | through that column's mapper |
| a CTE's / table subquery's column projected from a joined column | unmapped; digits as a number | the same | as the joined column reads |
| a condition on a MAPPED joined column (`where`, the join's `ON`, `joinFilter`, `inArray`, `eqAny`, …) | binds the JS value → PostgreSQL error | the same | binds it through the mapper (`{ hours: 1, minutes: 0 }` → `60`) |
| a self-join, a navigation off a joined table, the navigation form | correct | correct | unchanged |

**What to check in an application**: a manual join of a TABLE whose projection holds a joined column that is
custom-mapped, is named like a custom-mapped column of the queried table, or is a text of digits — its value changes as
above; code that compensated (converted `90` into an interval itself, passed a mapped column's DRIVER form to a
condition) now converts twice. In a QueryBatch, also a joined date / timestamp / bytea column the queried table has no
column of.

SQL: a plain comparison, an ORDER BY and the projection of a joined column render byte for byte as before. A helper
that types its SQL by a column's declared type renders for a joined column as for a column of the queried table: the
`eqAny()` / `neAll()` array cast (`= ANY($1::integer[])`), the `flag*` mask casts (`::smallint` / `::bigint`),
`agg.arrayAgg()` of an int8 / numeric column in a JSON projection (`to_json(CAST(array_agg(…) AS text[]))`),
`arrayContains()` and `unnest()` of a joined array column. In a QueryBatch, a joined column of a type JSON cannot carry
as the driver delivers it (an int8 / numeric, a date / timestamp, bytea) is sent as its text and parsed by the client,
as it reads standalone (see below).

#### A batched value read otherwise than the same query standalone — and by the DEFAULT drivers' rules

QueryBatch sends each query's rows as JSON, which bypasses the driver's type parsing. 1.0.10 restored a value only by
the DECLARED type of a selected column, by the default drivers' rules. Every other value arrived in its JSON form: a
`dateTrunc()` day as an ISO string, a `castAsBigInt()` as a lossy JSON number, a bytea as `\x…` text — silently, and
only in the batch. A column of a CTE, a table subquery or a set was looked up by its NAME on the query's own table (a
CTE text column named like a timestamp column came back an Invalid Date), or not at all.

A batched value is now the one THIS CLIENT delivers for the same query standalone, under its driver's configuration —
the driver's defaults or parsers of the application's own. The rule is the client's, not a guess at the driver: an
application whose postgres.js client reads `timestamp` / `timestamptz` / `date` as their text
(`types: { timestamp: { to: 1114, from: [1114], serialize: x => x, parse: x => x }, … }`) reads a batched collection
`max()` of a timestamp as that text, as standalone — restoring such a value by the DEFAULT drivers' rules would make
it a `Date`, which such an application's code does not expect (it formats the value as text).

Each value JSON cannot carry as the driver delivers it travels as its PostgreSQL TEXT — as the wire protocol sends it,
the type's output (`concat(value)`; a CAST to text differs for a boolean, an inet, a `char(n)`) — alongside the row,
with its type ONCE for the query (a domain as the type it is over: a domain over a type JSON carries, such as integer
or boolean, keeps its JSON value); the client parses the text as its driver parses a column of the type, through the
new `DatabaseClient.parseTypedText(oid, text, read?)`:

- `PostgresClient` — through the parser its postgres.js instance holds for the type (`sql.options.parsers`: the
  driver's defaults with the application's `types` over them; an array's as postgres.js calls it);
- `PgClient` — the pool's own `types.getTypeParser(oid, 'text')`, else node-postgres's `pg.types` (with any
  `pg.types.setTypeParser()` of the application);
- `PGliteClient` — the instance's `parsers` (PGlite's, the client's, the application's);
- `BunClient` — Bun exposes no parsers, so its decoding is reproduced: a boolean, an int2 / int4 / oid, a float, a
  json document as Bun reads them, an int8 as its text (a `BigInt` with `bigint: true`), a date at UTC midnight, a
  timestamp without a zone as a UTC wall time, ±infinity as ±Infinity, a date before Christ as an invalid Date, their
  arrays element by element; through its binary protocol — which Bun uses for a statement with parameters, unless
  `prepare: false` — a numeric zero loses its scale and a timestamp before Christ reads as that time
  (`read.parameterized`: whether the query binds parameters); `datesAsStrings` as the client makes it; verified value
  by value against Bun's own reads, in both modes;
- any other `DatabaseClient` — node-postgres's default rules, unless it overrides the method.

`DatabaseClient.customParsedTypeOids()` names the types a client parses with a parser of the application's own
(postgres.js `types`, a pool's `types` or `pg.types.setTypeParser()` over pg-types' defaults, PGlite `parsers`, with
their array types); the batch sends values of those types as their text too — an int4 parsed by the application's
parser reads through it in a batch.

The values sent as their text: those of `date`, `time`, `timetz`, `timestamp`, `timestamptz`, `interval`, `int8`,
`numeric`, `money`, `bytea`, `point`, `circle` and their arrays, of a user-defined type, and of every type the client
parses itself. Which values:

- a value only PostgreSQL knows the type of, by its runtime type (`pg_typeof`, tested row by row): an expression
  (`dateTrunc()` / `castAsDate()` / `castAsBigInt()` / `coalesce()` / `atTimeZone()` / `lower()` / `agg.arrayAgg()`, a
  raw `sql`, a CTE's expression column), an `agg.min` / `agg.max`, a mapped expression (`mapWith()`: its mapper gets
  the client's value), a scalar subquery (`asSubquery('scalar')`) of such a value, a collection's `.min()` / `.max()`,
  a UNION column whose legs declare different types — on the top level, in a nested object, as the one value of
  `select(r => …)`, in a UNION leg, under `selectDistinct()`;
- by the type it declares: a read-typed expression (`withReadType()`, also of a scalar subquery or a CTE's column), a
  column of a CTE, a table subquery, a set or a manually joined table, a declared column of a parameterised or aliased
  type (`bigserial`, `numeric(12,2)`, `timestamp(3)`, `timestamp with time zone`);
- a declared `bigint` / `numeric` / `decimal` column, always: the driver's exact text, as in 1.0.10, unless the client
  parses the type itself.

A plain select's declared `timestamp` / `timestamptz` / `date` / `bytea` column (of the query's table or a navigation)
is revived from its JSON form as in 1.0.10 — see Known limitations.

#### One envelope, evaluated once per row

A query with no value to send as its text is sent exactly as in 1.0.10, byte for byte:
`SELECT <ix> AS __batch_ix, coalesce(json_agg(row_to_json(__batch_q)), '[]'::json) AS __batch_items
FROM (…) __batch_q`. Every other query — whatever it sends as text — takes ONE envelope, over its query fenced by
`OFFSET 0`:

```sql
SELECT 2 AS __batch_ix,
       json_build_object('t', to_json(ARRAY[(SELECT (CASE WHEN __batch_t.typtype = 'd' THEN __batch_t.typbasetype
                                                          ELSE __batch_t.oid END)::bigint
                                             FROM pg_catalog.pg_type __batch_t WHERE __batch_t.oid = __batch_s.t0)]::bigint[]),
                         'r', __batch_s.r, 'x', __batch_s.x) AS __batch_items
FROM (SELECT coalesce(json_agg(row_to_json(__batch_q)), '[]'::json) AS r,
             json_agg(ARRAY[CASE WHEN (pg_typeof((__batch_q."day"))::oid = ANY('{1082,1083,…,719}'::oid[])
                                       OR pg_typeof((__batch_q."day"))::oid >= 16384)
                                 THEN concat((__batch_q."day")) END])
               FILTER (WHERE …the same test…) AS x,
             min(pg_typeof((__batch_q."day"))::oid) AS t0
      FROM (SELECT * FROM (…the query…) __batch_q0 OFFSET 0) __batch_q) __batch_s
```

The rows are `row_to_json`: a `json` value untouched (a `\u0000`, a lone surrogate) and every object's keys — a json
document's, a collection's items' — in their order. `x` holds each row's texts (NULL when no value of the query needs
one; a declared int8 / numeric column's text is sent unconditionally, `concat(…)`; a NULL value keeps its JSON null),
`t` the (base) type OID of each text-sent value, once. The `OFFSET 0` fence keeps PostgreSQL from inlining the query
into the envelope: inlined, it evaluated a runtime-typed expression at every reference the envelope makes to it — a
correlated subquery five times per row.

**SQL-text change (values unchanged):** a query with a declared int8 / numeric column was sent by 1.0.10 as
`coalesce(json_agg(to_jsonb(__batch_q) || jsonb_build_object('<col>', (__batch_q."<col>")::text)), '[]'::json)`;
it takes the envelope above now. Its int8 / numeric values are the same exact text (unless the client parses those
types itself). A `json` value or a collection in such a query no longer passes through `jsonb`: 1.0.10 returned its
object keys in `jsonb` order and failed the whole batch on a `\u0000` or a lone surrogate
(`unsupported Unicode escape sequence`).

Cost — PostgreSQL 18, node-postgres, `EXPLAIN ANALYZE` medians of 7:

| Query | standalone | 1.0.10 envelope | the envelope, not fenced | now (fenced) |
|---|---|---|---|---|
| 400 rows, a correlated scalar `max()` of a timestamp over 20 000 rows, no ORDER BY | 235.4 ms (400 subquery runs) | 237.9 ms (400) | 1 183.7 ms (5 × 400) | 244.0 ms (400) |
| the same, `LIMIT 1` of an int8 column | 4.9 ms | 5.0 ms | 24.7 ms | 5.3 ms |
| the same `max()`, ordered | 236.8 ms | 237.0 ms | 242.4 ms | 240.8 ms |
| 50 000 rows, one `lower()` | 6.4 ms | 20.3 ms | 34.0 ms | 26.8 ms |
| the same, ordered | 8.5 ms | 27.5 ms | 29.9 ms | 29.5 ms |

Per query the header costs about 50 bytes plus about 10 per text-sent value, and one catalog lookup per such value;
per row, a type test per runtime-typed value, and the texts that are needed.

#### A UNION column read by its first leg's type

A UNION was revived by its FIRST leg's declared types: a date in one leg and a timestamp in another came back an
Invalid Date on every row (PostgreSQL resolves the column to timestamp), an integer ∪ bigint column `9007199254740992`
instead of `'9007199254740993'`. A column whose legs declare different types is now runtime-typed — `pg_typeof`
reports the union's resolved type; a union whose legs agree is sent as before.

#### A value of a domain type

`pg_typeof` prints a domain's name, while the drivers read its value by the type it is over: a value of a domain over
date arrived as `'2024-03-01'` (a Date on its own), one over int8 as a lossy JSON number. The batch resolves the type
once per query (`pg_type.typbasetype`, one level) and the client parses the value by it.

#### A joined column's type taken from the reading context's registry

A batch typed a navigation's or a manually joined table's column by the READING context's schema registry, and by the
column's own ref only when the registry did not hold the table: a context that maps the same table otherwise (without
these columns) sent a joined date column as its ISO text. The ref's own type and mapper — which the standalone read
takes — are authoritative now; a table of another context joined in reads as standalone.

### Known limitations

Of the QueryBatch JSON transport — documented in the Querying guide:

- A plain select's **declared `timestamp` / `timestamptz` / `date` / `bytea` column** is revived from its JSON form as
  1.0.10 revived it — a `Date` by the DEFAULT drivers' rules, a `Buffer`; for a custom mapper the driver's text form —
  whatever the client's parsers. Pre-existing: a client with parsers of its own for these types (a text pass-through)
  reads such a column otherwise standalone; one whose driver parses timestamps into Dates hands a custom mapper a Date
  standalone. Read through an expression (``sql`${column}` ``), such a column is parsed as the client parses it.
- A **collection's list** (`toList()`, `toNumberList()`, a `withAggregation()` list) travels as the JSON the query
  builds for it; where the query itself reads a list as a native array, a date or timestamp element arrives as its ISO
  text and an int8 / numeric element as a JSON number.
- A **`withReadType()`** travels as the type it declares: a value declared as a type JSON carries (text, integer, …)
  that it does not have arrives as its JSON form.
- A **domain** over a domain is read by the type the outer domain is over (one level).

## Schema manager: INVALID indexes

`CREATE INDEX CONCURRENTLY` commits the new index before it builds it. When the build fails — a unique index over
duplicate rows, an index expression or predicate that raises for a row, a lock or statement timeout, a cancel —
PostgreSQL leaves the index behind INVALID (`pg_index.indisvalid = false`): it keeps its name, it is never used for
reads, and every later `CREATE INDEX … IF NOT EXISTS` skips it. `DbSchemaManager` read `pg_index` without looking at
`indisvalid` (`getExistingIndexes`), so such an index counted as present and correct: `analyze()` planned nothing,
`migrate()` never repaired it, and the application ran — silently — without the index its model declares (a unique
index that no longer rejected duplicates, a lookup index no plan used).

### Added

API — additive, but visible to typed callers:

- **`IndexRepairError`** — new root export. `failures: IndexRepairFailure[]` (each `indexName`, `tableName`, `schema`,
  `code` — SQLSTATE —, `cause` — the database error —, `reason`), and the first failure's `indexName`, `tableName`,
  `schema`, `code`, `cause` on the error itself. `migrate()` throws it after everything else has run.
- **`IndexRepairFailure`** — new type export.
- **`MigrationOperation` gains the `repair_index` variant** —
  `{ type: 'repair_index'; …index fields…; previousDef?: string }`, returned by `analyze()` for a model index present
  only INVALID. A `switch` over `MigrationOperation['type']` with a `never` exhaustiveness check stops compiling until
  it handles `'repair_index'`; one without such a check silently skips it.

### Fixed

#### An INVALID index is treated as missing

`getExistingIndexes` reads `indisvalid`, and `analyze()` plans a new operation for a model index that is present only
INVALID, `repair_index` — the model's definition plus `previousDef`, the INVALID index's `pg_get_indexdef`. The repair
runs whatever `recreateChangedIndexes` says (an INVALID index is missing, not changed) and builds the model's current
definition, so a definition that also changed needs nothing more:

- **concurrent** (the index is `.concurrent()`, or the manager runs with `concurrentIndexes: true`):
  `DROP INDEX CONCURRENTLY IF EXISTS` + `CREATE INDEX CONCURRENTLY IF NOT EXISTS` — neither blocks writes;
- **blocking** (neither): the model's index is built first, beside the INVALID one, under a temporary name
  (`<name>_lkgnew`, shortened by whole characters to fit 63 bytes), and swapped in only once built — `DROP INDEX` of
  the INVALID one and `ALTER INDEX … RENAME` in one transaction — with a
  `(blocking repair — enable concurrentIndexes or .concurrent() for non-blocking)` warning. The build blocks writes, as
  any `CREATE INDEX`; the swap holds an ACCESS EXCLUSIVE lock briefly.

```
📋 Found 1 operations to perform:
1. Repair INVALID index "uq_books_isbn" on "books" (build from the model as "uq_books_isbn_lkgnew", then swap it in)
```

```sql
-- before (1.0.10): no statement at all — the index stays INVALID
-- after, blocking
CREATE UNIQUE INDEX "uq_books_isbn_lkgnew" ON "books" ("isbn")
DROP INDEX IF EXISTS "uq_books_isbn"                            -- ┐ one transaction
ALTER INDEX "uq_books_isbn_lkgnew" RENAME TO "uq_books_isbn"    -- ┘
-- after, concurrent
DROP INDEX CONCURRENTLY IF EXISTS "uq_books_isbn"
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS "uq_books_isbn" ON "books" ("isbn")
```

#### A repair that fails never leaves the migration half done, and fails the same way every time

Repairs run last — a phase of their own, after every other operation (views re-created included) — each on its own.
Their failures are collected: `migrate()` runs its post-migration hook (`onMigrationComplete`), then throws ONE
`IndexRepairError` naming every index that could not be repaired and why (the database's message, DETAIL and HINT;
`failures` lists them, `code` is the first one's SQLSTATE, `cause` its error). A rebuild is never retried. What a
failed repair leaves:

- blocking: nothing new — a failed `CREATE INDEX` leaves nothing — so the INVALID index is as it was, and the next
  migration plans the same repair and throws the same `IndexRepairError`, never a raw `23505` from creating a dropped
  index anew.
- concurrent: the INVALID index was dropped, and the failed `CREATE INDEX CONCURRENTLY` left an INVALID index of its
  own under the name — not ready when the build itself failed, so the next migration repairs it again and throws the
  same `IndexRepairError`; ready when it failed while validating a unique index, so the next migration leaves it alone
  (below).
- a rebuild that leaves the index INVALID or missing (a drop that removed nothing makes the create's `IF NOT EXISTS`
  skip) is a failure too.

```
IndexRepairError: Could not repair INVALID index "uq_books_isbn" on "books": could not create unique index
"uq_books_isbn_lkgnew" — Key (isbn)=(978-0) is duplicated. Fix the cause and run the migration again.
```

#### Some INVALID indexes are left alone

With a warning naming the index and the remedy — at planning, and again right before each repair:

- **an index build is running on the table**: the index's own concurrent build, a `REINDEX INDEX CONCURRENTLY` of it
  (whose progress row names `<name>_ccnew`, never the INVALID index), any other build on the table — also one run by a
  role the migrating role cannot watch: `pg_stat_progress_create_index` then shows no table, and the locks the build's
  backend holds on the table (`pg_locks`, readable by every role) show it instead. Only builds in the current database
  count. Dropping the index would queue behind the build, lock the table out for readers and writers, and deadlock
  with it;
- **a partitioned index** (relkind `I`): INVALID by design while PostgreSQL's online procedure runs (`CREATE INDEX …
  ON ONLY`, each partition's index `CONCURRENTLY`, `ALTER INDEX … ATTACH PARTITION` one by one) — a repair would drop
  the whole tree being attached, or fail with `0A000` on every concurrent run. The warning names the partitions still
  without an attached valid index;
- **one a constraint requires** (`pg_constraint.conindid`): PostgreSQL refuses to drop it (`2BP01`, on every run). The
  remedy named: `REINDEX INDEX CONCURRENTLY`;
- **a unique one that is still ready** (`indisready`: a concurrent build that failed while validating, or was cancelled
  while waiting for older snapshots): it still rejects duplicates, which dropping it to rebuild would stop — one insert
  between a drop and the new build would admit a duplicate and make every later rebuild fail. The remedy named:
  `REINDEX INDEX CONCURRENTLY` (remove duplicate rows first if that fails). A non-unique INVALID index, and a unique
  one that is not ready, serve no read and enforce nothing, so they are repaired;
- **one that is no longer INVALID** by the time its repair runs (rebuilt by hand, validated) — and one dropped
  meanwhile is simply created.

```
⊘ INVALID index "uq_books_isbn" on "books" left alone: an index is being built on "books" (pg_stat_progress_create_index) — run the migration again once that build has finished.
⊘ INVALID unique index "uq_books_isbn" on "books" left alone: it is still ready (indisready), so it keeps rejecting duplicates, and dropping it to rebuild would stop that — rebuild it in place with REINDEX INDEX CONCURRENTLY "uq_books_isbn" (remove duplicate rows first if that fails).
```

#### The model index is validated before anything is dropped

For a repair and for `recreate_index`: one PostgreSQL cannot build (`INCLUDE` on a GIN index, a unique GIN index, an
unknown method) fails before the index is touched. `recreate_index` checked it only after its `DROP`, so an invalid
model index cost the existing one.

#### `MigrationScaffold` renders a repair safely for every database the file runs on

The up statements drop the index in a `DO` block only where the schema manager would repair it (INVALID, a plain index,
not required by a constraint, not a unique one still ready, no index build on its table), then create it if missing —
never `CONCURRENTLY`, not even for a `.concurrent()` index, as `MigrationRunner` runs a file in one transaction, where
a concurrent statement fails with `25001`. The down statement reverts nothing:

```sql
DO $lkg$ BEGIN IF EXISTS (SELECT 1 FROM pg_index x JOIN pg_class c ON c.oid = x.indexrelid WHERE x.indexrelid = to_regclass('"uq_books_isbn"') AND NOT x.indisvalid AND c.relkind = 'i' AND NOT (x.indisunique AND x.indisready) AND NOT EXISTS (…pg_constraint…) AND NOT EXISTS (…an index build on the table…)) THEN DROP INDEX "uq_books_isbn"; END IF; END $lkg$
CREATE UNIQUE INDEX IF NOT EXISTS "uq_books_isbn" ON "books" ("isbn")
-- down: -- Nothing to revert: INVALID index "uq_books_isbn" was rebuilt from the model
```

In the file's transaction the drop's ACCESS EXCLUSIVE lock — reads and writes wait — is held through the whole build,
until the file commits; a build that fails fails the file, which rolls the drop back.

#### The catalog reads return real arrays on every driver

`getExistingIndexes`' `column_names` and `getExistingForeignKeys`' `column_names` / `referenced_column_names` are
`string[]` as typed; on pg (and, for the index names, PGlite) they were the array literal text, `'{isbn}'`, because
`array_agg` over catalog identifiers is a `name[]` the pg driver does not parse. Both queries now aggregate with
`json_agg`.

### Behaviour changes

- `migrate()` now rebuilds an INVALID model index it used to ignore. On the blocking path (no `.concurrent()`, no
  `concurrentIndexes`) that is a `CREATE INDEX` that blocks writes to the table for the build, plus a brief ACCESS
  EXCLUSIVE lock for the swap — on the first deploy after upgrading, for every leftover INVALID model index
  (`SELECT indexrelid::regclass, indisready FROM pg_index WHERE NOT indisvalid` lists them). Where the rebuild fails,
  `migrate()` now ends with `IndexRepairError` — after doing everything else — where it used to "pass" by doing
  nothing; every later migration ends the same way until the cause is fixed.
- The INVALID indexes left alone (above) are never dropped: an index build on the table, a partitioned index, one a
  constraint requires, a unique one still ready. Each gets a warning at every `analyze()` / `migrate()` until it is
  valid.
- `ensureCreated()` is unchanged: it creates missing indexes by name and does not repair INVALID ones.
- The scaffolded repair's `DO` block holds an ACCESS EXCLUSIVE lock on the table — reads and writes wait — through the
  whole build, until the migration file commits (above).
- A model index PostgreSQL cannot build fails before anything is dropped, for `recreate_index` too (above).
- Prefer the concurrent form for expression and partial indexes: a **blocking** `CREATE INDEX` also indexes the row
  versions an older transaction in the same database can still see, so a row just fixed with an `UPDATE` can fail the
  rebuild again, with the same error, until those transactions end; a concurrent build reads only the live rows.
  (PostgreSQL behaviour, now visible through the repair; the in-memory engine builds over its own snapshot's rows, so
  there the same repair succeeds.)
- Index `column_names` (and the foreign keys' `column_names` / `referenced_column_names`) are real `string[]` on every
  driver, as their types always said (above). Internal reads only; nothing in the library consumed the array values.

## In-memory engine

### Fixed

#### A failed `CREATE INDEX CONCURRENTLY` leaves an INVALID index, as PostgreSQL does

It used to leave nothing, so a reconcile against the engine could not meet an INVALID index at all. The engine now puts
the failed index into the database's catalog once the statement's transaction has aborted, with `indisvalid` and
`indisready` false: not used for reads (EXPLAIN), not maintained or unique-checked on writes, skipped by
`CREATE INDEX … IF NOT EXISTS`. A statement that fails before the index exists (an unknown column, a missing operator
class) still leaves nothing. With it:

- index builds evaluate every index expression and the predicate over the table's own rows (the predicate first, so a
  row it excludes never evaluates the expressions): `CREATE INDEX … ((100 / n))` over a row with `n = 0` fails with
  `22012` as on PostgreSQL — it used to succeed — and leaves an INVALID index when it was CONCURRENTLY. An INHERITS
  child's rows are not read (they are not in the index), for a unique index too (it used to refuse a parent's unique
  index over a key its child repeats). An expression the engine cannot evaluate (a function it does not implement, such
  as `to_tsvector`) is not evaluated for a non-unique index, which builds as before — a full-text GIN index, also
  `.concurrent()` through the schema manager, ends valid;
- `pg_stat_progress_create_index` is an explicit, always empty view: a build runs within its statement.

#### `UPDATE pg_index SET indisvalid = …, indisready = …` works, as for a PostgreSQL superuser

It was refused (`42501`), so an INVALID-but-ready index — the state a superuser stages, and the one the repair's tests
stage — could not be produced in memory at all. The write changes the state of the index each selected row describes,
with PostgreSQL's meaning: `indisvalid = false` keeps reads off the index (and it is no longer an `ON CONFLICT`
arbiter), `indisready = false` stops writes maintaining it, so a unique index stops rejecting duplicates — the engine
now enforces a unique index by `indisready` (it went by `indisvalid`), which is what keeps an INVALID-but-ready unique
index enforcing, as on PostgreSQL. Either flag or both, a row assignment `SET (indisvalid, indisready) = (…)`, any
`WHERE` / `FROM` / `RETURNING`, a data-modifying `WITH`: each index row is written once. The write is transactional (a
`ROLLBACK` restores the flags), refused in a read-only transaction (`25006 cannot execute UPDATE in a read-only
transaction`), and a NULL or `DEFAULT` flag violates the column's NOT NULL (`23502`). Every other catalog write is
still refused with `42501 permission denied for table …`.

#### `DROP INDEX CONCURRENTLY` is refused where PostgreSQL refuses it

Only an explicit transaction block refused it; now also a multi-statement query string (`25001 … cannot run inside a
transaction block`) and a function or `DO` block (`25001 … cannot be executed from a function`) — both before any name
is looked up, so even `IF EXISTS` of a missing index is refused there — and, like PostgreSQL, several names
(`0A000 DROP INDEX CONCURRENTLY does not support dropping multiple objects`), `CASCADE`
(`0A000 … does not support CASCADE`) and a partitioned index (`0A000 cannot drop partitioned index "…" concurrently`).
All were executed before.

#### PostgreSQL's online procedure for a partitioned index

`CREATE INDEX … ON ONLY` a partitioned table with partitions created a valid index (`ONLY` was ignored); it is now
INVALID but ready, as on PostgreSQL. `ALTER INDEX … ATTACH PARTITION` was a syntax error; it attaches an index of one
of the partitions (`55000` for an index of another table, `42P17` when the definitions differ, attaching one already
attached changes nothing), and the partitioned index turns valid once every partition has an attached valid index. An
attached index cannot be dropped on its own (`2BP01`, with PostgreSQL's hint); dropping the partitioned index drops the
attached ones.

#### `lastval()` / `currval()` / `DISCARD` as PostgreSQL

The engine kept one "last value", set by `nextval()` AND `setval()`, never checked against the catalog and never reset.
It now keeps PostgreSQL's `last_used_seq`: `lastval()` reads the currval of the sequence the session's last `nextval()`
drew from, looked up when called — 55000 `lastval is not yet defined in this session` once that sequence is gone (DROP
SEQUENCE, DROP TABLE of its serial / identity owner, DROP … CASCADE of a column default, the session's own uncommitted
DROP — a ROLLBACK brings it back), also when a sequence drawn earlier still exists; `setval()` moves a sequence's
currval (and lastval when it is the last-used one) but never makes it the last-used one, so `setval()` alone never
defines `lastval()`; `DISCARD SEQUENCES` and `DISCARD ALL` forget every currval and the lastval. Probed against
PostgreSQL 18 over 20 scenarios; all agree.

### Behaviour changes

- **Stricter** — statements that used to succeed now fail with PostgreSQL's error:
  - an index build whose expression or predicate raises for an existing row of the table (`22012` and the like);
  - `CREATE INDEX CONCURRENTLY` in a multi-statement query string or from a function / `DO` block (`25001`), on a
    partitioned table (`0A000`);
  - `DROP INDEX CONCURRENTLY` in a multi-statement query string or from a function / `DO` block (`25001`), with
    several names, with `CASCADE`, on a partitioned index (`0A000`);
  - a failed `CREATE INDEX CONCURRENTLY` now leaves an INVALID index behind, whose name a later `CREATE INDEX` without
    `IF NOT EXISTS` meets (`42P07`) until it is dropped;
  - `CREATE INDEX … ON ONLY` a partitioned table with partitions creates an INVALID index; dropping an index attached
    to a partitioned index on its own is refused (`2BP01`);
  - `lastval()` fails with 55000 once its sequence is gone, and is never set by `setval()`.
- **More permissive** — `UPDATE pg_index` of `indisvalid` / `indisready` is executed (it was `42501`). Like every DDL
  statement it holds the database's DDL lock until its transaction ends. A `SET` of any other `pg_index` column — even
  one that does not exist, where PostgreSQL reports `42703` — stays `42501`. A unique index built on an INHERITS parent
  no longer checks its child's rows, and `ALTER INDEX … ATTACH PARTITION` is accepted.
- `DISCARD SEQUENCES` / `DISCARD ALL` reset `currval()` and `lastval()`.
- Index flags elsewhere: `TRUNCATE` makes a non-unique INVALID or not-ready index valid and ready again and leaves a
  unique one as it was (PostgreSQL's reindex without constraint checks). `REINDEX`, `VACUUM` and `CLUSTER` stay no-ops,
  so an INVALID index stays INVALID through them — in PostgreSQL plain `VACUUM` leaves it INVALID too, `REINDEX`
  rebuilds it valid, and `VACUUM FULL` / `CLUSTER` rebuild a non-unique one valid (a unique one stays INVALID, as after
  `TRUNCATE`). All listed in the in-memory guide.

## Test runner

### Behaviour changes

#### PostgreSQL runs use private worker databases, a one-file run too

`tests/run.ts` sized its PostgreSQL worker pool as `min(--pg-jobs, files)` and used worker databases only above 1: a
