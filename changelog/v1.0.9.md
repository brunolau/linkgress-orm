# v1.0.9

This release closes the gaps that forced hand-written `sql` templates: aggregates as expressions (`agg.*` with
`FILTER` / `DISTINCT` / `ORDER BY`), explicit-alias correlated subqueries (`db.<table>.as(alias)`), set-returning
functions (`unnest`, `jsonbArrayElements`, …) as projection values, row sources and lateral joins, statement-level
CTEs read by name from any nested subquery (including data-modifying CTEs), typed row guards and conflict-arbiter
predicates, `RETURNING old`, `INSERT … SELECT`, runtime-named sequences, index expressions written with the same
builders a query uses, and a set of small helpers (`param`, `literalOf`, `concatStrict`, `modulo`,
`jsonbValueText`, the `json` builders, `eqAnySubquery`, `Subquery.asExpression()`, `SqlFragment.withReadType()`).

It also fixes several long-standing defects found on the way — among them prepared statements that sent every
non-placeholder value as NULL, `and()` / chained `.where()` losing the grouping of a raw `sql` operand, a nested
`.with()` subquery or UNION binding its CTE body to the statement's parameters, VALUES casts that truncated
`char(n)` values, and advisory-lock keys that silently locked a different key.

## Upgrade notes

Read the **Behaviour changes** of each section below before upgrading. In short:

- SQL TEXT changes (same results): raw `sql` operands of `and()` / `or()` / chained `.where()` gain their own
  parentheses; expression-keyed grouped queries qualify their keys (`"q1"."key"`); `advisoryXactLockAll` orders
  by ordinality; nested subqueries read statement-level CTEs by name instead of re-declaring them; every
  expression helper that rendered a bare operator expression gains parentheses of its own — the JSON paths,
  `jsonbMerge`, `eqAny` / `neAll` (and the `= ANY` / `<> ALL` form of `inArrayOpt` / `notInArrayOpt`), the
  `flagHas*` and `normalized*` predicates, `notExists`, `eqAnySubquery` / `neAllSubquery`,
  `AliasedScope.notExists()` (`WHERE (NOT EXISTS (…))`, `("id" = ANY($1::integer[]))`). Tests that pin exact SQL
  text may need updating.
- RESULTS that change: compositions of those helpers that PostgreSQL read differently from the builder calls
  (see "Helpers that rendered an operator expression without parentheses of their own" — e.g.
  `jsonbRemoveKey(jsonbMerge(t, p), 'k')` kept `t`'s key); compositions that failed now evaluate.
- READS: a projected `searchNormalize()` reads text; `agg.min` / `agg.max` of a numeric column read numbers; a
  projected subquery reading one of two navigation paths that end in the same relation name reads its own path
  (it read the query's join of that name, silently) — every alias the query's own paths render under, which raw
  `sql` may name, stays what it was.
- REFUSALS that used to produce invalid SQL or wrong data now throw with a clear message (subquery / collection
  operands in comparisons, `exists()` over a query builder, advisory-lock keys that are not integers or strings,
  a data-modifying CTE declared inside a nested subquery or read by a temp-table collection, a CTE different by
  content under a name the statement already declares, a UNION leg correlated to the enclosing query's own
  table, a set-returning function outside a projection value or a row source).
- The in-memory engine now infers ON CONFLICT arbiters from the conflict WHERE (42P10 when it does not imply a
  partial unique index's predicate) — stricter than before, and in a few documented spellings stricter than
  PostgreSQL.
- The in-memory engine rejects a chain of two non-associative operators (`a = b = c`, `a LIKE b IN (…)`,
  `a BETWEEN x AND y BETWEEN …`, `a IS DISTINCT FROM b IS NULL`) with PostgreSQL's 42601 syntax error — it used
  to evaluate them left to right, so a statement could pass in memory and fail on the server.

## Expression helpers, aggregates, subquery values and fragment reads

### Added

#### `param(value, pgType?)` — an always-bound parameter as an expression

`param(v)` renders `$n`, `param(v, 'integer')` renders `CAST($n AS integer)`. It ALWAYS binds exactly one
parameter — `null` / `undefined` bind as NULL — and never inlines, so the statement text does not depend on the
value. Inside `eq()` it is compared, never rewritten into `IS NULL` (`eq(col, param(null, 'integer'))` →
`col = CAST($1 AS integer)`, no row matches). Usable as a comparison operand, a JSON path key
(`jsonbPathText(col, param(lang))` → `(col->>$1)`, no cast), a CASE arm, a function argument, a boolean operand of
`and()` / `or()`. The value binds as given (no column `toDriver`); a JS array binds as one array literal and needs
an array type; a JSON document or a column / expression is refused. The type name is validated like `cast()`'s.
Reads back as the driver value.

#### `literalOf<T>(value, pgType?)` — a literal typed as the declared union

Renders and reads exactly like `literal()`; only the TypeScript type differs: `literalOf<'a' | 'b'>('a')` is a
`SqlFragment<'a' | 'b'>` (a value outside `T` is a compile error), so UNION legs share one declared union type.
`literal()` is unchanged.

#### `concatStrict(...values)` — NULL-propagating `||`

`(v1 || v2 || …)`, at least two operands. Columns / fragments as they are (a navigation's column joins it),
`literal(' ')` inline, a plain value bound as text (`CAST($n AS text)`), `null` / `undefined` as
`CAST(NULL AS text)`. NULL when ANY operand is NULL; reads the text as delivered (a digits-only result stays a
string). `concat()` is unchanged (NULL counts as `''`).

#### `modulo(dividend, divisor)` — the `%` operator

`(<a> % <b>)` — the OpExpr an expression index written with `%` is matched by (`mod()` renders the function call,
which such an index never serves). Plain operands typed like `mod()`'s; reads a JS number; a value compared with
it binds unchanged (the mapper has no `toDriver`). `mod()` is unchanged.

#### `substring(value, pattern)` — the regex overload

A TypeScript overload of the existing runtime: `substring(v, literal('^([0-9]+)-'))` renders
`substring(<v>, '^([0-9]+)-')` (function-call syntax — never `SUBSTRING(… FROM …)` nor `regexp_substr`), typed
`SqlFragment<string | null>`.

#### `jsonbValueText(target)` — the whole jsonb value as text

`(<target> #>> '{}')`: a JSON string unquoted, a number / boolean as its text, an object / array as its JSON text,
SQL NULL and JSON `null` as NULL. Reads as the driver value.

#### `jsonBuildObject(entries)` / `jsonBuildArray(...values)` — the `json` builders

The `json` twins of `jsonbBuildObject` / `jsonbBuildArray` with identical operand rules (keys quoted, columns and
fragments inline, plain values typed binds, conditions as booleans, nested plain objects / arrays recursing into
`json_build_object` / `json_build_array`). `json` keeps the written key order. The jsonb builders render
byte-identically.

#### `agg` — aggregates as expressions, with `FILTER`, `DISTINCT` and `ORDER BY`

```ts
agg.count()                    // count(*)
agg.count(x) / agg.countDistinct(x)   // count(x) / count(DISTINCT x)
agg.sum(x, { distinct? }) / agg.avg(x, { distinct? })
agg.min(x) / agg.max(x) / agg.bitOr(x) / agg.bitAnd(x)
agg.arrayAgg(x, { distinct?, orderBy? }) / agg.jsonAgg(…) / agg.jsonbAgg(…)
agg.count().filter(condition)  // count(*) FILTER (WHERE condition)
```

`AggregateFragment<T>` (exported) is an immutable `SqlFragment` with `.filter(condition)` (a second call ANDs; a
collection's `exists()` is a condition too). Lower-case function names; an ORDER BY key always carries its
direction (default `ASC`); a plain ORDER BY key is refused, and so is — with `distinct` — a key that binds a
parameter (it would render a second `$n`, which PostgreSQL rejects: inline its constants with `literal()`). A
select of aggregate fragments without `groupBy()` is a whole-set aggregate (one row, also over zero rows: COUNT 0,
every other aggregate NULL — `array_agg` / `json_agg` NULL, not `[]`; its `count()` is refused); inside
`asSubquery('scalar')` a correlated aggregate subquery, which reads like the aggregate; inside a grouped select
(plain `GROUP BY` and the subquery-wrapped form of an expression key alike) an aggregate per group over the keys
read through `g.key`. Reads: count / countDistinct / sum / avg / bitOr / bitAnd → JS numbers (NULL stays null);
min / max → like `g.min()` / `g.max()`: through the operand's mapper, a numeric / int8 operand as a JS number, else
the driver value; arrayAgg → elements through the operand's mapper (unmapped: the driver's native array decoding
— a numeric element is a number on node-postgres and in memory, a string on postgres.js, Bun and PGlite);
jsonAgg / jsonbAgg → the driver-parsed JSON.

On a driver without native array results (Bun's binary protocol) the `arrayAgg` the driver reads directly — the
projected value itself (through `.as()` / `.mapWith()` / `.withReadType()`) of a select, a nested object, a grouped
or CTE-rooted select, a UNION ALL leg, or of a projected `asSubquery('scalar')` of one — renders as JSON:
`json_agg(…)` with the same arguments, and for int8 / numeric / money elements
`to_json(CAST(array_agg(…) AS text[]))` (each element its exact text, in the aggregate's own DISTINCT / ORDER BY
order; a date / timestamp element then reads as its JSON text). Wherever SQL consumes the list — a function
argument, an operand, a `coalesce` / CASE, a WHERE, a HAVING, a CTE body, a joined table subquery, a UNION /
INTERSECT / EXCEPT leg — it stays `array_agg`. Always-array defaults: `coalesce(agg.jsonAgg(x), literal('[]',
'json'))`, `coalesce(agg.arrayAgg(x), literal('{}', 'integer[]'))`.

#### `eqAnySubquery(field, subquery)` / `neAllSubquery(field, subquery)`

`(<field> = ANY (ARRAY(<subquery sql>)))` / `(<field> <> ALL (ARRAY(<subquery sql>)))` — membership in a one-column
subquery as one array (an InitPlan), not an `IN (SELECT …)` semi-join. Binds only the subquery's parameters;
reports the field's refs and the subquery's outer refs. NULL field → NULL; empty result → FALSE / TRUE.

#### `Subquery.asExpression<T>()` — a scalar subquery as a fragment

`(<subquery sql>)` as a first-class `SqlFragment`, usable in `coalesce`, `caseWhen`, `isNull`, `eq`, arithmetic,
UPDATE SET values and projections; reports the subquery's outer refs; carries NO mapper (reads like a raw
fragment — chain `.withReadType()` / `.mapWith()`). An `'array'` / `'table'` subquery is refused.

#### `SqlFragment.withReadType(pgType)` — read a fragment like a column of a type

No SQL change; the projection reads the value like a column of `pgType`: numeric-text coercion only for numeric
types, NULL → `undefined` at the top level and `null` inside nested objects, collection items as delivered. The
fragment's mapper is dropped (a later `.mapWith()` wins). Kept by `.as()`, `selectDistinct`, UNION legs, QueryBatch
parts, grouped selects (NULL stays `null` there, as for every grouped field), CTE / table-subquery columns (their
refs carry the read type as `__sqlType`), and a projected `asSubquery('scalar')` whose one value it is.
`getReadType()` exposes it.

#### A projected `asSubquery('scalar')` of ONE aggregate or read-typed fragment reads like it

`asSubquery('scalar')` records the read of the subquery's one projected value when that value is an aggregate
fragment (its mapper: `agg.max(text)` keeps `'007'`, `agg.max(mapped)` maps, NULL reads `null`) or a read-typed
fragment (its read type); the projection reads the subquery's value through it. Every other projected scalar
subquery reads as before — the generic conversion of a raw fragment (`'007'` → `7`); type such a value with
`.asExpression().withReadType()` / `.mapWith()`, or `AliasedScope.scalar()` for a scope's column.

#### `jsonbPathExists` — fragment path and fragment vars

`path` may be a fragment rendered verbatim (`literal(p, 'jsonpath')` → `CAST('<p>' AS jsonpath)` inline, no
parameter); `vars` may be a fragment rendered verbatim (`jsonbBuildObject({ d: expr })` — per-row SQL values).
A plain `vars` object holding columns or expressions is refused with a pointer to `jsonbBuildObject`. A string
path and plain vars keep today's rendering.

#### Comparison operators accept a scalar Subquery (types)

`eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `like`, `ilike`, `startsWith`, the regex operators, `isNull`, `isNotNull`,
`between`, `inArray`, `notInArray` accept a `Subquery<V, 'scalar'>` operand in their signatures (see Fixed for the
rendering). New type `ScalarSubqueryOperand<V>`.

### Fixed

#### `.as()` / `.mapWith()` on a fragment subclass kept nothing of it

A fragment subclass that renders its own way (`exists()`, `notExists()`, the bare condition of a CASE branch) was
rebuilt from its (empty) parts:

```sql
-- before: select(u => ({ id: u.id, x: exists(sub).as('x') }))
SELECT "users"."id" as "id", as "x" FROM "users"
-- after
SELECT "users"."id" as "id", EXISTS (SELECT 1 as "one" FROM "posts" WHERE "posts"."user_id" = "users"."id") as "x" FROM "users"
```

and its references were lost (a navigation read only there was not joined). The copy now wraps the subclass and
delegates to it. `sql.join([...])` had the same defect for subclass fragments and joins them as values now.

#### `searchNormalize()` read digits-only text back as a number

A projected `searchNormalize(x)` of `'01'` read as `1` (no result mapper → generic conversion). It now carries
the driver-value mapper: `'01'`, NULL → `null`.

#### A `Subquery` operand in comparisons rendered its object text or bound the object

```sql
-- before: isNull(subquery)            | eq(u.id, subquery)
WHERE "[object Object]" IS NULL        | WHERE "users"."id" = $1   -- params: [<Subquery>]
-- after
WHERE (SELECT "posts"."id" FROM "posts" WHERE "posts"."user_id" = $1) IS NULL
WHERE "users"."id" = (SELECT "posts"."id" FROM "posts" WHERE "posts"."user_id" = $1)
```

Either side, every comparison (`eq` … `lte`, `like`…, `isNull` / `isNotNull`, `between` bounds, `inArray` field);
the subquery's parameters number in textual order and its outer refs are reported (navigation joins). A collection
`count()` compared the same way used to render `"[object Object]" > $1` too; it renders its correlated count now.

#### `and()` / `or()` / chained `.where()` lost the grouping of a raw `sql` operand

A raw `sql` fragment holding a top-level OR, ANDed with another condition, was spliced in bare — AND binds
tighter than OR, so the statement filtered something else, silently:

```sql
-- db.users.where(u => sql`${u.age} > 40 OR ${u.age} < 30`).where(u => eq(u.isActive, true))
-- before: every user older than 40, active or not, and the active ones younger than 30
WHERE ("users"."age" > 40 OR "users"."age" < 30 AND "users"."is_active" = $1)
-- after
WHERE (("users"."age" > 40 OR "users"."age" < 30) AND "users"."is_active" = $1)
```

Every operand of `and()` / `or()` that is raw SQL — written with the `sql` tag or put together by `sql.join`,
and its `.as()` / `.mapWith()` / `.withReadType()` copies — now renders in parentheses of its own. The same
chaining in an aggregate's `.filter()` (`agg.count().filter(sql\`a OR b\`).filter(c)`) is fixed with it.
Comparisons, helper conditions and nested `and()` / `or()` render as before; `not()` already parenthesized
its operand.

#### Helpers that rendered an operator expression without parentheses of their own

A helper splices its operands into its own SQL as they render (`add(a, b)` is `(<a> + <b>)`, `eq(a, b)` is
`<a> = <b>`). Most helpers render ONE self-delimited expression — a call, a CAST, a CASE, a subquery or a
parenthesized group — but these rendered a bare operator form, so the operator a caller composed them with
could take part of them as its own operand:

| Helper | 1.0.8 / early 1.0.9 | now |
|---|---|---|
| `jsonbPath` / `jsonbPathText` | `t->'a'->>'b'` | `(t->'a'->>'b')` |
| `jsonbSelect` / `jsonbSelectText` | `(t #>> '{}')::jsonb->'k'` / `t->>'k'` | `((t #>> '{}')::jsonb->'k')` / `(t->>'k')` |
| a `jsonbArraySome` element path | `__elem->'a'->>'b'` | `(__elem->'a'->>'b')` |
| `jsonbMerge` | `COALESCE(t, '{}'::jsonb) \|\| (p)::jsonb` | `(COALESCE(t, '{}'::jsonb) \|\| (p)::jsonb)` |
| `eqAny` / `neAll` (and `inArrayOpt` / `notInArrayOpt` above the threshold) | `c = ANY($1::integer[])` | `(c = ANY($1::integer[]))` |
| `flagHas` / `flagHasAny` / `flagHasAll` / `flagHasNone` | `(c & $1::smallint) != 0` | `((c & $1::smallint) != 0)` |
| `normalizedEq` / `normalizedLike` / `normalizedStartsWith` | `search_normalize(a) = search_normalize(b)` | `(search_normalize(a) = search_normalize(b))` |
| `notExists` (subquery and collection) | `NOT EXISTS (…)` | `(NOT EXISTS (…))` |
| `eqAnySubquery` / `neAllSubquery` | `c = ANY (ARRAY(…))` | `(c = ANY (ARRAY(…)))` |
| `AliasedScope.notExists()` | `NOT EXISTS (SELECT 1 …)` | `(NOT EXISTS (SELECT 1 …))` |

What the bare forms did, evaluated on PostgreSQL 18 (the in-memory engine agreed, except where noted):

```sql
-- jsonbRemoveKey(jsonbMerge(t, p), 'k') — `-` binds tighter than `||`: the key of t SURVIVED (silent)
(COALESCE(t, '{}'::jsonb) || (p)::jsonb - CAST($1 AS text))          -- t || (p - 'k')
((COALESCE(t, '{}'::jsonb) || (p)::jsonb) - CAST($1 AS text))        -- now
-- concatStrict('x', jsonbMerge(t, p)) — the two documents' texts concatenated (silent): 'x{"a": 1}{"b": 2}'
-- sql`${jsonbMerge(t, p)}::text` — the cast bound to the patch (silent, same text as above)
-- sql`${jsonbPath(t, 'b')}::text` / sql`${jsonbPathText(t, 'n')}::int` — the cast bound to the KEY:
--   a jsonb object instead of its text (silent) / `invalid input syntax for type integer: "n"`
-- concatStrict(x, jsonbPathText(t, 'k')), startsWith(x, jsonbPathText(t, 'p')), regexMatches(x, …),
-- jsonbContains(x, jsonbPath(t, 'b')), jsonbPathText(t, jsonbPathText(u, 'key')), a `concatStrict` /
-- `startsWith` / `~` over a jsonbArraySome element path — the right operand of a same-level operator:
x || t->>'k'                                                          -- (x || t)->>'k': operator does not exist: text ->> unknown
-- jsonbRemoveKey(jsonbPath(t, 'a'), 'k') — t->('a' - 'k'): invalid input syntax for type json
-- isNull(notExists(s)) / isNotNull(…) — always the opposite (silent)
NOT EXISTS (…) IS NULL                                                -- NOT (EXISTS (…) IS NULL): TRUE
-- isDistinctFrom(notExists(s), flag) — wrong for every NULL flag (silent); the same for
-- isNotDistinctFrom, gt / gte / lt / lte, between, inArray, arrayContains, eqAnySubquery over notExists()
(NOT EXISTS (…) IS DISTINCT FROM "t"."flag")                          -- NOT (EXISTS (…) IS DISTINCT FROM flag)
-- eq(flag, eqAny(c, ids)) / eq(flag, flagHas(c, 1)) / eq(flagHas(c, 1), flag) / eq(normalizedEq(…), flag),
-- between / inArray over flagHas(…) / normalized*(…): syntax errors or type errors (in memory some of them
-- evaluated — see the in-memory engine entry below)
"t"."flag" = "t"."c" = ANY($1::integer[])                             -- syntax error at or near "="
-- concatStrict('x', normalizedEq(a, b)) — ('x' || sn(a)) = sn(b): a boolean instead of 'xtrue' (silent)
```

Every helper now renders ONE self-delimited expression (the parentheses change no parse tree: an index,
a partial-index predicate or an ON CONFLICT arbiter written with the same helpers matches as before, and an
index expression built with `withExpression` renders the same DDL). New test
`tests/queries/operator-precedence-composition.test.ts`: every such helper × every operator context it can
reach with a meaningful type, each value checked against a JS computation (686 cases), and a structural check
that every builder of the public surface renders self-delimited.

#### In-memory engine: non-associative operator chains were evaluated

gram.y declares the comparisons, `BETWEEN IN LIKE ILIKE SIMILAR` and `IS` `%nonassoc`: `a = b = c`,
`a LIKE b IN (…)`, `a BETWEEN x AND y BETWEEN …`, `a IS DISTINCT FROM b IS NULL` are syntax errors (42601) on
PostgreSQL. The in-memory parser evaluated them left to right — `SELECT 1 = 1 = true` returned `true`,
`eq(flagHas(c, 1), flag)` passed in memory and failed on the server. It now raises PostgreSQL's error at the
same token (`syntax error at or near "="`, same position); a rule that closes with a token of its own still
chains (`a = ANY (…) = b`, `a IN (…) IN (…)`, `a IS NULL IS NULL`). New `sql-parity-corpus` case "operator
precedence and associativity" (36 statements: the chains, and the bare / parenthesized helper spellings above).

#### Prepared statements sent every value that is not a placeholder as NULL

`PreparedQuery.execute()` built its parameter array as `new Array(paramCount).fill(null)` and filled only the
placeholder slots: a literal operand, a `param()` or a CTE parameter of a prepared query reached the server as
NULL — `db.users.where(u => and(eq(u.isActive, true), gt(u.age, sql.placeholder('minAge')))).prepare('q')`
matched no row (`"is_active" = NULL`). The prepared query now binds every value the build bound, the
placeholders filling only their own slots.

#### `exists()` / `notExists()` over a query builder started a stray query

`notExists(db.orders.where(...))` called the builder's own `.exists()` — starting a standalone query — and then
failed with `this.resolved.getFieldRefs is not a function`. A table, a select builder or anything else that is not
a subquery or a collection navigation is now refused BEFORE anything is called, with a message pointing at
`.select(...).asSubquery()`.

### Behaviour changes

- `searchNormalize(x)` projected: a digits-only value reads as the string (was a number), a top-level NULL reads
  `null` (was `undefined`); as an operand of `coalesce` / arithmetic / CASE it now contributes the driver-value
  mapper to the result (digits-only text stays text there too). In WHERE / ORDER BY nothing changes.
- `isNull(subquery)` / `isNotNull(subquery)` / `eq(x, subquery)` and the other comparisons: see Fixed — the
  statements they produced were invalid (or compared with a bound object), so no working query changes.
- `gt(collection.count(), n)` and other comparisons with a collection COUNT / EXISTS operand render the correlated
  subquery instead of `"[object Object]"`; a collection MIN / MAX / SUM operand now throws CollectionQueryBuilder's
  "only supported for EXISTS and COUNT" error instead of rendering invalid SQL.
- `exists(builder)` / `notExists(builder)` with a table or a select builder throws a `TypeError` up front (was a
  stray query plus a `TypeError`). A Subquery and a collection navigation (any object whose synchronous
  `exists()` returns a fragment) are accepted as before.
- `.as()` / `.mapWith()` on a CASE expression (a fragment subclass) now return a wrapper that renders the same
  SQL; `jsonbPathExists` with a PLAIN `vars` object holding a column / expression throws (it used to serialize the
  column objects into the JSON). A non-plain `vars` — a fragment, a jsonb column, a placeholder, `sql.raw(…)` — is
  the operand, rendered as it stands, as before.
- SQL text: a raw `sql` operand of `and()` / `or()` — also through chained `.where()` calls, a collection's
  `.where()` chaining and a CTE-rooted query's several `where()` conditions — renders in parentheses:
  `(a OR b AND c)` → `((a OR b) AND c)`, and `and(sql\`x\`, eq(…))` → `((x) AND "t"."c" = $1)`. A lone raw
  operand of `and()` is parenthesized too (`and(sql\`a OR b\`)` → `(a OR b)`), so it keeps its grouping when that
  `and()` is itself an operand. Statement texts (and a statement cache keyed on them) change; results change only
  where the old text had a top-level OR spliced into an AND (see Fixed).
- A prepared query binds its literal / `param()` / CTE values (they were NULL — see Fixed).
- Projected values build their fragments with the enclosing query's `useJsonArrayAggregation`: a subquery nested
  in a projected value (in a `select`, a UNION leg, a nested object) now renders its collections the way the
  enclosing query does, where it used to fall back to its own client's capability. Same value for an ordinary
  query; for a model-managed view (built with `useJsonArrayAggregation: false`) on a Bun client, a collection
  list inside a subquery of a projected value renders `array_agg` now instead of `json_agg` — the right, driver-
  independent text, but it shows up as a view definition diff on Bun deployments. `agg.arrayAgg` does not read
  this flag (see the `agg` entry: only the value the driver reads directly renders as JSON).
- SQL text: the JSON paths (`jsonbPath`, `jsonbPathText`, `jsonbSelect`, `jsonbSelectText`, a `jsonbArraySome`
  element path), `jsonbMerge`, `eqAny` / `neAll` (so the array form of `inArrayOpt` / `notInArrayOpt` and of
  `inArray` / `notInArray` under `inArrayUsesOpt`), `flagHas` / `flagHasAll` / `flagHasAny` / `flagHasNone`,
  `normalizedEq` / `normalizedLike` / `normalizedStartsWith`, `notExists`, `eqAnySubquery` / `neAllSubquery` and
  `AliasedScope.notExists()` render in parentheses of their own (see Fixed). Statement texts (and a statement cache
  keyed on them) change; a text match on `WHERE NOT EXISTS (` or `"c" = ANY(` must be updated. Results change
  only where a composition used to re-associate (see Fixed); PostgreSQL builds the same parse tree for a
  parenthesized helper, so plans and index matching are unchanged.
- In-memory engine: a chain of two non-associative operators is a syntax error, as on PostgreSQL (see Fixed).

## Mutations: row guards, conflict targets, RETURNING old, INSERT … SELECT, sequences, advisory locks, index expressions

### Added

#### Typed `rowGuard` on `MutationBatch.addInsertBulk`

`rowGuard` takes a typed condition over the candidate row `v` besides raw SQL:
`rowGuard?: string | ((v: ColumnRow<TEntity>) => Condition)`, and `addInsertBulk` infers `TEntity` from the
table (`addInsertBulk<TEntity>(table: DbEntityTable<TEntity> | …, rows, id, options?: InsertLegOptions<TEntity>)`).
The leg keeps the guarded shape; `v.<prop>` renders `"v"."<column>"`, and the guard's parameters continue the
VALUES cells' numbering, so the batch's whole-leg renumbering keeps them right:

```sql
INSERT INTO "posts" ("title", "content", "user_id", "views", "publish_time")
SELECT v."title", v."content", v."user_id", v."views", v."publish_time" FROM (VALUES ($1::varchar, …, $5::smallint), ($6::varchar, …, $10::smallint)) AS v("title", "content", "user_id", "views", "publish_time")
WHERE ("v"."views" > $11 AND "v"."title" != $12)
```

A guard may correlate subqueries to `v` (`notExists(db.x.where(x => eq(x.ownerId, v.ownerId)).select(…).asSubquery())`).
Every `v.<prop>` it reads must be a column some row provides — else
`MutationBatch: leg "<id>" rowGuard reads v.<prop>, but no row provides "<prop>"`; a navigation of `v` throws. The
blank / bare-`$N` checks stay on the string form; `rowGuard` + `onConflictDoNothing` / `overridingSystemValue` still
throws.

#### Typed `targetWhere` for upserts (partial unique indexes)

`EntityUpsertConfig.targetWhere`, the fluent `values(…).onConflict(…).targetWhere(…)` (now also on
`EntityInsertBuilder`) and `MutationBatch`'s `UpsertLegConfig.targetWhere` (new — the leg had no arbiter predicate)
take `string | ((row: ColumnRow<TEntity>) => Condition)`. The typed predicate renders the row's columns UNQUALIFIED
and bind-free:

```sql
… ON CONFLICT ("owner_ref", "slot") WHERE "is_current" = TRUE DO NOTHING
… ON CONFLICT ("provider", "subject") WHERE ("active" = TRUE AND "subject" IS NOT NULL) DO UPDATE SET …
```

A predicate that binds a value or reaches a placeholder throws `upsert targetWhere: the conflict-arbiter predicate
must not bind parameters — PostgreSQL infers the partial unique index from it at plan time; write constants with
literal()` (a bound `$n` breaks arbiter inference in a generic plan: 42P10). Navigations throw. The string form is
unchanged.

#### `RETURNING old` (PostgreSQL 18)

`where(…).update(…).returning((row, old) => …)` and `where(…).delete().returning((row, old) => …)` (also
`db.table.update(…)` / `db.table.delete()`): `old` is the table's own columns before the mutation (the deleted row
of a DELETE), typed `ColumnRow<TEntity>`, rendered `old."<column>"` — unqualified by the table even when the UPDATE
has a `FROM` — and read through the column's own mapper:

```sql
UPDATE "ro_tasks" SET "status" = $1 WHERE "ro_tasks"."id" = $2 RETURNING "id" AS "id", "status" AS "status", old."status" AS "oldStatus"
```

`old` works inside expressions (`ne(row.status, old.status)` → `("status" != old."status")`) and as a selector's
single value. A navigation of `old` throws; `old` next to navigations / collections / nested objects (the
navigation RETURNING, a CTE) throws a clear error. (`toStatement()` renders `old` too at run time; its selector's
declared type still takes one argument.)

#### `insertFrom` — `INSERT … SELECT`

`DbEntityTable.insertFrom(source, map, { where?, expectedErrorCodes? })` → `FluentInsertMany<TEntity>`:

```sql
INSERT INTO "if_badges" ("badge_number", "holder_id", "tier", "active")
SELECT "src"."nextNumber", CAST($6 AS integer), CAST($7 AS smallint), CAST($8 AS boolean)
FROM (SELECT (COALESCE(MAX("if_badges"."badge_number"), $4) + $5) as "nextNumber" FROM "if_badges" WHERE …) AS "src"
WHERE "src"."nextNumber" <= $9
RETURNING "id" AS "id", "badge_number" AS "badgeNumber", "tier" AS "tier"
```

Columns in `map` key order; a `src` ref renders `"src"."<key>"`, a fragment inline, a plain value binds through
the column's `toDriver` mapper and is CAST to the column's type (`null` → `CAST(NULL AS <type>)`, `undefined` leaves
the column out). Parameters: source, SELECT list, `where`. Zero source rows / a false `where` insert nothing (`[]`
from `.returning()`). Runs on the context's executor (inside its transaction). New types `InsertFromSourceRow`,
`InsertFromValues`, `InsertFromOptions`.

#### Expected SQLSTATEs — a per-statement executor option

`StatementExecutionOptions.expectedErrorCodes` (the executor's per-call options, exported): a failure whose SQLSTATE
is listed is still thrown but not reported by the failed-query logger (`logFailedQueries`); any other failure is
reported as before. `insertFrom` exposes it; other builders can later. SQLSTATEs are read from `code`, or Bun's
`errno`.

#### Runtime-named sequences

`DbContext.runtimeSequence(config): DbSequence` and `DbSequence.nextValueCreatingIfMissing(): Promise<number>`:

```sql
SELECT nextval($1::regclass) as value                               -- $1 = '"seq_doc_00001_2026"'
CREATE SEQUENCE IF NOT EXISTS "seq_doc_00001_2026" START WITH 1 INCREMENT BY 1 MINVALUE 1 CACHE 1   -- on 42P01 only
SELECT nextval($1::regclass) as value
```

Not registered (the schema manager never touches it), not cached, bound to the ROOT client even on a transaction's
context (a CREATE survives the caller's rollback), unlogged. A CREATE that loses a concurrent first use is
swallowed — PostgreSQL reports it as 23505 (the winner's catalog row still uncommitted) or 42P07 (the winner
committed between the loser's `IF NOT EXISTS` check and its insert; on PostgreSQL 18, 1.5–3 % of 10-way concurrent
first uses hit it), and
42710 is treated alike — any other error propagates; the second `nextval` is not retried. The name is quoted (`"`
doubled, NUL refused), schema-qualified when set; each option must be an integer within bigint — a number (also
above 2^53) or a JS `bigint` (`SequenceConfig` / `SequenceBuilder` options now take `number | bigint`). The schema
manager renders its `CREATE SEQUENCE` through the same renderer.

Called on a TRANSACTION's context, the root-client binding costs a second pool connection per call (concurrent
transactions that each wait for one can exhaust the pool — `pg.Pool` has no connection timeout by default), and
PGlite, which has one session, refuses the call at once. Both are documented in the schema-configuration guide:
draw on the root context, outside `transaction()`.

#### Index / statistics expressions from builders

`IndexBuilder.withExpression(...expressions: Array<string | ((e: ColumnRow<TEntity>) => SqlFragment | Condition)>)`,
and the same on `StatisticsBuilder.withExpression` (type `IndexExpression<TEntity>`). The builder gets UNQUALIFIED
refs carrying `__sqlType` / `__mapper`, renders with a fresh context, refuses any bound parameter / placeholder
(`Index "<name>": index expression binds a parameter — inline constants with literal()`), and keeps the text verbatim
when it is ONE function call or ONE parenthesised group, else wraps it in `( … )` (quote-aware paren scan). A
top-level `CAST(…)` counts as no call — PostgreSQL's `looks_like_function` is false for a cast, so it prints the
element as `((code)::text)`:

```sql
CREATE INDEX "ix_ixb_suffix7" ON "public"."ixb_items" (("n" % CAST(10000000 AS bigint)))
CREATE INDEX "ix_ixb_digits" ON "public"."ixb_items" (regexp_replace("code", '[^0-9]', '', 'g'))
CREATE INDEX "ix_ixb_code_text" ON "public"."ixb_items" ((CAST("code" AS text)))
```

### Fixed

- **Advisory lock keys** — the overload of `advisoryXactLock` / `tryAdvisoryXactLock` follows the number of
  arguments passed. `(classId, null)` locked key 0 (`Number(null)`), `(classId, undefined)` took the one-key overload
  and locked `CAST(classId AS bigint)`, `(classId, true)` locked key 1: all now throw
  `<method>: the key of a key pair must be an integer or a string, got <value>`.
- **In-memory engine: ON CONFLICT arbiter inference** — the arbiter `WHERE` was never analysed: any predicate
  (`WHERE active = false`, `WHERE true`, an unknown column, another table's column) made a partial unique index
  the arbiter. It is now analysed against the target table as an index predicate (42703 / 42P01, 42883 for an
  unknown function or operator, 22P02 for a literal its operand's type cannot read — `WHERE k = 'abc'` for an
  integer `k` —, no subqueries, aggregates, window or set-returning functions, with PostgreSQL's messages and
  positions), and a partial index is
  an arbiter only when the WHERE implies its predicate — else 42P10. Both sides are normalised as the planner's
  `eval_const_expressions` does before they are compared: casts of constants folded (`CAST(1 AS smallint)`,
  `'x'::varchar`, so the typed `literal(v, pgType)` works), `x = true` ≡ `x`, NOT pushed down (`NOT (a = b)` →
  `a <> b`, `NOT (x IS NULL)` → `x IS NOT NULL`, `NOT NOT x` → `x`, De Morgan), `x IS DISTINCT FROM NULL` →
  `x IS NOT NULL`, a constant on the left commuted to the right (`1 = x` → `x = 1`); coercion forms are ignored
  (`x::text` ≡ an implicit cast). A predicate conjunct is then implied by an equal WHERE conjunct, by the same
  comparison with an int2 / int4 / int8 constant of equal value (`st = 1::bigint` for `st = 1`), or — `x IS NOT
  NULL` — by any clause strict in `x`, through strict operators and functions, relabels, COLLATE and
  ScalarArrayOp (`lower(x) = 'a'`, `x IN ('a', 'b')`), as predtest.c's `clause_is_strict_for`. An IN list, `= ANY(…)`
  or `op ALL(…)` over constants is the OR (`ANY`) or the AND (`ALL`) of its comparisons, as predtest.c takes a
  ScalarArrayOp apart: `x IN ('a', 'b')` is implied by the same values in any order, by a subset of them, by one of
  them (`x = 'a'`) and by a one-element array (`x = ANY(ARRAY['a'])`, `'{a}'::text[]`), `x = 'a'` by
  `x = ANY(ARRAY['a'])`, and `x NOT IN ('a', 'b')` by a superset of its values — also written as separate conjuncts
  (`x <> 'a' AND x <> 'b'`); int2 / int4 / int8 values compare by value. Of 175 probed spellings (before this fix:
  93 differed), memory and PostgreSQL 18 agreed on 158 before those IN-list forms were modelled; in the other 17
  memory answers 42P10 where the server infers the index (the limits under Behaviour changes) or, once, raises
  22003 folding an out-of-range cast — none is a false accept. A `$n` in the arbiter WHERE was not even counted as a
  parameter ("bind message supplies 4 parameters, but prepared statement requires 3"). New `sql-parity-corpus`
  cases "ON CONFLICT arbiter inference over partial unique indexes", "ON CONFLICT arbiter inference: normalised
  predicate spellings" (78 statements) and "ON CONFLICT arbiter inference: IN lists and = ANY / <> ALL over
  constants" (59 statements: 50 spellings, 22 of them refusals PostgreSQL makes too).
- **In-memory engine: a parenthesised subquery that only STARTS an operand** — `x = ANY((SELECT …)::integer[])`,
  `x <> ALL((SELECT …)::t[])`, `x LIKE ANY((SELECT …)::text[])`, `x IN ((SELECT 1)::int, 2)` and
  `UPDATE … SET (a, b) = ((SELECT 1), 2)` failed with `syntax error at or near "::"` (or `","`): the parser took the
  first `((SELECT` for a sublink's query. It now tries the query and, when the operand continues past it, parses
  the operand as an expression, as PostgreSQL's grammar does; `x = ANY ((SELECT …))` stays a sublink. A syntax
  error inside such an operand is reported where parsing stops — at the furthest token either reading reached, as
  PostgreSQL and 1.0.8 report it (`IN ((SELECT 1 FROM), 2)`: `syntax error at or near ")"`; the expression
  reading alone would stop at `"SELECT"`). New statements in the `sql-parity-corpus` case "subqueries".
- **Index normaliser** — `normalizeIndexFragment` folds `CAST(<expr> AS <type>)` (balanced-paren and quote aware) as
  it strips `::type`, so a builder-rendered `("n" % CAST(10000000 AS bigint))` compares equal to a stored
  `((n % 10000000::bigint))`. The fold keeps the grouping the CAST gives a compound argument, as PostgreSQL prints it
  (`get_coercion_expr`): an identifier, constant, quoted literal, single call or single group folds to `<expr>`,
  anything else to `(<expr>)`. So `(CAST(a + b AS bigint) * 2)` compares equal to the stored `((a + b)::bigint * 2)`
  and DIFFERENT from `(a + b * 2)`. An equality the fold produced is not final, though: the fold equally hides a cast
  the model ADDS (`(n % 10)` stored, `(n % CAST(10 AS bigint))` declared — a different index, which the new spelling's
  queries cannot use). `compareIndexDefinition` therefore reports it `needsConfirmation`, and the schema manager
  settles such an index on the mirror table (PostgreSQL's own canonical form), as it settled every CAST-spelled index
  before: an unchanged one is left alone, an added or moved cast is recreated.
- **`char(n)` / `bit(n)` values truncated by the cast of a bound value** (pre-existing for every VALUES builder,
  inherited by the new `insertFrom`) — the cast type was the column's bare type name, and `char` is `character(1)`
  (`bit` is `bit(1)`): an explicit cast to it truncates SILENTLY, so `'ABCDEF'` for a `char(6)` column was stored as
  `'A     '`. One helper now gives the cast type of `insertFrom`'s SELECT list, the cast-annotated VALUES cells
  (row-guarded and dependent-insert `MutationBatch` legs, `insertWithChildren` / `insertBulkWithChildren`),
  `bulkUpdate` and `mergeBulk`: the type
  without a typmod — `char` / `character` → `bpchar`, `bit` → `varbit` — so the assignment to the column pads a
  short value and raises 22001 (22026 for `bit`) for an over-long one, exactly like `INSERT … VALUES`:

  ```sql
  -- before
  INSERT INTO "cc_codes" ("code", "label", "n") SELECT CAST($2 AS char), CAST($3 AS text), "src"."n" FROM (…) AS "src"
  … FROM (VALUES ($1::char, $2::text, $3::integer)) AS v("code", "label", "n") …
  -- after
  INSERT INTO "cc_codes" ("code", "label", "n") SELECT CAST($2 AS bpchar), CAST($3 AS text), "src"."n" FROM (…) AS "src"
  … FROM (VALUES ($1::bpchar, $2::text, $3::integer)) AS v("code", "label", "n") …
  ```

  New test file `tests/mutations/char-column-values.test.ts`.

### Behaviour changes

- `advisoryXactLockAll` orders the acquisition in SQL:

  ```sql
  -- before
  SELECT pg_advisory_xact_lock($1, k) FROM unnest(CAST($2 AS integer[])) AS t(k)
  SELECT pg_advisory_xact_lock($1, hashtext(k)) FROM unnest(CAST($2 AS text[])) AS t(k)
  -- after
  SELECT pg_advisory_xact_lock($1, t.k) FROM unnest(CAST($2 AS integer[])) WITH ORDINALITY AS t(k, ord) ORDER BY t.ord
  SELECT pg_advisory_xact_lock($1, hashtext(t.k)) FROM unnest(CAST($2 AS text[])) WITH ORDINALITY AS t(k, ord) ORDER BY t.ord
  ```

  Parameters unchanged (class id, sorted-deduplicated array literal). A capture matching the old text must be updated.
- `advisoryXactLock(classId, null | undefined | boolean)` / `tryAdvisoryXactLock(…)` throw instead of locking a
  different key (see Fixed).
- In-memory engine: an INSERT whose arbiter WHERE does not imply the partial index's predicate now fails with 42P10
  (PostgreSQL's behaviour); an arbiter WHERE with an unknown column / a foreign qualifier fails with 42703 / 42P01,
  one with an unknown function or operator with 42883, one comparing with a literal its operand's type cannot read
  with 22P02 (each as PostgreSQL does — 1.0.8 accepted all of them). A
  BOUND parameter in the arbiter WHERE proves nothing — as in a PostgreSQL GENERIC plan — so such a statement fails
  with 42P10 from its first execution (a server fails it once the plan turns generic; with custom plans it passes).
  Referencing `excluded.<col>` there reports `missing FROM-clause entry for table "excluded"` (PostgreSQL, for a
  DO UPDATE: `invalid reference to FROM-clause entry …` — same SQLSTATE and position; the engine's missing-relation
  message looks at the namespace only).
  The implication is PostgreSQL's for the forms above, not all of predtest.c. Where the server proves more, the
  engine answers 42P10 (a right `targetWhere` can fail in memory, a wrong one never passes): OR on either side
  (reordered arms, `a` for `a OR b`, `x = 'a' OR x = 'b'` for `x IS NOT NULL` — an IN list / `= ANY` / `op ALL`

  comparison under an explicit `COLLATE "default"`. The in-memory guide lists them.
- Index reconcile: a model index spelled with `CAST(x AS t)` compares equal to the stored `x::t` on the fast pass

- Sequences: `DbSequence` and the schema manager quote sequence / schema names as identifiers (`"` doubled, a NUL
  refused) — unchanged for every name without `"`. An option (`startWith`, `incrementBy`, `minValue`, `maxValue`,
  `cache`) that is not an integer within bigint — a fraction, NaN, ±Infinity, a value outside -2^63 … 2^63-1, a

  created); each of those PostgreSQL rejects anyway. An integer STRING (`'10'`, from a JSON / env config) renders

- Upserts: `EntityUpsertConfig.targetWhere` (a root export), `UpsertConfig.targetWhere` and the fluent

## Aliased subquery scopes, set-returning functions, statement-level CTEs, projected-subquery joins

### Added

#### Aliased subquery scopes — `db.<table>.as(alias)`

A correlated subquery over tables under explicit aliases, turned into one expression. Guide:
`docs/guides/aliased-scopes.md`.

```ts
class DbEntityTable<T> { as(alias: string): AliasedScope<[ColumnRow<T>]> }

class AliasedScope<TRows extends readonly unknown[]> {
  readonly row: TRows[0];
  innerJoin<TRow>(source: AliasedScope<[TRow]>, on: (...rows: [...TRows, TRow]) => Condition): AliasedScope<[...TRows, TRow]>;
  leftJoin<TRow>(source: AliasedScope<[TRow]>, on: (...rows: [...TRows, TRow]) => Condition): AliasedScope<[...TRows, TRow]>;
  where(predicate: (...rows: TRows) => Condition): AliasedScope<TRows>;          // repeated calls AND
  orderBy(keys: (...rows: TRows) => ReadonlyArray<readonly [SqlOperand | Condition, 'ASC' | 'DESC']>): AliasedScope<TRows>;
  limit(count: number): AliasedScope<TRows>;
  scalar<T>(selection: (...rows: TRows) => SqlOperand<T>): SqlFragment<T>;       // (SELECT …), the selection's mapper
  exists(): SqlFragment<boolean>;                                                // EXISTS (SELECT 1 …)
  notExists(): SqlFragment<boolean>;                                             // (NOT EXISTS (SELECT 1 …))
}
```

```ts
db.posts.as('p2')
  .innerJoin(db.users.as('au'), (p, a) => eq(a.id, p.userId))
  .where((_p, a) => eq(a.isActive, literal(true)))
  .where(p => gt(p.views, 50))
  .orderBy((p, a) => [[eq(a.username, 'bob'), 'DESC'], [p.views, 'ASC']])
  .limit(1)
  .scalar(p => add(p.views, 7));
```
```sql
(SELECT ("p2"."views" + $3) FROM "posts" AS "p2" INNER JOIN "users" AS "au" ON "au"."id" = "p2"."user_id"
 WHERE ("au"."is_active" = TRUE AND "p2"."views" > $4) ORDER BY ("au"."username" = $5) DESC, "p2"."views" ASC LIMIT 1)
```

- Renders with the enclosing statement's build context (its parameter sequence, its lateral aliases, the table of
  an `UPDATE`); `FROM "<table>"` directly, schema-qualified only for an entity with a schema.
- `getFieldRefs()` reports only the outer refs, so the enclosing query joins the navigations they read; the
  scope's own aliases never leak out. A nested scope contributes its own outer refs.
- Rows are column-only (`ColumnRow<T>`); aliases are plain identifiers of at most 63 bytes, unique in the scope;
  an outer ref under one of the scope's own aliases is refused (it would compare the row with itself).
- The rows carry a chain identity of their own: an entity query nested in the scope reads a scope column as a
  correlation, whatever the scope's alias is called (see Fixed).
- `scalar()` of a column without a custom mapper reads as a column of its SQL type (`withReadType(<type>)`): a
  text column's `'0042'` stays text. A row or an object of columns (`scalar(r => r)`) is refused.
- Immutable: every method returns a new scope (one scope feeds two probes, or both legs of an `or()`).

#### Set-returning functions — `unnest`, `unnestZip`, `jsonbArrayElements`, `jsonbEachText`

New module `src/query/set-returning.ts`, exported from the root. Guide: `docs/guides/set-returning-functions.md`.

```ts
function unnest<T>(array: SqlOperand<readonly T[] | null | undefined> | readonly T[] | null | undefined, elementType?: PgCastType): SetReturningFunction<{ value: T }>;
function unnestZip<T extends Record<string, unknown>>(columns: { [K in keyof T]: { values: readonly T[K][] | SqlOperand; type: PgCastType } }): SetReturningFunction<T>;
function jsonbArrayElements<T = unknown>(target: SqlOperand): SetReturningFunction<{ value: T }>;
function jsonbEachText(target: SqlOperand): SetReturningFunction<{ key: string; value: string | null }>;

function fromSet<TRow>(set: SetReturningFunction<TRow>, alias?: string): SetQueryBuilder<TRow, TRow>;   // context-free
DbContext.selectFromSet<TRow>(set: SetReturningFunction<TRow>, alias?: string): SetQueryBuilder<TRow, TRow>;
<entity query>.crossJoinLateral<TSetRow, TSelection>(source: row => SetReturningFunction<TSetRow>,
  selector: (row, set: SetRow<TSetRow>) => TSelection, alias: string)
```

- A JS array binds as ONE parameter, the array literal cast to `<type>[]` (`unnest(CAST($1 AS text[]))`); a JS
  array without its element type is refused. `unnestZip` renders a multi-argument `unnest(CAST($1 AS t1[]),
  CAST($2 AS t2[]), …)` — zipped by position, NULL-padded.
- As a **projection value** (single-column sets): the call as written, multiplying the rows
  (`select(b => ({ label: unnest(b.labels) }))` → `unnest("boxes"."labels") as "label"`). Refused with a clear
  error in a WHERE, HAVING, ORDER BY, GROUP BY key, CASE, an aggregate's argument or any other expression.
- `fromSet(set, alias?)` needs no context: `.where()`, `.select()`, `.orderBy()`, `.limit()`, `.offset()`,
  `.union()` / `.unionAll()`, `.asSubquery('scalar' | 'array' | 'table')` — usable in `exists`, `notExists`,
  `inSubquery`, `coalesce`, a projection. Renders `SELECT … FROM <call> AS "<alias>"("<c1>", …) …` in the
  enclosing parameter sequence; outer refs (in the function's argument too) are reported for join detection.
  The alias defaults to the function's name.
- `db.selectFromSet(set, alias?)`: the same builder bound to the context — `.toList()`, `.firstOrDefault()`.
- `crossJoinLateral(...)`: `CROSS JOIN LATERAL <call> AS "<alias>"(…)` after FROM and its navigation joins, before
  the WHERE; grouped queries over it, `count()`, `where()`, `asSubquery()` work. A query over it cannot
  `update()` / `delete()`.
- Set columns read as the driver delivers them (text stays text, jsonb is parsed, NULL is `null`) — never the
  numeric-text coercion. `SetReturningFunction.withReadType(type)` reads a projection value as a column of that
  type and keeps it a set (`.as()` keeps the read type; `.mapWith()` replaces it).
- The set's row carries a chain identity (a lateral set's: its query's): a query nested in it reads it as a
  correlation, whatever the alias is called.
- `count()` / `exists()` / `countOver()` of a query whose projection holds a set-returning value are refused (they
  cannot see the rows it multiplies). A join added after `crossJoinLateral()` whose ON reads the set is refused:
  the joins of a query render before its lateral sets, whatever the call order.
- A JS array or object holding column refs or expressions, passed to `unnest` / `jsonbArrayElements` /
  `jsonbEachText` as a value, is refused (it would be bound with the refs serialized into it).

#### Typed mutation CTEs

- `update(...).toStatement(selector)` / `delete().toStatement(selector)` return `CompiledStatement<TRow>`
  (`{ sql, params }` plus a phantom RETURNING row type).
- `DbCteBuilder.withMutation(name, statement)` (no columns map) returns `{ cte: DbCte<TRow> }`: the CTE is typed
  by the RETURNING selector (`db.selectFromCte(gate.cte).select(g => ({ id: g.id }))` — `g.id` is a number
  column). The compiled statement carries its RETURNING selection (a non-enumerable property), so each CTE
  column of this form reads as what it returns: a text column stays text, a mapped column goes through its mapper.
  The `(name, statement, columns)` overload is kept AS IT WAS — typed by the columns map, its columns read untyped
  (a digits-only text as a number, a mapped column as its stored value), even from a statement that carries a
  RETURNING selection: a program written against it reads what it always did.

#### `DbContext.selectFromCte(cte, alias?)`

`FROM "<cte>" AS "<alias>"`, the root row's columns `"<alias>"."<column>"` — for a CTE-rooted subquery
correlated to an enclosing query over the same CTE, which is refused without it.

#### `CteRootQueryBuilder.where(predicate)`

`db.selectFromCte(cte)[.join…].where((root, ...joined) => condition)`: `WHERE` after FROM and its joins, before
ORDER BY, in the statement and in the nested (`asSubquery`) form; repeated calls AND; its parameters follow the ON
predicates'; refs to any other query correlate (reported for join detection).

WITH "older_users" AS (SELECT "users"."id" as "id", "users"."age" as "age" FROM "users" WHERE "users"."age" > $1)
SELECT "older_users"."id" as "id" FROM "older_users"

### Fixed

#### A projected subquery's navigation refs were not joined (error)

A `Subquery` projected by a query, reading a navigation of the enclosing row, rendered the navigation's alias with
no JOIN. It is now joined — at any depth of the projection, through several levels, in a UNION leg, in a
collection's item — as a WHERE `exists(...)` already did.

```ts
db.posts.select(p => ({
  title: p.title,
  nextOlder: db.users.where(u => gt(u.age, p.user!.age)).orderBy(u => u.age).limit(1).select(u => u.username).asSubquery('scalar'),
}))
```
Before (`missing FROM-clause entry for table "user"`):
```sql
SELECT "posts"."title" as "title", (SELECT "users"."username" FROM "users" WHERE "users"."age" > "user"."age"
  ORDER BY "users"."age" ASC LIMIT 1) as "nextOlder"
FROM "posts"
```
After:
```sql
SELECT "posts"."title" as "title", (SELECT "users"."username" FROM "users" WHERE "users"."age" > "user"."age"
  ORDER BY "users"."age" ASC LIMIT 1) as "nextOlder"
FROM "posts"
INNER JOIN "users" AS "user" ON "posts"."user_id" = "user"."id"
```

The same holds for a UNION used as the subquery (`….unionAll(…).asSubquery()`, projected or in a WHERE
`exists(...)` / `inSubquery(...)`): its subquery now reports every leg's correlations, so a leg reading
`p.user!.age` gets the enclosing query's `"user"` join instead of the same error.

#### A projected subquery read another navigation path's join of the same name (silent wrong data)

A projected subquery reading a navigation PATH that ends in the same relation name as a path the query reads
itself (a loan's own `ln.book` and its `ln.edition.book`; `ln.book.category` and `ln.edition.category`) rendered
the relation's plain name and read the query's join of that name — the other path's row, without an error. The
subquery's path is its own join now, with the lowest precedence for the plain alias: every path the query reads
itself — its projection, WHERE, ORDER BY, the path a collection hangs off — keeps the alias it renders under
without the subquery (a raw `sql` fragment naming `"book"` reads the same join as in 1.0.8, at any depth and in any
projection order), and the subquery's path renders as `<parent>__<relation>` (past PostgreSQL's 63-byte
identifier limit, which a first hop's `<table>__<relation>` can reach, as `<relation>__<n>`). The same for a
subquery in a collection's item, under every collection strategy: its path is joined hop by hop on its own
parents, never by relation name — which would find the item's own relation of that name, so that
`m.loans.select(ln => ({ n: <subquery on ln.edition.book.id> }))` counted for the loan's own `book`.

```ts
db.libLoans.select(ln => ({
  printed: ln.edition!.book!.name,
  own: db.libBooks.where(b => eq(b.id, ln.book!.id)).select(b => b.name).asSubquery('scalar'),
  raw: sql<string>`"book"."name"`,
}))
```
Before (`own` read the edition's book):
```sql
SELECT "book"."name" as "printed", (SELECT "lib_books"."name" FROM "lib_books" WHERE "lib_books"."id" = "book"."id") as "own",
  "book"."name" as "raw"
FROM "lib_loans"
LEFT JOIN "lib_editions" AS "edition" ON "lib_loans"."edition_id" = "edition"."id"
LEFT JOIN "lib_books" AS "book" ON "edition"."book_id" = "book"."id"
```
After:
```sql
SELECT "book"."name" as "printed", (SELECT "lib_books"."name" FROM "lib_books" WHERE "lib_books"."id" = "lib_loans__book"."id") as "own",
  "book"."name" as "raw"
FROM "lib_loans"
LEFT JOIN "lib_editions" AS "edition" ON "lib_loans"."edition_id" = "edition"."id"
LEFT JOIN "lib_books" AS "lib_loans__book" ON "lib_loans"."book_id" = "lib_loans__book"."id"
LEFT JOIN "lib_books" AS "book" ON "edition"."book_id" = "book"."id"
```

#### A statement's CTE was re-declared in every nested subquery reading it

`db.selectFromCte(cte)...asSubquery()` nested in a query carrying `cte` re-declared the CTE inside its parentheses
and bound the body's parameters again — per occurrence (WHERE, projection, ORDER BY, collections, UNION legs,
nested queries attaching the same CTE, subqueries of a CTE-rooted query). It now reads the statement-level CTE by
name.

```ts
db.users
  .where(u => inSubquery(u.id, db.selectFromCte(older.cte).select(r => ({ id: r.id })).asSubquery('array')))
  .with(older.cte)
```
Before:
```sql
WITH "older_users" AS (SELECT "users"."id" as "id", "users"."age" as "age" FROM "users" WHERE "users"."age" > $1)
SELECT … FROM "users"
WHERE "users"."id" IN (WITH "older_users" AS (SELECT "users"."id" as "id", "users"."age" as "age" FROM "users" WHERE "users"."age" > $2)
                       SELECT "older_users"."id" as "id" FROM "older_users")
-- params: [31, 31]
```
After:
```sql
WITH "older_users" AS (SELECT "users"."id" as "id", "users"."age" as "age" FROM "users" WHERE "users"."age" > $1)
SELECT … FROM "users"
WHERE "users"."id" IN (SELECT "older_users"."id" as "id" FROM "older_users")
-- params: [31]
```

#### A data-modifying CTE ran once per reading subquery (invalid SQL)

A `withMutation` CTE read from nested subqueries was re-declared in each of them — a data-modifying `WITH` nested
in a subquery, which PostgreSQL rejects (and which would have run the UPDATE once per occurrence). With the fix
above it is declared once, at statement level:

Before:
```sql
WITH "gate" AS (UPDATE "users" SET "age" = ("users"."age" + $1) WHERE "users"."id" = $2 RETURNING "id" AS "id", "age" AS "age")
SELECT "users"."id" as "id", (WITH "gate" AS (UPDATE "users" SET "age" = ("users"."age" + $3) WHERE "users"."id" = $4 RETURNING …)
                              SELECT "gate"."age" as "age" FROM "gate") as "newAge"
FROM "users"
WHERE "users"."id" IN (WITH "gate" AS (UPDATE "users" SET "age" = ("users"."age" + $5) WHERE "users"."id" = $6 RETURNING …)
                       SELECT "gate"."id" as "id" FROM "gate")
```
After:
```sql
WITH "gate" AS (UPDATE "users" SET "age" = ("users"."age" + $1) WHERE "users"."id" = $2 RETURNING "id" AS "id", "age" AS "age")
SELECT "users"."id" as "id", (SELECT "gate"."age" as "age" FROM "gate") as "newAge"
FROM "users"
WHERE "users"."id" IN (SELECT "gate"."id" as "id" FROM "gate")
```

A data-modifying CTE that would still be declared inside a nested subquery — read by a subquery of a query that
does not carry it, attached by a subquery itself, or carried by a CTE body — is refused: `CTE "gate" is
data-modifying: a data-modifying CTE must be declared at statement level — attach it with .with() on the executing
query`.

#### A nested `.with()` subquery or UNION bound its CTE body to the statement's parameters (silent wrong data)

A subquery carrying its own CTE (one the statement does not declare), nested after parameters the statement had
already bound, rendered its CTE body with the body's own `$1…` — the statement's parameters. The body now numbers
its parameters after the statement's.

```ts
const carrying = db.users.where(v => inSubquery(v.id, olderIds)).select(v => v.id).with(older.cte).asSubquery('array');
db.users.where(u => and(gt(u.age, 20), inSubquery(u.id, carrying)))
```
Before (the CTE filtered `age > 20` — `$1` is the statement's `20`):
```sql
… WHERE ("users"."age" > $1 AND "users"."id" IN (WITH "older_users" AS (… WHERE "users"."age" > $1) SELECT "users"."id" FROM "users"
  WHERE "users"."id" IN (WITH "older_users" AS (… WHERE "users"."age" > $3) SELECT "older_users"."id" as "id" FROM "older_users")))
-- params: [20, 31, 31]
```
After:
```sql
… WHERE ("users"."age" > $1 AND "users"."id" IN (WITH "older_users" AS (… WHERE "users"."age" > $2) SELECT "users"."id" FROM "users"
  WHERE "users"."id" IN (SELECT "older_users"."id" as "id" FROM "older_users")))
-- params: [20, 31]
```

The same for a UNION nested in a statement: its CTE body was rendered with `$1` (before: `… IN (WITH "older_users"
AS (… > $1) (SELECT …) UNION ALL (SELECT … = $3))`, params `[20, 31, 'nobody']`); it now reads `$2`. When the
statement declares the CTE itself, the nested UNION no longer declares it again (before: params
`[31, 20, 31, 'nobody']`; after: `[31, 20, 'nobody']`, one `WITH`).

#### Correctness of the new scopes, sets and CTE reads in edge cases

**a query nested in a scope, a set or a CTE-rooted query compared that row with itself.** Scope rows, set
rows (`fromSet`, `db.selectFromSet`, `crossJoinLateral`) and a CTE-rooted query's rows carried no chain identity:
an entity query nested in them resolved their refs by alias NAME, and an alias equal to one of its navigations
(`user`, `group`) became its own join. They now carry one (`nextChainId()`, a lateral set its query's), so the
nested query reads them as correlations.

```ts
db.users.select(u => ({ hot: db.users.as('user').where(s => and(eq(s.id, u.id),
  exists(db.posts.where(p => and(eq(p.userId, s.id), gt(p.views, 180))).select(p => ({ id: p.id })).asSubquery()))).exists() }))
```
Before (every user `hot`):
```sql
EXISTS (SELECT 1 FROM "users" AS "user" WHERE ("user"."id" = "users"."id" AND EXISTS (SELECT "posts"."id" as "id"
FROM "posts" INNER JOIN "users" AS "user" ON "posts"."user_id" = "user"."id"
WHERE ("posts"."user_id" = "user"."id" AND "posts"."views" > $1))))
```
After:
```sql
EXISTS (SELECT 1 FROM "users" AS "user" WHERE ("user"."id" = "users"."id" AND EXISTS (SELECT "posts"."id" as "id"
FROM "posts"
WHERE ("posts"."user_id" = "user"."id" AND "posts"."views" > $1))))
```
The same for a set aliased `group` read by a `db.boxes` query with a `group` navigation (it counted every box),
and for a CTE named `user` read from a `where()` of `db.selectFromCte(...)`.

**grouped by an expression, a subquery in the SELECT or HAVING bound the grouping key to its own
column.** The keys and aggregate arguments of the wrapped form rendered unqualified; a scope (or a set / CTE-rooted
subquery) renders them in its own scope, where `"id"` was its own table's column. They render qualified by the
grouped subquery now (see Behaviour changes).

```sql
-- before: both groups true
SELECT "id" as "uid", EXISTS (SELECT 1 FROM "users" AS "u2" WHERE ("u2"."id" = "id" AND "u2"."age" > $2)) as "olderThan30"
FROM (SELECT ("posts"."user_id" + $1) as "id" FROM "posts") "q1" GROUP BY "id"
-- after
SELECT "q1"."id" as "uid", EXISTS (SELECT 1 FROM "users" AS "u2" WHERE ("u2"."id" = "q1"."id" AND "u2"."age" > $2)) as "olderThan30"
FROM (SELECT ("posts"."user_id" + $1) as "id" FROM "posts") "q1" GROUP BY "id"
```

**a CTE body was renumbered as part of its builder's block, whatever else the statement declared.** Each
`DbCte` records where its builder started its body (`paramBase`); every statement — entity query, `count()` /
`exists()`, a UNION, a CTE-rooted query, nested or not — renumbers each body from where its own parameters land.
Fixed: a nested query attaching the statement's `cte_a` and the same builder's `cte_b` (before `… < $3`, params
`[30, 40, 20]` — `42P18` on pg / postgres.js, `[]` on Bun; after `… < $2`); a builder's second CTE used alone at
top level (its `$2` bound the statement's next value, or nothing); CTEs of two builders in one `WITH` (the second
body's `$1` bound the first's value); a CTE-rooted query whose root is a later CTE than a joined one.

**a nested query's CTE was replaced by the statement's CTE of the same name.** Statement-level CTEs are
matched by CONTENT, not by name: a nested query attaching a CTE that is DIFFERENT under a declared name is refused
(`The CTE "filtered" a nested query attaches is not the CTE "filtered" its statement declares …`); it used to
read the statement's rows. "Different" means different by content: two CTEs are the same when their bodies —
each numbered from `$1`, whatever offset its builder was at — their `MATERIALIZED` flag and their parameters BY
VALUE are equal (`Object.is`; a `Date` by its time; a `Buffer` / typed array by its bytes; an array element by
element; a plain object — a JSON document — by its JSON text; any other object only as the same instance). So
the same definition built twice — a CTE factory called for the statement and again for a nested query, with an
array (`= ANY(${[1, 2]})`), `Date` or JSON parameter, or with no parameter but built after another CTE of its
builder — is the statement's CTE, as it worked in 1.0.8 (which declared it again inside the subquery). The UNION
legs' check is the same (1.0.8 refused equal array / `Date` / JSON parameters there too). A data-modifying CTE is
one execution of its statement: it is the same only as the same `DbCte` instance.

**a CTE-rooted subquery correlated to an enclosing query over the same CTE compared the row with itself**
(`WHERE "older_users"."age" > "older_users"."age"`). Refused now (`… Give one of them a distinct alias:
selectFromCte(cte, '<alias>')`) — for an enclosing `selectFromCte(cte)` and for an entity query that joined the
CTE; `db.selectFromCte(cte, alias)` is the way out:
```sql
(SELECT count(*) as "value" FROM "older_users" AS "other" WHERE "other"."age" > "older_users"."age")
```

**`AliasedScope.scalar()` of a plain text column read `'0042'` as `42`.** A column without a mapper reads as
a column of its SQL type.

**typed `withMutation(name, statement)` read every column as an untyped expression** (`username: 42`,
`last: 14740200`): the RETURNING selection now types the reads.

**a temp-table collection reading a data-modifying CTE was refused only after the UPDATE had committed** (the
collection statement could not declare the CTE: `… attach it with .with() on the executing query`, although it
was attached). Such a collection — reading the CTE through a subquery in its WHERE, its item or a collection
nested in it — is refused before anything runs now (see Behaviour changes). Temp-table collections that never
read the CTE run as in 1.0.8: the UPDATE runs once, in the base statement.

`count()`, `exists()`, `countOver()` over a set-returning projection value answered
for the unmultiplied rows (a paging total of 3 for 6 rows); a join after `crossJoinLateral` reading the set failed
with `missing FROM-clause entry for table "s"`; `db.selectFromSet()` rendered a projected `agg.arrayAgg` as `array_agg` on a
client without native array results (it now renders the JSON form there, like `selectFromCte`); `scalar(r => r)` /
`jsonbArrayElements({ … refs … })` bound the refs as a JSON value; `unnest(…).withReadType(…)` threw in a
projection. Each is refused with a clear error or works now (see Added).

**Pre-existing defects fixed**
- A `Subquery` projected in a **collection's item** was bound as a parameter (the item read the serialized
  Subquery object); it renders as `(SELECT …)` now, in every collection strategy, the item's navigations it reads
  joined in the collection.
- `min()` / `max()` / `sum()` ignored the query's `.with()` CTEs (`relation "older_users" does not exist` for a
  query joined to one). Before: `SELECT MAX("users"."age") as result FROM "users" INNER JOIN "older_users" AS
  "older_users" ON …`; after: `WITH "older_users" AS (…) SELECT MAX("users"."age") as result FROM "users" INNER
  JOIN "older_users" AS "older_users" ON …`.
- A grouped query joined to a CTE (`GroupedJoinedQueryBuilder`) declared it at the top but handed nothing nested
  the declaration: a subquery reading the CTE declared it again (`(WITH "older_users" AS (…) SELECT count(*) …)`,
  its parameters bound twice); it reads it by name now. Nested itself, it no longer re-declares a CTE its
  statement declares, and its body is renumbered from its own parameters (it was not renumbered at all).

### Behaviour changes

- **Nested CTE reads**: a subquery nested in a statement that declares the CTE renders `(SELECT … FROM "cte")`
  instead of `(WITH "cte" AS (…) SELECT … FROM "cte")`, and the statement binds the body's parameters once (see
  Fixed). Parameter positions after the first nested read shift accordingly.
- **Projected subqueries join the navigations they read** (see Fixed): the statement gains the JOIN it was
  missing — an `INNER JOIN` for a required navigation, as a WHERE `exists(...)` already rendered it. A subquery
  reading one of two paths that end in one relation name reads its own path now — its VALUE changes (it read the
  other path's same-named join) — under a path alias; every alias the query's own paths render under is
  unchanged. The joins a subquery adds can come before the query's own in the SQL text.
- **`toStatement()` is typed**: it returns `CompiledStatement<TRow>` instead of `{ sql: string; params: any[] }`
  (structurally the same object; the phantom `__rowType` is never set). `withMutation(name, statement)` without a
  columns map returns a `DbCte<TRow>` whose `columnDefs` is `{}`; its `as()` hands out a ref for any column name.
- **CTE-rooted joins**: the ON predicate renders in the statement's build context (the SQL is unchanged); this is
  what lets a CTE-rooted query nested in a statement correlate and read the statement's CTEs.
- **Refused now**: a data-modifying CTE declared inside a nested subquery (it was invalid SQL); a set-returning
  function anywhere but a projection value or a row source.
- **SQL text of expression-keyed grouped queries** (the subquery-wrapped form, `groupBy(r => ({ k: <expression> }))`):
  the grouping keys and aggregate arguments read by the outer SELECT / HAVING are qualified by the grouped
  subquery — `SELECT "q1"."parity" as "parity", count(*) FILTER (WHERE "q1"."parity" = 1) …`,
  `HAVING (SUM("q1"."__arg0") > $1 AND MAX("q1"."__arg1") < $2)`, `HAVING "q1"."initial" = $1` (were `"parity"`,
  `"__arg0"`, `"initial"`). `GROUP BY` and `ORDER BY` are unchanged; results are unchanged unless a subquery
  in the SELECT / HAVING read a key. Pins updated: `aggregate-fragments.test.ts` (grouped by an
  expression), `grouped-having-orderby.test.ts` (SUM / MAX over subquery columns; a condition on the expression
  key).
- **CTE parameter numbering**: each CTE body is renumbered from its own `paramBase`. Statements whose
  CTEs come from one builder, attached in creation order, render as before; others bind correctly now.
- **A nested CTE-rooted subquery whose CTEs the statement declares only in part** is rendered (the statement's
  read by name, the rest declared inside it) — it was refused (`Cannot nest this CTE-rooted subquery: … already
  declared at statement level while … is not`). Pin updated: `cte-root-as-subquery.test.ts` (partially hoisted
  list).
- **Refused now**: a nested query attaching a CTE different BY CONTENT under a name its statement declares
  (1.0.8 declared it inside the subquery; 1.0.9's hoisting read the statement's) — the same definition built
  twice is the same CTE (see Fixed), a data-modifying one only as the same instance (two of them are two
  UPDATEs; 1.0.8's nested declaration of one failed with 0A000); two UNION legs attaching two `DbCte` instances
  of one data-modifying statement under one name (1.0.8 declared one of them — one UPDATE for the two attached;
  attach the same `DbCte` to both legs, as 1.0.8 already required for any other two definitions that differ); a
  CTE-rooted subquery correlated to an enclosing query over the same CTE without a distinct alias; a temp-table
  collection that reads a data-modifying CTE of its query (1.0.8 ran the query's UPDATE in the base statement,
  then failed the collection statement, whose nested data-modifying `WITH` PostgreSQL rejects — 0A000;
  collections that never read the CTE run as before);
  `count()` / `exists()` / `countOver()` over a set-returning projection value; a join added after
  `crossJoinLateral()` whose ON reads the set; `scalar()` of a row / an object of columns; a JS value holding
  column refs passed to `unnest` / `jsonbArrayElements` / `jsonbEachText`; a UNION subquery (`….asSubquery()`)
  whose leg over the enclosing query's own table correlates to it — `Correlated standalone subquery over table
  "users" references the same table from the outer query …` (1.0.8 compared the row with itself,
  `"users"."id" = "users"."id"`, and returned wrong rows; the same subquery without the UNION was refused already).
  Correlate through a different table or key column, as the message says.
- **`count()` / `exists()` evaluate the projection** — once, for two refusals only (a set-returning projection
  value; `count()` of a whole-set aggregate select). 1.0.8 never evaluated it: a selector that cannot run on the
  query's mock row (`select(u => ({ x: u.age.toFixed(1) }))` — a column ref has no `toFixed`) skips both checks
  and counts as it did.
- **Read changes**: `AliasedScope.scalar()` of a mapper-less column reads as a column of its type
  (a text column's digits stay text); a typed `withMutation` CTE's columns read with their RETURNING types and
  mappers; a Subquery in a collection's item reads the subquery's value (it was the serialized Subquery object).
- **`min()` / `max()` / `sum()` render the query's `WITH`** (it was missing).
- **Chain identities**: an entity query joined to a CTE stamps its CTE row's refs with its chain identity; a query
  nested in it reads them as correlations. Under the `'lateral'` strategy the SQL is unchanged. Under `'cte'` /
  `'temptable'`, a collection that reads the joined CTE's column (`u.posts.where(p => gt(p.views, t.minViews))`)
  now reads its parent row: it renders as a correlated subquery in the one statement, where it failed with
  `missing FROM-clause entry for table "<cte>"`.
