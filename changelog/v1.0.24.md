# v1.0.24

## Fix: a select builder is an `IEntityQueryable` again — `lateralJoin()` on `EntitySelectQueryBuilder` (1.0.23 regression)

1.0.23 added `lateralJoin()` to `IEntityQueryable` as a required member, but not to `EntitySelectQueryBuilder` — the
type of `select()`, `selectDistinct()`, `innerJoin()`, `leftJoin()`, `crossJoinLateral()` and of their chains. Up to
1.0.22 a select builder had every member of `IEntityQueryable`, and code that hands one over where an
`IEntityQueryable<any>` is taken — an options field, a parameter, a return value — compiled. On 1.0.23 it does not:

```typescript
interface SyncOptions { baseQuery: IEntityQueryable<any> }

const options: SyncOptions = {
  baseQuery: db.books.where(b => eq(b.shelfId, shelfId)).select(b => ({ id: b.id, title: b.title })),
};
// 1.0.23: TS2741: Property 'lateralJoin' is missing in type
//   'EntitySelectQueryBuilder<Book, { id: number; title: string; }>' but required in type 'IEntityQueryable<any>'.
```

Affected: every consumer that hands a select builder to an `IEntityQueryable`, at type-checking only. The runtime
object always was the query builder that implements `lateralJoin()`, so 1.0.23 runs correctly; such code just does
not compile against it. 1.0.23's note that nothing was narrowed missed it because nothing inside linkgress assigns a
select builder to that interface.

`EntitySelectQueryBuilder` now declares the member:

```typescript
lateralJoin(navigation: (entity: EntityQuery<TEntity>) => unknown): EntitySelectQueryBuilder<TEntity, TSelection>;
```

so a select builder is an `IEntityQueryable` again, and `lateralJoin()` can be called after `select()` too. The
selector names a navigation of the query's ROOT row (`b => b.author`), whatever the projection, and the builder keeps
its projection and its chain. Navigation joins are rendered when the query is built, so the call order does not
matter: after `select()`, `selectDistinct()`, a join or at the end of the chain, the mark renders the statement it
renders before `select()` — the same text, the same rows, on PostgreSQL, PGlite and in memory.

Not chosen: an optional `lateralJoin?` on `IEntityQueryable` would break every 1.0.23 call under `strictNullChecks`
(`db.books.where(…).lateralJoin(…)` — "possibly undefined"); taking it off the interface would remove 1.0.23's API.

Docs: `docs/guides/lateral-navigation-joins.md` — "Where it applies" gains the select builder.

Tests: `tests/queries/lateral-navigation-join.test.ts`, "lateralJoin() — the select builder": every select builder —
`where().select()`, `select()`, `selectDistinct()`, a `where()` / `orderBy()` / `limit()` / `offset()` chain,
`innerJoin()`, `leftJoin()`, `withTimeout().forUpdate()`, an options field — assigned to `IEntityQueryable<any>` (on
1.0.23 each one fails `npm run type-check:tests` with TS2741), and probed through it: the author's plain join replaced
by the probe and nothing else, the same rows; and `lateralJoin()` after `select()`, at the end of the chain and through
the interface — the statement `lateralJoin()` before `select()` renders, the same rows, the builder's projection kept
(a compile-time assertion).

Backward compatible: the compiled JavaScript is byte-identical to 1.0.23's — of the published files only
`dist/entity/db-context.d.ts` changes, by this one member. Every exported interface, class and type alias of the
typings (647), as a source, against every type 1.0.23 or this release changed — `IEntityQueryable`,
`EntityCollectionQuery`, `NavigationJoin`, `EntitySelectQueryBuilder`, `DbEntityTable`, `QueryBuilder`,
`SelectQueryBuilder`, `CollectionQueryBuilder` — gets the verdict it got on 1.0.22: the one pair 1.0.23 broke
(`EntitySelectQueryBuilder` → `IEntityQueryable`) is assignable again, and no other verdict differs between 1.0.22,
1.0.23 and 1.0.24. (`EntityCollectionQuery` also gained a required `lateralJoin()` in 1.0.23; no linkgress type was
ever assignable to it.)
