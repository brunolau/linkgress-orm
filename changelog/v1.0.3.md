# v1.0.3

## In-memory database: the catalog is built once per version, not once per query

1.0.2 went after what the executor spends per row. This release goes after what a statement spends
before it reaches a row: reading the catalog. Every `pg_catalog` and `information_schema` relation
was MATERIALIZED on each scan of it — a fresh row per table, index, sequence, view, column,
constraint — and a schema migration is nothing but catalog reads. Nothing here changes what a
statement returns.

Measured on the downstream project's schema — 281 tables, 1 222 relations in `pg_class`, 6 813
columns, 1 936 constraints — migrating into a fresh in-memory database, the step that builds the
schema from the model and records the journal:

| | 1.0.2 | 1.0.3 |
| --- | --- | --- |
| migrate, inside the downstream suite's cold setup | 86 s | 4 s |
| migrate, run on its own (same box, separate measurement) | 128 s | 6 s |

Of that 128 s run, 89 s was engine `execute` time, and two statements held most of it: the schema
manager's per-table index introspection (424 calls, 56 s) and its `pg_statistic_ext` probe (424
calls, 29 s). Neither is expensive in itself — both join `pg_class`, and that join is what was
being paid for, 424 times over.

This package's suite passes in memory: 1 876 tests across 141 files, one of them new — a guard that
the two live columns below are never served from the cache. The downstream suite (17 740 tests over
1 490 files, every database in memory) passes with the same failure list before and after — no test
changed its outcome.

### Catalog relations are cached per catalog version

`catalogRelationRows` now keeps the rows it generated for a relation and returns them again while
`catalog.version` is unchanged; a DDL bumps that version and the next reader rebuilds. The views
that report live session or lock state — `pg_stat_activity`, `pg_locks`,
`pg_prepared_statements`, `pg_settings` — are exempt and still generated per query.

The cost this removes grows with the schema: the schema manager introspects per TABLE, so a
281-table model re-materialized `pg_attribute`, `pg_index`, `pg_constraint` and
`information_schema.columns` hundreds of times, each pass walking all 6 813 columns and 1 936
constraints.

### `pg_class` is cached too, with its one live column refreshed

`pg_class` was the relation left out of that cache, because `reltuples` is the relation's CURRENT
row count and every insert changes it. Leaving it out cost most of the win: nearly every
introspection query joins `pg_class`, so each one rebuilt a row for every table, index, sequence and
view in the database.

The rest of a `pg_class` row follows from the catalog, so the rows are now cached like any other and
only `reltuples` is written back per query, from live storage. Relations without storage keep their
`-1` and are skipped.

Two quadratic scans went with it. `relhassubclass` asked, for each relation, whether ANY relation
inherits from it — a scan inside a scan over a row set that counts every index and sequence, so
1 222 relations meant ~1.5 M comparisons on each rebuild, and the rebuilds numbered in the
thousands; the parents are now collected in one pass. `information_schema.referential_constraints`
searched all 1 936 constraints for the unique constraint behind each foreign key; those are now
indexed once per rebuild.

### `pg_sequences.last_value` is never cached

`last_value` moves with every `nextval`, and that is not a catalog change — no version bump, so a
cached row would keep reporting the value the sequence had when it was first read. A caller that
allocates from a sequence and then reads it back would see its own allocation missing. The view is
exempt from the cache for that reason.

This was caught by a downstream test that allocates an invoice number and asserts the sequence
advanced ("a CONCURRENT race over one key still yields one number", QA_AT-911); this package's own
suite did not cover it. The lesson generalizes: a generator that reads mutable state hanging off a
catalog object — `sequence.state` here — cannot be treated as a pure function of the catalog.

### The parse cache evicts instead of emptying

`Database.parse` kept parse trees in a Map and called `clear()` whenever it passed 2 000 entries.
The analyzed form of a statement hangs off its parse tree, so clearing threw away every prepared
statement's analysis at once, and any workload with more distinct statement texts than the cap
re-parsed AND re-analyzed everything it came back to — repeatedly, since it kept crossing the same
threshold. The cache now holds 8 000 entries and evicts the least recently used one (a hit
re-inserts, so insertion order is recency order). A test suite, which issues thousands of distinct
statement texts and returns to all of them, is exactly the workload that hit the cliff.
