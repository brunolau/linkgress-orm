# v1.0.34

Linkgress owns the parameter limit of a statement, and three places did not hold to it. A list of keys written as
an `or()` — `or(...keys.map(k => and(eq(t.a, k.a), eq(t.b, k.b))))`, the way two-column keys are written since
`inArrayOpt` takes one column — bound a parameter per value: 40 000 such keys were 80 000 parameters and every driver
refused the statement. It now binds ONE array parameter per column past `inArrayOptThreshold` arms. The bulk writes
sized their chunks by the keys of the FIRST row, so a first row carrying fewer columns than the others — or rows whose
`sql`-fragment cells bind several parameters each — sent chunks over the client's limit. They now count the columns
every row binds and the fragments' own parameters. And `PostgresClient` reported 65 535 as its limit while postgres.js
refuses 65 534 and more itself, so a `MutationBatch` statement filled to the reported limit failed on that driver: it
reports 65 533 now. Statements the 1.0.33 suite runs are unchanged — every one of its 127 284 statements in memory is
sent with the same SQL text and returns the same rows (see [Neutrality](#neutrality)).

## Changed: an `or()` that lists keys binds one array parameter per column

```typescript
const titles = await db.posts
  .where(p => or(...keys.map(k => and(eq(p.userId, k.userId), eq(p.title, k.title)))))
  .select(p => p.title)
  .toList();
```

```sql
-- nine keys (captured on PGlite)
SELECT "posts"."title"
FROM "posts"
WHERE (("posts"."user_id", "posts"."title") IN (SELECT "__keys"."k1", "__keys"."k2" FROM unnest($1::integer[], $2::varchar[]) AS "__keys"("k1", "k2")))
-- params: ["{1,1,2,2,1,1,2,2,99}", "{\"Alice Post 1\",…}"]
```

- **When:** an `or()` of more than `inArrayOptThreshold` (8) arms, every arm an `eq`, or an `and()` of `eq`s, over the
  SAME columns (in any order per arm), each comparing a column with a declared type to a plain value — a string, a
  number, a boolean or a bigint after the column's mapper. Over one column it renders what `inArrayOpt` renders,
  `("t"."a" = ANY($1::integer[]))`. Up to the threshold, and for anything else, the `or()` renders as written.
- **Rows:** the OR's. A row-constructor `IN` is NULL where a key compares NULL and none matches, as the OR of its arms
  is, so `not()` of it and a row whose key column is NULL read as before.
- **As written:** an arm comparing to NULL (`eq` renders `IS NULL`), to another column, an `sql` fragment, a
  placeholder or a subquery; a column without a declared type (a CTE column), a json/jsonb or array column; a `Date`
  or other object its column does not map (pg binds a Date in local time, an array literal in UTC); arms over
  different columns, or naming one column twice; an arm that is an `or()` or a nested `and()`; every `or()` under a
  substitution — a grouped `HAVING`, a `RETURNING` expression.
- **Casts:** as `eqAny`'s (`serial` → `integer[]`, `char` → `bpchar[]`, a mapped column its mapper's type). Values bind
  through the column's mapper — a collection item's column through its item mapper.
- **Switch:** `LinkgressConfig.orUsesOpt` (default `true`; `QueryOptions.orUsesOpt`; `configure({ orUsesOpt })`;
  `resetToDefaults()` turns it on). Off, every `or()` renders as written.
- One statement text for every key count above the threshold, so it prepares once.

## Fix: bulk-write chunks count the columns every row binds

`insertBulk`, `upsertBulk`, `bulkUpdate`, `mergeBulk` and `getTable()`'s `insertBulk` / `upsertBulk` chunk a large
input by `⌊⌊65 535 / columns⌋ · 0.6⌋` rows within the client's limit. `columns` was the key count of the first row: it
missed a column only later rows carry — every row of the statement binds every column (NULL where a row has none) —
and counted keys that bind nothing.

- `columns` is now every key, over ALL the rows, that names a column of the table (`boundColumnCount`). 300 rows of 5
  nullable columns whose first row carries only its key went as ONE statement of 1 500 parameters within a limit of
  1 000; now 1 000 + 500. For rows that all carry the same columns nothing changes; rows carrying keys that are not
  columns go in larger chunks (still within the 60 % budget).
- A cell holding an `sql` fragment binds the fragment's parameters, not one: such rows close their statement before
  it binds more than a chunk of plain cells does (`chunkBulkRows`). 300 rows of 5 columns with a 3-parameter fragment
  cell bind 2 100 in one statement on PostgreSQL; within a limit of 1 000, 994 + 994 + 112 (before: 1 400 + 700).
- An explicit `chunkSize` is still used as given. `insertBulk(…).toStatement()` follows the same chunks, and refuses a
  compiled insert (its RETURNING included) over the CLIENT's limit — it checked PostgreSQL's 65 535.
- `insertWithChildren` / `insertBulkWithChildren` size their single-statement budget from every child row's columns
  and within the client's limit. A `MutationBatch` leg's own budget counts every row's keys (an insert-with-children
  leg: its parents' keys, as before).

## Fix: `PostgresClient.maxParameters()` is 65 533

postgres.js refuses a statement of 65 534 parameters or more before sending it (`MAX_PARAMETERS_EXCEEDED: Max number
of parameters (65534) exceeded`; measured on postgres 3.4.9 — pg and Bun's SQL send 65 535, the protocol's limit).
`PostgresClient` reported 65 535, so `MutationBatch` packed statements the driver refuses. It reports 65 533:
`executeBatch()`, `ifFits` and the chunkers hold to it. The refusals name the limit as they did
(`… over PostgreSQL's 65 535`, `… over the 65 533 this client takes`).

## What a caller may notice

1. An `or()` of more than 8 equality arms over the same typed columns sends `IN (SELECT … FROM unnest(…))` (or
   `= ANY(…)` for one column) instead of the OR — the same rows. A test pinning the SQL text of such a query sees the
   new text; `LinkgressConfig.orUsesOpt = false` restores the old one. None of the 1.0.33 suite's statements changed.
2. Bulk writes whose rows carry different columns, or `sql`-fragment cells binding several parameters, may be sent in
   more statements; rows with keys that are not columns, in fewer.
3. On postgres.js, a `MutationBatch` statement of 65 534 or 65 535 parameters is refused by linkgress before sending
   (`MutationBatch: the statement binds … — over the 65 533 this client takes`) instead of by the driver, and an
   `ifFits` leg that would take it there is declined.
4. `PostgresClient` overrides `maxParameters()` now, so a stub on `DatabaseClient.prototype.maxParameters` no longer
   reaches it — nor a `PostgresClient` over the in-memory engine's `createPostgresSql()`. Stub the client the
   context runs on, `spyOn(db.getClient(), 'maxParameters')` (a transaction's client asks it), or
   `PostgresClient.prototype`.

### Neutrality

Every statement of the 1.0.33 suite, recorded (`LINKGRESS_TEST_RECORD_DIR`) in memory on a copy of this release with
the 1.0.33 behaviour restored (the `or()` as written, chunks by the first row's keys, the 1.0.33 budgets) and on this
release, paired by test and position: 127 284 statements, the same SQL text and the same rows for all of them. 188
texts and 64 results differ between ANY two runs — two runs of this release differ in exactly those (generated table
and index names, `now()` reads) — and are excluded as run-dependent.

Suite (233 files; 1.0.33: 232): `test:parity` — identical outcomes for all 233 files and 27 405 tests, in memory
27 405 / 0 in 30 s, PostgreSQL 27 405 / 0 in 114 s, 120 s; PGlite 27 166 / 0, 241 skipped (the 1.0.33 skips) in 51 s.

On the other drivers, beside the same copy (which keeps the 65 533 — the 9 cases above were measured on 1.0.33
itself): postgres.js (`--driver postgres`) 26 426 passed / 977 failed / 2 skipped in 87 s, the copy 26 373 / 991;
Bun's SQL (`--driver bun`) 27 317 / 88 in 113 s, the copy 27 264 / 102. No test fails here that passes on the copy.
The copy's 14 more are the 14 new chunking cases; the 977 and the 88 are the same tests on both — on postgres.js in
6 files (`cte-union-readback`, `dependent-mutation-ctes`, `scalar-subquery-read-type`, `insert-from-expression-cast`,
`rows-source`, and the timestamp readback of `mutation-batch-insert-returning`), on Bun in 3
(`insert-from-expression-cast`, `scalar-subquery-read-type`, `unique-index`).
