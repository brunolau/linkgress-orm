# v1.0.34

A `QueryBatch` leg that reads a table subquery or a CTE now keeps the plain envelope when that subquery projects
declared `timestamp` / `timestamptz` / `date` / `bytea` columns straight from its table, or a collection's `toList()`.
Before, every such column counted as "new to the batch": the leg was sent in the runtime-typed envelope (the rows,
each value's text and its type, `pg_typeof` tested per row, the query fenced by `OFFSET 0`) although the same column
read from the table itself rides in the JSON row. On a small leg that envelope is a fixed cost — 0.08–0.23 ms per
batch measured on PostgreSQL 18 for a two-column leg of 1–300 rows — and it is what made a subquery-fenced rewrite of a
gopass query slower than the plain join it replaced. The values a batch delivers do not change: every value is still
exactly what the client delivers for the same query on its own.

## Fix: a subquery's / CTE's declared columns travel as the table's own columns do

```typescript
const lines = db.orderItems
  .where(oi => inArray(oi.userEshopId, userIds))
  .select(oi => ({
    productPriceId: oi.productPriceId,
    effectiveStartDate: oi.effectiveStartDate,                  // timestamp
    pins: oi.orderItemPins.select(p => ({ state: p.state })).toList(),
  }));

batch.addList(db.productPrices
  .where(pp => eq(pp.product.requiresCarrierAssignment, true))
  .innerJoin(lines.offset(0).asSubquery('table'), (pp, l) => eq(pp.id, l.productPriceId),
    (_pp, l) => ({ effectiveStartDate: l.effectiveStartDate, pins: l.pins }), 'carrier_lines'), 'lines');
// 1.0.33: SELECT 0 AS __batch_ix, json_build_object('t', …, 'r', …, 'x', …) … FROM (SELECT * FROM (…) __batch_q0 OFFSET 0) …
// 1.0.34: SELECT 0 AS __batch_ix, coalesce(json_agg(row_to_json(__batch_q)), '[]'::json) AS __batch_items FROM (…) __batch_q
```

- A column of a CTE or a table subquery whose body projects a declared column of a table — its own, a navigation's,
  or such a column of a CTE / subquery it reads in turn — is marked as one (`projectedColumnRef`: `__tableColumn`). A
  manually joined table's column and a set's column are not: they stay "new to the batch", as they are read directly.
- Such a `timestamp` / `timestamptz` / `date` / `bytea` column travels `declared` — in the JSON row, revived from its
  JSON form exactly as the table's own column is (`jsonColumnDelivery`; a mapped column's mapper gets the driver's text
  form) — **when that revival gives what this client's driver gives for the type**. The batch checks it per client
  (`declaredColumnTransport`): one value of the type parsed by the client's own parser
  (`DatabaseClient.typedTextParser`, with and without parameters) against its revived JSON form, by value and JS type.
  So an unmapped column on a client with default parsers (a `Date`, a `Buffer`), and a mapped column on a client that
  hands its mappers the driver's text (text passthrough for timestamps — gopass's configuration), take the plain
  envelope. Everything else keeps 1.0.33's transport, so it reads as before: a client that parses the type otherwise
  (text passthrough with an unmapped column, `pg.types.setTypeParser`, Bun's `datesAsStrings`, postgres.js's `date` at
  UTC midnight outside UTC), a mapped column on a client whose parser makes a `Date`, a client that parses `json`
  itself.
- A collection's `toList()` a table subquery projects is a `json` list (`CollectionQueryBuilder.isJsonItemList()`):
  it rides in the JSON row (as its text only when the client parses `json` itself). Aggregates, `toNumberList()` /
  `toStringList()` and `firstOrDefault()` collections keep their transport.
- A grouped query's join to a CTE (`grouped-query.ts`) is unchanged: its flat-row metadata has no
  `declared` delivery.

## What a caller may notice

- The SQL of a batch leg as above: the plain envelope instead of the runtime-typed one. Values, JS types and key
  order are those of 1.0.33 (and of the query read on its own) — the tests below compare them.
- A leg that mixes such a column with a value only PostgreSQL knows the type of keeps the runtime-typed envelope,
  with one text column fewer.

### Tests

`tests/queries/query-batch-subquery-columns.test.ts` (new, 5 tests): a fenced table subquery and a CTE projecting
`timestamp`, `timestamptz` (with a NULL), `bytea` and a `toList()`, a subquery's `date` column, a subquery's mapped
timestamp on the suite's client (stays runtime-typed: its mapper gets a `Date` standalone), and a mapped timestamp plus
a `toList()` through postgres.js with text passthrough for timestamps. Each compares the batched rows with the same
query read on its own (values, JS types, key order); the envelope tests pin the batch statement to the plain envelope
of the standalone SQL. On the 1.0.33 source 3 of the 5 fail (the three envelope pins); on this code all pass.

Suite (233 files): PostgreSQL 27 357 passed / 0 failed in 101 s (`--pg-jobs 1`); in memory 27 316 passed / 0 failed /
42 skipped in 28 s.
