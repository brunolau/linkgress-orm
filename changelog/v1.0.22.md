# v1.0.22

## Added: an INSERT as a data-modifying CTE — `insertBulk(...).toStatement()`, `insertFrom(..., { with })`

A bulk insert could not feed a second insert in the same statement: `DbCteBuilder.withMutation()` takes a
compiled statement, which only an update or a delete could produce, and `insertFrom()` could not declare a
data-modifying CTE (PostgreSQL allows one only at the top level, so its source could not carry it either).
Writing generated rows plus one dependent row per row that landed took two statements.

```typescript
const ins = new DbCteBuilder().withMutation(
  'ins',
  db.codes
    .insertBulk(rows, { onConflictDoNothing: true })
    .toStatement(c => ({ id: c.id, code: c.code, userId: c.userId }))   // CompiledStatement<{ id; code; userId }>
);

await db.auditLog.insertFrom(
  db.selectFromCte(ins.cte).select(r => ({ id: r.id, code: r.code, userId: r.userId })).asSubquery('table'),
  src => ({ action: 'CODE_CREATED', source: caseWhen(isNull(src.userId), 'GENERATE').else('BULK_ASSIGN'), codeId: src.id, code: src.code, customerId: src.userId }),
  { with: [ins.cte] }
);
// WITH "ins" AS (INSERT INTO "codes" (…) VALUES (…), (…) ON CONFLICT DO NOTHING RETURNING …)
// INSERT INTO "audit_log" (…) SELECT … FROM (SELECT … FROM "ins") AS "src"
```

- `toStatement(selector?)` on `insertBulk(...)`, `insert(...)` and `insertFrom(...)` (`FluentInsertMany`,
  `FluentInsert`) compiles the statement execution runs — the same columns, `ON CONFLICT DO NOTHING`,
  `OVERRIDING SYSTEM VALUE`, values through the columns' mappers — `$1`-based, with the selector as its
  RETURNING (none without one), the selection attached so `withMutation(name, statement)` types the CTE and
  reads each column through its mapper. Constants in the selector bind as parameters. A navigation or
  collection in the selector, or a selector returning one value, is refused, as for update / delete.
- It compiles ONE statement: rows execution would split into chunks (the `chunkSize` option, or the automatic
  chunk under PostgreSQL's 65 535-parameter limit) are refused with the chunk size and the statement count —
  never one chunk silently; so are zero rows, rows with no insertable column, and more than 65 535 parameters.
- `InsertFromOptions.with`: CTEs `insertFrom` declares at the top of its statement (`WITH <ctes> INSERT …`),
  their parameters first — then the source's, the SELECT list's, `where`'s and the RETURNING's. Everything
  nested reads them by name. A navigation RETURNING declares them ahead of its own `"__mutation__"` CTE in the
  one `WITH`. Two different CTEs of one name are refused; a data-modifying CTE the statement reads without
  declaring it is refused with a message naming the option (it used to say to `.with()` it on the executing
  query, which `insertFrom` had no way to do) — still the same `NestedDataModifyingCteError`, only its message; `insertFrom(…, { with: [dml] }).toStatement()` is refused, as its
  DML CTE would be nested.

The in-memory database already executed this statement shape — a data-modifying INSERT … ON CONFLICT DO
NOTHING … RETURNING CTE feeding an INSERT … SELECT, a conflicting row absent from the RETURNING; nothing
changed there.

Docs: `docs/guides/insert-update-guide.md` ("One statement: a bulk insert feeding another insert"),
`docs/guides/cte-guide.md` ("Data-Modifying CTEs").

Tests: `tests/mutations/insert-mutation-cte.test.ts` — on PostgreSQL and in memory: the compiled SQL and
parameters of `insertBulk` / `insert` `toStatement` (mappers, ON CONFLICT DO NOTHING, a RETURNING constant,
nothing executed), the compiled insert run as a `withMutation` CTE read through its mappers, the chunk / empty
refusals, the one-statement code + audit insert (exact SQL, parameter order CTE → SELECT list, a CASE over a
CTE column, bound literals through mappers, stored values), a pre-existing conflicting code getting no audit
row (and an all-conflicting batch inserting nothing), `.returning()` / `.returning(selector)` on the outer
insert, rollback inside a transaction, the undeclared-CTE and nested-DML refusals, and a plain CTE in `with`
declared once — also under a navigation RETURNING.

Backward compatible: every existing call compiles and runs as before (the full suite passes unchanged on both
engines). The public API only gains members — `toStatement()` on the insert fluents and the optional
`InsertFromOptions.with`; no signature changed or was removed.
