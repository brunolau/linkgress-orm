# Feature: database-level settings — `model.hasDbSetting(name, value)`

Declare PostgreSQL configuration parameters on the model and every
environment built or migrated from it runs with them:

```ts
protected override setupModel(model: DbModelConfig): void {
  model.hasDbSetting('jit', 'off');
  model.entity(Order, entity => { ... });
}
```

## What it does

The schema manager converges the database toward the declarations through
`ALTER DATABASE <current> SET name = value`:

- `ensureCreated()` applies every declared setting on a fresh database;
- `migrate()` diffs the declarations against the database-wide
  (`setrole = 0`) entries of `pg_db_role_setting` and (re)applies any that
  are missing or whose stored value drifted — the plan reports each as a
  `set_database_setting` operation;
- the migration scaffold emits the same statement into generated files, with
  an `ALTER DATABASE ... RESET` down-migration.

`ALTER DATABASE ... SET` **persists**: the value lives in
`pg_db_role_setting`, survives restarts, and every NEW session on the
database inherits it at connect time. It does NOT travel with a plain
`pg_dump` — which is exactly why the declaration belongs on the model: a
freshly provisioned environment picks it up from the migrator instead of
from tribal knowledge.

## Semantics

- **Converge-only**, mirroring declared statistics objects: parameters the
  model does not declare are never touched, and REMOVING a declaration
  leaves the database value in place (`RESET` it via a hand migration when
  that is intended).
- Values: strings pass through verbatim (`'off'`, `'32MB'`, `'UTC'`),
  booleans normalize to canonical `on`/`off`, numbers to decimal text.
  Drift comparison is by that stored text.
- Names are validated (`jit`, `app.custom_setting`); invalid names and
  values that would break the emitted statement throw at declaration time.
- The emitted statement is a `DO` block resolving `current_database()` at
  RUN time, so the identical SQL works from the live migrator and from a
  scaffolded migration file. `ALTER DATABASE ... SET` is transactional, so
  it is safe inside the migration transaction.
- The migrating role must OWN the database (or be superuser) — PostgreSQL's
  own `ALTER DATABASE` privilege rule.

## Why

Born from a production investigation where `jit = on` (the server default)
cost an OLTP application 3.5–5.5s of per-execution LLVM compilation on a
wide query whose actual row work was under 2ms — the planner's cost
over-estimate crossed `jit_optimize_above_cost` on every call. The fix is a
database-level `jit = off`, and this API is what keeps such a fix from
silently missing on the next freshly built environment.

Covered by `tests/schema/database-settings.test.ts` (11 tests: DSL
validation/normalization, builder parity, ensureCreated, migrate
reconciliation incl. drift convergence and the undeclared-keys contract).
