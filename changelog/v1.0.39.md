# v1.0.39

## Behaviour change: an `or()` of no operand matches no row

`or()` with no operand rendered `1=1`, so it matched every row. An `or()` is usually spread from a list — "any of these
keys" — and when the list comes out empty (every requested key was dropped as invalid, a filter with nothing ticked)
the read meant to find a few rows returned the whole table, and an `update()` / `delete()` guarded the same way touched
every row:

```typescript
const isbns = requested.filter(isValidIsbn);                  // [] when nothing in the request is valid
await db.books.where(b => or(...isbns.map(isbn => eq(b.isbn, isbn)))).toList();
// 1.0.38: SELECT … FROM "books" WHERE 1=1   — the whole table
// 1.0.39: SELECT … FROM "books" WHERE 1=0   — no row
```

`or()` of nothing now renders `1=0`, the identity of OR, as `inArray(col, [])` already renders `1=0`. `and()` of nothing
still renders `1=1` (the identity of AND), and `not(or())` renders `NOT (1=0)`, so it matches every row. An `or()` with
at least one operand renders exactly as before, the key-list rewrite of `LinkgressConfig.orUsesOpt` included.

**Check your callers.** Code that spreads a possibly empty list into `or()` and relies on the empty list meaning "no
filter" now gets no row. Skip the `where()` for an empty list instead (the querying guide's pitfall says so).

## Tests

`tests/queries/or-equality-membership.test.ts`:

- `or()` and an `or()` spread from an empty list render `1=0`, `and()` renders `1=1`, `not(or())` renders `NOT (1=0)`,
  and an `and()` that holds one renders `(… AND 1=0)` (on 1.0.38 the `or()` cases render `1=1`);
- against the database, an `or()` spread from an empty list selects no row, and an `update()` and a `delete()` guarded
  by it touch no row, while `not()` of it and `and()` of nothing take every row (on 1.0.38 the select returns every row,
  the update and the delete take every row they can reach).
