# v1.0.28

`lateralJoin()` is concluded. Instead of the shape one call site needed, its whole surface is generated and tested:
`tests/queries/lateral-join-matrix.test.ts`, 4 572 cases on each of PostgreSQL, PGlite and the in-memory database. Each
case runs the same query with and without `lateralJoin()` and asserts the same rows, and that every statement is the
plain one with each plain join of a probed hop — the row's own and every re-join a subquery makes of it — replaced by
its probe, on every key pair, nothing else changed (the parameters included). The matrix found four defects and a gap
in the typings; all are fixed below. None of the defects needed a probe to exist: the plain query was wrong too, and
the probe only made it visible.

## Fix: an inline `count()` / `exists()` joins a navigation on every key pair, not the first one only

A collection's `count()` / `exists()` written in a `where()` or a `sql` fragment renders as a subquery of its own. That
subquery joins the navigation path the collection hangs off anew, and the navigations its own `where()` reads. Both kinds
of join were rendered on the FIRST key pair of the relation only:

```typescript
entity.hasOne(e => e.activeAuthor, () => Author)
  .withForeignKey(b => [b.authorId, true])
  .withPrincipalKey(a => [a.id, a.active]);

db.books.select(b => ({ title: b.title, n: sql<number>`${b.activeAuthor.books.count()}` }))
// before: … LEFT JOIN "authors" "activeAuthor" ON "books"."author_id" = "activeAuthor"."id" …
//         — a book of an INACTIVE author counted that author's books, while `b.activeAuthor` itself reads as missing
// now:    … ON "books"."author_id" = "activeAuthor"."id" AND true = "activeAuthor"."active" …
```

Every pair is rendered now: a constant key part on either side, and the second column of a composite key (which matched
every row sharing the first column, and multiplied the subquery's rows). A key of one column renders the text it rendered
before. Affected: every inline `count()` / `exists()` reached through a navigation whose key is composite or has a
constant part, with or without `lateralJoin()` (a probe of such a hop always rendered every pair — the probed and the
plain query read different rows).

## Fix: `min()` / `max()` / `sum()` of a column read through a navigation

`db.books.select(b => ({ author: b.author.name })).max(r => r.author)` rendered `MAX("author"."name")` without the join of
`author` — `missing FROM-clause entry for table "author"`. The aggregated column's navigations are joined now, as the
WHERE's always were (and probed when `lateralJoin()` names them).

## Fix: a navigation row projected whole inside a collection reads its columns

`s.books.select(b => ({ title: b.title, author: b.author }))` read every `author` back as `{}`: a navigation row inherits
its columns, and the collection's projection walked its own properties. It renders its columns now, read through their
mappers, as a navigation row projected whole at the root always did.

## Fix: after `with()` and a join of a table subquery, the row keeps its navigations

`db.books.with(cte)` — and the untyped `with()`, also after `where()` — started the query from the row itself, and so did
a `leftJoin()` / `innerJoin()` of a table subquery for its left row. Every operator after it reads the row it is handed
through its columns only, so a navigation was gone:

```typescript
db.books.with(cte).select(b => ({ title: b.title, author: b.author.name }))   // TypeError: b.author is undefined
db.books.with(cte).where(b => eq(b.author.name, 'Ann'))                       // column "undefined" does not exist
db.books.with(cte).orderBy(b => [b.author.name, b.id])                        // ORDER BY "id" — the first key silently dropped
db.books.with(cte).select(b => ({ age: b.author?.age }))                      // the field silently missing from every row
db.books.leftJoin(subquery, (b, s) => …, (b, s) => ({ author: b.author.name }), 's')  // TypeError
```

They start from the select-all row `where()`, `orderBy()`, `limit()` and `lateralJoin()` start from (its columns the
default projection, every navigation still reachable), and read the navigation — and probe it under `lateralJoin()` —
like any other query.

## Typings: a `lateralJoin()` selector that names no reference navigation does not compile

`lateralJoin()` takes a reference navigation of the row (or a path of them) and refuses anything else when the query is
built. On the typed builders — a table, `IEntityQueryable`, every select builder and a collection — the refusal now
happens at compile time as well:

```typescript
db.books.lateralJoin(b => b.title);        // error: Type 'DbColumn<string>' is not assignable to type 'never'
db.books.lateralJoin(b => b.author.books); // error: Type 'EntityCollectionQuery<Book> | undefined' is not assignable to type 'never'
db.books.lateralJoin(b => b.author);       // as before
```

The selector's return type is checked through the new exported `LateralNavigation<T>`: a column, a collection, a value or
nothing is `never`; a navigation, a selector typed `unknown` and an untyped (`any`) row are taken as they are. Code that
compiled against 1.0.27 and calls `lateralJoin()` on a navigation compiles unchanged; code that passes anything else
threw when the query was built and now does not compile.

Docs: `docs/guides/lateral-navigation-joins.md` — "Coverage" (new): the dimensions the matrix runs and what is not offered;
"Refused" names the compile-time refusal; "Where it applies" names `with()`.

Tests: `tests/queries/lateral-join-matrix.test.ts` (new). On 1.0.27, 426 of its 4 572 cases fail — the same 426 in
memory, on PostgreSQL and on PGlite: 158 through an inline `count()` / `exists()` (the probed and the plain query read different rows, and the
pinned counts), 36 `min()` / `max()` (`missing FROM-clause entry`), 54 a navigation row projected whole in a collection (`{}`,
no join to probe), 178 after `with()` or a subquery join (`undefined is not an object (evaluating 'b.author.name')`, a
dropped ORDER BY key). `tests/queries/lateral-navigation-join.test.ts`: its seven refusal assertions that pass a column or a
collection to `lateralJoin()` carry `// @ts-expect-error` — the runtime assertions are unchanged.

Backward compatible, except where the fixes change what a query reads. Recorded in memory, the 55 053 statements of the
other 216 test files differ from 1.0.27 in the 252 statements two runs of 1.0.27 already differ in (table names carrying
the process id, timestamps) — none of them beyond those numbers — and in 2 more: two tests of `subqueries.test.ts` project
`p.user?.age` / `p.user?.email` after `db.posts.with(cte)`, a field 1.0.27 silently dropped from every row; it is read now
(with the join of `user`). In the matrix file, every statement whose text differs from 1.0.27 is one of the four fixes',
and the 57 whose text is unchanged but whose rows differ read the temp table of a collection (`temptable` strategy) that
a fixed statement before them filled. Of the
published files, `dist/query/query-builder.js` and `dist/entity/db-context.js` change in code (`createSelectAllRow` is
exported for the query builder, `@internal`); the typings gain `LateralNavigation`, the narrowed `lateralJoin()`
signatures and the private `QueryBuilder.selectAllRow`. Type-checked against the server packages of a consumer that uses
`lateralJoin()`: no error.
