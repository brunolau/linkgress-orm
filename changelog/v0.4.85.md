# v0.4.85

## Fix: a shared memoized navigation fused independent predicates into a tautology

**Upgrade from any earlier 0.4.x if you build more than one condition or aggregate from the same
navigation reached through a reference** (`row.order!.campaignLinks!`). The natural two-leg gate

```typescript
or(
	notExists(dc.discount!.campaignLinks!),
	exists(dc.discount!.campaignLinks!.where(cl => eq(cl.campaign!.isPublic, true))),
)
```

compiled both legs from ONE builder and emitted `NOT EXISTS(P) OR EXISTS(P)` — always true. Valid
SQL, no error, every row returned. In a downstream application this shipped as a security defect:
a publication gate on coupon redemption waved unpublished campaigns through.

### Why

Three mechanisms interact. A collection navigation reached through a reference mock row is
memoized per row (`navCache[relName]`), so every access inside one lambda returns the same
`CollectionQueryBuilder`. `where()` mutated `whereCond` in place and `exists()` mutated
`aggregationType` on that shared instance. And conditions compile LATE — `ExistsConditionBase`
stores the builder itself and renders it at SQL time — so the second leg's `where()` rewrote the
node the first leg had already captured. Root-level collection getters deliberately mint fresh
builders per access (the code warns that memoizing would fuse repeated `where()` chains); the
reference-navigation path violated that invariant.

The same sharing also let two SEQUENTIAL conditions built from one navigation AND-contaminate
each other, two aggregations off one navigation collapse into the last one requested, and an
`orderBy` on one `select()`-derived list leak into a sibling list (`select()` aliased
`orderByFields`).

### What changed

- **Terminal reads capture a snapshot.** `exists()`, `count()`, `min()`/`max()`/`sum()`,
  `toList()`/`toNumberList()`/`toStringList()` and `firstOrDefault()` return a full-state clone
  (`captureSnapshot()`) instead of writing into the builder. A condition leg or projected
  aggregate owns its state from the moment it is written — for re-retrieved and
  variable-captured nodes alike. Condition resolution is now a true read: it persists nothing.
- **In-place ops keep their contract, but the memo stops re-serving written builders.**
  `where()`/`orderBy()`/`limit()`/`offset()` still mutate and AND-chain (statement-style
  accumulation — `links.where(p); links.count()` — behaves exactly as before), but they flag the
  instance, and the navigation memo re-mints instead of handing a written builder out again.
- `select()` copies `orderByFields` instead of aliasing it.
- Object identity of handed-out builders was audited before choosing this design: nothing keys
  on it (caches key on schema objects or SQL text), so only capture-time state is semantically
  meaningful. Pure copy-on-write on `where()` was rejected — it would silently drop filters in
  statement-style code, a worse silent failure than the one fixed.

Consumers who worked around the fusion by `.select()`-deriving each leg need no changes.

Performance: the diff runs entirely in the query-build phase. With the build caches off the fix
is cost-neutral to faster (a dead per-call mock-item mint in `min`/`max`/`sum` was removed along
the way — terminal-heavy builds got measurably cheaper); with caches on, terminal-heavy chain
construction pays +0.05–0.14 µs per build — under ~0.2 % of a realistic query lifecycle. All new
allocations are young-generation and dropped with the build.

### How it was found

By a downstream code review: a campaign-publication gate's suites proved every campaign coupon —
unpublished included — passed redemption. The compiled SQL showed the identical predicate in both
subqueries of the `or()`.

## Feature: migration journal knows what was baselined, and migrations can opt out of the shortcut

On a FRESH database `MigrationRunner.up()` builds the schema from the model and records every
journal migration as applied WITHOUT executing it. Anything a migration does that the schema
model cannot represent — storage parameters such as per-table autovacuum reloptions, data
backfills, seeded/config rows — therefore never exists on a freshly built database, and nothing
recorded that fact.

### What changed

- The journal table gains **`baselined BOOLEAN NOT NULL DEFAULT FALSE`**. Rows recorded by the
  fresh-database shortcut are marked `true`; genuinely executed migrations stay `false`. Existing
  journals upgrade automatically and idempotently (`ADD COLUMN IF NOT EXISTS` in
  `ensureTable()`); `MigrationJournal.getApplied()` and `MigrationRunner.status()` expose the
  flag, so consumers can replace heuristics (e.g. `applied_at` clustering) with
  `EXISTS(SELECT 1 FROM __migrations WHERE baselined)`.
- A migration may declare **`runOnBaseline: true`** when its effects are not representable in
  the schema model. The fresh path then records all non-flagged files first (`baselined = true`)
  and EXECUTES the flagged ones — in journal order, after the model build, each in a
  transaction — recording them `baselined = false`. A failing `runOnBaseline` migration fails
  the run like any migration failure; it and its followers stay unrecorded, and the next `up()`
  (now non-fresh) retries them through the normal pending path.
- `MigrationRunResult` gains an optional `baselined` list, and the runner logs
  `"N migration(s) baselined (recorded, not executed), M runOnBaseline migration(s) executed"`.

Default behavior is unchanged for existing consumers: no migration carries the flag yet, and
baselined files still appear in `skipped`.

### How it was found

By rebuilding a downstream test database from scratch: 342 journal rows appeared within ~111 ms
of each other, and a migration-applied `cart_item` autovacuum setting was absent — the journal
claimed a history no one had executed.
