# v1.0.33

Five places where linkgress did not do what its types or its docs said. All five were found while the docs were rebuilt
AI-first (#38), with every example run against the code. In each case the docs had either promised the behaviour or
documented the trap. Each fix is pinned by tests that fail on the 1.0.32 code. No statement changes:
- the select builder's `sum()` / `min()` / `max()` send the same SQL and only read their value differently;
- a prepared query sends the same statement through another path;
- a CTE-rooted `forUpdate()` is refused before anything is sent.

Everything that behaves differently from 1.0.32 is listed under [What a caller may notice](#what-a-caller-may-notice).

## Fix: `first()` after `where()` / `orderBy()` / `select()` is typed `T | null`

`first()` on a query is `firstOrDefault()`: it resolves to `null` when no row matches. It was typed `T`, so a missing
row reached the caller as a `null` the compiler had promised away. Only the table's own `first()` throws.

```typescript
const user = await db.users.where(u => eq(u.username, 'nobody')).first();   // null
user.username;   // 1.0.32: compiled, then threw a TypeError — 1.0.33: TS18047 'user' is possibly 'null'
```

- `IEntityQueryable.first()`, `EntitySelectQueryBuilder.first()` and the third select-query interface declare
  `Promise<T | null>`, which is what their implementation returned.
- The table's own `db.users.first()` is unchanged. It throws `Sequence contains no elements` on an empty table and stays
  typed `T`.
- A select builder's `firstOrThrow()` throws `No results found` on no row and is typed `T`.

## Fix: the select builder's `sum()` / `min()` / `max()` read their value like `agg.sum()` / `agg.min()` / `agg.max()`

They returned the driver's raw value under a `number` type:

| Call | 1.0.32 | 1.0.33 (= the `agg.*` projection) |
|---|---|---|
| `db.posts.select(p => ({ v: p.views })).sum(r => r.v)` (int column) | `'450'` | `450` |
| `db.orders.select(o => ({ a: o.totalAmount })).sum(r => r.a)` (decimal) | `'249.98'` | `249.98` |
| `db.orders.select(o => ({ a: o.totalAmount })).max(r => r.a)` | `'149.99'` | `149.99` |
| `db.posts.select(p => ({ t: p.publishTime })).max(r => r.t)` (mapped column) | `1125` | `{ hour: 18, minute: 45 }` |

- The value is read through the read the same aggregate gets in a projection (`agg.sum()` reads a number,
  `agg.min()` / `agg.max()` read like the column, through its mapper). The statement is unchanged:
  `SELECT SUM("posts"."views") as result FROM "posts" …`.
- No row → `null`, as before.
- `disableMappers` keeps the stored value (`1125`), and `rawResult` the driver's (`'450'`).
- A column given by name only (no ref) reads as the driver hands it, as before.

## Fix: `disableMappers`, `rawResult`, `traceTime` and `useBinaryProtocol` work on their own

The query builders read these options from the context's executor. An executor was only created for a logging,
failure-logging, timing, slow-query or prepared-statement option, so set alone they were ignored:

```typescript
await db.posts.withQueryOptions({ disableMappers: true }).where(p => eq(p.title, 'Alice Post 1')).select(p => ({ at: p.publishTime })).toList();
// 1.0.32: [{ at: { hour: 9, minute: 30 } }]  (mapped anyway)   1.0.33: [{ at: 570 }]
```

- `QueryExecutor.isNeeded()` counts the four options. This applies to `withQueryOptions()` on tables and accessors,
  and to a context constructed with them.
- The table's own `toList()` / `first()` / `firstOrDefault()` honour `rawResult`: the driver's rows, keyed by the
  database's column names. They also honour `disableMappers`: stored values, with the property names kept. Both reads
  ignored the options whatever else was set.

## Fix: a prepared query's executions run through the context's executor

`PreparedQuery.execute()` sent its statement to the client directly, so none of the context's or the builder's
execution options applied to it:

- `logQueries` / `logParameters`: no `[SQL Query]` line;
- `logFailedQueries`: no `[SQL Error]` line;
- `onQueryTakingTooLong` and `.expectedExecutionTime()`: no slow-query callback;
- `.withTimeout()`: a `pg_sleep(5)` per row ran its 15 s instead of failing after 400 ms;
- `preparedStatements` and `.withPreparedStatements(true)` on `PostgresClient`: the statement stayed unnamed (0 named
  statements).

Each now applies. `prepare()` hands its builder's executor to the `PreparedQuery` (a new, optional last constructor
parameter), and `execute()` runs through it. On `PostgresClient` with `preparedStatements: true`, a prepared query is
built once AND planned once per connection.

## Fix: `forUpdate()` on a CTE-rooted query is refused — it locked no rows

`db.selectFromCte(cte).select(…).forUpdate()` appended `FOR UPDATE` to a SELECT whose FROM holds only CTEs. PostgreSQL
applies a `FOR UPDATE` without `OF` to the plain tables of its own FROM and skips the WITH queries the FROM reads, so
the clause held no lock. On PostgreSQL 18.3, a second session's `SELECT … FOR UPDATE NOWAIT` of the same row went
through while the first transaction was still open. The JSDoc said it locked the rows the root CTE's body read.

```typescript
db.selectFromCte(guard.cte).select(r => ({ id: r.id })).forUpdate();
// 1.0.33: Error: forUpdate() on a CTE-rooted query locks no rows: PostgreSQL applies FOR UPDATE to the plain tables of
// its own FROM only, and this query reads only CTEs. Call .forUpdate() on the builder that forms the CTE body instead …

const guard = new DbCteBuilder().with('guard', db.users.where(u => eq(u.id, id)).select(u => ({ id: u.id })).forUpdate());
await db.selectFromCte(guard.cte).select(r => ({ id: r.id })).toList();   // locks the row the body reads
```

- `CteRootQueryBuilder.forUpdate()` throws when called, before anything is sent, and is marked `@deprecated`. The lock
  clause it rendered is gone.
- `forUpdate()` on the builder a CTE body is made of is the supported form: its `FOR UPDATE` is inside the WITH query and
  locks the rows the body reads. This is now checked live with a second session.

## What a caller may notice

1. **TypeScript:** dereferencing a query's `first()` without a check no longer compiles (TS18047). Check for `null`, or
   use a select builder's `firstOrThrow()` or the table's own `first()`, both of which throw when no row exists. The
   runtime is unchanged.
2. **The select builder's `sum()` / `min()` / `max()`:**
   - `sum()` and a numeric `min()` / `max()` return numbers. Code that converted the string (`Number(…)`, `parseFloat`)
     keeps working; code that compared with the string (`=== '450'`) does not.
   - `min()` / `max()` of a mapped column return the mapped value.
3. **Read options set alone now take effect:**
   - a context or a `withQueryOptions()` with only `disableMappers` reads stored values;
   - with only `rawResult`, it returns the driver's rows;
   - with only `traceTime`, it logs the time trace through the logger's `'timing'` section.
   The table's own `toList()` / `first()` / `firstOrDefault()` honour `rawResult` and `disableMappers` whatever else is
   set.
4. **A prepared query** is logged, reported on failure, measured against the slow-query threshold, and cancelled by
   `.withTimeout()` like any statement of its context. On `PostgresClient` with `preparedStatements` it runs as a named
   server-side statement.
5. **`forUpdate()` on a CTE-rooted query throws.** Move it to the builder that forms the CTE body; the old call locked
   nothing. The method stays on the type, marked `@deprecated`.
6. **A `QueryBatch` refuses a leg built with one of these options next to legs without it.** This covers
   `withQueryOptions()` with `disableMappers`, `rawResult`, `traceTime` or `useBinaryProtocol`. The option now gives the
   leg an executor of its own, and the batch refuses it as it refuses a `withTimeout()` leg: `QueryBatch: query "…"
   uses a different database client or transaction than the rest of the batch`. 1.0.32 accepted such a leg and
   ignored its option. Such a leg alone in a batch runs, and a leg that only sets `collectionStrategy` still mixes
   with plain legs.

### Tests

New or extended, each run on PostgreSQL, in memory (parity: identical outcomes for all 235 files, 27 377 tests) and on
PGlite (27 136 passed, 243 skipped). Every new test failed on the 1.0.32 code (PostgreSQL), except the characterization
cases named below:

- `tests/queries/select-builder-terminal-reads.test.ts` (new, 10 cases).
  - `first()` typing: two `@ts-expect-error` assertions, unused, so failing `tsc -p tests/tsconfig.json`, on 1.0.32.
  - The table's own `first()` keeps throwing and stays typed `T`.
  - `sum()` / `min()` / `max()` against the `agg.*` projection (int, decimal, mapped), with `null` on no row,
    `disableMappers` / `rawResult`, and the unchanged statement.
  - Red: 3 cases plus the 2 type assertions.
- `tests/queries/read-options-alone.test.ts` (new, 6 cases). `disableMappers` alone on a select, on the table's own
  `toList()` / `firstOrDefault()` and in a context's options; `rawResult` alone on a select and on the table's own
  `toList()`; `traceTime` alone. Red: 6.
- `tests/queries/prepared-query-executor.test.ts` (new, 5 cases). Statement and parameter logging, failure logging,
  the slow-query callback, a builder's `expectedExecutionTime()`, and unchanged results. Red: 4.
- `tests/database/prepared-statements.test.ts`: 2 new cases (`PostgresClient`). A prepared query on a prepared context
  names one server-side statement, and `withPreparedStatements(true)` carries into `prepare()`. Red: 2.
- `tests/queries/query-timeout.test.ts`: 1 new case, `.withTimeout(400)` cancels a prepared query's execution with
  `QueryTimeoutError`. Red: 1, checked by handing `PreparedQuery` no executor (the 1.0.32 path): the execution ran 15 s.
- `tests/queries/for-update.test.ts`:
  - the CTE-root case asserts the refusal and that no `FOR UPDATE` is rendered (red: 1);
  - a new live case, with a second session's `NOWAIT`, shows `forUpdate()` on the CTE body locks. It passes on 1.0.32
    too: it pins the supported form.
- Six existing files (`navigation`, `returning-old`, `basic-queries`, `basic-queries-fixed`, `queryable-interface`,
  `with-query-options`) now assert the row their query's `first()` expects (`(await … .first())!`). The nullable type
  surfaced them; several only asserted `toBeDefined()`, which a `null` passes.
