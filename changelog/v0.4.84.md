# v0.4.84

## Fix: a nested collection correlating through the ENCLOSING collection's item

**Upgrade from 0.4.81, 0.4.82 or 0.4.83 if you project a collection inside another collection.**
Such a query could silently filter on the wrong row — no SQL error, no type error, just an empty
or wrong result.

```typescript
db.loans.select(ln => ({
  lines: ln.lines!.select(line => ({
    pass: line.reader!.passes!
      .where(p => and(eq(p.active, true), eq(line.book!.genre!.lendable, true)))
      .select(p => ({ id: p.id }))
      .firstOrDefault('pass'),
  })).toList('lines'),
}))
```

`line.book.genre` is a navigation of the ENCLOSING item, while `pass` declares a `genre`
navigation of its OWN. From 0.4.81 — which made the projection path resolve a collection's
where-navigations — the inner subquery joined ITS `genre` and filtered every pass by the pass's
genre instead of the line's book's.

### Why

A collection told its own refs from correlations by whether a ref carried a chain id, and the
rows a collection minted carried none. "Carries an id at all" identifies a correlation only while
every enclosing query is a stamped one. Inside another COLLECTION the enclosing item was just as
anonymous as the inner collection's own rows, so a ref reached through it passed for the inner
collection's own navigation — and was then name-resolved against the inner table's navigation
graph, which happily found a same-named relation one hop away.

### What changed

- Every `CollectionQueryBuilder` carries a chain id and stamps it on the rows it mints — item
  rows, their column refs, and the navigation rows reached through them. Builders derived by
  `select` / `selectMany` keep the id, so a `where` written before the `select` stays its own.
- The collection paths compare against that id instead of asking whether a ref carries one.
- A collection now resolves what its NESTED collections' correlations need in its OWN FROM: the
  inner subquery leaves such a ref foreign, so the alias has to be joined one level out or it
  renders unbound. The collection's own WHERE and those correlations go through one resolver, so
  both obey the same alias rules — including 0.4.82's inverse-navigation drop and the shadowing
  refusal.

A collection's OWN same-named navigation still binds to itself; that is pinned by the new test.

### How it was found

By upgrading a downstream application. The shape — a lookup nested in a per-item projection,
filtered on a flag reached through the enclosing item's navigation — returned nothing, and the
only visible difference was a set of joins that had appeared INSIDE the inner subquery.

### Files Changed

- `src/query/query-builder.ts` — `CollectionQueryBuilder.chainId`, stamped in `createMockItem`
  and carried by `select` / `selectMany`; `getFieldRefs` and `addNavigationJoinForFieldRef`
  compare against it; `resolveRefNavigationJoins` extracted from `resolveWhereNavigationJoins`
  and also fed the correlation refs `detectNavigationJoins` collects from nested collections
- `src/query/query-utils.ts` — `isForeignChainRef`'s contract doc
- `tests/queries/correlated-nested-collection-outer-item-ref.test.ts` — new: the projection,
  the inline aggregate and the EXISTS render paths, plus the own-navigation guard
