# v0.4.78

## `LinkgressConfig.inArrayUsesOpt` — make plain `inArray` render as `inArrayOpt`

`inArrayOpt` / `notInArrayOpt` (v0.4.72) bound how many statement texts one query family
leaves in a pooled connection's plan cache: an exact-length `IN ($1, $2, …)` list up to
`inArrayOptThreshold`, a single `= ANY($1::type[])` parameter above it, and — with
`inArrayPadBuckets` — one text per rung in between. All of that only ever reached the call
sites somebody had rewritten to say `inArrayOpt`, and in a codebase with hundreds of `inArray`
calls that rewrite is both a large diff and a race against the next feature branch, which
reaches for `inArray` again.

`LinkgressConfig.inArrayUsesOpt` (default `false`) closes the gap with one switch:

```typescript
LinkgressConfig.inArrayUsesOpt = true;

db.widgets.where(w => inArray(w.slotId, slotIds));
// slotIds.length <= 8:  "w"."slot_id" IN ($1, $2, $3)
// slotIds.length  > 8:  "w"."slot_id" = ANY($1::integer[])
```

With it on, `inArray` and `notInArray` render exactly what `inArrayOpt` and `notInArrayOpt`
render — the same threshold, the same pad ladder, the same array form above it, the same
`1=0` / `1=1` constants for an empty or non-array list. The rows a query returns do not change
at any length; only its statement text does. With it off — the default — `inArray` is the
literal exact-length operator it has always been, so nothing changes for anyone who does not
ask for this.

Set it the same three ways as its siblings, all writing the same process-wide value:

```typescript
LinkgressConfig.inArrayUsesOpt = true;
LinkgressConfig.configure({ inArrayUsesOpt: true, inArrayOptThreshold: 8 });
new AppDatabase(client, { inArrayUsesOpt: true });    // QueryOptions key
```

A non-boolean throws and leaves the current value in place, matching how the threshold and the
ladder validate. `LinkgressConfig.resetToDefaults()` puts it back to `false`.

Leave it off where hand-tuned queries depend on the planner seeing an exact-length `IN` list
and its exact row estimate — the two operators stay distinct in the source, so those call sites
can adopt `inArrayOpt` individually with the switch off.

### The recursion this deliberately avoids

`inArrayOpt` used to reach its sub-threshold branch by calling the public `inArray`:

```typescript
export function inArrayOpt(column, values) {
  if (!Array.isArray(values) || values.length <= inArrayOptThreshold) {
    return inArray(column, padToInArrayBucket(values));   // ← the public operator
  }

  return eqAny(column, values);
}
```

Teaching `inArray` to delegate to `inArrayOpt` on top of that makes the pair mutually
recursive: `inArray` → `inArrayOpt` → `inArray` → …, overflowing the stack on the very first
short list — with the switch on, that is essentially every list, so the failure would be
immediate and total rather than an edge case.

Both operators now bottom out in private `renderInArrayOpt` / `renderNotInArrayOpt` functions
that construct the `InComparison` / `NotInComparison` directly instead of routing back through
a public operator. `inArrayOpt` calls the renderer unconditionally; `inArray` calls it only
when the switch is on and otherwise builds the comparison itself. The duplication is one `new`
expression per operator and it is deliberate — a comment at the renderer says so, and a test
(`inArray and inArrayOpt do not recurse into each other`) exercises the routed short-list path
from an already-deep stack so a future refactor back to the public call cannot pass quietly.
