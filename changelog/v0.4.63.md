# v0.4.63

## Fix: `jsonbArraySome` no longer aborts a statement on a non-array JSONB row

`jsonbArraySome(col, predicate)` compiled to an `EXISTS` subquery that handed the
column straight to `jsonb_array_elements`:

```sql
EXISTS (SELECT 1 FROM jsonb_array_elements("shelf"."tags") AS __elem WHERE __elem->>'kind' = $1)
```

`jsonb_array_elements` is strict about its input. Given an object it raises
`cannot extract elements from an object`; given a scalar,
`cannot extract elements from a scalar`. The subquery is evaluated per candidate
row, so **one** row whose column holds `{}` or `"x"` instead of an array aborted
the entire statement.

A JSONB column has no shape guarantee — that is the point of the type. Nothing in
PostgreSQL stops a migration, a manual data fix, or a double-encoded write from
parking a non-array value in a column the application models as `T[]`. The
predicate should answer "this row has no matching element" for such a row, which
is exactly what it already did for SQL `NULL`.

### What a user would have observed

A query that had worked for months starts failing outright, and the error names
neither a column nor a row:

```
error: cannot extract elements from an object
```

Because the failure is raised by the set-returning function rather than by any
row-level check, nothing in the message points at the one malformed row that
caused it. The natural reading is that the ORM emitted bad SQL — the emitted SQL
is in fact valid, and re-running it against a copy of the data with the offending
row absent succeeds, which makes the fault look intermittent or environment-specific
rather than data-dependent. Every consumer of the query is taken down, not just
the row that is wrong.

### The fix

The element source is now guarded, so the function only ever sees an array:

```sql
EXISTS (SELECT 1 FROM jsonb_array_elements(
          CASE WHEN jsonb_typeof("shelf"."tags") = 'array' THEN "shelf"."tags" ELSE '[]'::jsonb END
        ) AS __elem
        WHERE __elem->>'kind' = $1)
```

`CASE` rather than an `AND jsonb_typeof(col) = 'array'` conjunct: PostgreSQL does
not define an evaluation order for the operands of `AND`, and the planner is free
to evaluate the `EXISTS` first, so a conjunct would not reliably shield the call.
`CASE` is one of the constructs whose branch-wise evaluation is guaranteed, and
because the `WHEN` reads a column it is not constant-folded away.

### Behaviour

No query that previously returned rows changes its answer:

| Column value        | Before               | After            |
|---------------------|----------------------|------------------|
| JSON array          | evaluated normally   | unchanged        |
| SQL `NULL`          | no rows, no error    | unchanged        |
| JSON `null`         | no rows, no error    | unchanged        |
| object, e.g. `{}`   | **statement aborts** | no match         |
| scalar, e.g. `"x"`  | **statement aborts** | no match         |

The only queries whose behaviour changes are the ones that used to fail. A
malformed row still never *matches* — an object carrying the very key the
predicate asks about does not match either, because the predicate asks about array
**elements** and the row has none.

Note that this makes malformed rows silent rather than loud. If a JSONB column is
meant to hold arrays, a failing query was at least a signal that some row does
not; that signal is now gone, and finding such rows is a data-quality task:

```sql
SELECT id, jsonb_typeof(tags) FROM shelf
WHERE tags IS NOT NULL AND jsonb_typeof(tags) <> 'array';
```

Enforcing the invariant belongs in the schema, with a check constraint, rather
than in whichever query happens to read the column first.

### Coverage

`tests/queries/jsonb-array-some-non-array.test.ts` is an integration test against
a real database. It seeds one table with array, empty-array, SQL-`NULL`,
JSON-`null`, object, populated-object, and scalar rows (all written as raw SQL
with explicit `::jsonb` casts, since the malformed shapes cannot be expressed
through the ORM and writing every row the same way keeps the test free of
driver-specific array encoding), then asserts the predicate returns exactly the
matching array row. Every one of its four cases fails on the previous code with
`cannot extract elements from an object`.

`tests/queries/jsonb-array-some.test.ts` pins the emitted SQL, including an
assertion that the raw column is never passed to `jsonb_array_elements`. Its
fixtures were rewritten onto a neutral shelf/tags schema at the same time.
