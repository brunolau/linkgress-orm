# v0.4.59

## Fix: `exists()`/`notExists()` collections join reference navigations used in `.where()`

A collection used as an EXISTS source whose `.where()` navigates a REFERENCE of
the collection target — e.g.

```typescript
db.discounts.where(d => or(
  notExists(d.campaignLinks),
  exists(d.campaignLinks.where(cl => eq(cl.campaign.isPublic, true))),
))
```

— failed at runtime with `missing FROM-clause entry for table "campaign"`.
Navigation joins were derived from selectors only, and an EXISTS aggregation has
no selector, so the where-navigated alias rendered unjoined.

`CollectionQueryBuilder.buildSql()` (the EXISTS path used by `exists()` /
`notExists()` in WHERE clauses and in sql-fragment projections) now derives the
missing joins from the where-condition's FieldRefs with the same machinery the
selector path uses (`addNavigationJoinForFieldRef` + `resolveNavigationJoins`),
including multi-hop chains and reference-rooted collection sources
(`pc.order.orderTasks.where(ot => eq(ot.task.status, 'pending'))`).

The rendered subquery stays correlated:

```sql
EXISTS (SELECT 1 FROM "discount_campaign_link"
JOIN "discount_campaign" "campaign" ON "discount_campaign_link"."campaign_id" = "campaign"."id"
WHERE "discount_campaign_link"."discount_id" = "discount"."id" AND "campaign"."is_public" = $1)
```

This makes correlated EXISTS the planner-friendly spelling for reachability
gates that previously had to be written as uncorrelated `IN`/`NOT IN` subquery
pairs (which Postgres plans as hashed SubPlans that scan the whole inner table
once per statement, and which cannot be anti/semi-joined under `OR`).

Known remaining gap (unchanged by this release): the collection STRATEGY paths
(CTE/lateral/temp-table projections, e.g. `.where(nav).select(...).toList()`)
still derive joins from the selector only — a projected collection whose
`.where()` navigates a relation the selector does not reference keeps failing
with the same missing-FROM error there.

## Fix: EXISTS collections inside laterals anchor on the lateral's alias

An EXISTS collection rendered inside a LATERAL projection (e.g. the fragment
`sql`${not(...exists(cdc.discountCode.discount.campaignLinks...))}`` inside a
collection selection) anchored its bridge joins / root correlation on the RAW
table name, while the lateral exposes that table only under its generated alias
(`FROM "cart_discount_code" "lateral_3_cartDiscountCodes"`) — failing with
`invalid reference to FROM-clause entry for table "cart_discount_code"`.

`CollectionQueryBuilder.buildSql()` now resolves the λ-root through
`context.lateralTableAliasMap` (the same mechanism
`lateral-collection-strategy` uses for its own correlations), translating ONLY
the λ-root — bridge-internal aliases are emitted by the subquery itself and are
never remapped. The collection-CTE fragment builder threads
`lateralTableAliasMap` into the fragment build context so the scope is visible
there.
