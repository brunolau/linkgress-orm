## Fix: `SqlFragment` on the value side of comparisons is now inlined

`eq(field, sqlFragment)` (and every comparison built on `WhereComparisonBase` — `ne`/`gt`/`gte`/`lt`/`lte`/`like`/`ilike`, plus `between` bounds) previously fell through `getRightSide`'s literal branch when the VALUE argument was a `SqlFragment`: the fragment object was pushed as a bound parameter, so the driver serialized the fragment's SQL text as a string value and Postgres rejected the statement at runtime — e.g.

```
PostgresError: invalid input syntax for type integer: "case "product_integration_definition"."integration_type""
```

The type system always accepted it (`FieldLike` includes `SqlFragment`), and the FIELD side already inlined fragments (`getDbColumnName`), so the asymmetry only surfaced at execution time. Both operand orders now emit identical SQL:

```typescript
// both render: "installation"."id" = (config->'axess'->>'installationId')::int
eq(sql`(${p.field}->'type'->>'installationId')::int`, i.id);
eq(i.id, sql`(${p.field}->'otherType'->>'installationId')::int`);
```

Details:

- `getRightSide` inlines `SqlFragment` values via `fragment.buildSql(context)` (params embedded in the fragment keep their emission-order indices), mirroring the field-side handling;
- `WhereComparisonBase.getFieldRefs()` and `BetweenComparison.getFieldRefs()` now surface `FieldRef`s embedded in value-side fragments, so alias resolution sees tables referenced only through a fragment;
- `IN`/`NOT IN` value arrays are unchanged (array items remain literal parameters).

### Files Changed

- `src/query/conditions.ts` — `getRightSide` fragment inlining; value-side fragment refs in `WhereComparisonBase.getFieldRefs` / `BetweenComparison.getFieldRefs`
- `tests/queries/sqlfragment-as-value.test.ts` — defect-proving coverage (value-side mirror of `sqlfragment-as-field.test.ts`)
