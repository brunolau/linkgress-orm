# v1.0.25

## Added: `lateralJoin()` on a nested reference path — `row => row.author.region` probes the last hop

1.0.23's `lateralJoin()` probed a reference navigation of the row itself (`b => b.author`) and refused one reached
through another navigation. When a query's rows reach a large table through a smaller one, the join of the LAST hop
is made off the intermediate table, and it is the statistics of THAT table's foreign-key column that decide its
plan: when the intermediate table references only a slice of the target, its histogram can end far below the
newest keys the rows hold, and the planner merge-joins the few rows against the target's whole primary-key index.
Probing the intermediate hop alone does not help — the last hop's plain join merges off the probe's output — and
nothing in the query could rule that plan out.

The selector may now name a path of reference navigations. The probe replaces the join of the path's last hop and
reads its foreign key off the join of the hop before it, which keeps its own join:

```typescript
await db.books
  .where(b => eq(b.shelfId, shelfId))
  .lateralJoin(b => b.author.region)
  .select(b => ({ title: b.title, author: b.author.name, region: b.author.region.name }))
  .toList();
// LEFT JOIN "authors" AS "author" ON "books"."author_id" = "author"."id"
// LEFT JOIN LATERAL (SELECT "region__probe".* FROM "regions" "region__probe"
//                    WHERE "region__probe"."id" = "author"."region_id" OFFSET 0) "region" ON true
```

- Opt in each hop that needs it: `.lateralJoin(b => b.author).lateralJoin(b => b.author.region)` probes both, the
  second probe reading the first one's alias; the call order does not matter.
- The path is resolved through the build's navigation plan: a path that renders under a path alias because another
  path ending in the same relation owns the plain one (`b.author.mentor.region` → `"mentor__region"`) probes under
  its own alias, and the other path keeps its plain join.
- Everywhere a one-hop probe renders: root queries (a table, after `where()`, `QueryBuilder`, `SelectQueryBuilder`),
  every select builder (after `select()`, through an `IEntityQueryable`), collections under the `lateral`, `cte` and
  `temptable` strategies (a collection's `count()` / `exists()` included), `count()` / `exists()` / `max()`,
  `QueryBatch` legs and `unionAll()` legs. Navigations and collections hanging off the probed alias read it.
- Every hop must be a reference (many-to-one / one-to-one) navigation. Refused when the query is built: a path that
  ends in or runs through a collection, naming it (`lateralJoin(): "author.books" is a collection of "authors"`);
  a column, plain (`b => b.title`) or reached through navigations (`b => b.author.name`); and, as for any probe,
  `update()` / `delete()`, `groupBy()` and a collection flattened by `selectMany()`.
- No signature change: the selector of every `lateralJoin()` returns `unknown`, so a path type-checks on every
  builder as it is.

Docs: `docs/guides/lateral-navigation-joins.md` — "A navigation reached through other ones" (new), the rendering
table, "Where it applies", "Refused".

Tests: `tests/queries/lateral-navigation-join.test.ts`, "lateralJoin() — a nested reference path", and a planner
case — each probed query against the same query without the probe (identical rows) and its exact SQL: the last hop
probed off the intermediate's plain join with nothing else changed; both hops probed, in either call order; the
untyped `QueryBuilder` / `SelectQueryBuilder`, a select builder (its projection kept — a compile-time assertion) and
an `IEntityQueryable`; a three-hop path under its path alias beside a shallower path ending in the same relation;
`count()` / `exists()` / `max()` with a WHERE on the probed alias; a collection's item path, and a navigation and a
collection hanging off the probe, under each strategy; a collection's `count()` and `exists()` filtering through the
probe; a `QueryBatch` leg and a `unionAll()` leg; the refusals; and, on PostgreSQL, the plans — with hash joins and
nested loops switched off, the plain two-hop read has two merge joins, the nested probe one (its own hop's is gone,
the regions read only through an index scan of the probe) and both probes none. On 1.0.24 each of the 15 new cases
fails (the selector is refused: "not a navigation reached through another one"). One assertion of "refused uses"
named `b => b.author.region` as refused; it now names a column reached through a navigation, which still is.

Backward compatible: a query without a nested path renders the SQL it rendered before. Of the published files only
`dist/query/query-builder.js` changes in code — the selector's reading (`lateralNavigationPath`), and the two places
that tell the opted-in joins (`isLateralNavigationJoin`, `markLateralJoins`): a query without `lateralJoin()` returns
at their unchanged first check, and a one-hop path matches exactly the joins 1.0.24 matched (its alias as the plan
gives it, joined from the root / item table). The typings change in comments only. Recorded in memory on 1.0.24 and
on this release, the 43 936 statements the suite runs outside the lateral test file differ in exactly the 298
statements (table names carrying the process id, timestamps) two recordings of 1.0.24 already differ in, and the
531 statements of that file's 21 earlier tests — every one-hop probe among them — are byte-identical, with identical
results.
