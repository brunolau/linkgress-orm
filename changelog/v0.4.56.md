## Feature: `MutationBatch` — independent bulk mutations in ONE database round trip

`QueryBatch` (v0.4.49) collapsed heterogeneous READS into one statement; write-heavy
flows kept paying one round trip per mutation. A checkout that inserts custom-field
values into three tables, attribute bindings into a fourth and patches order items
issued five sequential statements even though the writes are mutually independent.

`MutationBatch` composes independent `insertBulk` / `bulkUpdate` legs into one
data-modifying-CTE statement:

```sql
WITH "__mb_0" AS (UPDATE "order_task" AS t SET ... FROM (VALUES ...) v WHERE ... RETURNING 1),
     "__mb_1" AS (INSERT INTO "order_task_attribute" (...) VALUES (...) RETURNING 1)
SELECT (SELECT count(*)::int FROM "__mb_0") AS "0", (SELECT count(*)::int FROM "__mb_1") AS "1"
```

```typescript
const batch = new MutationBatch();
const itemsKey = batch.addBulkUpdate(db.orderTasks, itemUpdates, 'items');
batch.addInsertBulk(db.orderTaskAttributes, ddRows, 'dd');
batch.addInsertBulk(db.orderTaskTags, attrRows, 'attrs');
await batch.executeBatch();               // ONE round trip; no-op when every leg was empty
batch.getAffectedCount(itemsKey!);        // rows the update leg matched
```

### Semantics

- Each leg's SQL is EXACTLY what its standalone execution runs — the compile
  steps were extracted from `insertBulkSingle` / `bulkUpdateSingle` into
  internal `_buildInsertBulkStatement` / `_buildBulkUpdateStatement` (plus the
  shared `_resolveBulkUpdatePrimaryKeys`), so column mappers (Temporal, jsonb,
  custom `toDriver`) and bulkUpdate's per-row `"col__provided"` CASE flags are
  identical in and out of a batch.
- PostgreSQL data-modifying-CTE rules apply and are the batch's contract:
  every leg sees the SAME snapshot (one leg's writes are invisible to the
  others — legs must be independent), touching the same ROW from two legs is
  unsupported, and the statement is atomic (any leg's error rolls back all).
- Registration mirrors the standalone early-returns: empty row arrays register
  nothing and return `null`, so conditional legs need no caller guards; an
  empty batch's `executeBatch()` resolves without touching the database.
- Cross-leg `$N` renumbering reuses QueryBatch's quote-aware renumberer
  (string literals containing `$1` pass through verbatim).
- One-shot lifecycle, duplicate-id rejection and a same-client/executor guard,
  all as in QueryBatch. A leg above the single-statement parameter budget
  (the standalone chunking threshold) throws at registration.
- `ON CONFLICT DO NOTHING` legs count only genuinely inserted rows
  (`RETURNING` skips conflict-suppressed rows).

## Feature: `insertWithChildren` — guarded parent + dependent child bulk insert in ONE statement

The remaining two-statement pattern batching could not touch was the true data
dependency: insert an aggregate root, then bulk-insert its children with the
fresh parent id. `insertWithChildren` executes both — plus an optional
duplicate-guard probe — as one statement:

```typescript
const { parent, children } = await db.orders.insertWithChildren({
  row: orderRow,
  unlessExists: db.orders.where(o => and(eq(o.cartId, cartId), ...)).select(o => ({ id: o.id })),
  children: { table: db.orderTasks, foreignKey: 'orderId', rows: itemRows },
  returning: {
    parent: p => ({ id: p.id, createdAt: p.createdAt }),
    children: itemsProjection, // full navigation/collection returning surface
  },
});
// parent === null ⇔ the guard matched: NOTHING was inserted (same-snapshot NOT EXISTS)
```

Emitted shape: `WITH "__iwc_parent__" AS (INSERT … SELECT FROM (VALUES …) [WHERE
NOT EXISTS (guard)] RETURNING *), "__mutation__" AS (INSERT INTO child (fk, …)
SELECT p.pk, v.* FROM "__iwc_parent__" p CROSS JOIN (VALUES (0,…),(1,…))
v("__iwc_ord", …) ORDER BY v."__iwc_ord" RETURNING …) SELECT …`.

- The ordinal ORDER BY pins sequence allocation to INPUT-ROW order, and the
  outer select orders by the child pk — deterministic child ordering even under
  plans that would shuffle the navigation joins (the returning-order hazard).
- Child→parent reference navigations in the child projection are REWRITTEN to
  read from the parent CTE (`joinTableOverrides` on the returning builder) —
  the real parent table is snapshot-stale inside the same statement, so a join
  against it would silently drop every row. Collection projections must not
  traverse the parent table (unsupported).
- Values ride cast-annotated VALUES cells (`$n::type` / `NULL::type`, the
  bulkUpdate technique) so a bare VALUES source keeps correct column types;
  column selection and mappers match `insertBulk` exactly.
- Single-statement atomicity; single-column serial parent pk; flat parent
  returning; non-empty, single-statement-budget child rows; child rows must not
  carry the FK property. Guard/child client-context consistency enforced.
- Concurrency note: the guard is same-snapshot, NOT a serialization primitive —
  two concurrent statements cannot see each other's uncommitted rows. Callers
  race-guarding duplicates keep their own lock.
