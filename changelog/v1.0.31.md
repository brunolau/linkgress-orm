# v1.0.31

Six things a consumer's sweep of "statements that could be one" ran into: a union could not be counted inside a
`QueryBatch`; a value compared with a mapped column inside a collection's `where()` was bound unconverted (and the
collection's `min()` / `max()` of such a column read back raw); there was no way to TRY a list of advisory locks in
one statement; a grouped select could not aggregate the group's members into a list or count them distinctly; an
array column had no in-statement "append unless present" / "remove"; and `sum()` over a nested `count()` whose summand
goes through a reference rendered a hop nobody joined. Each comes with tests that fail without it, run on PostgreSQL,
PGlite and the in-memory database. Additions only: no existing signature changed. Everything that behaves
differently from 1.0.30 is listed, completely, under [What a caller may notice](#what-a-caller-may-notice).

## Added: `UnionQueryBuilder.futureCount()` and `futureFirstOrDefault()`

A union offered `future()` only. `batch.addCount(union, id)` threw `query.futureCount is not a function`, so the count
of a union cost a round trip of its own beside the batch — or the batch shipped the union's ROWS for a `.length` in JS.

```typescript
const batch = new QueryBatch();
const cart = batch.addFirstOrDefault(cartSummary(cartUuid), 'cart');
const cards = batch.addCount(
  db.campaigns.where(c => and(eq(c.active, true), inSubquery(c.id, linkedToScope)))
    .select(c => ({ id: c.id, holderId: literal(0) }))
    .with(scope.cte)                                                 // MATERIALIZED, read by both legs
    .unionAll(db.codes.where(c => inSubquery(c.discountId, scopeIds))
      .select(c => ({ id: c.discountId, holderId: c.userId }))
      .selectDistinct(r => ({ id: r.id, holderId: r.holderId }))),
  'cards',
);

await batch.executeBatch();   // ONE statement
batch.getCount(cards);        // number
```

- `futureCount(): FutureCountQuery` — `count()` fixed now and run later (`execute()`, `FutureQueryRunner.runAsync()`,
  `QueryBatch.addCount()`): the very statement `count()` runs, `SELECT COUNT(*) as count FROM (<union, its WITH
  included>) as union_count`, the union's own LIMIT / OFFSET counted as `count()` counts them.
- `futureFirstOrDefault(): FutureSingleQuery<T>` — `firstOrDefault()` fixed now and run later; LIMIT 1 is the
  future's, the builder keeps its paging; the row reads as `future()`'s rows do (the first leg's projection).
- Both REFUSE a union whose legs declare a data-modifying CTE (`withMutation`): a batch reads every member as a
  subquery, where PostgreSQL allows no such `WITH` (0A000) — and would run the mutation as a side effect of a read.
  `count()` / `firstOrDefault()` run it as a statement of its own. `future()` is unchanged.

## Fix: a mapped column of a collection's item — compared directly, and its `min()` / `max()`

`CollectionQueryBuilder` minted its item's column refs with `__fieldName`, `__dbColumnName`, `__tableAlias` and
`__chainId` only; the root's columns and a reference navigation's have always carried their mapper. Two symptoms:

```typescript
// WHERE side: the values were bound as written — never through the column's toDriver
db.tickets.where(t => and(
  t.product.timeSlots.where(s => and(eq(s.startsAt, slotStart), eq(s.endsAt, slotEnd))).exists(),
  not(exists(t.product.timeSlots.where(s => and(lte(s.startsAt, now), gte(s.endsAt, now))))),
));
// READ side: the stored value came back, not the mapped one
db.products.select(p => ({ lastEnd: p.timeSlots.max(s => s.endsAt) }));
```

With a `Temporal.PlainDateTime` mapped to `timestamp`, postgres.js threw `ERR_INVALID_ARG_TYPE` before the statement
was sent; with `{ hour, minute }` mapped to `smallint`, PostgreSQL answered 22P02; a driver that happens to serialize
the value (PGlite's `toString()`) ran the statement with whatever text that gave.

The fix is deliberately NARROW. An item's ref of a mapped column carries the mapper under a marker of its own
(`__itemMapper`), not under `__mapper`: every expression helper inherits `__mapper` from its operand — binding its
plain operands through `toDriver`, reading its result through `fromDriver` — and an expression over an item column
must keep doing what it did. The marker is read in exactly two places:

1. **A value compared DIRECTLY with the bare column** inside `collection.where(...)` is bound through `toDriver`:
   `eq` / `ne` / `gt` / `gte` / `lt` / `lte` / `like` …, `between`, `inArray` / `notInArray`, `eqAny` / `neAll` and
   the `…Opt` forms — in `exists()` / `not(exists(...))` / `notExists(...)`, in a collection of a projection, through
   reference navigations (`o.user.posts.where(...)`), nested in another collection, under every strategy.
2. **`min()` / `max()` of the bare column** — the item's, or one reached through the item's navigations
   (`max(p => p.user.lastSeenAt)`, whose ref already carried `__mapper`) — reads back through `fromDriver`: as a
   value of a root projection, of a collection's items, of a mutation's RETURNING, and through a QueryBatch.

Everything else over a mapped item column binds and reads EXACTLY as on 1.0.30:

- `coalesce`, `add` / `sub` / `mul` / `div`, `greatest` / `least` / `nullIf`, `caseOf`, `caseWhen`, an `sql` template —
  in the collection's filter (`gt(add(p.at, 60), 1000)` binds 60 and 1000 as written) and in its projection
  (`{ t: coalesce(p.at, 0) }` reads the stored value), in a list, a list of one value, `firstOrDefault()`, a nested
  collection;
- an aggregate of an EXPRESSION: `max(p => coalesce(p.at, …))`, `max(p => sql\`${p.at}\`)`, `sum(p => add(p.at, 5))`
  — and `sum()` / `count()` of anything — are numbers;
- a `min()` / `max()` read as a COLUMN of something else — a CTE column (`with('per_user', db.users.select(u => ({ last:
  u.posts.max(…) })))` then `c.last`), a joined table subquery's — is the value the body computed, the stored one;
- the collection's item LISTS of a bare mapped column were mapped already, through the collection's field configs,
  and still are — once (the tests use mappers that give NaN / an Invalid Date when applied twice);
- `disableMappers` turns the two off like every other read.

The typings are unchanged: a collection's `min()` / `max()` are still declared `SqlFragment<number | null>` whatever
the column's type is.

`tests/queries/collection-item-mapper-scope.test.ts` pins the expression shapes to the values 1.0.30 returns (it
passes on the 1.0.30 code — 120 of its tests, on PostgreSQL, PGlite and in memory); the eight that fail there are
the two behaviours above, the ref's shape and the cache test below.

**MockRowCache.** With the cache on, mock-row prototypes were keyed by table NAME, and a prototype holds what its
builder read of its model: the registry its navigations resolve in, a navigation's column mappers — and now an
item's. Two models that name a table alike (two context classes in one process) shared them: the second model's
rows read the first one's. The keys now carry the model of an entity-first context — its class
(`MockRowCache.registerModel`, called by the context) — so each such model gets prototypes of its own; one model
shares exactly as before. A schema-first `DataContext` registers none and shares by table name, as it always did
(its schema object may be made per instance: keyed by it, the cache would have nothing to share).

## Added: `tryAdvisoryXactLockAll(classId, keys): Promise<boolean>`

Every key tried WITHOUT waiting, in ONE statement — beside `advisoryXactLockAll` (which waits) and
`tryAdvisoryXactLock` (one key):

```typescript
await db.transaction(async tx => {
  if (!await tx.tryAdvisoryXactLockAll(LockClass.Order, orderIds)) {
    return 'busy';   // another transaction is settling one of them — nothing was waited for
  }
  // … every order is ours until COMMIT / ROLLBACK
});
```

- The keys are tried in the order `advisoryXactLockAll` takes them (duplicates removed, numbers ascending / strings in
  code-unit order, hashed with `hashtext()`); the statement STOPS at the first busy key and answers `false`. The keys
  before it stay held until the transaction ends — advisory locks are not given back one by one — and the keys after
  it are never tried. All taken: `true`. An empty list: `true`, no statement. Same validation and transaction
  requirement as `advisoryXactLockAll`.
- The statement is a recursive walk — one step per key, a next step only while the last try succeeded:

  ```sql
  WITH RECURSIVE walk(ord, ok) AS (
    SELECT 1, pg_try_advisory_xact_lock($1, (CAST($2 AS integer[]))[1])
    UNION ALL
    SELECT walk.ord + 1, pg_try_advisory_xact_lock($1, (CAST($2 AS integer[]))[walk.ord + 1])
    FROM walk WHERE walk.ok AND walk.ord < cardinality(CAST($2 AS integer[]))
  ) SELECT bool_and(walk.ok) AS "acquired" FROM walk
  ```

  The shorter `… FROM unnest(…) WITH ORDINALITY … WHERE NOT pg_try_advisory_xact_lock($1, s.k) LIMIT 1` stops at the
  busy key on PostgreSQL only because its executor is lazy under a LIMIT, which SQL does not promise: the in-memory
  database evaluates every row before it applies the LIMIT and took the keys AFTER the busy one. The recursive form is
  correct on both by construction.

## Added: `g.arrayAgg()` and `g.countDistinct()` — list / distinct aggregates over the grouped row

A grouped select aggregates with `g.count()` / `sum` / `min` / `max` / `avg`; `agg.arrayAgg(...)` in it could read the
grouping KEY only. A column of the grouped row inside `agg.arrayAgg()` named a table the statement does not have once
it groups by an expression (42P01 `missing FROM-clause entry`), so "the member ids of each group" was a fold in JS.

```typescript
const optionSignature = (p: ProductPrice) => coalesce(
  db.priceOptionLinks.where(l => eq(l.priceId, p.id))
    .select(l => agg.arrayAgg(l.optionId, { orderBy: [[l.optionId, 'ASC']] }))
    .asSubquery('scalar'),
  literal('{}', 'integer[]'),
);

const definitions = await db.productPrices
  .select(p => ({ id: p.id, slotId: p.slotId, optionIds: optionSignature(p), segmentIds: segmentSignature(p) }))
  .groupBy(r => ({ optionIds: r.optionIds, segmentIds: r.segmentIds }))      // array-valued keys
  .select(g => ({
    ...g.key,
    priceIds: g.arrayAgg(r => r.id, { orderBy: [[r => r.id, 'ASC']] }),      // number[]
    slots: g.countDistinct(r => r.slotId),                                    // number
    members: g.count(),
  }))
  .toList();
```

- `g.arrayAgg(r => r.col, { distinct?, orderBy? })` — `array_agg([DISTINCT] col [ORDER BY …])`: one element per row
  of the group (a NULL value is an element), each read like the column — through its mapper. `orderBy` is a list of
  selectors over the grouped row, each alone (ascending) or as `[selector, 'ASC' | 'DESC']`. A group has at least one
  row: the list is never NULL (a query without rows has no groups). On the Bun client's binary protocol it travels as
  `json_agg`, as `agg.arrayAgg` does. One driver caveat, not new: postgres.js hands an unquoted NULL element of any
  native array to the element's parser (`'NULL'`, `NaN`) where pg, Bun, PGlite and the in-memory database read
  `null` — on postgres.js, aggregate a nullable column only with its NULLs filtered out before grouping.
- `g.countDistinct(r => r.col)` — `count(DISTINCT col)`: the distinct non-NULL values, as a number.
- The selector returns a column of the grouped row (also one read through a navigation) or an `sql` expression of it;
  anything else — a constant, a nested aggregate — is refused with a message naming the call.
- `distinct` orders by the aggregated value only: `orderBy: [r => r.col]` for `g.arrayAgg(r => r.col, …)`, or the
  SAME expression written again (two selectors returning `sql\`${r.views} + 1\`` are one operand — one `__arg<n>`
  column — to the statement). Any other key is refused where the call is written (`g.arrayAgg(): with distinct, the
  list can be ordered by the aggregated value only …`) rather than by PostgreSQL's 42P10.
- A grouping key the caller named `__arg<n>` no longer collides with a generated operand column of the subquery
  form (42702 `column reference "__arg0" is ambiguous` — also for `g.sum()` & co. before): the generated names skip
  it.
- Both are available in `having()` (`gt(g.countDistinct(r => r.slotId), 1)`), inside `sql` expressions of the
  projection, over plain-column keys and expression keys (the subquery form: the operand is projected as an `__arg<n>`
  column of the subquery that computes the keys), as a CTE body, a joined table subquery and a `QueryBatch` member
  (`future()`, `futureFirstOrDefault()`, `futureCount()`).
- New exported types: `GroupedListAggregateOptions`, `GroupedAggregateOrderKey`.

## Added: `arrayAppendUnique(column, value)` and `arrayRemove(column, value)`

Values for the SET of a criteria `update()` over an array column: the change is made by the statement on each row's
current array — no read-modify-write, and running it twice changes nothing more.

```typescript
await db.products
  .where(p => inArray(p.id, touchedIds))
  .update(p => ({
    locationIds: caseWhen(inArray(p.id, addIds), arrayAppendUnique(p.locationIds, locationId))
      .else(arrayRemove(p.locationIds, locationId)),          // both directions, one UPDATE
  }));
```

- `arrayAppendUnique(column, value): SqlFragment<V[]>` —
  `(CASE WHEN value = ANY(col) THEN col ELSE array_append(COALESCE(col, '{}'), value) END)`: the value is appended
  unless the array holds it; a NULL array is treated as empty (the result is `{value}`). A `null` value is refused
  (NULL equals nothing: it would be appended on every call).
- `arrayRemove(column, value): SqlFragment<V[] | null>` — `array_remove(col, value)`: every occurrence removed
  (`null` removes the NULL elements); an array without the value is unchanged and a NULL array stays NULL.
- A plain value is ONE parameter cast to the column's element type when the ref carries it, as `arrayContains` casts.

## Fix: `sum()` over a nested `count()` whose summand goes through a reference hop

```typescript
campaign.links.sum(l => l.discount.codes.where(c => and(eq(c.userId, userId), gt(c.usedCount, 0))).count())
```

The count renders as a correlated subquery that reads the hop it hangs off (`"discount"."id"`) and leaves the join to
the collection being summed — which skipped a collection summand when it collected the navigations of its selector
(a summand directly on the item, `posts.sum(p => p.comments.count())`, has no hop and always worked). So the hop was
never joined, and what happened depended on what the enclosing statement had in scope under that name:

- nothing: 42P01 `missing FROM-clause entry for table "discount"` (the summed collection at the top level);
- a join of an ENCLOSING query — the list the sum sits in was itself reached through `….discount.…`: the count read
  THAT row. To PostgreSQL the SUM then reads only an outer query's columns, which makes it an aggregate of that outer
  query: 42803 `column … must appear in the GROUP BY clause or be used in an aggregate function`. The in-memory
  database evaluated it in place and answered with a number — the count of the enclosing row's codes, summed.

A collection summand is now walked like a collection of a projection: its navigation path, and the navigations of the
item its own filter correlates through, are joined by the collection being summed — under the lateral, CTE and
temp-table strategies, at the top level and nested in a list. A summand that joins its path inside its own subquery
(the hop's name was taken by an enclosing row — the one hop shape that worked) is left alone: it renders the
statement it rendered on 1.0.30, as a summand directly on the item does.

## Fix (in-memory database): an aggregate that reads only an outer query's columns is refused

PostgreSQL places an aggregate in the query of the LOWEST-level column its aggregated arguments, its ORDER BY keys
and its FILTER read (`check_agg_arguments`): `(SELECT sum(o.n) FROM t)` is an aggregate of the OUTER query, grouped
and evaluated there. The engine evaluated every aggregate in the query it is written in — the silent wrong number of
the fix above. It models no outer-level aggregates, so it now refuses one: 0A000 `aggregate function sum() reads only
columns of an outer query: outer-level aggregates are not supported by the in-memory database`, with PostgreSQL's
reading in the detail.

The rule this release holds the refusal to: **nothing PostgreSQL accepts and 1.0.30 answered as PostgreSQL does is
refused.** One column of the aggregate's own query anywhere among its operands keeps it that query's, as it always
was — `array_agg(o.n ORDER BY t.id)` (the argument outer, the ORDER BY key its own), `sum(o.n) FILTER (WHERE t.n >
1)`, `sum(t.n + o.n)`, a whole-row argument, a subquery argument that reads the aggregate's query, an ordered-set
aggregate's direct argument; an aggregate that reads no column at all (`count(*)`, `sum(1)`, a parameter) and a
window aggregate are their own query's too. 20 such statements are in the differential corpus now, identical on
PostgreSQL and in memory. What IS refused — 11 shapes pinned in `tests/memory/in-memory-database.test.ts` — is what
1.0.30 answered differently from PostgreSQL: a row per outer row where PostgreSQL raises 42803 (`p.id` is not
grouped) or returns ONE row (the aggregate over the outer rows), and 42803 `subquery uses ungrouped column` where
PostgreSQL returns the outer query's aggregate per group.

## Fix (in-memory database): what the array helpers ran into

- `array_remove`, `array_replace`, `array_position` and `array_positions` of a NULL array failed with XX000 (`null is
  not an object`): they are not strict in PostgreSQL — the element they look for may be NULL — and answer NULL for a
  NULL array themselves.
- An unnamed `CASE … END` column was always named `case`. PostgreSQL names it after its ELSE result when that names
  itself — a function (`array_append`), a column — and `case` otherwise.

Both are in the differential corpus (`tests/memory/sql-parity-corpus.ts`) now.

## What a caller may notice

The complete list of what behaves differently from 1.0.30. Everything not listed emits the SQL, binds the parameters
and reads the values it did (see Neutrality below).

**The ORM**

1. **A plain value compared DIRECTLY with a mapped column of a collection's item is converted** — `eq` / `ne` / `gt`
   / `gte` / `lt` / `lte` / `like` …, `between`, `inArray` / `notInArray`, `eqAny` / `neAll`, `inArrayOpt` /
   `notInArrayOpt` inside `collection.where(...)`. Code that worked around the missing conversion by passing the
   DRIVER value itself (`eq(p.publishTime, 570)` for a `{ hour, minute }` column, `toDbText(value)`) now has that
   value handed to `toDriver`: pass the application value. A `toDriver` that is idempotent over its own output is
   unaffected; one that is not binds what it makes of the driver value (NaN → 22P02) or throws.
   A JS array compared with a native array column (`.array()`) of an item binds as an array literal, through the
   column's implicit mapper: the same rows as before on pg, postgres.js, PGlite and in memory; on the Bun client,
   which cannot bind a JS array, the comparison failed before and works now.
2. **A collection's `min()` / `max()` of a bare mapped column returns the mapped value**, not the stored one — the
   item's column, or one reached through the item's navigation — as a value of a root projection, of a collection's
   items, of a mutation's RETURNING, and in a QueryBatch. Code that mapped the raw extreme by hand must stop. The
   declared type is still `number | null`. NOT changed: an aggregate of an expression, `sum()` / `count()`, and a
   `min()` / `max()` read through a CTE column or a joined table subquery (the stored value, as before).
3. **`sum(l => l.ref.collection.count())` works** where it raised 42P01 / 42803. The shapes that worked — a summand
   directly on the item, and one whose hop name an enclosing row had already taken (it joins its hop inside its own
   subquery) — render the statement they rendered.
4. `GroupedItem` (and the `having()` group) carry two new members, `arrayAgg` and `countDistinct`: code that types an
   object of its own as `GroupedItem` must add them.
5. A grouped query over an expression key whose key is NAMED `__arg<n>` (42702 before) works: the generated operand
   columns skip the name.
6. With `MockRowCache` on, two entity-first models (two `DbContext` classes) that name a table alike no longer share
   mock-row prototypes: the second model reads its own columns, relations and mappers (it read the first one's).
   One model per table name — the usual case — and schema-first contexts share as before.
7. New: `UnionQueryBuilder.futureCount()` / `futureFirstOrDefault()`, `tryAdvisoryXactLockAll()`, `g.arrayAgg()` /
   `g.countDistinct()`, `arrayAppendUnique()` / `arrayRemove()`, the exported types `GroupedListAggregateOptions` /
   `GroupedAggregateOrderKey`. An item's ref of a mapped column has one more (internal) key, `__itemMapper`.

**The in-memory database**

8. An aggregate that reads only an OUTER query's columns is refused (0A000). Before: another result than
   PostgreSQL's — a row per outer row where PostgreSQL raises 42803 or returns one row — or 42803 `subquery uses
   ungrouped column` where PostgreSQL returns a result. Through the ORM this is `u.posts.sum(_p =>
   u.orders.count())` (a summand that reads nothing of the summed collection: PostgreSQL 42803, memory answered) and
   `agg.sum(outer.col)` in a scalar subquery. An aggregate with one column of its own query among its arguments,
   ORDER BY keys or FILTER answers as before.
9. `array_remove` / `array_replace` / `array_position` / `array_positions` of a NULL array answer NULL (XX000 before).
10. An unnamed `CASE … END` whose ELSE result names itself (a function, a column) is named after it, as in
    PostgreSQL (`case` before) — visible to raw SQL that reads a row by the name PostgreSQL gives an unaliased
    column.

Not a change, but worth knowing: postgres.js hands an unquoted NULL element of ANY native array to the element's
parser (`'NULL'`, `NaN`); `g.arrayAgg()` of a nullable column is affected as `agg.arrayAgg()` is. And `disableMappers`
takes effect only on a context that has an executor (one that logs, prepares, or watches slow queries).
