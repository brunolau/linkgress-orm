# Feature: candidate-CTE reads — union CTE bodies, `MATERIALIZED`, `joinFilter(cte)`

Three composable additions that together express the **candidate-set read
shape** in one statement:

```ts
const cteBuilder = new DbCteBuilder();
const candidates = cteBuilder.with('ticket_candidates',
  buyerLeg.union(assignedLeg).union(cardLeg),   // id-only visibility legs
  { materialized: true });                       // optimizer fence

const rows = await db.orderItems
  .where(p => and(...gates, ...productFilters))
  .select(p => ticketProjection(p, language))
  .joinFilter(candidates.cte, (row, c) => eq(row.id, c.id))
  .orderBy(...)
  .toList();
```

## 1. `UnionQueryBuilder` as a CTE body

`DbCteBuilder.with(name, legA.union(legB), ...)` now works: the union renders
through the outer parameter context (placeholder numbering chains correctly
across CTEs and the outer statement), and the FIRST leg's selection metadata
provides the CTE's typed column refs — sound because PostgreSQL enforces
column-shape equality across all union legs.

## 2. `with(name, query, { materialized: true })`

Emits `WITH name AS MATERIALIZED (...)` — the optimizer fence that forces
PostgreSQL to compute the CTE once as an opaque relation. Since PG12 a
single-reference CTE is inlined into the outer plan by default; for a
candidate-set CTE that inlining dissolves the "candidates first" shape and
lets a bitmask-misestimated join flip the whole statement into full-scan
merges. Measured on a production-sized dataset (122M-row `order_item`,
worst-case 1,392-member household): inlined 6,400ms, `MATERIALIZED` 161ms.

## 3. `joinFilter` / `leftJoinFilter` accept a `DbCte`

The pure-row-filter join now takes a CTE as its right side: the ON/filter
callbacks address the CTE's columns, the selection shape is preserved, and
the CTE is **auto-attached** to the statement's WITH list (as if `.with(cte)`
had been called), deduplicated by name. Typed overloads on
`IEntityQueryable`, the entity select builder and `SelectQueryBuilder`.

An INNER `joinFilter` against the deduplicating `UNION` of id legs is the
load-bearing half of the shape: the semi-join spelling
(`WHERE id IN (SELECT id FROM candidates)`) measured 3,339ms against the
join's 161ms on the same data — the join keeps the fenced CTE the driving
side of the plan.

The composed statement rides `QueryBatch` unchanged (a parenthesized
`WITH ... SELECT` is a valid envelope branch).

## Why

Born from the same production tickets read as v0.4.52's `hasDbSetting`: the
two-phase fallback (fetch candidate ids, hydrate by literal id array) was
robust but cost a second round trip. This shape delivers the identical plan
guarantees in ONE statement — and one shared round trip when batched.

Covered by `tests/queries/cte-union-materialized-joinfilter.test.ts` (union
CTE body + dedupe, MATERIALIZED emission, auto-attach, QueryBatch ride).
