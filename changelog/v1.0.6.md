# v1.0.6

## Feature: model-managed views

A database VIEW can now be declared in the model, next to the entities, and linkgress owns its
lifecycle — the same way it owns tables, indexes and CHECK constraints.

```ts
model.view(OrderSummary, view => {
  view.toView('order_summary');
  view.definedAs(`SELECT o."id", o."label", o."amount" / 100 AS "amount_eur" FROM "orders" o`);
  view.property(e => e.id).hasType(integer('id'));
  view.property(e => e.label).hasType(varchar('label', 50));
  view.property(e => e.amountEur).hasType(integer('amount_eur'));
});

get orderSummaries(): DbViewTable<OrderSummary> {
  return this.view(OrderSummary);
}
```

A view can equally be defined with the query builder instead of SQL text:

```ts
model.view(OrderStats, view => {
  view.toView('order_stats');
  view.definedAs((db: AppDatabase) => db.orders
    .where(o => gt(o.amount, 0))
    .select(o => ({ id: o.id, label: o.label, lineCount: o.lines.count() })));
  view.property(e => e.id).hasType(integer('id'));
  view.property(e => e.label).hasType(varchar('label', 50));
  view.property(e => e.lineCount).hasType(integer('line_count'));
});
```

The context renders the query (any shape with `asSubquery()`: `select`, grouped `select`, unions,
CTE-rooted queries) when a schema manager needs it: the projection is renamed to the declared column
names in declaration order, bound values are inlined as escaped literals (a view has no parameters),
and array aggregations render natively whatever the driver. The compiler checks that every view
property is projected; a missing, extra or nested key is refused by name at render time.

### Semantics

- `ensureCreated()` creates views after the tables; `ensureDeleted()` drops them first.
- `analyze()` plans `drop_view` / `create_view` operations from a marker stored with
  `COMMENT ON VIEW … IS 'linkgress:view:sha256:<hash of the definition>'`: a missing view is created, a
  changed definition is dropped and re-created, and ANY column or table change in the plan
  (`alter_column`, `drop_column`, `drop_table`) drops every managed view first and re-creates it last —
  PostgreSQL refuses `ALTER COLUMN … TYPE` / `DROP COLUMN` under a dependent view (`0A000` / `2BP01`).
- Because the view operations are part of `analyze()`'s output, `migrate()` also restores a view that
  was dropped by hand on a database whose tables are already in sync (it no longer returns early).
- Drops are placed FIRST in the operation list and creates LAST, so a `MigrationScaffold` file runs
  them in a safe order too.
- A view in its own schema (`view.toSchema(...)`) creates that schema.
- `DbViewTable` exposes the read surface of a table only; `update()` / `delete()` on a query over a view
  throw before any SQL (a single-table view is auto-updatable in PostgreSQL).
- Declare a view AFTER the views it reads: a view that is dropped takes every view declared after it along
  (dropped before it, re-created after it) — PostgreSQL refuses to drop a view another view reads (`2BP01`).
  Removing a view from the model does not drop it.
- A re-create is `DROP VIEW` + `CREATE VIEW`: grants on the view, a changed owner and any comment other than
  the marker are lost. Give read-only roles their access through `ALTER DEFAULT PRIVILEGES … GRANT SELECT ON
  TABLES` (or re-grant in `onMigrationComplete`).
- A scaffolded `create_view` is preceded by `DROP VIEW IF EXISTS`, so the file also runs on a database whose
  view already exists (e.g. created by the model's own `migrate()` first).

### What changed

- `getSchemaManager()` hands `DbSchemaManager` the TABLE registry and the views as a separate
  `views` option, so none of the manager's whole-registry loops can mistake a view for a table.
- The view's `TableSchema` carries `view: { definition }`; the query builder reads it like a table.

### Plumbing

- `src/migration/view-sql.ts` holds the statement builders and the marker, shared by the live migrator
  and the scaffold (the `check-constraint-sql.ts` pattern).
- In-memory engine: no change needed — it already parses `CREATE VIEW`, `DROP VIEW`, `COMMENT ON VIEW`
  and serves `obj_description`. A parity case now pins that lifecycle against PostgreSQL.

### No regression for models without views

- A table's `TableSchema` has no `view` key at all (only a view's entry gets one).
- The schema manager of a model without views receives the registry's own schema objects and sends no
  view-related statement through `ensureCreated()` / `analyze()` / `migrate()` / `ensureDeleted()`.
- Declaring a view changes nothing in the table part of a migration plan.
- The full suite of the previous source (1 860 tests) has the identical outcome, test by test, on
  PostgreSQL 18 and in memory (`--parity`).

## Fix: navigations and collections of a joined table

A table added with `leftJoin` / `innerJoin` lives in the query under the join's alias (`posts_0`), not
under its table name. Its navigations used neither:

- A **reference navigation** of the joined row (`post.user.username` in
  `db.orders.innerJoin(db.posts, …, (order, post) => …)`) rendered under its relation name and was resolved
  against the ROOT's relations: with a root navigation of the same name (`order.user`) it silently read the
  ROOT's row — every post's author came back as the order's owner — and otherwise failed with
  `missing FROM-clause entry`. A chain below it (`orderTask.task.level.createdBy`) had no relations at all.
- A **collection** of the joined row (`user.posts.count()`) correlated to the table name — `invalid reference
  to FROM-clause entry` — or, when the root had that name, to the root row.

Now such a navigation renders under an explicit alias, `<join alias>__<relation>` (`posts_0__user`,
`posts_0__user__profile`), and its columns carry their join path, so the query emits exactly those joins —
always as LEFT JOINs: below a LEFT join whose row is missing, a required hop's INNER JOIN would drop the row
the join kept. A collection of the joined row (or of a navigation below it) correlates to that alias. An
alias past PostgreSQL's 63-byte identifier limit is refused (it would be truncated and could collide).
`leftJoin` / `innerJoin` now hand the schema registry to the builder they return (it had none, which is why
a navigation's target had no relations of its own).

The `cte` and `temptable` collection strategies attach a collection to the ROOT row's id, so for a collection
of a joined table they refuse the query by name instead of pairing it with the wrong parent; `lateral` (the
default) renders it.

Two more shapes of the same kind: a whole navigation row of a joined table (`author: post.user`) is selected
as a JSON object (it was dropped from the row without an error), and a ROOT navigation chain resolved by name
(`comment.order.user`) is never answered by a joined table's navigation target that happens to have a relation
of the same name.

## Fix: `orderBy` of an unlimited `toNumberList()` / `toStringList()` (lateral strategy)

Without `limit` / `offset` a list aggregation renders as a correlated subquery, and its `ORDER BY` was dropped
("for array aggregations, ORDER BY doesn't matter") — the array came back in scan order. It is now written
into the aggregate — `array_agg(expr ORDER BY "inner"."col" …)` — qualified with the subquery's alias, since a
navigation joined for the selector can carry a column of the same name. Only an ordering by the collection's
own columns is rendered; any other keeps the previous rendering. (`selectDistinct` lists: unchanged.)

## Feature: `count()` inside a `sql` fragment

A collection's `count()` renders inside a fragment as a correlated scalar subquery, the way `exists()`
already did — e.g. to keep a view column `integer` rather than `bigint`:

```ts
lineCount: sql<number>`${o.lines.count()}::int`,
```

The count names its own table (`"<relation>__count"`), so a count through a navigation back to the SAME
table (`post.user.posts`) correlates to the outer row instead of to itself. Any other aggregate inside a
fragment still throws.

### Not covered yet (each fails loudly, none silently)

- `groupBy` over a joined table's navigation — `missing FROM-clause entry` (the grouped builder has its own
  join detection).
- A navigation of a joined table inside a LATER join's ON clause — `missing FROM-clause entry`; join that table
  explicitly before the join that reads it.
- (Unchanged, and not an error:) an unlimited list ordered by a navigation column, or a `selectDistinct` list,
  keeps its unordered rendering.

Together these let a view be written the way a hand-written view joins — explicit joins on computed keys,
navigations of the joined rows, ordered lists, casts — with no SQL text (see
`tests/schema/views-query.test.ts`, "a view over an explicit join").
