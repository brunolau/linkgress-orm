## Fix: timeout errors on a pre-built `postgres` instance no longer report `0ms`

A `PostgresClient` constructed from an **already-built** porsager instance could not see the
connection-level `statement_timeout`, so every cancellation by that cap surfaced as the
`timeoutMs ?? 0` sentinel:

```
QueryTimeoutError: Query exceeded its timeout of 0ms and was cancelled
```

`0ms` names no limit, which makes the error — and any `[SQL Error] ${error.message}` line
`DbContext` logs from it — undiagnosable: the reader cannot tell which cap fired, or even that
a cap was configured at all.

The cause was a gap between the two constructor paths. `statement_timeout` is recorded into
`defaultStatementTimeout` only by `normalizeConfig()`, which runs exclusively on the config-object
path:

```typescript
// config object → normalizeConfig() records the cap → errors report it
new PostgresClient({ ...connectionOptions, statement_timeout: 20_000 });

// pre-built instance → normalizeConfig() never runs → errors reported "0ms"
const sql = postgres(url, { connection: { statement_timeout: 20_000 } });
new PostgresClient(sql);
```

The second form is what an application uses when it needs to own the pool itself — for example to
drop and rebuild it on a failover — so the path that most needs diagnosable timeouts was the one
that lost the value.

The instance already carries its connection parameters, so the client now recovers the cap from
them at construction:

```typescript
const sql = postgres(url, { connection: { statement_timeout: 400 } });
const client = new PostgresClient(sql);

await client.query('SELECT pg_sleep(5)');
// QueryTimeoutError: Query exceeded its timeout of 400ms and was cancelled
//   err.timeoutMs === 400
```

Details:

- `readConnectionStatementTimeout()` reads `sql.options.connection.statement_timeout`, accepting a
  number or a numeric string (porsager passes connection parameters through as given, and one that
  arrived from a connection string is a string);
- it returns `undefined` when the instance sets no timeout, so the sentinel behaviour is unchanged
  for pools that genuinely have no connection-level cap;
- the recovered value flows through the existing `defaultStatementTimeout` plumbing, so it also
  covers statements run inside `transaction()` and connections handed out by `connect()`;
- a per-query `.withTimeout(ms)` override still takes precedence — it reaches the driver explicitly
  and was always reported accurately.

### Files Changed

- `src/database/postgres-client.ts` — `readConnectionStatementTimeout()`; recover the cap in the
  `isPostgresSqlInstance` constructor branch
- `tests/queries/query-timeout.test.ts` — defect-proving coverage for the pre-built-instance path
  (direct query, statement inside a transaction, per-query override precedence, and a no-timeout
  instance as the control)
