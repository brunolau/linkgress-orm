## Feature: `QueryBatch` — heterogeneous queries in ONE database round trip

Dashboards that fire N independent queries pay N round trips (and under postgres.js
`prepare: false`, actually 2·N — every unprepared parameterized query does a
describe-first round trip before executing, and describe-first also blocks wire
pipelining). The existing `FutureQueryRunner` only truly batches when the client
supports multi-statement simple protocol AND every query is parameterless, so real
parameterized workloads silently fell back to sequential execution.

`QueryBatch` executes any mix of list / firstOrDefault / count queries as one
UNION ALL statement of uniform json envelopes:

```sql
SELECT 0 AS __batch_ix, coalesce(json_agg(row_to_json(__batch_q)), '[]'::json) AS __batch_items FROM (<query 0>) __batch_q
UNION ALL
SELECT 1, ... FROM (<query 1>) __batch_q
```

PostgreSQL plans each branch independently (`Append` node) — every query keeps its
own indexes, verified with EXPLAIN ANALYZE. Parameters are merged and renumbered
across branches. Works on every driver (PgClient, PostgresClient, BunClient) since
the envelope is plain json.

```typescript
const batch = new QueryBatch();
const ordersKey = batch.addList(
  db.orders.where(o => eq(o.userId, userId)).select(o => ({ id: o.id, total: o.totalAmount })),
  'orders'
);
const userKey = batch.addFirstOrDefault(db.users.where(u => eq(u.id, userId)).select(u => u), 'user');
const cntKey = batch.addCount(db.tickets.where(t => eq(t.eventId, eventId)), 'tickets');

await batch.executeBatch();               // ONE round trip

const orders = batch.getList(ordersKey);  // typed from the selection
const user = batch.getItem(userKey);      // typed | null
const tickets = batch.getCount(cntKey);   // number
```

`add*` returns a typed key so the getters infer element types without manual
generics; plain string identifiers work as an escape hatch (`batch.getList('orders')`).

### Result fidelity

Batched results are **identical** to standalone `.toList()` / `.firstOrDefault()` /
`.count()` execution — same values, same types. JSON delivery bypasses the
driver's type parsers, so the query builder now attaches a declared-type-driven
reviver to futures (`FutureQuery._batchMeta`): `timestamp`/`timestamptz`/`date`
strings are revived to `Date` (dates at local midnight, mirroring the drivers),
`decimal`/`numeric` JSON numbers back to scale-formatted strings, `bigint` to
strings — then the rows run through the SAME transform pipeline as standalone
execution (nested-path reconstruction, custom mappers via `fromDriver`).
Revival is keyed on declared column types, never value shape, so text columns
holding date-like strings are never touched.

### Semantics

- One-shot: register → `executeBatch()` once → read. Adding or re-executing after
  execution throws.
- Duplicate identifiers, unknown identifiers, kind-mismatched lookups
  (`getItem` on a list key), reads before execution, and empty batches all throw
  descriptive errors.
- All queries must share one client/executor (transaction) — mixing throws.
- Nested **object** selections (`select(p => ({ a: { b: ... } }))`) are rejected at
  `add*` time with a descriptive error — use flat selections (flat
  navigation-property fields like `{ author: p.user.username }` are fully
  supported). Whole-entity selections (`select(u => u)`) are supported.
- Per-branch ORDER BY / LIMIT / OFFSET are preserved.

### Performance (measured, `bench/querybatch/`)

At 31 ms RTT, a 30-query dashboard: sequential 1 853 ms → QueryBatch 62 ms
(2 round trips: describe + execute), → 31 ms (1 round trip) when the batch
statement is prepared. Server-side json_agg overhead is negligible at dashboard
result sizes (0.84 ms for a 12-branch batch), ~37% on 20k-row payloads.
