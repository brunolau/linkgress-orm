# v1.0.16

## Fix (in-memory database): each key of a multi-expression index gets its own lookup

The in-memory engine answers `<index expression> = <value>` through a hash map over the heap, built on first
use and cached on the heap. The cache key was the index oid and the value type only:
`'expr:' + ix.oid + ':' + type`. An index over two expressions therefore shared one map between both keys.
Whichever key was probed first built the map, and every later lookup on the other key read it.

```sql
CREATE INDEX ix_user_search ON "user" (search_normalize(name), search_normalize(surname));

SELECT id FROM "user" WHERE search_normalize(name) = search_normalize('novak');    -- builds the map over name
SELECT id FROM "user" WHERE search_normalize(surname) = search_normalize('novak'); -- probed the name map
```

The second query probed the `name` map with the surname value. The rows it found were then filtered by the
real predicate, so it returned only rows whose name AND surname both matched (usually none) instead of its own
rows. No error was raised. PostgreSQL was never affected.

The key now includes the position of the expression in the index:
`'expr:' + ix.oid + ':' + <key position> + ':' + type`. The poisoned-index bookkeeping uses the same key, so
an expression that cannot be evaluated for some row now disables only the lookups on that key, not on the
other keys of the index.

Other heap-index caches were checked and are not affected: unique indexes (`uniq:<oid>`) cache one map over the
whole composite key, and plain-column and foreign-key lookups are keyed by their columns.

Reported with the diagnosis by Stas Polianychko, from 7 gopass server tests that read one index key after the
other.

Tests: `tests/schema/expression-index.test.ts`, "lookups on each key of a multi-expression index return that
key's rows". It probes both keys of `(lower(name), lower(email))` in both orders, and fails in memory without the
fix.

### Upgrade notes

- In-memory databases only. No change to SQL generation or to PostgreSQL behaviour.
