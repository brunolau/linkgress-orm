# v1.0.2

## In-memory database: less work per row, fewer objects per database

1.0.1 closed the gaps that showed up on a full-size seed. This release goes after what the executor
spends per ROW: a CPU profile of a downstream suite's shapes — point selects, an indexed join, a
grouped aggregate, a filtered sequential scan, a write transaction, a repeated prepared statement —
put 71 % of engine time in `exec`, almost all of it in allocations and closure hops that the row
loop repeated for every tuple it touched. Nothing here changes what a statement returns.

Measured over the downstream suite's own 46 MB snapshot (~58k rows; postgres.js over the in-process
socket, so protocol encode/decode is included; best of three interleaved rounds):

| | 1.0.1 | 1.0.2 |
| --- | --- | --- |
| point select by primary key | 80 µs | 37 µs |
| indexed lookup + join (price → slot), 200 rows | 874 µs | 488 µs |
| grouped aggregate over a price grid | 1 177 µs | 562 µs |
| filtered sequential scan over 33k rows | 5 796 µs | 2 254 µs |
| insert + update + delete in one transaction | 2 019 µs | 825 µs |
| prepared statement repeated with new parameters | 825 µs | 319 µs |
| **whole workload** | **3 420 ms** | **2 291 ms** |

The downstream suite (17 729 tests over 1 486 files, four workers, every database in memory) passes
unchanged on both, and this package's own suite passes in memory (1 875 tests).

### Comparisons no longer allocate

`col = $1`, `price > 1000`, `active = true` — the shape of nearly every scan filter and index qual —
compiled to an implementation taking an argument ARRAY, so each row allocated a two-element array
whose only consumer read it back immediately, through two closure hops. A two-argument comparison is
now called directly with its operands. Where the left side is a plain column of the current query
level, the column read is fused into the same closure: the row pays one call for the whole
comparison instead of three.

### Column reads are inlined into the projection

A compiled evaluator for a plain column now carries what it reads (`VarRead`: range-table index,
physical column, missing value), so a caller running it over many rows can take the value straight
out of the tuple. `SELECT a, b, c` previously cost one closure call per column per row; the
projection loop now reads them inline and calls an evaluator only for expressions.

### Frozen rows skip the transaction table

Every tuple a scan reads went through the full visibility rules, whose first step resolves the
top-level transaction of `xmin` — a map lookup per tuple. A tuple that is frozen and not deleted is
visible to every snapshot, which is the state of every row of a restored database, so that case is
now answered before the general path.

### Grouping and aggregation

The hash key of a GROUP BY column resolved its type through a switch per key per row; the type is
now resolved once per column into a function, and for the types whose key IS the value (integers,
text, dates, booleans, uuid) that function is a null check. Transition functions receive a reusable
argument array instead of a fresh one per row — every built-in aggregate reads its arguments during
the call — and `count` accumulates a double, widening to `bigint` once at the end, instead of
allocating a BigInt per counted row.

### Restored databases hold fewer objects

`PgNumeric` is immutable, and a seeded database repeats the same amounts thousands of times (prices,
VAT rates, zero). Restoring a snapshot now shares one instance per distinct value. On the same 46 MB
snapshot the restored database went from 1.37 M objects to 0.82 M, of which BigInts fell from 326 k
to 72 k, and the JS heap it occupies from 138 MB to 112 MB — per database, so a test worker per core
saves a multiple of that.

### Scans

The per-tuple emit path lost a per-row iterator allocation (`for…of` over the filter list) and
repeats less index arithmetic; the row template is hoisted out of the loop.
