# v1.0.41

## Fix: a union joined as a table — rows typed as rows, columns read and bound like the first leg's

`UnionQueryBuilder.asSubquery('table')` — a union used as a table source (`innerJoin` / `leftJoin`, `insertFrom`,
`view.definedAs(db => …)`) — fell short of a select's table subquery in two ways:

- **Its rows were typed as an ARRAY** of the legs' row (`Subquery<TSelection[], 'table'>`), where every other builder
  types the row. A join's selector over it saw `r.authorId` on an array (`TS2339: Property 'authorId' does not exist on
  type '{ id: number; authorId: number; }[]'`, with TypeScript 5.9 and 7), and a union could not satisfy a view's row
  type in `definedAs`. It is `Subquery<TSelection, 'table'>` now.
- **Its columns carried no column mapper.** The subquery kept no selection, so a column read back out of it read the
  driver value, and a value compared with it was bound raw — a `Date` against an integer column behind a custom mapper:

  ```
  invalid input syntax for type integer: "2025-03-01T00:00:00.000+00:00"
  ```

  A table subquery of a union now keeps its FIRST leg's selection — the same metadata a union CTE body already reads
  (`getSelectionMetadata()`), as `SelectQueryBuilder.asSubquery('table')` keeps its own — so its columns read and bind
  like the first leg's: the `Date` binds through the mapper (`5097600`) and every value reads back as a `Date`.

```typescript
const activity = db.users.where(u => eq(u.isActive, true)).select(u => ({ id: u.id, name: u.username, lastActiveAt: u.lastActiveAt }))
  .unionAll(db.users.where(u => eq(u.isActive, false)).select(u => ({ id: u.id, name: u.username, lastActiveAt: u.lastActiveAt })))
  .asSubquery('table');

await db.users
  .innerJoin(activity, (u, a) => eq(u.id, a.id), (_u, a) => ({ name: a.name, lastActiveAt: a.lastActiveAt }), 'activity')
  .where(r => gte(r.lastActiveAt, new Date('2025-03-01T00:00:00Z')))
  .toList();
```

`'array'` and `'scalar'` union subqueries (`inSubquery`, `exists`, a scalar comparison) are unchanged.

## Behaviour change: a union is checked like any other query where a table subquery's projection is checked

With its selection known, a union now meets the checks a select already met:

- `view.definedAs(db => union)`: the first leg's projection must match the view's properties — a property it does not
  project, a key the view does not declare, or a nested object is refused by name when the schema manager is created.
  Before, a union view was not checked: an extra key was dropped by the view's outer SELECT, a missing one failed at
  `CREATE VIEW`.
- `insertFrom(union.asSubquery('table'), …)`: a column the union does not project is refused by name when the INSERT
  is built, where it used to reach PostgreSQL.

## Tests

- `tests/queries/union-subquery.test.ts`, "a union joined as a table: typed rows, columns read and bound through the
  first leg's mappers" — fails on 1.0.40 with the error above, on PostgreSQL and in memory.
- `tests/types/subquery-helper-inference.test.ts`: the consumer (published declarations) joins a union as a table —
  `TS2339` on 1.0.40, with TypeScript 5.9.3 and 7.0.2.
- `tests/schema/views-query.test.ts`: "a union works as a view" (passes on 1.0.40 too: a valid union view is unchanged)
  and "a union is checked like any other query: a key its first leg projects that the view does not declare" (did not
  throw on 1.0.40).
