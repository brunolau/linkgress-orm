# v0.4.61

## Fix: CTEs are now visible across UNION legs and inside `count()` / `exists()`

Two independent places dropped a query's `.with(...)` CTEs, both of which made
the canonical "fence the expensive candidate set behind one MATERIALIZED CTE and
read it from several places" shape impossible to express fluently.

### 1. `UnionQueryBuilder` hoists its legs' CTEs to statement level

Each leg rendered its own `WITH` prefix and `buildSql()` wraps every leg in
parentheses, so a CTE attached to the first leg ended up scoped **inside**
`(WITH x AS (...) SELECT ...)`. The next leg could not see it and PostgreSQL
answered SQLSTATE `42P01`, `relation "x" does not exist`:

```sql
-- before
(WITH "scope" AS MATERIALIZED (...) SELECT ... FROM "a" WHERE ... "scope" ...)
UNION ALL
(SELECT ... FROM "b" WHERE ... "scope" ...)   -- 42P01
```

The legs' attached CTEs are now collected up front, deduplicated by name (first
declaration wins, so the same `DbCte` may be attached to every leg), and emitted
as a single statement-level `WITH`:

```sql
-- after
WITH "scope" AS MATERIALIZED (...)
(SELECT ... FROM "a" WHERE ... "scope" ...)
UNION ALL
(SELECT ... FROM "b" WHERE ... "scope" ...)
```

Two legs attaching **different** CTEs under the **same name** now throw. A
statement-level `WITH` can declare each name only once, so the second definition
would be dropped together with its params — its leg would silently read the first
one's rows and every later placeholder would shift. Attaching the same `DbCte`
instance (or two indistinguishable definitions) to several legs still collapses to
one declaration, as before.

Parameter order is part of the fix, not a side effect: `DbCte` bodies carry
placeholders numbered from `$1`, so the hoisted CTEs' params are pushed **before**
any leg body is built — the same contract `buildQueryCore` already honoured on
the non-union path. `SqlBuildContext.hoistedCteNames` / `QueryContext.hoistedCteNames`
carry the "already declared upstream" signal down to the legs, which then emit
neither the params nor a second `WITH` entry. The set is restored after the legs
are built, so the hoist never leaks into an enclosing expression, and a union with
no attached CTE emits byte-identical SQL to before.

**Limitation — the param guarantee covers the OUTERMOST statement only.** It holds
when the union is the statement being built (`toList()`, `count()`, `buildSql()`
with no argument, ...), which is where its own fresh context starts the counter at
`$1`. The nested path — `asSubquery()`, i.e. `buildSql(outerContext)` — reuses the
enclosing context, so the hoisted params are appended at whatever offset the union
already sits at while the CTE body still numbers its placeholders from `$1`. That
is a pre-existing ORM constraint rather than a regression (`buildQueryCore` has the
same shape, and only `withMutation` calls `renumberPlaceholders`), but it means a
`.with(cte)` union must be the outermost statement to bind correctly.

### 2. `count()` / `exists()` / `futureCount()` carry the query's CTEs

`buildAggregateQuery` emitted no `WITH` clause at all, so
`.with(cte).where(<references cte>).count()` failed with the same `42P01` even
without a union. It now assembles the `WITH` clause exactly as `buildQuery` does
(user CTEs first, then generated collection CTEs) and pushes the CTE params ahead
of the WHERE params.

**Behaviour change to be aware of:** an attached CTE is now emitted even when the
aggregate never references it, and PostgreSQL always executes a data-modifying CTE
— so `.with(dmlCte).count()` / `.exists()` / `.futureCount()` now RUN that DML,
where before the dropped `WITH` meant it silently did not. Read-only CTEs are
unaffected (PostgreSQL does not execute an unreferenced one) and placeholders stay
correct either way, since `$N` is absolute.

### Why this matters

Both gaps were hit by the same read path: a security-critical visibility gate
that must be evaluated **once** and then read by both legs of a
`unionAll(...).count()`. Before, the predicate was textually duplicated — once
per leg — so PostgreSQL planned and executed the whole gate twice inside a single
statement (measured on that workload at 60k junction rows: 3,720 -> 2,074 shared
buffers, 9.97 -> 4.43 ms). The `MATERIALIZED` fence pins that: PostgreSQL
auto-inlines a CTE referenced exactly once, and a forced inline (explicit
`NOT MATERIALIZED`) measures byte-identical to the duplicated predicate — so the
fence keeps the win independent of how many legs end up reading the CTE. Without
these two fixes, such a CTE could not be attached to that statement at all.

Covered by `tests/queries/cte-union-count-hoisting.test.ts`: cross-leg visibility,
statement-level single emission with `AS MATERIALIZED` preserved, parameter order
(`[cteParam, legParam]`), dedupe when the same CTE is attached to several legs,
the same-name/different-body collision throwing from both `buildSql()` and
`count()`, `unionAll(...).count()`, `.with(cte).count()`, `.with(cte).exists()`,
and a no-CTE control asserting unions without CTEs are unchanged.
