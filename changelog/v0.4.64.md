# v0.4.64

## Fix: `renumberPlaceholders` no longer corrupts placeholders around apostrophes in SQL comments

`renumberPlaceholders` — the quote-aware `$N` rewriter shared by `QueryBatch`,
`MutationBatch` and `insertWithChildren` for cross-leg parameter renumbering —
tokenized only two pass-through classes: single-quoted string literals and
double-quoted identifiers. **SQL comments were not a token class of their
own.**

The consequence is quiet and catastrophic in equal measure. An apostrophe
inside a `--` comment — `-- the user's own orders` — opens what the
string-literal arm believes is a literal, and that phantom literal runs to the
**next apostrophe anywhere later in the statement**. Every real placeholder in
between is swallowed as "inside a string" and passes through **verbatim,
unrenumbered**, still carrying its standalone numbering into a statement whose
earlier legs already own those positions.

```sql
SELECT ... WHERE (
  o."user_eshop_id" = $15            -- renumbered correctly
  -- the user's own orders PLUS ...   -- apostrophe #1 opens a phantom literal
  AND o."status" = $10               -- WRONG: standalone number kept verbatim
  AND o."payment_type" <> $11        -- WRONG
  ...
  -- ... members' household ...       -- apostrophe #2 closes the phantom
  AND oi."status" IN ($28, $29)      -- renumbering resumes, correctly
)
```

The walk then resynchronizes at the closing apostrophe, which makes the damage
a contiguous run of stale placeholders rather than everything after the
comment — the signature that makes this diagnosable from the emitted SQL.

### What a user would have observed

Any batched statement whose SQL contains a comment with an apostrophe (or a
`$N`-bearing comment followed by an apostrophe-bearing one). In the wild: a
gopass-eshop magic-SQL fold fragment riding the paid-webhook's fused
`MutationBatch` tail gained a documented household-spend arm whose comments
contained `user's` / `members'`. The four placeholders after the comment kept
their standalone numbers; `$10` collided with a preceding leg's `payload`
binding, and PostgreSQL rejected the **whole batch**:

```
error: operator does not exist: integer = jsonb
```

The batch then decomposed into its standalone fallback statements — for the
webhook that meant the roundtrip count jumped from 2 to 9 and its
statement-budget test failed. Nothing points at the comment: the error names a
parameter collision, and the same fragment executes perfectly as a standalone
query (offset 0 never renumbers), which makes the fault look like a batch
composer bug rather than a tokenizer gap — which, to be fair, it is.

Fragments whose comments contain no apostrophes were never affected, which is
why every existing comment-bearing query kept working.

### The fix

The tokenizer regex gains two pass-through arms, so a comment is consumed as
one verbatim token and its contents — apostrophes **and** `$N` sequences, which
are prose, not parameters — never reach the other arms:

- `--[^\n]*` — a line comment runs to end-of-line (or end of input).
- `/\*[\s\S]*?\*/` — a block comment runs to its closing delimiter.

Ordering against the quote arms is unambiguous: the arms start on distinct
characters, and where a `--` appears **inside** a literal or quoted identifier
the literal arm has already consumed the whole token by the time the scan
reaches that position, so `'a--b$3'` and `"col--name"` still pass through
untouched — the comment arms cannot fire inside them. Conversely a comment
arm consumes apostrophes inside itself, so the string arm can no longer be
poisoned by them.

Dollar-quoted strings (`$$ ... $$`) remain unrecognized, exactly as before;
that is a pre-existing, unchanged limitation, not a regression introduced here.

### Behaviour

| Input fragment                          | Before                    | After            |
|-----------------------------------------|---------------------------|------------------|
| placeholder outside any token           | renumbered                | unchanged        |
| `$N` inside a string literal / ident    | verbatim                  | unchanged        |
| apostrophe inside a `--` comment        | phantom literal, inner `$N` **kept at standalone numbers** | comment skipped verbatim |
| `$N` inside any comment                 | renumbered **as if bound** (when the comment held no apostrophe) | verbatim |
| `--` inside a literal / quoted ident    | part of the literal       | unchanged        |
| block comment with apostrophes / `$N`   | phantom literal           | skipped verbatim |

The only statements whose behaviour changes are the ones that were already
broken (colliding parameters) or silently wrong (a bare `$N` inside an
apostrophe-free comment was renumbered into the offset sequence while binding
no parameter — harmless unless the numbered position existed, which is exactly
the collision case).

### Coverage

`tests/queries/renumber-placeholders.test.ts` pins the tokenizer directly:
plain renumbering, literals and identifiers (pre-existing behaviour), the
apostrophe-in-comment regression both isolated and in the exact
fold-shaped sequence (params → commented arm → params, asserting the tail
resumes the renumbered sequence), `$N` inside comments staying verbatim, a
comment at end-of-input, block comments, `--` inside literals and identifiers,
and the interaction ordering. All ten cases pass; the regression cases fail on
the previous tokenizer.
