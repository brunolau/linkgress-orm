# v0.4.64

## Feature: row-guarded insert legs — `addInsertBulk({ rowGuard })`

`MutationBatch.addInsertBulk` accepts a new `rowGuard` option. A guarded leg
compiles the bulk insert to an `INSERT .. SELECT` over a `VALUES` source instead
of a plain `INSERT .. VALUES`, with the predicate applied per candidate row:

```typescript
batch.addInsertBulk(db.bookings, rows, 'bookings', {
  rowGuard: `NOT EXISTS (
    SELECT 1 FROM "club" c
    WHERE c."id" = v."club_id"
      AND c."max_bookings_per_member" IS NOT NULL
      AND (SELECT count(*) FROM "booking" b
           WHERE b."club_id" = v."club_id"
             AND b."member_id" = v."member_id") >= c."max_bookings_per_member"
  )`,
});
```

```sql
INSERT INTO "booking" ("club_id", "member_id", ...)
SELECT v."club_id", v."member_id", ...
FROM (VALUES ($1::int, $2::int, ...), ...) AS v("club_id", "member_id", ...)
WHERE <guard>
```

Rows that fail the guard are silently skipped rather than raising, and the
caller detects them through the leg's affected count
(`batch.getAffectedCount('bookings')` comes back short). This turns
"insert unless a data-dependent cap/invariant says no" into a single statement
of the fused batch instead of a select-then-insert pair.

The predicate is raw SQL — the same developer-authored-string contract as
`hasIndex().where(...)` — evaluated per candidate row with the row exposed
under the `v` alias (`v."<db_column_name>"`, cells are bound `$n::type`
parameters). It takes no parameters of its own; anything else it needs must be
reachable by joining from the row's columns. Cells reuse the
`insertWithChildren` cast technique so a bare `VALUES` source keeps correct
column types.

### Concurrency contract

The guard is **not** a cross-transaction race arbiter. It judges every
candidate row against the rows committed before the statement takes its
snapshot (READ COMMITTED), so two *concurrent* transactions can both pass a
count-based guard. Callers must serialize concurrent writers first — e.g. an
exclusive row or advisory lock taken earlier in the same transaction; the
blocked transaction's later statement then re-snapshots and the guard is
effective.

Within one statement, PostgreSQL never shows the insert its own rows, so two
rows of one batch that would collide with each other both pass — guard only
batches whose rows are mutually independent.

### Registration errors

`addInsertBulk` refuses a misused guard at registration time, not at runtime:

- `rowGuard` combined with `onConflictDoNothing` or `overridingSystemValue`
  throws — the guarded insert compiles to `INSERT .. SELECT` and supports
  neither.
- A blank/whitespace-only guard throws.
- A guard containing an unquoted `$N` placeholder throws. Guards take no
  parameters, and `MutationBatch`'s cross-leg parameter renumbering would
  otherwise silently rebind the `$N` to a *different leg's* parameter — a
  wrong-value guard with no error. The scan is the same quote-aware
  `QUOTED_OR_PLACEHOLDER` pass `renumberPlaceholders` uses (a pure re-export,
  so the tripwire and the renumberer cannot diverge); a `$1` inside a quoted
  literal stays legal.

### Coverage

`tests/queries/mutation-batch-row-guard.test.ts` (integration, real database):
per-row admit/block mixes with affected-count detection, zero-admit, an
unguarded-path regression pin, both option-conflict throws, both registration
tripwires plus quoted-`'$1'` legality, an adversarial `VALUES` cell
(`O'Br\ien costs $1` lands byte-intact through the new `SELECT` source), a
snapshot self-visibility pin (two rows that jointly exceed a cap both land —
the documented limitation, asserted so a change is loud), and a multi-leg
composition with the guarded leg at a nonzero parameter offset — the
renumbering path production batches exercise.
