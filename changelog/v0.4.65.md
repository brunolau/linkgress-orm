# v0.4.65

## Feature: `forUpdate()` — row-level lock clause on SELECT builders

`SelectQueryBuilder`, `CteRootQueryBuilder`, and the
`EntitySelectQueryBuilder` interface now expose:

```ts
.forUpdate(options?: { skipLocked?: boolean; noWait?: boolean })
```

appending `FOR UPDATE` — optionally `FOR UPDATE SKIP LOCKED` or
`FOR UPDATE NOWAIT` — to the built SELECT, emitted after `ORDER BY` /
`LIMIT` / `OFFSET` per SQL grammar.

### Why: a DB-side TOCTOU guard

Read-then-write sequences guarded by application-level distributed locks
(Redlock over Redis, advisory locks, "check outside, write inside" mutexes)
pay for the lock what they are trying to protect: an acquire round trip,
retry/backoff jitter on contention, a TTL whose expiry silently **fail-opens**
the gate, and a release that must ride every error path. `FOR UPDATE` gets
the same mutual exclusion from PostgreSQL itself — the lock is taken on the
rows the statement reads, in the statement's round trip, and it cannot
fail-open because it is not a lease.

The pattern this unlocks (the reason it exists):

```sql
WITH locked AS (
    SELECT id, total_capacity FROM capacity_group
    WHERE id IN ($1, $2)
    ORDER BY id                 -- stable lock order, no deadlocks
    FOR UPDATE                  -- ← the guard
),
consumed AS (
    SELECT ... -- derived consumption over the guard rows' consumers
),
fits AS (
    SELECT ... >= $demand AS ok FROM consumed, locked ...
)
INSERT INTO reservation (...)
SELECT ... FROM fits WHERE ok
RETURNING id;                   -- zero rows = guard rejected the write
```

One statement, one round trip, atomically serialized against every other
`forUpdate` reader of the same guard rows. Check and write commit or abort
together — the application lock, its retries, and its TTL hazard all
disappear. The gopass-eshop capacity reserve path is the driving consumer
(measured there: 16 concurrent reserve critical sections on one shared guard
row serialized with ~445 ms median lock-acquire under Redlock, versus an
in-statement row lock with no acquire cost at all).

### Emission rules

| Context | Clause emitted? |
|---|---|
| Top-level `SelectQueryBuilder` (`.select(...).orderBy(...).forUpdate().toList()`) | yes, after LIMIT/OFFSET |
| `CteRootQueryBuilder` (`.select(...).forUpdate()` off a `selectFromCte`) | yes, after LIMIT/OFFSET |
| A query used as a **CTE body** via `DbCteBuilder.with(...)` | **yes, verbatim** — `WITH name AS (SELECT ... FOR UPDATE)`; this is the fused-INSERT lock leg |
| Nested-collection legs (LATERAL / collection-CTE strategy) | no — a lock on a lateral join leg is meaningless (and illegal in some leg shapes) |
| `UnionQueryBuilder` legs | no |

`skipLocked` and `noWait` are mutually exclusive; combining them throws
(`forUpdate: skipLocked and noWait are mutually exclusive`).

### Lock-ordering contract (documented on the method)

Always pair with `.orderBy(...)` on a stable key (e.g. ascending `id`) when
the statement locks multiple rows. Two concurrent multi-row locking
statements that acquire the same rows in different orders are a textbook
deadlock; a stable order makes the lock acquisitions form a queue instead.
This is guidance, not enforcement — the builder does not require an
`orderBy`, because single-row guards (the common case) are safe without one.

### Coverage

`tests/queries/for-update.test.ts`:

- SQL shape on `SelectQueryBuilder` — clause lands after `ORDER BY`, statement
  ends with `FOR UPDATE`.
- Modifier construction — `SKIP LOCKED` / `NOWAIT` strings and the mutual-exclusion throw.
- **CTE-body passthrough** — a `.with('locked', ...forUpdate())` body renders
  `SELECT ... FOR UPDATE` inside the `WITH` declaration (the fused-INSERT leg).
- `CteRootQueryBuilder` — `toSql()` ends with `FOR UPDATE` after LIMIT.
- **Live lock behaviour** — two separate pooled transactions: the first reads
  a row `FOR UPDATE` and holds it; inside that window the second transaction's
  `FOR UPDATE NOWAIT` read of the same row is rejected with a
  lock-not-available error, proving the emitted clause produces a genuine
  row lock (not just SQL text).
