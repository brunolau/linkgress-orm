# v1.0.36

With `MockRowCache` on, a table-level RETURNING could correlate a collection through ANOTHER table's foreign key.
Two tables that reach one table by the same navigation name over different key columns (`pass.member` through
`holder_id`, `line.member` through `member_id`) shared one cached navigation row inside the RETURNING of `insert`,
`insertBulk`, `upsert`, `upsertBulk`, `mergeBulk` and the children of `insertWithChildren` /
`insertBulkWithChildren`. Whichever of them a process ran first decided, until a restart, the key every collection
off the other one's navigation joined through:

```sql
LEFT JOIN LATERAL (SELECT json_build_object('kind', "kind") as data
FROM (
  SELECT "lateral_0_badges"."kind" as "kind"
  FROM "ck_badges" "lateral_0_badges"
  LEFT JOIN "ck_members" "member" ON "__mutation__"."holder_id" = "member"."id"   -- the PASS's key, on a line
  WHERE "lateral_0_badges"."member_id" = "member"."id" AND …
  LIMIT 1
) sub) "lateral_0" ON true
```

The statement then failed with `column __mutation__.holder_id does not exist` every time. When the mutated table has a
column of that name and the RETURNING reads it, it ran instead and returned the other row's collection. Only the
collections hanging off the navigation were affected, directly or through deeper navigations: the navigation's own
columns join from the mutated table's own relations. It happened only with `MockRowCache.setEnabled(true)`, and only
from 1.0.7, which anchored the RETURNING's navigations on `"__mutation__"`.

## Fixed: a navigation row's cache key carries its own join

`ReferenceQueryBuilder.createMockTargetRow` keyed the cached prototype of a navigation row on five parts: the model,
the target table, the relation name, the source alias and the path ABOVE the navigation. It did not key on the
navigation's own foreign keys, principal keys and INNER / LEFT, which the row's collections and deeper navigations
carry as the last hop of their path.

Every other source row names its table in the source alias: a root row, a collection item, or a manually joined
table's `<table>_<n>`. A table-level RETURNING's row is anchored on `"__mutation__"` for every table, so two tables
collided there. The key now carries the hop's own join as well.

Statements that did not collide render exactly as before. The cache only keeps one more prototype per navigation name
that two tables reach through different keys.

## Tests

`tests/mutations/insert-returning-navigation.test.ts`, under "MockRowCache: one navigation name, two tables, two
foreign keys (a schema of their own)", has 13 cases. Each starts from emptied caches, as a fresh process would:

- **9 matrix cases.** Each RETURNING path that mints the navigation first (`insert` / `insertBulk`, `upsert` /
  `upsertBulk`, `mergeBulk`) is paired with each one that then reads collections off the other table's navigation
  (`insertWithChildren` children, `insertBulkWithChildren` children, `insert`).
- **A line that also reads its own `holder_id`.** This is the silent wrong-row case.
- **A collection two hops below the shared name.**
- **The reverse order.**
- **The cache-on statement compared with the cache-off build.**

All 13 fail on 1.0.35: 11 with `column __mutation__.holder_id does not exist`, 1 with `member_id`, and 1 with the wrong
rows.
