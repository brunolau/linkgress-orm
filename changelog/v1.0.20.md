# v1.0.20

## Fix: a foreign key is created only once the key it references exists

A foreign key may reference columns that are unique only through a unique INDEX declared on the target table —
a composite key such as `(group_id, group_kind) → (id, kind)` over `hasIndex('ux_group_id_kind', e => [e.id,
e.kind]).isUnique()`. PostgreSQL accepts the FOREIGN KEY only once that index exists, yet the schema manager
created every foreign key before every index:

- `ensureCreated()` wrote each table's foreign keys inline into its `CREATE TABLE` and built all indexes
  afterwards. A foreign key onto a table created later — two tables whose foreign keys form a cycle — was
  inlined too, onto a table that did not exist yet;
- `migrate()` added foreign keys in phase 2 and built or recreated indexes in phase 3 — for new tables, for an
  index and a foreign key both added to existing tables, and for an index recreated as unique together with a
  new foreign key onto it;
- `analyze()` listed a table's foreign keys right after its own index operations, so a foreign key could come
  before the unique index of a table later in the model (a migration file scaffolded from it ran that order).

The build failed with `42830: there is no unique constraint matching given keys for referenced table` (or
`42P01` for the cycle), on PostgreSQL, PGlite and the in-memory database alike.

Now:

- `ensureCreated()` builds a table's unique indexes right after the table, and puts a foreign key inline into
  `CREATE TABLE` only when the key it references exists at that point: the referenced table is there (created
  before it, or the table itself) and the key is its primary key, a UNIQUE column or — another table's — unique
  index. Every other foreign key (onto a table created later, onto the table's own unique index, onto a key
  nothing covers yet) is added with `ALTER TABLE … ADD CONSTRAINT` once every table and its unique indexes exist,
  and skipped when a previous run added it. A foreign key onto an earlier table's primary key stays inline: the
  DDL of a schema without such keys is byte-identical (checked on the test suite's `AppDatabase`);
- `migrate()` runs every index build whose result is unique — a new unique index, or an index recreated as
  unique — at the start of phase 2, before the foreign keys; the other index operations stay in phase 3;
- `migrate()` recreating a unique index that existing foreign keys rest on (`pg_constraint.conindid`) no longer
  fails with `2BP01: cannot drop index … because other objects depend on it`: it drops those foreign keys, drops
  and creates the index and adds them back, in one transaction. The rebuild is blocking even for a `.concurrent()`
  index (a warning says so). When the new index no longer covers their key, the transaction fails with 42830 and
  leaves the index and the foreign keys as they were. Only a recreate of an index that was unique costs the one
  extra query that finds those foreign keys;
- `analyze()` lists the foreign keys to add after every table's index operations, so a migration file runs a
  unique index's creation or recreation before the foreign key that needs it.

In-memory database: `DROP INDEX` of a unique index a foreign key rests on is refused with `2BP01`, as
PostgreSQL refuses it (`CASCADE` drops the foreign key); it used to drop the index and keep the foreign key.

A scaffolded migration file still recreates an index with `DROP INDEX` + `CREATE INDEX`: run where a foreign
key rests on that unique index, its `DROP INDEX` fails with `2BP01`; move the foreign key by hand in that file.

Tests: `tests/schema/unique-index.test.ts` — "a composite foreign key referencing a composite unique index"
(`ensureCreated()`, `migrate()` on an empty database, `migrate()` adding the index and the foreign key to
existing tables, `migrate()` recreating a non-unique index as unique with a new foreign key onto it, `migrate()`
recreating a unique index an existing foreign key rests on, `DROP INDEX` refused under a foreign key, and the
inline `CREATE TABLE` text of foreign keys onto an earlier table's primary key and unique index) and "a foreign
key whose referenced key does not exist yet when its table is created" (a self-referencing composite foreign key
onto the table's own unique index, and two tables in a foreign-key cycle, each by `ensureCreated()` and
`migrate()`, run twice). All of them fail without the fix.
