# v1.0.40

## New: `DbCteBuilder.with(name, query, { reads })` — a CTE body reads the CTEs it lists by name

A CTE body renders when `with()` is called, before any statement exists. A `db.selectFromCte(other)` read inside it — an
`exists()`, an `inSubquery()`, a projected subquery — therefore declared `other` again INSIDE itself, even when the
statement declares `other` too (`.with(other.cte)`, a join):

```sql
WITH "older_users" AS (SELECT … WHERE "users"."age" > $1)
SELECT … (WITH "older_posts" AS (SELECT …
  WHERE EXISTS (WITH "older_users" AS (SELECT … WHERE "users"."age" > $2)      -- a second copy, a second parameter
                SELECT … FROM "older_users" WHERE …))
  SELECT … FROM "older_posts" WHERE …)                                          -- params: [30, 30]
```

PostgreSQL cannot pull a sub-select that carries its own `WITH` up into a semi-join: the `EXISTS` stays a `SubPlan` over
a copy that is written, bound and planned once more per occurrence. `reads` lists the CTEs the body reads:

```typescript
const olderPosts = new DbCteBuilder().with(
  'older_posts',
  db.posts
    .where(p => exists(db.selectFromCte(older.cte).where(r => eq(r.id, p.userId)).select(r => ({ id: r.id })).asSubquery()))
    .select(p => ({ userId: p.userId, title: p.title })),
  { reads: [older.cte] },
);
```

The body now reads `older_users` by name (`WHERE EXISTS (SELECT … FROM "older_users" WHERE …)`, `params: [30]`), and
whoever declares the body declares `older_users` just before it, once — the statement's `.with()`, or the subquery that
reads the body when the statement does not declare it. PostgreSQL plans the `EXISTS` as a `Nested Loop Semi Join` over
a `CTE Scan` (checked on PGlite, PostgreSQL 18). It is the mechanism `withMutation()` already used for the data-modifying
CTEs a body reads (`DbCte.dependencies`), now open to plain CTEs.

- A body that does not list a CTE it reads declares it inside itself, exactly as before.
- The statement may declare a CTE of a listed name only if it is the same CTE by content; a different one is refused
  (`The CTE "older_users" a nested query attaches is not the CTE "older_users" its statement declares`).
- A listed CTE may read others: every level is declared once, each after the CTEs it reads.
- An entry that is no `DbCte`, or a CTE of the body's own name, is refused when `with()` is called.
- `reads` is an option of `with()` only, like `materialized`.

## Behaviour change: `sameCteDefinition()` compares what two CTEs read

Two CTEs of one body text that read different CTEs under one name read different rows, but compared equal. They are now
different CTEs: each dependency (`DbCte.dependencies`) of one must be the same CTE by content as one of the other's. It
only matters for a CTE that has dependencies — `reads`, or a plain body that reads a data-modifying CTE — where two
such CTEs with the same text and different dependencies used to be "the same" statement-level CTE.

## Tests

`tests/queries/cte-statement-hoisting.test.ts`, "a CTE body that reads another CTE by name" (10 cases, on PostgreSQL
(PGlite) and in memory): the statement declares the CTE (declared once, `params: [30]`, no `EXISTS (WITH`); it does not
(declared first, once, in the subquery and at statement level); a grouped body whose WHERE reads the CTE; a grouped body
that also joins a CTE the statement never declares; a body that reads a body that reads a CTE; parameter numbering across
the statement's, the read CTE's and the body's parameters; a different CTE under a declared name is refused; a body
without `reads` is unchanged; `reads` is validated; `sameCteDefinition()` compares dependencies. 9 of them fail on
1.0.39; the tenth pins what stays.
