# v1.0.43

## Fixed: an `exists()` over the table a navigation of its path is named like

A collection reached through a navigation (`ci.product.groupSiblings`) joins that navigation inside its `EXISTS`
subquery, under the navigation's name. When the navigation is named like the table the collection reads (here both are
`product`), the collection's own table kept its bare name too, so both took one alias and the statement failed:

```sql
-- db.cartItems.where(ci => ci.product!.groupSiblings!.where(m => gt(m.stock, 0)).exists())
-- 1.0.42: table name "product" specified more than once (42712; in memory: table reference "product" is ambiguous)
WHERE EXISTS (SELECT 1 FROM "product"
LEFT JOIN "product" "product" ON "cart_item"."product_id" = "product"."id"
WHERE "product"."group_id" = "product"."group_id" AND "product"."stock" > $1)

-- 1.0.43
WHERE EXISTS (SELECT 1 FROM "product" "groupSiblings__exists"
LEFT JOIN "product" "product" ON "cart_item"."product_id" = "product"."id"
WHERE "groupSiblings__exists"."group_id" = "product"."group_id" AND "groupSiblings__exists"."stock" > $1)
```

The collection's table now takes its `<relation>__exists` alias whenever one of its own path joins renders under its
table's name, as it already did when that name was the row it correlates to or a row of the enclosing scope. This
covers `exists(…)` and `.exists()` wherever they render as a correlated subquery (a WHERE, a `sql` fragment).

Unchanged: `count()` always named its table apart; a navigation of the collection's ITEM named like its table already
took a path alias (`"item__item"`); a collection a strategy (LATERAL, CTE, temp table) builds in a projection names its
table `lateral_<n>_<relation>` or reads it in a statement of its own. Only a statement that failed renders differently.
