# v1.0.43

PostgreSQL passes at most 100 arguments to a function call (`FUNC_MAX_ARGS`, fixed at compile time), so one
`json_build_object` holds at most 50 keys. linkgress rendered every object it builds in SQL as ONE call, whatever the
number of keys: a collection item of 51 keys failed on every execution against PostgreSQL —

```text
54023  cannot pass more than 100 arguments to a function
```

— while the in-memory database evaluated the 102-argument call and every test passed. gopass-eshop shipped such a
projection (a per-item collection of 51 keys in its order-confirmation PDF): every PDF download returned 500 in
production with a green suite.

## Fixed: objects of more than 50 keys

Every object the ORM builds in SQL goes through one helper, `renderJsonBuildObject(entries)`
(`src/query/sql-utils.ts`), which now takes `{ key, value }` entries instead of pre-rendered pairs.

- **Up to 50 keys**: the one `json_build_object('k', v, …)` call, byte for byte as before, under every setting —
  statement texts, prepared-statement names and plan caches keyed by them do not change (the SQL of 24 query shapes — 8
  per strategy — at 50 keys compared with 1.0.42's, with `serverVersion` unset and set to 18: identical).
- **Past 50 keys on PostgreSQL 16+** (`LinkgressConfig.serverVersion`, below): ONE SQL/JSON constructor —

  ```sql
  json_agg(JSON_OBJECT('id' VALUE "id", 'k0' VALUE "k0", …, 'k49' VALUE "k49" RETURNING json))
  ```

  `JSON_OBJECT` is not a function call (a `JsonConstructorExpr`, no `FUNC_MAX_ARGS` check in PostgreSQL 16, 17 or 18)
  and runs the worker `json_build_object` runs: the same json text (`{"k" : v}`), keys in written order, every value as
  `json_build_object` writes it (checked per type against PostgreSQL), each value evaluated where the object is. Keys
  are quoted literals, so an empty key, a 64-byte key or 2 000 keys need no other form. `RETURNING json` is not
  optional: without it one jsonb value turns the whole object jsonb (keys re-sorted).
- **Past 50 keys below 16, or with the version unknown (the default)**: `row_to_json` over a one-row sub-select whose
  columns are named by the keys —

  ```sql
  json_agg((SELECT row_to_json(r.*) FROM (SELECT "id" AS "id", "k0" AS "k0", …, "k49" AS "k49") r))
  ```

  json, keys in the written order, every value as `json_build_object` writes it; only the object's own text is compact
  (`{"a":1}` rather than `{"a" : 1}`). `r.*`, not `row_to_json(r)`: a bare `r` resolves to a COLUMN named `r` first (a
  key, or an outer table's column) and fails with 42883. Keys that cannot name a column — empty, or longer than 63
  bytes (PostgreSQL would truncate the name) — and objects of more than 1 664 keys (the most a target list holds): the
  json TEXTS of calls of 50 keys spliced and cast back to json once, `(left(json_build_object(…)::text, -1) || ', ' ||
  right(json_build_object(…)::text, -1))::json` — byte for byte the text one call would print, no sub-select.
- Where: collection items under the `cte`, `lateral` and `temptable` strategies (`toList()`, `firstOrDefault()`), nested
  objects inside them, `DbCteBuilder.withAggregation()` items and their nested objects, a navigation row rendered as one
  object, a `MutationBatch.addInsertBulkWithChildren` RETURNING list.
- **The values of such an object are columns of the row it is built from** (`JsonObjectEntry.value`): below 16 /
  unknown, past 50 keys they are evaluated inside the sub-select, one query level down, where an aggregate would count
  the sub-select's one row (`count(*)` = 1), a window would see one row and an uncorrelated `random()` would be computed
  once per statement. Every builder already hands it columns — a nested collection, a `count()` or a `sum()` in an item
  is computed in the row source and referenced by its column; a test pins that a wide item with all three reads exact,
  under both forms.
- Not affected: the top-level row and a nested object at the top level render as flat columns, not as one object.
  Bounded call sites keep their one call: `QueryBatch`'s 4-key envelope, the 2-key constraint lookup of the schema
  manager.

## Fixed: `jsonBuildObject()` / `jsonbBuildObject()` / `jsonBuildArray()` / `jsonbBuildArray()` past 50 keys / 100 elements

The helpers take arbitrary operands (an aggregate, a window, `random()`), so they never use the sub-select. Past the
limit:

- **PostgreSQL 16+**: one `JSON_OBJECT('k' VALUE v, … RETURNING json|jsonb)` / `JSON_ARRAY(v, … NULL ON NULL RETURNING
  json|jsonb)`. `NULL ON NULL` is not optional: `JSON_ARRAY` drops NULL elements by default.
- **Below 16 / unknown**: calls of 50 keys (100 elements) joined into the one value — `jsonBuildObject()` /
  `jsonBuildArray()` splice their json texts, as above (keys and elements in written order, the text one call would
  print); `jsonbBuildObject()` / `jsonbBuildArray()` merge their jsonb, `(jsonb_build_object(…) || jsonb_build_object(…))`
  (objects merged, arrays concatenated in order).

Parameters bind once each, in order, in every form.

## New: `LinkgressConfig.serverVersion` and `LinkgressConfig.detectServerVersion(client)`

linkgress cannot learn the server's version before it builds the first statement, and PostgreSQL 15 cannot parse
`JSON_OBJECT('k' VALUE …)` (`syntax error at or near "VALUE"`), so the constructor form waits for the application to
say so — once, at boot, beside the other process-wide statement-text switches (`inArrayUsesOpt`, `orUsesOpt`):

```ts
LinkgressConfig.serverVersion = 18;                       // the OLDEST major this process sends statements to
const major = await LinkgressConfig.detectServerVersion(client); // or: one SHOW server_version_num, sets it
LinkgressConfig.configure({ serverVersion: undefined });   // back to unknown; resetToDefaults() too
```

- `undefined` (the default) or below 16: exactly the SQL above for the version unknown. 16 or more: the constructors.
- An integer of 12 or more, or `undefined`; anything else throws a `RangeError` and keeps the current value.
- Read when a statement is BUILT: set it before queries are built. The lateral strategy's SQL cache (`LateralSqlCache`)
  keys on it; a `.prepare()`d query keeps the text it was prepared with.
- `detectServerVersion` takes any client, pooled connection or transaction client: `pg`, postgres.js, Bun SQL, PGlite
  (18) and the in-memory database (18).
- A model view holding an object of more than 50 keys gets a new marker hash once the setting is turned on, and is
  recreated by the next migrate.

## Changed: the in-memory database refuses a call of more than 100 arguments

As PostgreSQL does, while the statement is parsed and before any lookup: SQLSTATE `54023`, message
`cannot pass more than 100 arguments to a function`, the position of the call; pg raises its `DatabaseError`, postgres.js
its `PostgresError`. A `VARIADIC ARRAY[…]` argument is one; `WITHIN GROUP` arguments count; `CALL` is checked too.
`COALESCE`, `GREATEST` / `LEAST`, `CASE`, `IN (…)` and `ARRAY[…]` are not function calls and stay unlimited. A test
suite on the in-memory database now fails where its statements would fail on PostgreSQL — e.g. `concat()` of more than
100 operands or `concatWs()` of more than 99 after the separator, which stay one call: split the list. `row_to_json(r.*)`
and the text splice needed no engine change (sql-parity corpus).

## New: the in-memory database parses and runs `JSON_OBJECT(…)` / `JSON_ARRAY(…)`

The SQL/JSON constructors of PostgreSQL 16+, as constructors (no argument cap): `'k' VALUE v` and `'k' : v` pairs,
`NULL ON NULL` / `ABSENT ON NULL` (defaults: `JSON_OBJECT` NULL ON NULL, `JSON_ARRAY` ABSENT ON NULL), `WITH` /
`WITHOUT UNIQUE [KEYS]` (22030 on a repeated key), `RETURNING json | jsonb | text …` (no `RETURNING`: jsonb once an
argument is jsonb, else json), `FORMAT JSON` on a string value, the empty `JSON_OBJECT()` / `JSON_ARRAY()`; result
columns named `json_object` / `json_array`. They share the bodies of `json(b)_build_object` / `json(b)_build_array`.
The legacy `json_object(text[])` function still parses as a function call; the `JSON_ARRAY(SELECT …)` query form is
not supported. A NULL key now raises what PostgreSQL 18 raises: `json_build_object` / `JSON_OBJECT(… RETURNING json)`
22004 `null value not allowed for object key`, `jsonb_build_object` / `RETURNING jsonb` 22023 `argument 3: key must not
be null` (both used to say 22004 `argument N: key must not be null`).
