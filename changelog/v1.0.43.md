# v1.0.43

PostgreSQL passes at most 100 arguments to a function call (`FUNC_MAX_ARGS`, fixed at compile time), so one
`json_build_object` holds at most 50 keys. linkgress rendered every object it builds in SQL as ONE call, whatever the
number of keys: a collection item of 51 keys failed on every execution against PostgreSQL —

```text
54023  cannot pass more than 100 arguments to a function
```

— while the in-memory database evaluated the 102-argument call and every test passed. gopass-eshop shipped such a
projection (a per-item collection of 51 keys in its order-confirmation PDF): every PDF download returned 500 in
production with a green suite.

## Fixed: objects of more than 50 keys

Every object the ORM builds in SQL goes through one helper, `renderJsonBuildObject(entries)`
(`src/query/sql-utils.ts`), which now takes `{ key, value }` entries instead of pre-rendered pairs.

- **Up to 50 keys**: the one `json_build_object('k', v, …)` call, byte for byte as before — statement texts,
  prepared-statement names and plan caches keyed by them do not change (the SQL of 24 query shapes — 8 per strategy — at
  50 keys compared with 1.0.42's: identical).
- **Past 50 keys**: `row_to_json` over a one-row sub-select whose columns are named by the keys:

  ```sql
  json_agg((SELECT row_to_json(r.*) FROM (SELECT "id" AS "id", "k0" AS "k0", …, "k49" AS "k49") r))
  ```

  json, keys in the written order, every value as `json_build_object` writes it (checked per type against PostgreSQL:
  int8, numeric, timestamptz, date, json, jsonb, arrays, bytea, NaN / Infinity, …); only the object's own text is
  compact (`{"a":1}` rather than `{"a" : 1}`). `r.*`, not `row_to_json(r)`: a bare `r` resolves to a COLUMN named `r`
  first (a key, or an outer table's column) and fails with 42883.
- **Keys that cannot name a column** — empty, or longer than 63 bytes (PostgreSQL would truncate the name) — and
  objects of more than 1 664 keys (the most a target list holds): the json TEXTS of calls of 50 keys spliced and cast
  back to json once, `(left(json_build_object(…)::text, -1) || ', ' || right(json_build_object(…)::text, -1))::json` —
  byte for byte the text one call would print, no sub-select.
- Where: collection items under the `cte`, `lateral` and `temptable` strategies (`toList()`, `firstOrDefault()`), nested
  objects inside them, `DbCteBuilder.withAggregation()` items and their nested objects, a navigation row rendered as one
  object, a `MutationBatch.addInsertBulkWithChildren` RETURNING list.
- **The values of such an object are columns of the row it is built from** (`JsonObjectEntry.value`): past 50 keys
  they are evaluated inside the sub-select, one query level down, where an aggregate would count the sub-select's one
  row (`count(*)` = 1), a window would see one row and an uncorrelated `random()` would be computed once per
  statement. Every builder already hands it columns — a nested collection, a `count()` or a `sum()` in an item is
  computed in the row source and referenced by its column; a test pins that a wide item with all three reads exact.
- Not affected: the top-level row and a nested object at the top level render as flat columns, not as one object.
  Bounded call sites keep their one call: `QueryBatch`'s 4-key envelope, the 2-key constraint lookup of the schema
  manager.

## Fixed: `jsonBuildObject()` / `jsonbBuildObject()` / `jsonBuildArray()` / `jsonbBuildArray()` past 50 keys / 100 elements

The helpers take arbitrary operands (an aggregate, a window, `random()`), so they never use the sub-select. Past the
limit they render calls of 50 keys (100 elements) joined into the one value:

- `jsonBuildObject()` / `jsonBuildArray()`: the json texts spliced, as above — keys and elements in written order, the
  text one call would print.
- `jsonbBuildObject()` / `jsonbBuildArray()`: `(jsonb_build_object(…) || jsonb_build_object(…))` — the jsonb one call
  builds (objects merged, arrays concatenated in order).

Parameters bind once each, in order, across the calls.

## Performance

`bench/json-object` (local PostgreSQL, read-only `EXPLAIN ANALYZE` over `generate_series`), µs per object, against
nesting the keys by hand into containers of ≤ 50 — what a consumer had to do before:

| keys | shape | hand-nested µs | jsonb merge µs | row_to_json µs | text splice µs | merge / hand | row_to_json / hand | splice / hand |
|---|---|---|---|---|---|---|---|---|
| 51 | select | 5.67 | 11.15 | 4.60 | 8.15 | 1.97× | 0.81× | 1.44× |
| 51 | json_agg | 6.22 | 11.56 | 5.11 | 8.83 | 1.86× | 0.82× | 1.42× |
| 60 | select | 6.72 | 12.95 | 5.65 | 9.53 | 1.93× | 0.84× | 1.42× |
| 60 | json_agg | 7.20 | 13.33 | 6.12 | 9.83 | 1.85× | 0.85× | 1.37× |
| 120 | select | 13.48 | 28.76 | 14.61 | 18.88 | 2.13× | 1.08× | 1.40× |
| 120 | json_agg | 14.25 | 29.85 | 15.57 | 19.69 | 2.10× | 1.09× | 1.38× |
| 200 | select | 23.06 | 51.31 | 40.46 | 42.87 | 2.23× | 1.75× | 1.86× |
| 200 | json_agg | 30.62 | 69.92 | 40.21 | 38.79 | 2.28× | 1.31× | 1.27× |
| 51 + 20-child json_agg | select | 15.25 | 30.37 | 14.06 | 20.33 | 1.99× | 0.92× | 1.33× |
| 51 + 20-child json_agg | json_agg | 16.35 | 34.76 | 14.96 | 20.96 | 2.13× | 0.91× | 1.28× |

(PostgreSQL 18.6 on localhost, 200 000 rows, median of 5 runs; `select` = the object in the select list, `json_agg` =
inside `json_agg(…) GROUP BY`; `51 + 20-child json_agg` = one of the 51 values is a 20-element `json_agg`.)

Over four runs `row_to_json` costs 0.80–0.88× the hand-nested object at 51–60 keys (0.90–0.92× with a 20-child
`json_agg` among 51), +1–12 % at 120 keys and +28–75 % at 200 (the 200-key ratio varies most with the machine's load);
the crossover between 60 and 120 keys was not measured. A projection of 120 keys or more on a hot path is cheaper
nested by hand; correctness does not depend on it. The jsonb merge (the form 1.0.43's first draft used) costs about
twice the hand-nested object at every width and reorders the keys; the text splice costs 1.27–1.44× in the run above
(1.86× in its 200-key select row, under a load spike) and is what the fallback and the json helpers use.

## Changed: the in-memory database refuses a call of more than 100 arguments

As PostgreSQL does, while the statement is parsed and before any lookup: SQLSTATE `54023`, message
`cannot pass more than 100 arguments to a function`, the position of the call; pg raises its `DatabaseError`, postgres.js
its `PostgresError`. A `VARIADIC ARRAY[…]` argument is one; `WITHIN GROUP` arguments count; `CALL` is checked too.
`COALESCE`, `GREATEST` / `LEAST`, `CASE`, `IN (…)` and `ARRAY[…]` are not function calls and stay unlimited. A test
suite on the in-memory database now fails where its statements would fail on PostgreSQL — e.g. `concat()` of more than
100 operands or `concatWs()` of more than 99 after the separator, which stay one call: split the list. The engine
needed no change for the new forms: `row_to_json(r.*)` and the text splice give PostgreSQL's results (sql-parity
corpus).

## Tests

- `tests/queries/projection-reads.test.ts` ("an object wider than one function call takes"): 51 and 120 keys — an
  integer, a numeric, a timestamp, a boolean, a NULL, an enum and a mapped column — in collection items, a
  `firstOrDefault()` item and a nested object in an item under each strategy, and in a `withAggregation()` item; each
  read equals the same rows read as projections of ≤ 40 keys, keys in written order. Keys `r`, `Upper_Case`, 63 bytes
  and `Ünï` read through `row_to_json(r.*)`; a 64-byte key and 32 × `é` through the splice, whole and in order. A wide
  item holding a nested collection, a `count()` and a `sum()` reads exact. The 49 / 50 / 60-key SQL pinned (one call up
  to 50). On 1.0.42 every wide read fails with 54023 on PostgreSQL.
- `tests/queries/sql-param-and-text-helpers.test.ts`: `renderJsonBuildObject()` at 50 / 51 keys, `a"b` / `r` / 63-byte
  keys, the empty / 64-byte key and 1 665 keys (splice); the helpers' SQL at 50 / 51 / 120 keys and 100 / 150 elements,
  parameter order across calls; 60 keys and 130 elements read back from the database, the json text equal to one call's.
