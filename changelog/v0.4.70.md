# v0.4.70

## Feature: `preparedStatements` — named server-side prepared statements on the postgres.js driver (opt-in)

postgres.js hard-codes `prepare: false` on `unsafe()`, and `PostgresClient` runs every statement
through `unsafe(sql, params)`. Every linkgress statement was therefore an UNNAMED statement: the
server parsed it, described it (a second round trip before Bind/Execute) and planned it again
on every execution. For planning-heavy OLTP statements that is most of the server time — a
16 KB cart read in gopass-eshop measured 7.35 ms unprepared against 0.95 ms prepared on one
connection (EXPLAIN: 5.3 ms planning, 1.0 ms execution) — and the describe round trip doubles
the per-statement network cost in a cluster.

- `QueryOptions.preparedStatements?: boolean` — context default. `true` sends every
  parameterised statement as a named prepared statement: one per distinct text per connection,
  cached by postgres.js after its first execution. **Default `false`**: nothing changes for
  existing contexts.
- `.withPreparedStatements(prepare)` on `DbEntityTable` and `TableAccessor` — per-query
  override in both directions: keep a wide analytical query on custom plans inside a prepared
  context (`false`), or prepare a single hot lookup on an unprepared context (`true`). Mirrors
  `.withTimeout()`; the override survives `.withTimeout()` / `.expectedExecutionTime()`
  chaining.
- `QueryExecutionOptions.prepare?: boolean` — the driver-level knob the executor sets. Honored by
  `PostgresClient` (plain queries, reserved connections, statements inside `transaction()`, and
  the `SET LOCAL statement_timeout` wrapper of a per-query timeout); `PgClient` and `BunClient`
  ignore it. A postgres.js instance created with `prepare: false` ignores it too — leave the
  instance default alone.
- **Exempt regardless of the option**: `insertWithChildren`, `insertBulkWithChildren` and the
  fused `MutationBatch` statement. Their text embeds per-call VALUES lists, so a prepared
  statement would be created per variant and never reused — pure cache growth on the server.
- Zero-parameter statements are unaffected (postgres.js already sends them over the simple
  protocol).

### Why opt-in, and what to measure before turning it on

After five executions PostgreSQL may switch a prepared statement to a GENERIC plan
(`plan_cache_mode = auto`). That is right for statements whose parameters have uniform
selectivity (primary-key and foreign-key lookups, the cart read above) and wrong for some wide
analytical shapes: a July 2026 bench of a 19 KB catalogue query (1,560 parameters, planning
19 ms of 367 ms) ran SLOWER prepared, because the generic plan lost the hand-tuned custom
plan. Opt such queries out with `.withPreparedStatements(false)`. Statements rendered with
`IN ($1, $2, …)` lists are cached once per list length; that is bounded for small lists and
wasteful for large ones — the catalogue query above is the same case. Pair the option with a
connection `max_lifetime` so per-connection caches are recycled, and read
`pg_prepared_statements` (`generic_plans` / `custom_plans`) and `pg_stat_statements`
(`calls` vs `plans` with `track_planning = on`) on the target database before and after.

A cached plan whose RESULT SHAPE changes (`SELECT *` over a table that just gained a column)
is rejected by PostgreSQL once; postgres.js drops the cached statement and re-prepares it
transparently (`tests/database/prepared-statements.test.ts` pins this). Inside an explicit
transaction that retry lands on an aborted transaction, so prefer explicit column lists in
statements that run inside transactions — linkgress's own builders already emit them.

Tests: `tests/database/prepared-statements.test.ts` (9 cases, PostgresClient): context default,
per-query opt-out and opt-in, the three exempt bulk paths, the driver's re-prepare after a
result-shape change, and the per-query timeout wrapper in prepared mode. The assertions read
`pg_prepared_statements` on a pinned session and ignore postgres.js's own named statements (its
type-catalogue bootstrap and the tagged `rollback`), which every connection carries anyway.
