## Fix: nested-collection navigation anchors on the projected path, not a same-table sibling FK

A projection inside a collection (`parent.children.select(...).toList()`) that navigated **more than
one hop** away from the collection root could silently resolve its deepest joins against a completely
different relation — returning another row's data with no error, no warning, and perfectly valid SQL.

The trigger is a collection root that carries **two different ways to reach the same table**: the
multi-hop path the projection actually asks for, and a shorter direct FK. Real-world shape:

```
loan -> edition -> book -> category   // what the projection navigates
loan -> book                          // competing one-hop FK (featured_book_id)
```

```typescript
db.members.select(m => ({
  items: m.loans.select(l => ({
    categoryName: l.edition.book.category.name,   // asked for the BORROWED book's category
  })).toList(),
})).toList();
```

Emitted SQL before the fix:

```sql
LEFT JOIN "edition"  "edition"      ON "lateral_0_loans"."edition_id"       = "edition"."id"
LEFT JOIN "book"     "book"         ON "edition"."book_id"                  = "book"."id"
LEFT JOIN "book"     "featuredBook" ON "lateral_0_loans"."featured_book_id" = "featuredBook"."id"
LEFT JOIN "category" "category"     ON "featuredBook"."category_id"         = "category"."id"  -- wrong anchor
```

`featuredBook` was never mentioned in the projection — the resolver invented it.

### Cause

Two independent defects in `CollectionQueryBuilder`, either of which was enough to reach the bad
path.

**1. The alias set was incomplete.** `addNavigationJoinForFieldRef` registered only the *terminal*
alias of each field ref (`category`), never the chain that led to it. Intermediates like `edition`
and `book` therefore entered `allTableAliases` only when some *other* field in the same projection
happened to terminate on them (`l.edition.bookId`, `l.edition.book.categoryId`).
A projection naming only the deep leaf left the resolver with nothing but `category` to work with.

**2. The anchor map went stale mid-pass.** `resolveNavigationJoins` snapshotted its `joinedSchemas`
map **once per outer iteration** and did not update it as joins were added during that same
iteration. `book` is two hops from the collection root, so — even when it *was* in the alias set —
it was joined mid-iteration and never entered the snapshot.

Either way the alias `category` failed the direct-relation lookup and fell through to
`findNavigationPath` — a breadth-first search over the whole schema graph that matches on relation
**name** and has no knowledge of the path the projection took. BFS reached `category` one hop sooner
through the sibling FK, so that became the anchor, and the intermediate `featuredBook` join was
materialised as a side effect of the path it returned.

Flat root queries were unaffected: there the intermediate join lands before its dependants are
resolved, so the fallback never fires. Only projections nested inside a collection — lateral, CTE and
temptable strategies alike — could reach the bad path.

### Fix

**1. The projection's own navigation chain is now seeded into the alias set.**
`addNavigationJoinForFieldRef` reads the `__navigationAliases` each field ref already carries — the
same signal `QueryBuilder.collectTableAliasesFromSelection`, `GroupedQueryBuilder` and `DbContext`
have always consumed, and the same treatment nested `CollectionQueryBuilder` values already get — so
every hop the projection actually navigated is registered, not just the last one. Resolution no
longer depends on which sibling scalars a projection happens to also select.

**2. Direct-relation lookups run to a fixpoint before any BFS fallback**, with `joinedSchemas` kept
current as joins are added. A parent that is itself several hops from the root can therefore anchor
its own children in the same pass.

Together these make `findNavigationPath` unreachable for any alias the projection spelled out a
navigation path for; it is now only consulted for aliases that arrive without one (e.g. a bare
alias reference with no navigation chain attached), which is what it was meant for.

```sql
LEFT JOIN "category" "category" ON "book"."category_id" = "category"."id"
```

The `featuredBook` join disappears entirely — nothing asked for it.

An explicit `l.featuredBook.category.name` still resolves through `featuredBook`, so the
one-hop sibling is not penalised; only the *guessing* is removed.

Covered by `tests/queries/lateral-nav-multipath-anchor.test.ts` (lateral + CTE repro, lateral + CTE
leaf-only repro with no sibling scalars, one-hop counter-test, flat-root control).
