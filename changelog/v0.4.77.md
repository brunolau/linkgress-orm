# v0.4.77

## Performance: the lateral collection strategy renders a projection in one pass

`LateralCollectionStrategy.buildJsonbAggregation` (a `.toList()` collection) and
`buildSingleJsonAggregation` (a `.firstOrDefault()` collection) turned the selected fields into
SQL with three separate walks, each allocating as it went: `collectLeafFields` flattened the
nested aliases into an array of `{ alias, expression }` objects (spread-pushing the nested
results), `buildJsonbObject` produced the `json_build_object(...)` text through a parts array
and `join`, and `collectNestedCteJoins` gathered the nested lateral joins into a third array.
The select list then went through one more `map` with a `RegExp` test per leaf to tell a bare
column from an expression, and one more `join`:

```typescript
const allSelectFields = leafFields.map(f => {
  const isSimpleColumn = /^"[^".]+"$/.test(f.expression);
  ...
});
```

For a wide collection projection — the gopass-eshop cart items carry fifty fields, several
nested objects and two nested collections, and the cart is loaded four times per order — that
was three allocations per field and three joins per statement, on every build.

The two builders now share one recursive `renderFields` pass: it returns the
`json_build_object` text of its level and appends the flattened inner select list and the
nested lateral joins to an accumulator by string concatenation (rope strings on both V8 and
JSC — no intermediate arrays, no `join`). `renderLeafSelect` decides "bare column" with two
`charCodeAt` and two `indexOf` calls instead of the regex, and the marker rewrite lives in one
`rewriteMarker`. `buildNavigationJoinsWithAlias` is handed the relation name instead of
recovering it from the alias with `split('_')`, `slice` and `join` on every call. The walk
order — depth first, a field's own nested join before its children's — is the one the three
walks produced, so the SQL text is byte-identical; the dead `collectNestedCteJoins` is gone.

On the builder side of the same path (`CollectionQueryBuilder.buildCTE`, which calls the
strategy): `detectNavigationJoins` iterates the selection's own keys with `for…in` +
`hasOwnProperty` instead of allocating `Object.entries` pairs (the set of keys is the same;
own-only matters, because reference mock rows carry enumerable getters on their prototype),
`resolveNavigationJoins` returns at once when every referenced alias already has its join
(the common case — direct relations of the target table are joined while the field refs are
collected, and the resolver loop only re-marked them), and `processField` no longer rebuilds
the `"__collection_<table>__"` marker string for every field.

Measured on the gopass-eshop `order/create` burst (one process, prepared statements on, cart
projection with nested lateral collections), **Bun 1.3.14 first** since that is the production
runtime. Same-workload CPU profiles, two backends alternating on identical bursts (1 400 orders
each), share of the process' busy time:

| function | 0.4.76 | 0.4.77 |
| --- | ---: | ---: |
| `LateralCollectionStrategy.buildAggregation`, inclusive | 4.4 % | 3.6 % |
| `buildJsonbAggregation`, inclusive | 3.0 % | 1.8 % |
| `buildSingleJsonAggregation`, inclusive | 0.8 % | 0.7 % |
| `CollectionQueryBuilder.buildCTE`, inclusive | 16.1 % | 14.6 % |
| `detectNavigationJoins`, inclusive | 3.1 % | 2.6 % |
| `executeSinglePhase` (build + execute + transform) | 26.4 % | 25.8 % |

A lighter-load run of the same profile puts it in absolute terms per 700 orders:
`buildAggregation` 741 ms → 520 ms, `buildJsonbAggregation` 518 ms → 295 ms. About a point and
a half of process CPU on Bun; the Node (V8) numbers are of the same shape and smaller, since V8
was cheaper at the array work to begin with. Request throughput on a shared machine moves
±30 % run to run, so the profiles are the measure; the paired throughput runs were within that
noise.

What remains in `buildCTE` after this step is per-field work the projection genuinely needs —
the field-ref getters allocate one descriptor per column per mock row, and
`MockRowCache.getOrBuild` hashes a freshly built key — plus the navigation-row minting the next
section removes.

## Performance: one navigation mock row per row and relation

A `hasOne` navigation read on a root mock row (`p.user`) or on a collection item (`it.product`)
minted a new `ReferenceQueryBuilder` and a new mock target row on **every access** — the nested
levels already memoised them per row, the first level did not. A selector that reads
`it.product.name`, `it.product.resortId`, `it.product.resort.currency`, … fifteen times built
fifteen builders and fifteen rows, each with its own field-ref cache, per collection build. The
navigation row is now cached on the row that produced it (the same per-row slot the nested
levels use); `hasMany` navigations keep returning a fresh builder per access, since a
`CollectionQueryBuilder` carries its own `where` / `select` / `limit` state.

Same path, three smaller trims: the root selection loops of `buildQuery` / `buildQueryCore`
iterate own keys without allocating `Object.entries` pairs, and `createSelectAllRow` (the
whole-row selector) reuses the schema's column-name array instead of `Object.keys` per row.

Bun same-workload profile, 0.4.76 vs. this version alternating on identical bursts (two
backends, 1 400 orders each, share of the process' busy time), both changes together. Both
processes ran with the mock-row cache ON (`MockRowCache.diagnostics()` logged at boot:
`enabled: true` in each), so this is the production configuration:

| function | 0.4.76 | 0.4.77 |
| --- | ---: | ---: |
| `LateralCollectionStrategy.buildAggregation`, inclusive | 4.8 % | 4.1 % |
| `buildJsonbAggregation`, inclusive | 3.6 % | 2.2 % |
| `CollectionQueryBuilder.buildCTE`, inclusive | 17.5 % | 12.7 % |
| `processField`, inclusive | 4.4 % | 3.3 % |
| `detectNavigationJoins`, inclusive | 3.3 % | 2.3 % |
| `executeSinglePhase` (build + execute + transform) | 26.8 % | 23.5 % |
| `toList`, inclusive | 27.0 % | 23.7 % |

Paired throughput in the same run (orders/s, 0.4.76 → 0.4.77): N=200 162/174/168/178 →
178/187/175/183 (every pair up, mean **+6 %**), N=100 156/159/157/160 → 176/180/178/180
(every pair up, mean **+13 %**); mean request latency 1 101 → 1 028 ms at N=200 and
588 → 523 ms at N=100.

Tests: `tests/queries/lateral-aggregation-rendering.test.ts` pins the rendered SQL (select-list
order and aliasing, nested `json_build_object`, marker rewrite, `LIMIT`, `firstOrDefault`,
nested-lateral join placement, multi-hop navigation, join de-duplication, `DISTINCT`, an
underscore relation name) and lateral ≡ cte rows, plus the navigation-row memo (same row → same
navigation row, different rows → different rows, `hasMany` still a fresh builder); the SQL half
of the spec passes unchanged on 0.4.76. Full suite green (124 suites, 1 640 tests) after each
step.
