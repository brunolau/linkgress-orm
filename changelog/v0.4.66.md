# v0.4.66

## Performance: cached property descriptors for reference mock rows (opt-in via static switch)

`ReferenceQueryBuilder.createMockTargetRow()` rebuilt its entire mock row from scratch on
**every call**: an `Object.defineProperty` per column AND per relation, fresh getter closures,
fresh mapper/type lookup objects — and every reference-navigation access constructed a brand-new
`ReferenceQueryBuilder` plus a recursive nested mock. Deep selectors (e.g. a cart selector walking
cart → items → product → price → relations) pay that cost for the whole sub-graph on every single
query build.

Under load this was measurable as the #1 application CPU consumer: `createMockTargetRow` alone
showed up at ~19 % of total process CPU in a V8 profile of a purchase-path load run (with
`findNavigationPath`, `_createMockRow`, proxy `get` and GC pressure from the per-row allocations
adding several more percent).

Everything the descriptors close over is deterministic in `(target table schema, relation alias,
source alias, navigation-path content)`, so the `PropertyDescriptorMap` can be built **once per
signature** and reused: each new mock row is a bare object + a single `Object.defineProperties`
call with the shared descriptors, and navigation getters memoize their sub-graph per row.

### Static feature switch — `MockRowCache` (default OFF)

The cross-row cache is **opt-in**: the host application enables it at boot via

```ts
import { MockRowCache } from 'linkgress-orm';

MockRowCache.setEnabled(true);   // flip per environment, from the app's own config
MockRowCache.isEnabled();        // runtime state
MockRowCache.diagnostics();      // { enabled, entries, maxEntries } — verify on a live process
```

With the switch off, every mock row still gets a **fresh** descriptor set — the pre-0.4.66
memory profile (nothing retained beyond a row's lifetime). The switch is deliberately a
static, programmatic API (not an environment read) so the library stays runtime-agnostic and
the application owns its configuration. The retained cache is hard-capped at 2 000 signature
entries (measured real-world usage plateaus at ~64, sub-megabyte).

Measured on the gopass-eshop purchase path against a real database (cache enabled): sustained
order/create throughput on one instance went **9.7 → 10.5 orders/s** on top of the caller-side
cache fix (7.3 → 9.7), with the mock-row CPU share dropping accordingly. Memory A/B under the
same load: peak RSS unchanged (~1.3 GB, dominated by in-flight request data), idle baseline
unchanged, clean return to baseline after load.

Behaviour is unchanged in both modes: the full existing test suite (1 515 tests) passes
untouched.
