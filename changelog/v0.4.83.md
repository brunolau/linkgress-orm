# v0.4.83

## Feature: covering indexes — `.include()` renders `INCLUDE (...)`

`IndexBuilder.include(selector)` adds non-key (covering) columns to an index:

```typescript
entity.hasIndex('ix_loan_book', e => [e.bookId, e.isActive])
  .include(e => [e.loanedAt, e.returnedAt, e.readerId]);
// → CREATE INDEX "ix_loan_book" ON "loan" ("book_id", "is_active") INCLUDE ("loaned_at", "returned_at", "reader_id")
```

INCLUDE columns are stored in the index entries but are not part of the key. A query that filters
on the key columns can read them from the index alone (an index-only scan), and they take no part
in a UNIQUE check, so a unique index can carry extra columns without changing what it enforces.

### Why not just more key columns

Same size on disk, different plans. Measured on PostgreSQL 18 with 1M rows (two versions per key)
and an as-of lookup — `WHERE key = $1 AND starts_at <= $2 AND (ends_at > $2 OR ends_at IS NULL)` —
probed 100k times through a lateral join:

| index | plan | time |
|---|---|---|
| `(key, flag, ends_at, starts_at, value)` | BitmapOr of two index scans + Bitmap Heap Scan (visits the table) | 1818 ms |
| `(key, flag) INCLUDE (ends_at, starts_at, value)` | Index Only Scan, 0 heap fetches | 773 ms |

Both indexes are 47 MB. With the validity columns in the key, PostgreSQL 18's skip scan makes them
usable as index conditions past the low-cardinality `flag`, and the planner splits the `OR` into a
BitmapOr, which always reads the table. INCLUDE columns can only be filtered, so the index-only
plan is the one left.

### Migration behaviour

- The INCLUDE list is part of the compared definition: adding, removing or changing it recreates the
  index (non-blocking with `.concurrent()`), and an unchanged list is never rebuilt.
- **Behaviour change:** a live index whose definition carries `INCLUDE` used to be treated as
  "unknown" by the change detector and was never recreated, whatever the model declared. It is now
  parsed and compared. A same-named model index declared WITHOUT `.include()` over a live INCLUDE
  index will be recreated without the INCLUDE columns on the next `migrate()` — declare them with
  `.include()` to keep them.
- `WITH (...)` storage parameters and `TABLESPACE` are still not modelled; an index carrying them is
  still left untouched.
- Rejected with a clear error instead of a raw PostgreSQL one: INCLUDE on `gin`, `hash` or `brin`
  (PostgreSQL stores INCLUDE columns only in btree, GiST and SP-GiST indexes), and an expression
  inside `.include()` (plain columns only).
