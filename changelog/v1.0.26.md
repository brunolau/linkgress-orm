# v1.0.26

## Fix: a collection hanging off a `lateralJoin()` path probes it too, where its subquery joins the path anew

1.0.25 probes the hop `lateralJoin()` names in the query's own FROM. A collection reached through that path
(`b.author.region.landmarks`) is correlated through it, and where its subquery is correlated to the row by itself,
it joins the path ANEW, from the row the path starts from: the LATERAL of a list (`toList()`, a `limit()`ed list,
`firstOrDefault()`), and the subquery of a `count()` / `exists()` in a `where()` or a `sql` fragment. That join of the
probed hop stayed plain — and with it the merge join the probe exists to rule out: off the hop before it, PostgreSQL
could still merge-join the few rows against the target's whole primary-key index inside the collection's subquery,
on the very statistics that made the query's own join need a probe. A collection's own `lateralJoin()` could not
express it: its selector starts at the collection's item, not at the row the path starts from.

The hop the query probes is now probed there as well — nothing to call on the collection:

```typescript
await db.shelves.select(s => ({
  label: s.label,
  books: s.books
    .lateralJoin(b => b.author.region)
    .select(b => ({
      title: b.title,
      landmarks: b.author.region.landmarks.select(l => ({ name: l.name })).toList(),
    }))
    .toList(),
})).toList();
// the landmarks' LATERAL, inside the books':
//   FROM "landmarks" "lateral_1_landmarks"
//   LEFT JOIN "authors" "author" ON "lateral_0_books"."author_id" = "author"."id"
//   LEFT JOIN LATERAL (SELECT "region__probe".* FROM "regions" "region__probe"
//                      WHERE "region__probe"."id" = "author"."region_id" OFFSET 0) "region" ON true
//   WHERE "lateral_1_landmarks"."region_id" = "region"."id"
```

- A hop of the collection's path is probed when the query whose row the path starts from probes the same relation
  path: a root query's row, or a collection's items (`s.books.lateralJoin(b => b.author.region)` and, in its
  projection, `b.author.region.landmarks`). One-hop and nested probes alike; a probed first hop reads the row's own
  foreign key (`"lateral_0_books"."author_id"`), a deeper one the hop before it as the subquery joins it. The other
  hops keep their plain joins.
- Every strategy: a list's LATERAL under the `lateral` strategy and nested in a temp-table aggregation, a `count()` /
  `exists()` subquery under all three. What joins nothing of the path is unchanged: the CTE and temp-table
  aggregations (the row's own join — the probe — correlates them) and an aggregate correlated to the row's join
  (`toStringList()`, a projected `count()`).
- Every builder: root queries, every select builder, the untyped `QueryBuilder` / `SelectQueryBuilder`, `lateralJoin()`
  after `select()`, a `QueryBatch` leg — each build makes its probes known to the collections built inside it while
  it builds. With the query-build caches on (`MockRowCache`), the probed and the plain shape keep
  texts of their own.
- Same rows: the probe returns what the plain join returned. No API change — nothing new to call, no signature
  changed; the typings change in comments and a private member of `CollectionQueryBuilder`.

On PostgreSQL, with hash joins and nested loops switched off, a collection of the books' landmarks hanging off
`b.author.region` plans 4 merge joins plain (2 in the books' FROM, 2 in the landmarks' re-join of the path); 1.0.25
with `lateralJoin(b => b.author.region)` still merge-joins the region inside the landmarks' subquery; now that
subquery reads the regions through the probe only (1 merge join left, the books → authors hop no probe was asked
for), and with both hops probed no merge join is left.

Docs: `docs/guides/lateral-navigation-joins.md` — "A collection hanging off a probed navigation" (new), "Where it
applies", the rendering table; the `lateralJoin()` JSDoc.

Tests: `tests/queries/lateral-navigation-join.test.ts`, "lateralJoin() — a collection hanging off the probed path"
(the fixture gains `landmarks` of a region), and a planner case — each probed query against the same query without
the probe (identical rows), and its exact SQL: the plain text with every join of the probed hop — the row's own and
each re-join a subquery makes of it — as the probe, nothing else changed. Collections of an item off the probed hop
and off a hop beyond it (a list, an ordered and limited list, a `count()` in a `sql` fragment) and of the root row
(a list, a limited list, `firstOrDefault()`, a `count()`, a `toStringList()` that joins nothing), each under the
three strategies; a probed first hop off the root row and off an item; an `exists()` in a WHERE of the root row and
of a collection's item; the untyped builders, `lateralJoin()` after `select()` and a `QueryBatch` leg; the
query-build caches on; and the plans. On 1.0.25 each of the 11 new cases fails (the plain re-join is still there:
`Expected to not contain: "LEFT JOIN "lnj_regions" "region" ON "author"."region_id" = "region"."id""`, the planner
case `Expected: 1` merge join). No existing assertion changed; the fixture gains a table and its rows.

Backward compatible: a query without `lateralJoin()` renders the SQL it rendered before — without a probe in the
build, the collection's path is the very join list it was (`probedPathsInBuild` is empty), and of the published
files only `dist/query/query-builder.js` changes in code. Recorded in memory with the same tests on 1.0.25 (45 380
statements) and on this release (45 391), the statements differ in the 252 that two recordings of 1.0.25 already
differ in (table names carrying the process id, timestamps), plus 46 of `lateral-navigation-join.test.ts`: 15 that
are their 1.0.25 text with the plain re-join of the probed hop replaced by the probe, with identical results — 3 of
"a navigation and a collection hanging off the nested probe" (lateral, temp-table), whose collection hangs off the
probed `b.author.mentor`, and 12 of the new cases — and 31 cleanup statements shifted by the 4 new cases that stop
early on 1.0.25. Every other statement of the suite, every one-hop and nested probe among them, is byte-identical
with an identical result.
