# v1.0.4

## In-memory database: `json(b)_populate_record(set)`, and plpgsql's `RETURNING … INTO`

Two gaps a downstream test suite ran into, both of them statements PostgreSQL accepts and the
in-memory engine refused. Nothing here changes what an already-working statement returns.

Both are pinned by the differential corpus (`tests/memory/sql-parity-corpus.ts`), so every case
below is compared against a live PostgreSQL 18 on every `npm run test:parity`.

### `json_populate_record`, `jsonb_populate_record` and their `recordset` / `_valid` forms

`SELECT * FROM jsonb_populate_record(NULL::my_table, $1::jsonb)` failed with

```
function jsonb_populate_record (jsonb_populate_record) is not implemented
```

The catalog already declared the family (`pg_proc` is generated from a real server) and the analyzer
already resolved `anyelement` to the row type of the `NULL::my_table` argument — only the executor
side was missing. The two idioms that motivated it are a row CLONE,

```sql
INSERT INTO product_price OVERRIDING SYSTEM VALUE
SELECT (jsonb_populate_record(NULL::product_price, to_jsonb(pp) || jsonb_build_object(
    'id', nextval('product_price_id_seq'), 'uuid', gen_random_uuid(), 'slot_id', $1::int
))).*
FROM product_price pp WHERE pp.id = $2
```

and a verbatim RESTORE of a row saved as json, under a table name the caller composes:

```sql
INSERT INTO <table> OVERRIDING SYSTEM VALUE
SELECT * FROM jsonb_populate_record(NULL::<table>, $1::text::jsonb)
```

Implemented with PostgreSQL's semantics, which is `populate_record_worker` with a row type taken
from the first argument rather than a column definition list:

- keys match column names by name and case-sensitively; a key matching no column is ignored
- a column with no key keeps the value the base record holds, or NULL when the base is NULL
- a json `null` is SQL NULL even when the base record has a value there
- values go through each column's input function (`int`, `numeric` with its typmod, `bool`, `uuid`,
  `timestamp`, arrays element-wise, `json` / `jsonb` verbatim), and nested composite columns are
  populated recursively
- no json argument returns the base record unchanged — NULL when there is none
- a first argument that is not a row type is `42804`, and an anonymous `record` one with neither a
  non-null base nor a column definition list is `0A000`, both with PostgreSQL's wording
- `jsonb_populate_record_valid` reports the same work as a boolean, NULL where the populate itself
  would be NULL

Both positions work: `SELECT * FROM jsonb_populate_record(…)` (including
`… AS x(a int, b text)` over a `record` base) and `(jsonb_populate_record(…)).*` inside an
`INSERT … SELECT`.

The coercion of one json value to one column type is now ONE function shared with
`json(b)_to_record(set)`, which fixes two long-standing differences in those as well: a json value
that is not an array where an array column is expected is `22P02`, not `22023`, and a non-object
argument reports `cannot call populate_composite on an array` / `… on a scalar` the way PostgreSQL
does instead of naming the outer function.

### plpgsql: `RETURNING … INTO` on a data-modifying statement

```sql
DO $$ DECLARE v int; BEGIN INSERT INTO t (n) VALUES (1) RETURNING id INTO v; END $$;
```

failed with `syntax error at or near "INTO"` — for `INSERT`, `UPDATE`, `DELETE` and `MERGE`, with or
without `STRICT`, in a `DO` block and in a `CREATE FUNCTION … LANGUAGE plpgsql` body.

The statement parser only ever split a target list off a statement whose first word was `SELECT` or
`WITH`, a guard meant to keep the `INTO` of `INSERT INTO` out of it. So the `INTO` after `RETURNING`
stayed in the SQL text handed to the parser, and `WITH … INSERT INTO t … RETURNING id INTO v` lost
the wrong one — the `INTO` of its own `INSERT`.

It now follows `make_execsql_stmt`: every `INTO` of the statement is the target list except the
three the SQL grammar uses itself — the one directly after `INSERT`, the one directly after `MERGE`,
and any in an `IMPORT FOREIGN SCHEMA … INTO`. A second target list is
`INTO specified more than once at or near "INTO"` at parse time, as in PostgreSQL.

### plpgsql: a statement that returns rows needs a destination

Related, and found in the same place: the engine silently accepted a row-returning statement with
nowhere to put the rows. `INSERT … RETURNING id;` (no `INTO`) inside a block ran and threw the rows
away, as did a bare `SELECT 1;`. Both are now `42601 query has no destination for result data`,
raised when the statement runs, and the `use PERFORM instead` hint appears for a plain query only —
never for an `INSERT` / `UPDATE` / `DELETE` / `MERGE … RETURNING`, exactly as PostgreSQL splits it.
