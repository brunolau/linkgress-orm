# v1.0.7

Two themes. A built-in vocabulary for the SQL expressions that applications kept writing as raw `sql`
templates — casts, CASE, GREATEST / LEAST / NULLIF, IS DISTINCT FROM, string / math / date-time functions,
JSONB paths and mutations, array-column operators — plus typed SET expressions for the keyed bulk writes,
transaction-scoped advisory locks, and conditions that select as boolean columns.

And a round of correctness fixes in how navigations and collections are joined and read, most of them
silent wrong data rather than errors: conditions nested inside a fragment now report their navigations;
navigation paths that end in the same relation name no longer collapse into one join (in queries and in
every `.returning()`); ORDER BY keys read through navigations, at the root and inside collections;
collections hanging off navigation paths, keyed on non-id principal keys, reading their parent row,
reading the very table of the row they hang off, or over a table of another schema; and a temp-table
collection strategy that now aggregates everything the CTE strategy does. Every collection shape is pinned
under all three strategies, on PostgreSQL and the in-memory engine.

Then grouped queries (HAVING in every shape, ORDER BY aggregates, MIN / MAX of any type, aggregates over
expressions), every `orderBy()` form (a flat pair, NULLS FIRST / LAST, conditional keys, refusals instead
of silent drops), selectors returning one value (they returned empty objects), navigations in the
RETURNING of `mergeBulk` and both sides of the child inserts, and Bun: Dates, bytes, array columns and
array results — array columns could not be written through `BunClient` at all.

Finally, every mutation's `.returning()` reads what a `select()` reads — `sql` expressions (over the row
or its navigations), conditions, literals, one value on its own — each value through the mapper of what
it IS; a string literal in a projection is a value, not a column name; literals read back exactly;
collections aggregate `sql` expressions; a join of a grouped query reads its rows; `sql` values reach
every write path inline; and the suite runs on PGlite out of the box.

And every value of a projection reads back the way its own column reads — in a nested object, in a
navigation row projected whole (now rendered as its columns), through a CTE, a table subquery or a
`withAggregation` item — with a CTE body's and a subquery's literals typed for the query reading them;
CTEs join with `innerJoin` too; `selectFromCte` projections, one-literal selectors, arrays of columns,
the temp-table strategy's nested objects and `doUpdate({ set })` behave as written.

## Feature: SQL expression helpers

New module `src/query/sql-functions.ts`, exported from the package root; guide:
`docs/guides/sql-expressions.md`.

```ts
import {
  cast, castAsInt, castAsString, caseWhen, caseOf, literal, typedNull, asBoolean,
  greatest, least, nullIf, isDistinctFrom, lower, concatWs, round, atTimeZone, dateTrunc,
  datePart, toChar, addInterval, jsonbPathText, jsonbSet, jsonbContains, arrayContains,
} from 'linkgress-orm';

db.loans.select(l => ({
  state: caseWhen(isNotNull(l.returnedAt), 'returned').when(lt(l.dueAt, today), 'overdue').else('open'),
  qty: jsonbPathText(l.payload, 'qty').castAsInt(),
  local: toChar(atTimeZone(atTimeZone(l.dueAtUtc, 'UTC'), l.branch.timeZone), 'YYYY-MM-DD HH24:MI'),
  member: concatWs(' ', l.member.firstName, l.member.lastName),
}));
```

- **Casts** — `cast<T>(value, pgType)` and `castAsInt / castAsSmallInt / castAsBigInt / castAsNumeric /
  castAsDouble / castAsString / castAsVarchar / castAsBoolean / castAsDate / castAsTimestamp /
  castAsTimestamptz / castAsJsonb / castAsJson / castAsUuid`, also as methods on every fragment
  (`fragment.castAsInt()`, `fragment.cast<number>('integer')`). Rendered `CAST(x AS type)`; the type name is
  validated (it is inlined); a plain value becomes one typed parameter, `null` a typed NULL; JS objects /
  arrays cast to json/jsonb are serialized, and JSON text is bound as `text` and parsed by the cast
  (`CAST(CAST($1 AS text) AS jsonb)`) — a parameter typed `jsonb` is JSON-encoded once more by postgres.js.
- **Literals** — `literal(value, pgType?)` inlines a safely quoted constant (for index predicates, UNION
  discriminators); `typedNull<T>(pgType)`; `asBoolean(condition)`; `quoteSqlLiteral(text)`.
- **CASE** — `caseWhen(cond, value).when(…).else(…)` and `caseOf(subject).when(match, value)…`. Results
  unify: a column branch fixes the type (and its mapper), all-literal results are typed from their JS type.
- **Scalars** — `greatest`, `least`, `nullIf`, `isDistinctFrom`, `isNotDistinctFrom`.
- **Strings** — `lower`, `upper`, `trim`, `trimStart`, `trimEnd`, `length`, `concat`, `concatWs`,
  `substring`, `replace`, `regexpReplace`.
- **Math** — `round`, `floor`, `ceil`, `abs`, `mod` (read back as JS numbers).
- **Date / time** — `currentTimestamp`, `localTimestamp`, `currentDate`, `utcTimestamp`, `atTimeZone`
  (zone name or zone column, cast to text so enum zone columns work), `dateTrunc` (optionally in a zone),
  `datePart`, `toChar`, `toInterval`, `addInterval`, `subInterval`.
- **JSONB** — `jsonbPath` / `jsonbPathText` (plain `->` / `->>` paths — no `#>> '{}'` text round trip;
  quoted keys, integer indexes, bound keys through a fragment), `jsonbSet`, `jsonbRemoveKey`,
  `jsonbRemovePath`, `jsonbContains`, `jsonbContainedBy`, `jsonbHasKey`, `jsonbHasAnyKey`,
  `jsonbHasAllKeys`, `jsonbArrayLength`, `jsonbTypeOf`, `jsonbBuildObject` (recursive, column refs stay
  live), `jsonbBuildArray`, `toJsonb`, `jsonbPathExists` (vars, silent).
- **Array columns** — `arrayContains`, `arrayContainsAll`, `arrayOverlaps`, `arrayContainedBy`,
  `arrayLength`, `arrayIsEmpty`, `arrayIsNotEmpty`; a JS list binds as one parameter cast to the column's
  array type.

Plain values are always bind parameters (except through `literal`). Where PostgreSQL cannot infer a
parameter's type (all-literal CASE branches, VARIADIC functions, function arguments) it is typed from its JS
type; where a column fixes the type, literals stay untyped, as `eq()` binds them.

Helpers with an explicit result type (casts, string functions, JSON paths, literals, CASE) return the
driver's value exactly — NULL stays `null` and numeric-looking text stays text. The generic result
conversion for untyped fragments (NULL → `undefined`, `'01234'` → `1234`) is unchanged.
`coalesce` and the arithmetic helpers prefer a column's real mapper over this one when both occur.

## Feature: SET expressions for `upsertBulk` and `bulkUpdate`

```ts
await db.counters.upsertBulk(rows, {
  primaryKey: 'key',
  updateSet: (existing, excluded) => ({ hits: add(existing.hits, excluded.hits) }),
  updateWhere: (existing, excluded) => lt(existing.version, excluded.version),
});

await db.tasks.bulkUpdate(changes, {
  set: (target, values) => ({ label: coalesce(target.label, values.label) }),
  where: (target) => eq(target.status, TaskStatus.Planned),
});
```

- `upsertBulk` `updateSet` / `updateWhere` render `DO UPDATE SET "col" = <expr>` / `WHERE <cond>` over the
  existing row (the table name) and `"excluded"`. With `updateSet` alone only its columns are updated;
  with `updateColumns` / `updateColumnFilter` both apply (an expression wins for its column).
  `updateWhere` is ANDed with a raw `setWhere`.
- `bulkUpdate` `set` / `where` render over `"t"` (the updated row) and `"v"` (the VALUES row): an
  expression replaces the provided-flag CASE of its column, may assign a column no row provides, and rows
  may carry only the key. Reading a `v` column no row provides, or assigning a match key, throws.
- `MutationBatch.addUpsertBulk` / `addBulkUpdate` accept the same options.
- Without the new options, the statement text is unchanged.

## Feature: transaction-scoped advisory locks

`db.advisoryXactLock(key)` / `(classId, key)`, `db.tryAdvisoryXactLock(…)` → boolean, and
`db.advisoryXactLockAll(classId, keys)` (one statement, keys deduplicated and sorted — no deadlock between
overlapping sets). Keys are integers (int8 single, int4 pairs) or strings hashed with `hashtext()`. Called
outside a transaction they throw (the lock would end with the statement). Statements run through the
context's executor, so they are logged like any other.

## Fix: conditions nested in a `sql` fragment report their navigations

`SqlFragment.getFieldRefs()` returned the refs of interpolated columns and nested fragments only — a
condition interpolated into a fragment (`sql\`${eq(post.user.name, x)}\``) hid its refs, so a navigation
used only there was never joined (`missing FROM-clause entry for table "user"`, or — where an alias of the
same name was in scope — a silently wrong column). Nested conditions now report their refs and nested
subqueries their outer (correlation) refs, which every helper above relies on.

## Fix: JSON keys are quoted, not spliced

`jsonbSelect`, `jsonbSelectText` and the `jsonbArraySome` element paths wrote the key into the SQL between
single quotes without escaping — a quote in a key broke out of the literal. Keys are now quoted with
`quoteSqlLiteral()`; ordinary keys render exactly as before.

## Feature: a condition projects as a boolean column

```ts
db.members.select(m => ({ name: m.name, isAdult: gte(m.age, 18), flags: { vip: eq(m.tier, 'gold') } }))
```

A condition placed directly in a projection — top level or inside a nested object literal, in `select`,
collection `select`, grouped `select`, CTE-root `select` and join selections — selects as a boolean column
(its navigations are joined; `exists()` keeps working as before). It used to be walked as a nested object.
The result type is `boolean`. Grouped-select result types also unwrap fragments now (`coalesce`, `caseWhen`,
casts resolve to their value type instead of the fragment's structure).

## Fix: navigation paths ending in the same relation name read another row (silent wrong data)

A reference navigation rendered under its relation *name* and was joined by that name:

- Two paths ending in one relation collapsed into one join —
  `db.loans.select(ln => ({ own: ln.book.name, printed: ln.edition.book.name }))` returned the
  loan's own book for both.
- A deep path hung off the first joined table that had a relation of that name —
  `ln.edition.book.category.name` joined `book` from the loan and `category` from the edition.

Every navigation path now has its own join on its own parent: in projections (fields, `sql`
fragments, whole navigation rows), `where`, `orderBy` over projected fields, `groupBy` (selection,
key, `where`, `having`), `count` / `exists` / `min` / `max` / `sum`, UNION legs, correlated
subqueries, collections under every strategy (including nested collections, collections
hanging off a navigation path, and `exists()` / `count()` over a collection in a condition),
`UPDATE … FROM` / `DELETE … USING` with `.returning(...)`, and insert / upsert `.returning(...)` (next
section).

**Aliasing rule.** The shallowest path to a relation name (on a tie, the first one to appear:
projection before `where`) keeps the plain alias (`"book"`); every other path to that name renders
as `<parentAlias>__<relation>` (`"edition__book"`, `"edition__book__category"`). A navigation named
like the query's own table never keeps the plain name. Queries whose joins were already correct
render the same SQL as before — every statement the suite records (27 000+) is byte-identical with the
alias plan switched on and off — and a raw `sql` fragment naming `"book"` keeps resolving to the path
that owns the plain alias; only queries that read the wrong row get new statement text.

**Refused with an error instead of rendered wrong** (the message names both paths and a way out):
a path alias longer than PostgreSQL's 63-byte identifier limit; a path alias equal to another path's
alias.

Implementation: `NavigationAliasPlan` (`src/query/join-utils.ts`) records each build's navigation refs by
PATH, picks the owner of each plain alias and re-aliases the colliding refs for the duration of the
synchronous build; the root, grouped and collection resolvers anchor planned aliases on their recorded
parent instead of searching by name. When every navigation is one hop deep and none is named like the
anchor table, no plan is built. Build cost: unchanged for one-hop queries; about 1–1.5 µs more per build
when a query navigates two or more hops.

## Fix: navigations in insert / upsert `.returning()` read another row (silent wrong data)

`insert`, `insertBulk`, `upsert`, `upsertBulk` and `insertWithChildren` render a `.returning()` that
reads navigations as a `"__mutation__"` CTE with the navigations joined onto it. Those joins were still
resolved by relation *name* — the mock row did not even record the path a navigation was reached by, so
`ln.book.name` and `ln.edition.book.name` were one and the same ref:

- `db.loans.insert(row).returning(ln => ({ own: ln.book.name, printed: ln.edition.book.name }))`
  returned the loan's own book for both, and `ln.edition.book.category.name` its category;
- a path whose middle hop was not projected (`ln.edition.category.name` alone) failed with
  `missing FROM-clause entry for table "category"`;
- a collection hanging off a deep path (`ln.edition.book.editions`) correlated to the loan's own book;
- a mapped column read through a deep path or a path alias came back without its `fromDriver`, and
  no navigation column inside a nested object was mapped at all;
- a navigation row projected whole (`printed: ln.edition.book`) vanished from the result.

The RETURNING now runs under the same `NavigationAliasPlan` as a SELECT and `.where(...).update() /
.delete()` `.returning()`: every path has its own join on its own parent, the shallowest path keeps the
plain alias and every other one renders as `<parentAlias>__<relation>` — for an insert and for both
branches of an upsert (the joins read the keys the conflict update set). Also:

- a collection hanging off a renamed path joins that path itself in its correlated form (`count()`,
  `min()` / `max()` / `sum()`, `exists()`, `toNumberList()` / `toStringList()`) and, with `limit()` /
  `offset()`, in its LATERAL form; collections are anchored on the mutated row instead of having their
  SQL rewritten table name → alias afterwards — the rewrite was ambiguous for two joins to one table,
  and turned a nested `exists()` inside a collection into a comparison with an outer join that held for
  every row (it now reads the collection's own item);
- a navigation column goes through its own column mapper at any depth and nesting level;
- a whole navigation row comes back as an object of its columns, as in a SELECT;
- `insertWithChildren`: a child `returning` that does not project the child key no longer fails with
  `column __mutation__.id does not exist`.

**SQL text.** A RETURNING without a collision renders the statement it rendered before (9 statements
captured from 1.0.6 are pinned). One deliberate exception: a collection off a navigation rendered as a
LATERAL join (`toList()`, `firstOrDefault()`, anything with `limit()`) joins its path inside the
subquery, from `"__mutation__"`, as a SELECT renders it — same rows.

**Refused before anything is written, instead of rendered wrong:** a path alias longer than PostgreSQL's
63-byte identifier limit.

## Fix: ORDER BY through navigations on the root query (silent wrong order, or an error)

- `db.table.orderBy(...)` handed its selector a columns-only row: a key through a navigation read
  `undefined` and silently vanished from the ORDER BY (`ln.book.name`), or threw
  (`ln.edition.book.name`); a `.select()` with a collection chained after it threw as well;
- after `select()`, every key rendered as a bare name: a nested object's leaf or a column of a
  navigation row projected whole named a column the root table does not have;
- a key a later `select()` renamed ordered by whatever the new projection selects under that name.

Every key that is a column now keeps its ref: it renders as the projection's output alias while the
projection still selects that very column under it, and otherwise as the qualified column — joined,
and aliased by path, like a projected navigation (on the relation's principal key; a missing navigation
sorts like NULL). `db.table.orderBy()` / `limit()` / `offset()` without a `select()` still return whole
rows; `first()`, `countOver()` and prepared queries order the same way, `count()` ignores the ORDER BY,
and a second `orderBy()` replaces the first together with its joins. Queries ordering by their own
columns render the SQL they rendered before.

## Fix: ORDER BY inside collections (silent wrong order, or an error)

Collection ORDER BY keys rendered as bare column NAMES:

- LATERAL bound a name its inner table lacks to the ENCLOSING row — ordering a member's loans by
  `ln.edition.book.name` ordered them by the member's own `name`, i.e. not at all — and a name the
  projection reuses as an alias to that alias (ordering by `label` while projecting
  `label: ed.category.name` ordered by the category);
- the CTE and temp-table aggregates ordered by names their subquery output does not carry
  (`column "name" does not exist`);
- a DISTINCT list could not order by what it lists, a LIMITed count / min / max / sum / exists ignored
  its ORDER BY and LIMIT, and the correlated `toStringList()` / `toNumberList()` form dropped every key
  read through a navigation (and, unlimited, its ORDER BY altogether).

Every key now renders as its qualified expression — or, where an aggregate reads an inner SELECT's
output (`json_agg(… ORDER BY …)`, `ROW_NUMBER() OVER (… ORDER BY …)`), as the projected column selecting
that very expression, or a hidden `"__order_<n>"` column carrying it. A key read through a navigation
of the item joins that navigation like a projected one. A LIMITed / OFFSET scalar aggregates exactly
the rows the ordered, limited collection yields, under every strategy. A DISTINCT collection ordered by
a value it does not select is refused, naming the key (PostgreSQL refuses it too). An unordered
collection renders its previous SQL.

## Fix: an ORDER BY key that is an SQL expression was dropped silently

`orderBy()` walked its keys for COLUMNS and skipped everything else, so a key that is an expression —
`orderBy(ln => [[sql\`lower(${ln.title})\`, 'ASC']])`, a condition, `m.loans.count()` — vanished from
the statement: no ORDER BY, no error, rows in plan order. On the root query (before and after
`select()`) and inside collections under every strategy, such a key now renders parenthesized, its
parameters numbered in the statement's sequence and the navigations it reads joined like projected
ones. After `select()`, a fragment reads a projected column as that column (under its path alias); one
reading a projected fragment or literal — there is no column behind it, and ORDER BY sees an output
alias only standing alone — is refused by `orderBy()`, naming the value. Inside a collection the key
renders over the collection's own alias (LATERAL) or as a hidden column of the aggregated SELECT (CTE,
temp table); the single round-trip temp-table form does not take such a collection.

## Fix: collections off a navigation path, on a principal key, or reading their parent row

- **Off a navigation path** (`ln.edition.book.editions` from a loan): the CTE and temp-table strategies
  joined the aggregate back on the ROOT row's id — pairing the book's editions with the loan whose id
  happened to match — and a count or flat list in the correlated form referenced the path's last hop
  without the query joining it (`missing FROM-clause entry for table "book"`). The aggregate now joins
  on the path's last hop (under its planned alias), and the query joins the path for it.
- **On a non-id principal key** (`withPrincipalKey(c => c.code)`): the CTE and temp-table aggregates
  joined back on `id`. They join on the principal key now, and the temp table's key column takes its type.
  A `selectMany()` through such a relation (`c.booksByCode.selectMany(b => b.editions)`) correlated
  `category_code = category.id` under every strategy — an error for a text code, silently another
  category for an integer one — and bridged to the intermediate table on its `id` whatever the inner
  relation's key; both now use the relations' own keys.
- **Reading the parent row** (a WHERE, projection or ORDER BY on a column or navigation of the row the
  collection hangs off, `ln.edition.loans.where(x => eq(x.note, ln.note))`): the CTE and temp-table
  strategies aggregate apart from that row, so they could not render it. Such a collection renders as
  LATERAL under every strategy, with the parent's navigations joined where the parent lives.
- **A navigation named like one the enclosing row's refs render under**
  (`m.favoriteBook.category` next to `ln.edition.book.category` inside a member's loans): the inner join
  shadowed the outer row and the comparison became the inner row with itself. Such a navigation of the
  collection renders under a path alias.
- **Nested scalars under CTE**: a `count()` / `min()` / `exists()` nested inside a collection came back
  as `{}` (or as a string exploded into an object). They are plain values now, as under LATERAL, and
  RETURNING reads counts back as numbers.

## Fix: collections over the table of the row they are read from (silent wrong data)

- A relation of a table to itself (`n.children`) under LATERAL correlated to its own inner row: a
  collection registered its table under its own inner alias before rendering its own correlation, so
  `"lateral_0_children"."parent_id" = "lateral_0_children"."id"` — every list came back empty.
- A collection reached back through a navigation (`ed.book.editions` from an edition, `ln.member.loans`
  from a loan) joined the first hop of its path from its OWN inner row under LATERAL — the correlation
  `inner.book_id = book.id` then held for every edition, and every row listed all of them (lists,
  `firstOrDefault()`, anything with `limit()`, and such a collection nested in a LATERAL or temp-table
  collection). The first hop now starts from the enclosing row, the others from the previous hop.
- `exists()` over such a collection in a WHERE (`where(ed => exists(ed.book.editions.where(…)))`,
  `where(n => exists(n.children))`) left its table unaliased, shadowing the outer row of the same
  table: it held for every row. It names its own table apart (`"editions__exists"`) whenever the bare
  name is one it reads from the enclosing scope; otherwise its SQL is unchanged.
- A nested collection reading its ENCLOSING collection's item (`ln.member.loans.where(x => gt(x.id, ln.id))`
  inside a member's loans): the enclosing item's refs carry a marker that names a TABLE, not a query,
  so over the same table the inner collection rewrote them to its own alias (`x.id > x.id`, false for
  every row), and over another table nobody rewrote them (`missing FROM-clause entry for table
  "__collection_…__"`). They render under the alias the enclosing row has — its LATERAL alias, or the
  table itself inside a CTE / temp-table aggregation.

## Fix: collections over a table of another schema

A collection read its table unqualified — `FROM "pets"` for a table configured `toSchema('zoo')` —
under every strategy, and so did the `exists()` / `count()` of a collection in a WHERE or a `sql`
fragment, the hop of a navigation a collection hangs off, a `selectMany()` bridge, and the single
round-trip temp-table form: `relation "pets" does not exist`, or silently a same-named table earlier in
the `search_path`. They read `"zoo"."pets"` now.

## Fix: the temp-table collection strategy aggregates what the CTE strategy does

The strategy used to render its own, much smaller aggregation: no navigation of the item (`t."book"."name"`,
an error), no ORDER BY through navigations, no nested collections (refused), a WHERE whose parameters
were written in with `replace('$1', …)` — which also hit the `$1` of `$10` and assumed the WHERE's
parameters were numbered from `$1`.

- Each collection now runs the CTE strategy's aggregation restricted to
  `fk IN (SELECT id FROM <temp table>)`, over the parent keys the base query returned (the root row's,
  or that of the navigation the collection hangs off; distinct, NULL-free), merged back by that key.
  Nested collections render as LATERAL inside the aggregation; a collection reading its parent row
  renders as LATERAL in the base query.
- `.limit(1).count()` came back `undefined` and `.limit(1).exists()` `null` (read as single rows);
- a query built as ONE statement (`countOver()`, `prepare()`, a UNION leg, a batched future) has no
  phase for the parents' ids: its temp-table collections take the CTE form (they used to land in the SQL
  as a join to a CTE nobody declared);
- on multi-statement drivers each aggregation's parameters are numbered from `$1` and written into the
  script by a tokenizer that skips what PostgreSQL does not read as a placeholder — quoted literals and
  identifiers, `E'…'` and dollar-quoted strings, `--` and `/* */` comments, a `$` inside an identifier —
  and refuses a placeholder without a value. A string with a backslash is written as `E'…'` (read the
  same whatever `standard_conforming_strings` says), a negative number is parenthesized (`a-$1` must
  not become the comment `a--1`), `NaN` / `±Infinity` are quoted;
- the single round-trip form takes only plain lists of the item's own columns: it read a column through
  a navigation as the item's own column of that name, and its ORDER BY bound to an output column of the
  same name (`ORDER BY "id"` next to `"book_id" as "id"`); its keys are qualified now, and a projected
  `parent_id` sends the collection to the two-phase form.

The in-memory engine drops an `ON COMMIT DROP` temp table inside the committing transaction, as
PostgreSQL does. The drop used to run after the commit and failed with `DDL outside a transaction`, which
broke every multi-statement temp-table script run against the engine.

## Fix: grouped queries — HAVING, ORDER BY, MIN / MAX and aggregates over expressions

- **HAVING** rendered only a top-level comparison with an aggregate on its left (`gt(g.count(), 5)`).
  An aggregate inside `and` / `or` / `not`, on a comparison's right-hand side, in `between` / `inArray`
  or in an `sql` fragment rendered as the column `"count"` / `"max"`; `g.sum(r => r.x)` over a projection
  that renamed its field rendered `SUM(*)` (its selector ran against the raw row); a grouping key read
  `"[object Object]"` when the projection reused a navigation's name; `between` lost its upper bound;
  and over the grouped subquery of an expression key, aggregates referenced the base table. The
  condition now renders through the condition builder with the aggregates and keys substituted (a new
  `SqlBuildContext.substitute` hook), over the SAME group the projection reads: the having() callback
  runs at build time. Chained `having()` calls — before and after `select()` — are combined with AND
  (a second call replaced the first). The callback's group is typed as columns (`HavingGroupedItem`):
  `gt(g.count(), 5)`, `eq(g.key.status, 'open')` need no cast.
- **ORDER BY** an aggregate named its function (`ORDER BY "count"` — an error); an `sql` fragment of the
  projection was dropped; a grouping key rendered as the base column, wrong over the grouped subquery.
  A projected key, aggregate or fragment orders by its output alias now; an expression written inside
  `orderBy()` is refused.
- **MIN / MAX** read back as a value of their column: they all went through `Number()`, so the extreme of
  a text column came back `NaN`, of a timestamp epoch milliseconds, and a mapped column skipped its
  mapper. Numeric columns still read as numbers; a grouped CTE or subquery keeps the mapper.
- **An aggregate over an `sql` expression** — projected (`len: sql\`length(${e.label})\``, then
  `g.max(r => r.len)`) or written in the aggregate (`g.sum(r => sql\`${r.x} * 2\`)`) — was left out of the
  SELECT and the result. It renders now; over the grouped subquery every argument is projected once,
  under a column of its own (`"__arg<n>"`, also fixing two joined tables' same-named columns colliding
  there). A selector returning nothing is refused.
- **The projection** may hold constants, `null` and `sql` expressions over keys and aggregates
  (`sql\`${g.sum(r => r.x)} / ${g.count()}\``); a nested object or any other value is refused naming the
  field (it was dropped). A grouping key that is a condition groups through the subquery form like a
  fragment; no key at all aggregates over every row.

## Fix: `orderBy()` forms

One flat pair (`u => [u.name, 'DESC']`) was read as two keys: the direction became an ignored key and the
column sorted ascending. Every builder's `orderBy()` now reads one key, keys, `[key, direction]` pairs,
one flat pair, pairs and keys mixed, and a pair without a direction; a direction may carry `NULLS FIRST`
/ `NULLS LAST` (`OrderDirection` widened) in any case and spacing; a key that is `false` / `null` /
`undefined` is left out. A string, a number, `true`, a function, a whole navigation row, a direction that
is none, or a pair of the wrong length is refused with the reason — they were dropped silently.

## Fix: a selector returning one value reads as its values

`db.books.select(b => b.name).toList()` is typed `string[]` but returned EMPTY objects (the value's own
ref keys were read as the projection's fields) — at the root, in `first()` / `firstOrDefault()`, a
union, a batch and `countOver()`; `e => e.book.name` there did not join its navigation ("missing
FROM-clause entry"). In a collection, `b.editions.select(e => e.label).toList()` returned
`[{ label: 'E-1' }]` (and `firstOrDefault()` an object), and an expression (`e => sql\`upper(...)\``) was
not projected at all — `[{}]`. All read as the values now, through the column's mapper, in selects, nested
collections and mutation RETURNING. The SQL is unchanged, so such a query still serves as a subquery or
CTE body naming its column. `DbEntityTable.selectDistinct()` unwraps its selection's types as `select()`
does. A collection as the whole selection is refused with the way to project it.

## Fix: a navigation's column read through the root's mapper

The result mapping looked a column's mapper up by its property NAME in the root table first: a
navigation's column named like an unmapped root column skipped its own mapper, and one named like a
mapped root column got the root's. A navigation's column reads through its own mapper now.

## Feature: navigations in `mergeBulk` and `insertBulkWithChildren` RETURNING; parent navigations

- `mergeBulk(...).returning(selector)` takes navigations and collections (it threw): the MERGE …
  RETURNING runs in the `"__mutation__"` CTE, its columns qualified by the target alias.
- `insertBulkWithChildren` takes them on the child side (it threw), in the same statement.
- The PARENT selector of `insertWithChildren` / `insertBulkWithChildren` may read navigations,
  collections, nested objects and expressions (it threw): own columns still ride the statement, anything
  else is read back by the parents' keys once it ran — including the new children — in input order. An
  empty parent selector no longer renders a dangling comma.
- A child's navigation to the parent TABLE read only the rows the statement inserted: a child pointing
  at an EXISTING row of that table through another key got NULL. It reads the inserted rows together
  with the table's other rows (`(SELECT * FROM <cte> UNION ALL SELECT * FROM <table>)`).
- `.returning(selector)` results are typed `ReturningRow<T>`: columns as before, an `sql` expression or a
  collection aggregate as its value, a collection as its items, a nested object field by field (they
  were typed as fragments / builders).

## Fix: Bun — parameters, array columns and array results

- **Dates.** Bun serializes a `Date` with `Date.prototype.toString()` wherever the server does not
  describe a timestamp parameter (a `date` column, a text or untyped parameter) and everywhere with
  `prepare: false`: "invalid input syntax", or the text stored as is. `BunClient` sends the ISO instant,
  as postgres.js does.
- **Bytes** with `prepare: false` were JSON-stringified (`{"0":1,"1":2}`); they are left to Bun, as are
  value classes with a `toString()` of their own. Plain objects and arrays still go as JSON text.
- **Array columns.** Bun cannot bind a JS array to an array parameter ("insufficient data left in
  message" / a malformed literal), so no write to an `integer('ids').array()` column worked on
  `BunClient`. A native array column now binds as a PostgreSQL array literal — a default mapper on
  `.array()`, replaced by a mapper of the column's own — on every driver. `toPgArrayLiteral` writes a
  `Date` as its ISO instant, bytes in the bytea hex form, a plain object as its JSON text, a value
  class as its `toString()`. `cast(values, 'int[]')` binds the literal too.
- **Array results.** Through the binary protocol Bun decodes `int4[]` as an `Int32Array` and `float4[]`
  as a `Float32Array`; `BunClient` returns plain arrays (`int8[]` elements as strings), as the other
  drivers do.
- Known Bun divergences, pinned by the contract tests: a multidimensional array result cannot be
  decoded through the binary protocol, and a numeric zero read through it loses its scale (`0.0000` →
  `"0"`).
- **The numeric zero's scale is restored.** `DatabaseClient.losesNumericZeroScale()` (default `false`;
  `BunClient` answers `true` in its binary mode, a transaction's client answers like its parent) makes
  the query builders give the zero of a column declared with a scale (`decimal('amount', 10, 2)`) its
  scale back — in entity rows, projections, one-value selections and every mutation's `.returning()`,
  plain and navigation. A column without a declared scale, non-zero values and raw SQL are untouched.

## Fix: every mutation's `.returning()` reads what a `select()` reads

A RETURNING selector could select the written row's columns and, through the navigation CTE, its
navigations and collections. Everything else was dropped or broken:

- An `sql` expression, a literal and `null` were dropped from the result on the navigation path and on
  the plain path of `insert` / `upsert` / `merge` / `bulkUpdate` (only `update` / `delete` rendered
  expressions). An expression reading a navigation rendered on the plain path ("missing FROM-clause entry
  for table \"book\""), and one reading nothing but a navigation rendered `RETURNING ) SELECT FROM`.
- A condition (`eq(ln.memberId, x)`) came back as its own internals (`{ field: 7 }`).
- A selector returning ONE value (`ln => ln.note`) rendered an empty RETURNING list — a syntax error —
  on every mutation, though `.returning()` was typed to return that value.
- Rows were mapped by their result KEYS against the table's columns: a mapped column returned under
  another key came back as its storage value (`when: 570` for 09:30), and a value returned under a
  mapped column's name went through that column's mapper (a `views` count read as a date).
- A collection's items came back raw — a mapped column in them as its storage value.
- A WHERE reading a navigation next to a navigation RETURNING failed: the CTE returned bare column
  names and the joined table had an `id` too ("column reference \"id\" is ambiguous").
- `bulkUpdate(...).returning()` rendered a navigation's column as the updated row's column of the same
  name (`t."username"`).
- The compiled `UPDATE` (`toStatement()`) rendered a navigation the same way; a literal was dropped.

Now each value renders and reads back as what it is: a column (own or a navigation's) through its own
mapper whatever key it is returned under; an `sql` expression (or condition, or subquery) over the
row's own columns in the mutation's own RETURNING, and over a navigation through the navigation CTE —
its parameters bound in the statement's sequence, its columns qualified where the table is aliased
(`t."note"` under MERGE / bulkUpdate), its `mapWith` applied; a literal as itself (it is not read from
the database); a collection's items through their columns' mappers, as a SELECT reads them; nested
objects field by field. One value on its own reads as that value (a single `insert`) or their list.
`bulkUpdate` takes the navigation RETURNING too. The CTE returns the mutated table's columns
qualified by the table. A selection of literals only still returns one row per written row; an array of
columns is refused (it has no single SQL value); `toStatement()` binds a literal as a parameter and
refuses a one-value selector and navigations, for UPDATE as for DELETE.

`.where(...).update()` / `.delete()` over an entity table type the RETURNING selector's row as the
entity (`EntityQuery`), like an insert's: conditions, `sql` expressions and collection aggregates over
it type-check (it was typed as the row's plain values). `ReturningRow` resolves a one-value `sql` /
condition selector to its value, and a nullable column (`DbColumn<Date> | null`) to `Date | null`.

## Fix: a string literal in a projection read a column of that name (silent wrong data)

`select(u => ({ kind: 'member' }))` rendered `"users"."member"` — an error — and
`select(u => ({ kind: 'email' }))` silently returned the email column: a string in a projection was
taken for a column NAME at the root, in a collection's items and in `JoinQueryBuilder`, while its
TypeScript type said it was the literal. A string is now a value there, bound as a parameter like a
number. **Behaviour change** for code relying on the old reading: select the column itself (`u.email`).

The other literals rode the statement as parameters and were read back from the database, which hands
an untyped parameter back as text: `true` came back `"true"`, a `Date` as a string, `null` as
`undefined`, and inside a collection item `42` as `"42"`. A literal now reads back as exactly the value
the projection holds — at the top level, in nested objects, in collection items (every strategy,
`firstOrDefault()`, nested collections), in a grouped query's projection and in a join of one. The
statement still carries it, so subqueries, CTE bodies and UNION legs see the column; a UNION reads each
leg's literal from its rows, since every leg may project its own (`literal()` inlines a typed one).

Also in projections:

- A nested object holding a `Date` (or any value object) fell off the flat path after its siblings'
  columns were emitted, and the whole object was bound as ONE JSON parameter — mock column refs and
  all. A value object is a value there; a navigation row projected whole inside a nested object reads as
  its columns; a collection found anywhere in the object is decided before anything is emitted.
- In a collection's items, an `sql` expression's `mapWith` was ignored, a value returned under a mapped
  column's NAME went through that column's mapper, and the columns of a nested object were not mapped.
- `db.table.values(...).onConflict(...).execute()` returned rows keyed by COLUMN name, unmapped; they
  read as entities now.

## Fix: collection aggregates over an `sql` expression

`u.posts.max(p => sql\`length(${p.title})\`)` (and `min` / `sum`) threw "MAX requires an aggregate
field". The expression is the aggregate's argument now, under every strategy (LATERAL rewrites the
item's marker to its alias), with its parameters, the collection's WHERE / ORDER BY / LIMIT, nested in
another collection and in a mutation's RETURNING. The navigations such an expression reads are joined —
as are those of a collection selecting ONE `sql` value (`ln.select(l => sql\`upper(${l.book.name})\`)`),
which rendered unjoined ("missing FROM-clause entry").

## Fix: a join of a grouped query

`grouped.leftJoin(cte, on, (grp, u) => ({ … }))`:

- rendered a literal as a column named like its key (`"kind"` — "column \"kind\" does not exist"); a
  literal is a parameter now (`NULL` for null), read back as itself; a subquery renders as an expression;
- returned the driver's rows as they were: a count as a string, a MIN of a mapped column as its storage
  value, an `sql` expression without its `mapWith`. The grouped fields read back as the grouped query
  reads them (`GroupedSelectQueryBuilder.buildFieldReaders()`), the joined side's columns and
  expressions through their mappers;
- a nested object or a collection is refused, naming the field.

A grouped query's own constants read back as themselves too (they came back as text).

## Fix: `sql` values in every write path

An `sql` fragment as a row value renders inline — its parameters in the statement's sequence — in
`insert`, `insertBulk`, the upsert `VALUES`, `values(…).execute()`, the rows of `insertWithChildren` /
`insertBulkWithChildren`, the cells of `bulkUpdate` (cast to the column's type like the plain cells),
and the schema-level `TableAccessor` `insert` / `insertBulk` / `update`. Several of these bound the
fragment object AS a parameter.

## Fix: `update()` / `delete()` over every row

`db.table.update(data)` / `db.table.delete()` without a `where()` now run as the query update / delete
over a condition every row meets (`WHERE TRUE`): the same SET rendering, `.returning()`,
`.affectedCount()` and `.toStatement()` as `where(...).update()`. The update-all bound its values
without their column mappers and read a navigation in its RETURNING as the root's column of that name.

## Typing: `mapWith`

`fragment.mapWith(fn)` types the fragment by what `fn` returns (`.mapWith(Number)` is a
`SqlFragment<number>`); an unannotated parameter is `any` (it was an implicit-`any` error, and the return
type was ignored). A mapper object keeps the fragment's declared type.

## Fix: every projected value reads back the way its own column reads (silent wrong data)

A value's read used to depend on where the projection put it:

- **A nested object's values**: every numeric-looking string became a number (`{ who: { name: u.username } }`
  read the username `'01234'` as `1234`), and no mapper ran — a mapped column came back as its storage
  value, an `sql` expression without its `mapWith`. Each nested value now reads as it would at the top
  level: a column through its mapper and as the driver types it, an expression's numeric string (a count,
  a SUM) as a number, NULL as null.
- **A navigation's text column** (`p.user.username`, a jsonb column holding a JSON string) was coerced to
  a number when numeric-looking. A column read through a navigation keeps its type; a numeric one
  (`o.user.balance`, a decimal) still reads as a number, as before.
- **A navigation row projected whole** (`{ author: p.user }`) rendered as ONE `json_build_object`: its
  timestamps came back as strings, its mapped columns unmapped, a `selectDistinct` over it failed (json has
  no equality operator) and a UNION leg bound the row object as a parameter and read back `"{}"`. It
  renders as its columns now (`"__nested__author__createdAt"`), flattened like a nested object, and reads
  back typed and mapped — at the root, two hops deep, in UNION legs, `selectDistinct`, `first()`,
  futures, `countOver()`, prepared statements and next to collections under every strategy. A missing
  row still reads as an object of nulls. The row a `where()` hands on, projected whole
  (`where(...).select(u => ({ me: u }))`), reads through its mappers too (it came back unmapped, and one
  level deeper was bound as a parameter). **Behaviour change**: a navigation row's timestamps are `Date`s
  and its mapped columns mapped, as its type says.
- **The temp-table strategy** left a nested object's columns flattened when a collection sat next to it:
  the object came back without them. Both the two-phase and the single-round-trip path rebuild it now.

## Fix: columns read through a CTE or a table subquery (silent wrong data)

The refs of a CTE's columns (and a table subquery's) carried an expression's `mapWith` and nothing else:

- a mapped column read through a CTE came back as its storage value, and a comparison with it bound the JS
  value unconverted (`eq(x.time, { hour: 9, minute: 30 })`); it reads — and converts — through the body
  column's own mapper now;
- a CTE column named like a mapped column of the READING table went through THAT column's mapper (a view
  count named `lastActiveAt` read back as a `Date`);
- a text column holding digits read back as a number;
- the body's literals rode it as untyped parameters, which the reading query got as text: `true` as
  `'true'`, and `gt(x.n, 5)` over a literal `42` compared strings and matched nothing. A CTE body's and a
  subquery's literals render typed from their JS type (`CAST($1 AS boolean)`, an integer, a double, text,
  a `timestamptz` for a `Date`, jsonb for a list of values) and read back as their values — a `bigint` as
  the `bigint` it was. A plain `select()` still binds them untyped (its literals are read from the
  projection itself);
- a nested object or a navigation row of the body could not be selected at all — the reader named a
  column the body does not have. `x.meta` is now the object of the body's flattened columns, `x.meta.t` one
  of them, usable in selections and conditions.

`withAggregation` items went through the reading table's mappers, found by NAME — another table's mapper,
or none — and a nested object (or navigation row) in the aggregated projection named a column the inner
query does not have. Items read through the aggregated query's own mappers now, nested objects key by
key, literals as themselves; a grouping key reads through its column's mapper. So do they at a CTE root
and in a join of a grouped query.

`innerJoin` of a CTE threw "rightTable._getSchema is not a function" — after a `select()`, and straight off
the table like `db.table.leftJoin(cte, ...)` — though the typings offer both. Every such join works now
and attaches the CTE to the statement's WITH list when it is not there yet (as `joinFilter` does).

## Fix: `selectFromCte(...).select(...)`

- A string rendered as a column of that NAME of the root CTE; it is a value, like everywhere else.
- A nested object was bound as ONE parameter; it is flattened and rebuilt, each value read its own way.
- A selector returning one value (`x => x.id`, `() => 'x'`, an `sql` expression) projected the ref's own
  keys (`__fieldName`, …); it reads as that value's list, and `orderBy(id => id)` orders by it.
- A subquery in the projection was bound as a parameter; it renders.
- As a `table` subquery its literals render typed for the enclosing query.

## Fix: a selector returning one literal; arrays of columns

`select(() => 'x')` read back `[{ "0": "x" }]` — a string was walked as an object of its characters — and
`select(() => 7)` projected no column at all. A selector returning one literal reads as that literal on
every row: at the root, in a collection (`toList()`, `firstOrDefault()`, and `toNumberList()` /
`toStringList()`, which threw "arrayField is required"), in UNION legs.

An array of columns (`{ pair: [u.id, u.username] }`, `[p.user]`) has no single SQL value: at the top level it
vanished from the result, nested it was bound as a parameter with the column refs serialized into it. It
is refused now, naming the field — in a root selection, a nested object, a collection's items, a UNION leg,
a CTE root, a join of a grouped query and `JoinQueryBuilder`. An array of values still reads back as itself.
`JoinQueryBuilder` reads a list or plain object of values as itself too (it bound it as JSON and read back
the text) and refuses one of columns.

## Fix: `doUpdate({ set })` dropped the values

`values(...).onConflict(...).doUpdate({ set: { age: 77 } })` rendered `"age" = EXCLUDED."age"`: the
conflicting row took the value being INSERTED, and `77` was silently dropped. `set` updates exactly its
columns to its values now — a value through the column's mapper, or an `sql` expression, which can read the
proposed row as `EXCLUDED."column"` (the entity-level `set` is typed to take one); a key that is no column
is refused. **Behaviour change** for code that
passed `set` to name the columns to take from the proposed row: pass `updateColumns` for that (now offered
by the entity-level `doUpdate()` too).

## Typing: value objects in entity and RETURNING rows

`UnwrapDbColumns` (every entity row, every `.returning()`) tested "is this a navigation entity?" against an
empty marker interface, which EVERY object and function satisfies: a value object no type test recognizes
as one — a Temporal type declared only through augmentations, nothing but symbol-keyed methods — was walked
as an entity and each of its methods typed `{}`. The test uses the branded `DbEntity` now; an optional
column (`age?: DbColumn<number>`), which the empty marker unwrapped by accident, unwraps explicitly.
`ReturningRow` resolves a returned object field by field only when it holds an `sql` expression, a
condition or a column; anything else types exactly as `UnwrapDbColumns` does.
