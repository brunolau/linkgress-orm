# v1.0.10

## Feature: `MigrationConfig.appliedBy` labels journal rows with the release that applied them

An optional `appliedBy?: string` on `MigrationConfig` is stored in a new nullable `applied_by TEXT`
column of the migration journal, on every row the runner records as applied — the normal pending
path, fresh-database baselined rows, and `runOnBaseline`-executed rows alike.

```ts
const runner = new MigrationRunner(db, {
  migrationsDirectory: './migrations',
  appliedBy: '2026.09.25-88a9dc5', // typically the release/image tag
});
```

The label is free-form and linkgress never reads it from the environment — the caller decides what
it means and passes it in. The point is traceability: given a journal, you can tell which release
applied which migration, so a rollback several releases back can pick the exact files and the build
that contains them.

Leaving `appliedBy` unset stores `NULL`, exactly like every row written before this column existed.
`MigrationJournal.ensureTable()` upgrades an older journal idempotently (`ADD COLUMN IF NOT EXISTS
applied_by TEXT`), the same way it already upgrades a pre-`baselined` journal.

### Files Changed

- `src/migration/migration.interface.ts` (`MigrationConfig.appliedBy`, `MigrationJournalEntry.applied_by`)
- `src/migration/migration-journal.ts` (constructor takes `appliedBy`, `CREATE TABLE` / `ALTER TABLE …
  ADD COLUMN IF NOT EXISTS applied_by`, `recordApplied` / `getApplied` read and write it)
- `src/migration/migration-runner.ts` (`status()` exposes `appliedBy`)
- `tests/migration/manual-migration.test.ts` (journal + runner: labelled rows, `NULL` when unset,
  `applied_by` column present)
- `tests/migration/baseline-migrations.test.ts` (fresh-DB baseline: baselined AND `runOnBaseline`-executed

- `docs/guides/migrations.md` (`MigrationRunner` config example, "Journal Table" section)

## Fix: `down()` silently "reverted" a migration whose file was missing

`MigrationRunner.down()` treated a missing migration file as a successful revert: it logged a
warning, deleted the journal row, and counted the migration under `result.applied` — without running
its `down()`, because there was no file to run it from. The schema change it made stayed in place,
but the journal no longer knew the migration had ever run, so the next `up()` re-applied it against a
schema that already had it (reproduced on a real Kubernetes dev cluster after rolling back to a build
that predated the migration file).

A missing file is now treated exactly like a `down()` that threw: `result.failed` is set to the
migration's filename and an error explaining nothing was reverted and the journal row was kept, it is
logged at `'error'` level, and the loop stops — older migrations in the same batch are left untouched
and pending revert, same as any other mid-batch failure. The journal row is never removed for a
migration whose `down()` did not actually run.

### Files Changed

- `src/migration/migration-runner.ts` (`down()`, and its JSDoc)
- `tests/migration/manual-migration.test.ts` (missing-file `down()` keeps the journal row and the
  schema change; a missing OLDER file in a multi-revert batch stops after reverting the present newer
  migration first)
- `docs/guides/migrations.md` (Rolling Back Migrations)
