# v0.4.60

## Feature: table CHECK constraints (`entity.hasCheckConstraint`)

Declarative table CHECK constraints, motivated by conditional NOT NULL pairs —
a column that becomes mandatory once its sibling is set:

```typescript
model.entity(Product, entity => {
  // cashback_product_id becomes mandatory once cashback_id is set:
  entity.hasCheckConstraint(
    'chk_product_cashback_requires_product',
    '"cashback_id" IS NULL OR "cashback_product_id" IS NOT NULL'
  );
});
```

The expression is raw SQL over quoted DATABASE column names — the same
convention as partial-index `where` clauses.

### Semantics

- `ensureCreated()` adds the declared constraints after tables and indexes;
  `migrate()` plans a `create_check_constraint` operation for every declared
  constraint missing on an existing table AND for brand-new tables created in
  the same run (phase 3, alongside their indexes).
- **Reconciled by NAME only** (the extended-statistics model): a missing
  constraint is added; existing constraints are never diffed, dropped, or
  rebuilt — PostgreSQL's stored form (`pg_get_constraintdef`) normalizes the
  expression away from the author's spelling, so definition diffing would
  thrash. Rename the constraint to change its definition.
- PostgreSQL has no `ADD CONSTRAINT IF NOT EXISTS`, so the ALTER is guarded by
  a `pg_constraint` (`contype = 'c'`) existence lookup — `ensureCreated()` and
  operation replays stay idempotent.
- PostgreSQL **validates existing rows** as part of the ALTER: a table holding
  violating rows fails the migration loudly. Backfill data first (journal
  migrations run before auto-migrate in the standard two-step setup).

### Plumbing

- `EntityConfigBuilder.hasCheckConstraint(name, expression)` →
  `EntityMetadata.checkConstraints` → `TableBuilder.withCheckConstraints()` →
  `TableSchema.checkConstraints` (all three `buildTables()` assembly passes).
- New shared SQL module `migration/check-constraint-sql.ts`
  (`buildAddCheckConstraintStatement` / `buildDropCheckConstraintStatement`),
  used by both the live schema manager and the migration scaffold (up:
  drop-if-exists + add — the index idiom; down: drop-if-exists).
- `describeOperation` renders
  `Add check constraint "<name>" on "<table>" CHECK (<expression>)`.

Covered by `tests/schema/check-constraints.test.ts`: ensureCreated build +
PostgreSQL-level enforcement of the conditional-not-null pair (violating
insert rejected, all legitimate combinations writable), migrate() on an
existing table (plan → apply → in-sync), migrate() on a brand-new table,
metadata capture, and canonical SQL emission.
