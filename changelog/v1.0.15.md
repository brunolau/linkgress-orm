# v1.0.15

## Fix: a correlated `exists()` in a `SelectQueryBuilder` WHERE binds to the outer row

A WHERE lambda on a `SelectQueryBuilder` — a `.where()` written after `.select()`, a second `.where()`, or the
filter callback of `joinFilter()` / `leftJoinFilter()` — receives a row rebuilt from the projection. That rebuild
copied each column reference's alias, mapper and navigation path but dropped its chain identity (`__chainId`), so an
outer column passed into a correlated subquery arrived anonymous. The subquery then took it for one of its own and
resolved its alias by NAME against its own relations: when the inner table has a hasOne navigation named like the
outer table (`orderItem.order` under an outer `order`, `shelf.library` under `library`), it LEFT JOINed a second copy
of that table under the outer alias and compared the inner row with itself.

```ts
db.libraries
  .select(l => ({ id: l.id, name: l.name }))
  .where(l => exists(db.shelves
    .where(s => and(eq(s.libraryId, l.id), eq(s.isOpen, true)))
    .select(s => ({ id: s.id }))
    .asSubquery()))
  .toList();
```

```sql
-- before: true for every library that any open shelf exists for — the filter silently stops filtering
WHERE EXISTS (SELECT "shelf"."id" AS "id" FROM "shelf"
  LEFT JOIN "library" AS "library" ON "shelf"."library_id" = "library"."id"
  WHERE ("shelf"."library_id" = "library"."id" AND "shelf"."is_open" = $1))
-- after: correlated to the outer row
WHERE EXISTS (SELECT "shelf"."id" AS "id" FROM "shelf"
  WHERE ("shelf"."library_id" = "library"."id" AND "shelf"."is_open" = $1))
```

`exists()` returned every row and `notExists()` none — no SQL error, no type error. The same query written as
`db.libraries.where(l => exists(…))` directly on the table was already correct (v0.4.81); the rebuilt row now keeps
the identity, so every entry point takes the same path.

### Behaviour changes

- `exists()` / `notExists()` / any correlated subquery in a WHERE after `.select()`, in a chained `.where()` or in a
  `joinFilter` callback now returns the correct rows where it used to match everything (or nothing).
- A subquery there that correlates to the outer table AND traverses its own same-named navigation
  (`s.library!.name` next to `eq(s.libraryId, l.id)`) now throws "would shadow the outer table", as the table-level
  path has since v0.4.81, instead of rendering and misbinding silently.
