# v0.4.80

## Fix: correlated subquery silently misbound when the inner table had a navigation named like the outer table

A standalone correlated subquery whose inner table declares a **hasOne navigation whose
property name equals the outer table's alias** stopped filtering. It compiled, it ran, it
returned rows — the predicate was simply true for every one of them.

```typescript
// `shelf` has a hasOne navigation named `library`; the outer table is also `library`.
db.libraries.where(l => exists(db.shelves
  .where(s => and(eq(s.libraryId, l.id), eq(s.isOpen, true)))
  .select(s => ({ id: s.id }))
  .asSubquery()));
```

```sql
-- before
EXISTS (SELECT 1 FROM "shelf"
        LEFT JOIN "library" AS "library" ON "shelf"."library_id" = "library"."id"  -- invented
        WHERE "shelf"."library_id" = "library"."id" AND "shelf"."is_open")         -- always true

-- after
EXISTS (SELECT 1 FROM "shelf"
        WHERE "shelf"."library_id" = "library"."id" AND "shelf"."is_open")         -- correlates outward
```

`detectAndAddJoinsFromCondition` resolved every alias in the WHERE against the subquery's own
`schema.relations`, keyed by navigation **property name**. When an outer reference's alias
matched one of those names, the builder read the correlation as its own navigation, joined a
second copy of the outer table into the subquery, and bound the predicate to that inner copy —
comparing the inner row with itself. `extractOuterFieldRefs` had the mirror of the same bug and
dropped the reference instead of reporting it outward.

Alias identity cannot decide this; **chain identity** can. Field refs carry the `__chainId` of
the builder chain that minted them, and a ref stamped by a different chain is a correlation to
an enclosing query, whatever it is named. The new `isForeignChainRef` helper makes that the
first question both call sites ask, ahead of any name comparison.

> **Correction (v0.4.81):** this release originally claimed navigation sub-builders inherit
> their root's chain id, so that a navigation ref shares its owner's chain. That was **wrong** —
> `ReferenceQueryBuilder` stamped no id at all, which left every correlation written *through* a
> navigation invisible to these guards. v0.4.81 makes the claim true by propagating the id, and
> fixes the paths that depended on it.

### Why it went unnoticed

The collision needs a child's navigation property to be named exactly like the parent's table.
The plural-table / singular-navigation convention (`users` + `post.user`) never produces it;
singular table names (`library` + `shelf.library`) produce it constantly. Every pre-existing
correlated-EXISTS test used the plural convention.

The one exception — a `posts` → `users` case where `users` does declare a `posts` relation —
sat behind a fixture in which every row satisfied the inner predicate, so a working correlation
and one that matched everything returned the same list. That case is now marked as
non-discriminating and a discriminating twin was added beside it. Only a **hasOne** collision
misbinds; a hasMany of the same name is not auto-joined into a WHERE, which is why that case
rendered correctly anyway.

### New: the unrenderable shape now throws instead of misbinding

A subquery that correlates to an outer `library` **and** traverses its own `library` navigation
wants one alias for two tables in a single scope. There is no correct SQL to emit, so it is now
refused at build time with an error naming the alias and the ways out — traverse the navigation
in the outer query, correlate on a plain key column, or rename the navigation property. Same
contract as the existing same-table self-correlation guard: refuse loudly rather than return a
wrong answer quietly.

### Known limitation (CLOSED in v0.4.81)

This release fixed only the standalone-subquery WHERE path. The same defect remained in the
collection-lambda, subquery-SELECT and grouped-subquery paths, and was swept in **v0.4.81** —
upgrade past this version if you correlate in any of those shapes.

### Coverage

- `tests/queries/correlated-exists-nav-name-collision.test.ts` (new) — a singular-table schema
  that reproduces the collision: EXISTS filters to the qualifying parent, NOT EXISTS yields the
  exact complement (so an inverted misbinding cannot satisfy both), the correlate-and-traverse
  shape throws, and traversing the navigation *without* correlating on it is unaffected.
- `tests/queries/correlated-standalone-exists.test.ts` — a discriminating twin of the
  `posts` → `users` case, plus a note on the original that it does not discriminate.

### Files Changed

- `src/query/query-builder.ts` — new module-level `isForeignChainRef`; used by
  `detectAndAddJoinsFromCondition` (skip foreign refs when collecting join aliases, and refuse
  the correlate-and-traverse alias clash) and by `extractOuterFieldRefs` (chain identity now
  outranks the relation-name check)
- `tests/queries/correlated-exists-nav-name-collision.test.ts` — new suite
- `tests/queries/correlated-standalone-exists.test.ts` — discriminating case added
