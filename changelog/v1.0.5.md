# v1.0.5

## In-memory database: implicit LATERAL, boolean → text, and a jsonb scalar subscript

Three divergences from PostgreSQL, found by running a real application's end-to-end corpus against
the engine. The first returned WRONG DATA rather than raising, which is why it had gone unnoticed.

### A set-returning function in FROM is implicitly LATERAL

The worst of these, because it never raised anything — it returned wrong data:

```sql
SELECT p.id, cfg FROM product p, jsonb_array_elements(p.integration_config) cfg
-- PostgreSQL: one row per element        the engine: no rows at all
SELECT p.discount_product_id, b.id FROM pair p, unnest(ARRAY[p.discount_product_id, p.eshop_product_id]) AS b(id)
-- PostgreSQL: 7,7 / 7,8 / 9,9 / 9,10     the engine: 7,NULL / 7,NULL / 9,NULL / 9,NULL
```

`transformRangeFunction` sets `is_lateral = r->lateral || contain_vars_of_level(funcexprs, 0)`: a
function in FROM whose arguments read a preceding FROM item is LATERAL whether or not the keyword is
written. The engine implemented only the first half, so the function was evaluated ONCE against a
context that had no outer tuple — the outer column read as NULL, and from there a strict SRF yielded
zero rows while a non-strict one yielded a row of NULLs. Neither raised an error.

The analyzer already resolved the reference (function arguments are transformed with lateral
visibility), and the executor already derived the dependency edge for function RTEs from the
argument expressions — only the flag that gates it was missing, so the fix is the missing half of
the condition and nothing else:

```ts
lateral: item.lateral || functions.some((f) => containsVarsOfLevel(f.expr, 0)),
```

A function with no outer reference stays NON-lateral and is still evaluated once for the whole scan,
not once per row — the corpus pins that with a sequence, which counts the evaluations.

This is also why a correlated COLLECTION lateral could come back empty: an implicitly-lateral SRF
anywhere inside the subquery took its correlation with it. A `LEFT JOIN LATERAL (SELECT count(*), array_agg(c.id)
FROM child c, jsonb_array_elements(c.opts) o WHERE c.parent = p.id)` returned `0 / NULL` instead of
`4 / {101,102,103,104}` — the collection looked like missing data rather than a failure. Pinned with
the count AND the distinct ids.

### `'x' || true` is `xtrue`, not `xt`

A boolean concatenated into text came out in the one-letter form:

```sql
SELECT string_agg(d.id || ':' || (d.a IS NULL AND d.b IS NULL), ',' ORDER BY d.id) FROM discount d
-- PostgreSQL: 9802:true,9803:true       the engine: 9802:t,9803:t
```

PostgreSQL has TWO boolean → text conversions, and they disagree on purpose:

| | writes | used by |
| --- | --- | --- |
| `bool_out`, the type's OUTPUT function | `t` / `f` | the wire encoding of a boolean COLUMN, `concat()`, `format()`'s `%s` `%I` `%L`, a boolean inside a composite's or array's output |
| `booltext`, the pg_cast FUNCTION | `true` / `false` | `::text`, and the SQL bodies of `textanycat` / `anytextcat` (the `text \|\| anynonarray` and `anynonarray \|\| text` operators) and of `quote_literal` / `quote_nullable` over `anyelement` |

`::text` was already right; the `||` operators were not — they called the output function. Both
spellings of those operators (the proc's name and the SQL body pg_operator carries in `oprcode`) now
reach one implementation that CASTS: pg_cast is consulted for a function cast from the value's type
to `text`, domains resolved to their base, falling back to the output function only when there is
none — which is exactly PostgreSQL's `COERCE_VIA_IO`. That cast table is now shared with the
`::text` pathway, so the two can no longer drift apart.

`quote_literal` and `quote_nullable` over a non-text argument took the same wrong path, and worse:
they crashed with an internal `XX000` rather than returning anything. They cast now too. The
distinction is visible without booleans — `quote_literal('a  '::char(4))` is `'a'` (the
`bpchar → text` cast is `rtrim1`) while `format('%L', 'a  '::char(4))` keeps the padding.

Unchanged, and now pinned so they stay that way: a boolean COLUMN still goes over the wire as `t`,
`concat('x', true)` is still `xt`, `format('%s', true)` is still `t`, `ROW(1, true)::text` is still
`(1,t)`, and `to_jsonb(true)` is still JSON `true`. `bool` is the only common type that reaches `||`
this way — `bpchar` and `name` cast to text IMPLICITLY, so they resolve to plain `textcat` before
`anytextcat` is ever considered.

### `'5'::jsonb -> 0` is the scalar

Found while probing the above. jsonb keeps a top-level scalar as a one-element array carrying the
scalar flag, so `JB_ROOT_IS_ARRAY` holds for it and `jsonb_array_element(_text)` reaches it:
`'5'::jsonb -> 0`, `-> -1` and `to_jsonb(true) ->> 0` return the scalar where the engine returned
NULL. Only those two operators do it — `#>`, the `[...]` subscript and the `json` (text) type all
return NULL for the same input, and the corpus pins that half too.

### Not fixed, and still divergent

`inet` / `cidr` have no `::text` (`network_show`) implementation, so `'10.0.0.0/8'::cidr::text` is
still `0A000 not implemented`. Pre-existing and untouched: `'x' || '10.0.0.0/8'::cidr` keeps working
through the output-function fallback, which is the same text PostgreSQL produces for `cidr`.
