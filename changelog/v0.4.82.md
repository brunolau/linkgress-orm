# v0.4.82

## Fix: v0.4.81's alias-shadowing refusal was too broad on the collection path

**Upgrade from 0.4.81 immediately if you use navigation collections.** v0.4.81 could refuse
ordinary, correct queries at build time.

v0.4.81 added a build-time refusal for a subquery that correlates to an outer table AND joins a
navigation of its own under the same alias. On the COLLECTION path it applied that rule to the
collection's implicit parent correlation, on the reasoning that "an own navigation named like
the parent shadows it every time". That reasoning was wrong, and the case it breaks is common:

```typescript
db.usersEshop.where(u => exists(u.cards!.where(c => eq(c.userEshop!.state, active))));
```

`card.userEshop` is the **inverse** of the `userEshop.cards` collection — the same key pair — so
the navigation IS the parent row. Nothing is ambiguous; the join would simply be the identity.
0.4.81 refused the query with `… would shadow the outer table …`.

### What decides it

The key pair, not the name:

| the navigation | meaning | 0.4.82 |
|---|---|---|
| same key pair as the collection's FK (`card.user_id = user_eshop.id` both ways) | it IS the parent row; the join is the identity | drop the redundant join, keep the alias denoting the parent |
| a DIFFERENT key pair (a second FK to the parent's table) | it points at ANOTHER row of that table, so one alias would have to mean two rows | still refused |

Dropping the join is not merely permissive — it is the correct rendering. Emitting it would
shadow the collection's correlation and detach every child from its parent, which is the
misbinding this family of fixes exists to prevent.

The refusal is unchanged everywhere else: the standalone subquery WHERE and SELECT list, and the
grouped path.

### How it was found

Only by running a real consumer. The defect needs a schema whose child navigations are named
after their parent tables — singular table names with inverse navigations, which is the norm in
application schemas and absent from this repo's plural-named fixtures. Three independent audits
of the 0.4.81 diff did not reach it; the first full run of a downstream application's test
suite hit it 135 times on its checkout path.

`tests/queries/correlated-exists-nav-name-collision.test.ts` now pins the inverse-navigation
case to its correct ANSWER rather than to a throw.

### Files Changed

- `src/query/query-builder.ts` — `CollectionQueryBuilder.resolveWhereNavigationJoins` compares
  key pairs before refusing, and drops the redundant inverse join
- `tests/queries/correlated-exists-nav-name-collision.test.ts` — the collection case now asserts
  the resolved rows
