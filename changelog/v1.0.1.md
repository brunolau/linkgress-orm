# v1.0.1

## In-memory database: performance on large data and long-lived databases

1.0.0's in-memory database fell behind PostgreSQL on a downstream suite once its tests ran against a
full-size seed (~147k `product_price` rows): wide reporting queries with correlated `json_agg`
subqueries, and single-row writes into tables with statement-level audit triggers. A database kept
alive for many test files also slowed down over time. This release closes those gaps.

Measured on that suite's heaviest files (the database in a host process reached over loopback TCP,
PostgreSQL 18 on the same machine):

| | 1.0.0 | 1.0.1 | PostgreSQL |
| --- | --- | --- | --- |
| product price search (correlated `json_agg` per product), warm | ~620 ms | ~330 ms | ~315 ms |
| single-row INSERT firing a statement-level audit trigger (in process) | ~260 µs | ~70 µs | ~190 µs (TCP) |
| test file doing 21.7k such inserts, run on its own | 19.0 s | 14.3 s | 16.6 s |

### Autovacuum

Row versions deleted or replaced by committed transactions, and inserts of aborted ones, stayed in
the heap for the life of the database: a long-lived database (a test host serving many files) scanned
and probed ever more dead versions. When a transaction ends, the heaps written since are now vacuumed
once their possibly-dead versions exceed 50 + 20 % of their tuples (`autovacuum_vacuum_threshold` /
`_scale_factor`). A version is kept while a running transaction or an open REPEATABLE READ /
SERIALIZABLE snapshot may still see it; a pass that had to keep some is repeated only once that
horizon moved. The xmax of an aborted transaction is cleared on the way.

### Reused statement analysis

A query statement's analysis is reused while nothing it depends on changed — the parse tree, the
catalog (object and version), parameter types and names, the trigger transition tables in scope, the
search path, and the settings literal input reads (`TimeZone`, `DateStyle`, `IntervalStyle`). An
analysis that read the transaction timestamp (a `'now'` literal) is not reused. This covers prepared
statements, repeated statement texts, and the statements of PL/pgSQL functions and triggers, like
PostgreSQL's plan cache. Transition tables are looked up when the statement runs instead of being
built into the analysis.

### Functions and triggers

- A non-volatile SQL function whose body is one `SELECT <expression>` (no FROM, grouping, ordering,
  set operation, sub-select or aggregate; no SET options, not SECURITY DEFINER) is evaluated as that
  expression, as PostgreSQL's function inlining achieves, instead of running a nested statement per
  call.
- The triggers of a relation are looked up from a per-catalog-version index instead of scanning and
  sorting every trigger of the database for each statement and row.
- PL/pgSQL statement texts are tokenized once.

### Executor

- Aggregation without grouping sets, `ORDER BY` / `DISTINCT` aggregates or direct arguments hashes
  each input row into its group and feeds the transition functions right away; neighbouring rows
  sharing their leading group keys skip the map walk.
- Plain projections (also with `DISTINCT`) keep only the output arrays; filter, join and projection
  loops reuse one evaluation context.
- The base row of a query level is a filled array: every row of the level is a copy of it, and
  JavaScriptCore copies an array holding only holes about 10× slower.
- Uncorrelated `x IN (SELECT …)` with integer / text / bool / uuid / date-time equality probes a hash
  set built once per statement.
- An index lookup on an integer key does not re-evaluate its own equality on every candidate.
- An `UPDATE` that leaves a unique index key unchanged does not search for conflicting versions, as a
  HOT update adds no index entry.
- Call contexts of functions and operators are built once per statement, not per row.

### JSON and date-time functions

- `to_jsonb(record)` sorts a row type's keys once; integers convert to JSON / jsonb numbers directly.
- The JSON text of timestamps is memoized; `json_build_array` / `json_build_object` concatenate.
- `date_trunc` by day / hour / minute / second is arithmetic on the microsecond count.

## Fix: `date_trunc` of a `timestamptz` below a day across a DST change

`date_trunc('hour' | 'minute' | 'second' | …, timestamptz)` resolved the truncated local time's UTC
offset again, so `date_trunc('hour', '2024-10-27 00:30:00+00')` in `Europe/Bratislava` returned
`02:00:00+01` instead of PostgreSQL's `02:00:00+02`. Sub-day truncation now keeps the value's offset.

## Feature: `db.query()` executes a `sql` fragment

`db.query()`, the context's raw-SQL entry point, now takes a `sql` template as well as SQL text.
Interpolated values are bound as parameters, so a raw statement needs no hand-numbered `$1`, `$2`:

```typescript
import { sql } from 'linkgress-orm';

const minAge = 18;
const adults = await db.query<{ id: number; username: string }>(
  sql`SELECT id, username FROM users WHERE age >= ${minAge} ORDER BY id`
);
// → SELECT id, username FROM users WHERE age >= $1 ORDER BY id   (params: [18])
```

It returns the rows, exactly like the text form `db.query(text, params)`, which is unchanged.

### What changed

- `DataContext.query` is overloaded: `query<T>(fragment: SqlFragment): Promise<T[]>` beside the existing
  `query<T>(sql: string, params?: any[]): Promise<T[]>`. `DbContext` inherits it, and so does the context
  `db.transaction()` hands its callback, so `tx.query(sql`…`)` runs inside the transaction.
- The fragment renders through its own `buildSql()`: every interpolated value becomes a `$n` parameter,
  nested fragments and `sql.join()` continue one numbering, and `sql.raw()` text is inlined as written.
- A named `sql.placeholder()` is refused with an error. It only binds inside a prepared query
  (`.prepare()`); a raw statement would otherwise be sent with a dangling `$n`.
- Arrays and JSON pass as ordinary values with an explicit cast (`${ids}::int[]`,
  `${JSON.stringify(doc)}::jsonb`).
- The client-level `query()` / `querySimple()` / `querySimpleMulti()` still take text only: the simple
  protocol that runs several statements in one call cannot carry parameters.

Existing callers are unaffected: the text form keeps its signature and its result.

### Why

Raw statements through `db.query()` had to be written as text with hand-numbered placeholders, so code
that needed raw SQL tended to reach for a driver's own tagged template instead, outside linkgress. A
downstream test suite is moving every statement it sends onto linkgress's execution path, so that the
whole suite follows the configured database client (including the in-memory database) instead of a
driver. A fragment keeps those statements parameterised without leaving `db.query()`.
