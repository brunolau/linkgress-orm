# v1.0.29

Five capabilities for writing a change in ONE statement — insert-or-skip, a close-then-open of a versioned row,
the rows of every leg read back typed, rows bound as one array per column, an insert leg's generated keys — and
the defects they ran into. Each is tested over its whole surface by a generated matrix (8 new files, 4 962 cases,
run on PostgreSQL, PGlite and the in-memory database) against an oracle: the same result computed without the
feature. Queries that do not use a feature emit the SQL they emitted before: of the 77 762 statements the
1.0.28 suite runs, one changed — an expression `insertFrom` writes into a `bigint` column now carries its cast.

## Added: `insertFrom(…, { onConflictDoNothing: true })`

`INSERT … SELECT … [WHERE …] ON CONFLICT DO NOTHING [RETURNING …]`: a source row whose key a unique index of the
table already holds — the primary key, a composite or partial one, a row the statement inserted before it, a row a
concurrent transaction inserts (the statement waits, then skips it once that transaction commits) — is skipped
instead of failing the statement with 23505. RETURNING yields the inserted rows only. It compiles into
`toStatement()` too, so a data-modifying CTE can insert-or-skip.

```typescript
await db.lockers.insertFrom(
  db.candidates.where(c => eqAny(c.batch, batches)).select(c => ({ code: c.code, bank: c.bank, slot: c.slot })).asSubquery('table'),
  src => ({ code: src.code, bank: src.bank, slot: src.slot, active: true }),
  { onConflictDoNothing: true },
);
// INSERT INTO "lockers" ("code", "bank", "slot", "active")
// SELECT "src"."code", "src"."bank", "src"."slot", CAST($2 AS boolean) FROM (SELECT … WHERE ("candidates"."batch" = ANY($1::integer[]))) AS "src"
// ON CONFLICT DO NOTHING
```

A `where: src => notExists(…)` guard is not the same: it judges the statement's snapshot, so a row a concurrent
transaction inserts passes it and then collides (23505) — the test pins both.

## Fix: `insertFrom` casts an expression to its column's type

A value of the map that is an EXPRESSION — `caseWhen`, `caseOf`, `greatest`, `nullIf`, an `sql` template — reached
PostgreSQL with the type PostgreSQL resolves for it: a CASE of string values is `text`, which a `timestamp`, `uuid`,
enum, number, `jsonb` or array column does not take (42804 "column … is of type timestamp … but expression is of
type text"). It is now cast to the column's type — the cast a plain value of the column gets, never a typmod:

```typescript
src => ({ shippedAt: caseWhen(inArrayOpt(src.kind, shippedKinds), at).else(null) })
// before: CASE WHEN … THEN CAST($5 AS text) ELSE NULL END                 → 42804
// now:    CAST(CASE WHEN … THEN CAST($5 AS text) ELSE NULL END AS timestamp)
```

A string column (`text`, `varchar`, `char`) takes any value as it is: its expressions render as before, as do a
source ref and a plain value. Affected: an expression into any other column — which either failed with 42804 or
assigned the same value, now through an explicit cast.

## Added: a compiled statement reads data-modifying CTEs created before it; `afterMutation()` orders it after one

A statement compiled with `toStatement()` (`update`, `delete`, `insertFrom`) — and a CTE's body (`with()`,
`withAggregation()`) — may read data-modifying CTEs created before it: through its source, its WHERE, a subquery of
its values, its `with`. A body that executes nowhere itself cannot declare such a CTE (PostgreSQL allows it only
in the WITH of the statement that executes), so it reads it by name, and the CTE built over it records it
(`DbCte.dependencies`): every statement that declares that CTE declares the ones it reads FIRST, each once,
whichever of them the statement reads and however its `.with()` lists them. It used to be refused.

PostgreSQL runs the sub-statements of a WITH on one snapshot and in no order it promises — a data-modifying CTE
runs when the main query first reads it. Close a versioned row and insert its successor in one statement under a
unique index over the scope (one current lease per unit), and the insert collides with the row it replaces whenever
the main query reads it first: 23505 — or, with `ON CONFLICT DO NOTHING`, it is silently skipped and the unit is
left with no current lease. `afterMutation(cte)` — `((SELECT count(*) FROM "<cte>") >= 0)`, a data dependency
PostgreSQL plans as a one-time filter — makes the statement yield no row before `cte` has run to completion:

```typescript
const builder = new DbCteBuilder();
const closed = builder.withMutation('closed', db.leases
  .where(l => and(eqAny(l.unitId, units), eq(l.isCurrent, true), /* key not desired */))
  .update({ validTo: now, isCurrent: false })
  .toStatement(l => ({ id: l.id, unitId: l.unitId })));
const opened = builder.withMutation('opened', db.leases.insertFrom(
  fromRows(db.leases, desired, { columns: ['unitId', 'tenantId'] }).asSubquery('table'),
  src => ({ unitId: src.unitId, tenantId: src.tenantId, validFrom: now, isCurrent: true }),
  { where: () => afterMutation(closed.cte), onConflictDoNothing: true },
).toStatement(l => ({ id: l.id, unitId: l.unitId })));

await db.selectFromCte(opened.cte).select(r => ({ id: r.id })).toList();
// WITH "closed" AS (UPDATE …), "opened" AS (INSERT … WHERE ((SELECT count(*) FROM "closed") >= 0) ON CONFLICT DO NOTHING RETURNING …)
// SELECT "opened"."id" as "id" FROM "opened"          — reading the open leg declares the close leg, first
```

The barrier orders what the statement writes, not what it sees: the open leg still reads the statement's snapshot,
where the retired row is current. A statement that executes and reads a data-modifying CTE it does not declare is
refused as before (an `afterMutation()` in it too), as is `afterMutation()` of a plain CTE and two different CTEs
under one name. Proven on PostgreSQL, PGlite and in memory: without the barrier, the open leg read first → 23505
(and the lost current row under ON CONFLICT); with it, every read order is correct; `EXPLAIN` shows the one-time
filter.

## Added: `union()` / `unionAll()` on CTE-rooted queries; `onFalse()`

`db.selectFromCte(a).select(…).unionAll(db.selectFromCte(b).select(…))` — a CTE-rooted query is a union leg, beside
other CTE-rooted, entity and set queries. Every leg's CTEs are declared once at the top of the statement (a
data-modifying one after the CTEs it reads), every leg reads them by name, and each row reads the way the FIRST
leg's projection reads it: a column through its own mapper, a text column's `'0042'` as text, a literal — a leg's
tag — from the row. The rows several data-modifying CTEs returned come back in one typed result, tagged by leg,
instead of through a FULL JOIN (which PostgreSQL plans only on merge- or hash-joinable conditions — never on the
null-safe key such a readback needs). `onFalse()` renders `FALSE` beside `onTrue()`'s `TRUE`.

## Fix: a union whose first leg is a set query read every row's literal from the first leg

`fromSet(…).select(() => ({ tag: 'a', … })).unionAll(…({ tag: 'b' }))` read `'a'` for every row: the literal was
read as the first leg's value. It is read from the row, as an entity union always did.

## Fix (in-memory database): a FULL JOIN is refused where PostgreSQL refuses it

PostgreSQL plans a FULL JOIN as a merge join (every condition a mergejoinable equality between the two sides, or a
constant) or a hash join (at least one hashjoinable equality between the sides; any other condition then filters
each pair), and refuses anything else with 0A000 "FULL JOIN is only supported with merge-joinable or hash-joinable
join conditions": `IS NOT DISTINCT FROM`, an inequality, an OR, a condition on one side alone, a volatile equality.
The in-memory engine accepted every condition — a test passed in memory and failed on PostgreSQL. It now refuses
the same conditions; a WHERE that makes a side non-nullable turns the FULL JOIN into another join first, as
PostgreSQL's `reduce_outer_joins` does.

## Fix (in-memory database): a statement that waited at a unique check keeps its snapshot

An INSERT whose key a running transaction had just inserted waited for it, then RESTARTED with a new snapshot: an
`INSERT … SELECT … WHERE NOT EXISTS (…)` then saw the committed row and skipped it, where PostgreSQL raises 23505
(it waits inside the check and judges the key against the outcome; the rest of the statement keeps its snapshot).
A restart after a unique-check wait now reads the snapshot the statement started with: committed → 23505 (or the
skip ON CONFLICT DO NOTHING makes), rolled back → the row is inserted.

## Added: typed rows — `unnestRows(table, rows, columns?)` / `fromRows(table, rows, { columns?, alias? })`

JS rows as a set typed by a TABLE's columns: one array parameter per column, every cell bound through its column's
mapper (a Date as drivers bind it, a json value as its JSON text, a numeric column's precision and scale, an array
cell as its array literal — cast back in a derived table, since `unnest` would flatten it):

```typescript
fromRows(db.shipments, rows, { columns: ['code', 'route', 'weight'] })
// unnest(CAST($1 AS varchar[]), CAST($2 AS integer[]), CAST($3 AS numeric(8, 2)[])) AS "rows"("code", "route", "weight")
```

The statement's text does not change with the number of rows (it can be prepared), zero rows are a legal empty set
(never an empty `VALUES`), and the row reads and compares through the columns' mappers. An `insertFrom` source, a
set a `notExists` correlates to inside a data-modifying CTE, a `crossJoinLateral()` set. `unnestZip` needed an
explicit type per column and bound raw values.

## Added: a `MutationBatch` insert leg's `returning`; the statement's parameter guard

`addInsertBulk(table, rows, id, { returning: ['id', 'route'] })` → `getLegRows(id)`: the rows the leg inserted, in
the batch's one statement — the contract of the upsert leg's `returning` (raw JSON values, no particular order),
only the rows inserted (not those `onConflictDoNothing` skipped or the `rowGuard` blocked). The names are typed
against the entity's columns.

Each leg was checked against its own parameter budget when it registered; the SUM was not, so a batch of legs each
within budget could exceed PostgreSQL's 65 535 and fail at the driver. `executeBatch()` now refuses such a statement
before sending anything, naming each leg's share, and `parameterCount` reports the sum — a caller that registers a
leg only when it fits checks it first. The limit is the client's (`DatabaseClient.maxParameters()`: 65 535, PGlite
32 767).

## Fix: PGliteClient refuses a statement over 32 767 parameters

PGlite counts a statement's parameters in a signed 16-bit field: a statement binding more desynchronized the
session — it, and every statement after it, returned no rows, with no error. `PGliteClient` (root queries,
transactions, leased connections) now refuses it before sending it, and `maxParameters()` reports 32 767. Found by the
`MutationBatch` guard's matrix on PGlite. (An `insertBulk` large enough to chunk above 32 767 parameters is refused on
PGlite rather than corrupting the session; its chunk size still follows PostgreSQL's limit.)

## Fix: a scalar subquery of one column reads like that column

`….select(m => m.code).asSubquery('scalar')` projected somewhere read like a raw `sql` fragment: a text column's
digits-only `'0042'` came back as the number 42, and a mapped column as its stored value. One COLUMN — of a table, a
navigation, a CTE, a set, a grouped query's key or MIN / MAX, a union's first leg — now reads like that column,
wherever the subquery is projected (an entity query, a nested object, a CTE-rooted query, a set query, a QueryBatch,
a CTE body read back through `selectFromCte`): through its mapper, or as a value of its SQL type — text stays text,
a numeric column reads as a number, as before. A grouped query's MIN / MAX of a text column, read through a CTE,
kept '0042' as 42 for the same reason, and does not anymore. An expression keeps reading raw.

## Fix: `DbCteBuilder.with()` / `withAggregation()` take every query builder

A set query as a CTE body threw `query._createMockRow is not a function` (`db.selectFromSet(unnestZip(…))`,
`fromSet(…)`), and so did a CTE-rooted query (`db.selectFromCte(a).select(…)`); a union of set queries lost its
columns' types ('0042' read as 42). Every query a statement can run is a CTE body now, its columns read the way the
query reads them.

## What a caller may notice

- `insertFrom(…, { with: [dataModifyingCte] }).toStatement()` compiles (it was refused): the statement reads the
  CTE by name, and the CTE `withMutation()` makes of it declares that one first.
- `with(name, query)` over a query carrying a data-modifying CTE (`.with(dml)`) is accepted (it was refused): the
  CTE body reads it by name.
- A projected `asSubquery('scalar')` of ONE text-like or mapped column reads as text / through the mapper (it read
  digits-only text as a number, a mapped column as its stored value). Numeric columns read as before.
- An expression `insertFrom` writes into a non-string column carries `CAST(… AS <type>)`.
